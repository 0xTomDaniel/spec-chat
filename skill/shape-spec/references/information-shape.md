# Information shape

Ask: what shape is this information, and what medium loses the least of it?

Use non-prose only when prose would destroy a contract-bearing property.

- Peer axioms: identified peer cards; numbering would invent sequence.
- Cycles with no first step: loop or flywheel; sentences force a false start.
- Guarded transitions: state machine with guards on edges and meaningful self-loops.
- Direction-dependent state: time path plus state-versus-input loop; one snapshot loses hysteresis.
- Order-sensitive procedure: bare numbered list; the ordinal is the content.
- Quantitative relations: math notation with an adjacent one-line gloss.
- Cross-product mapping: table with one explicit cell per combination.
- Precedence logic: numbered first-matching-predicate table.
- Spatial rules: wireframe drawn to true proportion.
- Obligations: identified acceptance rows pairing scenario and observable.
- Negative space: grouped failure families plus explicit non-goals.
- Epistemic status: provenance or caveat adjacent to the affected claim.
- Ownership: boundary statement before the contract and source map after it.
- Predictable confusion: disambiguation beside the conflicting terms or values.

Everything contract-bearing is addressable through stable section, clause, figure, row, and acceptance identifiers.
A visual is load-bearing only when changing it changes the contract; otherwise it is decoration.
Repeat a rule only to present the same authority at a different useful resolution.
Choose forms that expose likely mistakes: bad order in ordinals, missing cases in empty cells, precedence errors in predicate order, layout violations in proportional drawings, and false confidence beside provenance.

## Modular boundaries

When a spec spans multiple modules, include a concise Modular boundaries section.
Name each module's responsibility, the interface or seam callers depend on, and the direction of dependency.
Prefer a semantic diagram when the section contains more than one meaningful relationship, because prose hides ownership and direction.
Keep the view architectural: omit classes, functions, files, and replaceable implementation detail.
