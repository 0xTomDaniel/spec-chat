Pages served at another address

docs / specs / served-pages.spec.html

A host may serve any page of the review service at another address, often in a frame with no origin, or load the comment layer into a page of its own; the page works as it does served directly. Extends Box review service and providers.

User stories

As a human reviewer on a Spec Chat page that a host serves at another address, in a frame with no origin, I review as on the page served directly: I see its threads, comment, hand off, and move to other specs and the review index, all in the host's frame; served directly, the page works unchanged.

Acceptance criteria

Given a human reviewer with a spec that has a comment thread, which a host serves at another address in a frame with no origin, When the reviewer opens the spec in the host, Then the page shows the spec with that thread.

Given a human reviewer with a spec which a host serves at another address in a frame with no origin, When the reviewer opens the spec in the host, saves a comment on it, and hands off, Then the page shows the comment's thread as pending.

Given a human reviewer on a phone with a spec which a host serves at another address in a frame with no origin, When the reviewer opens the spec in the host, saves a comment on it, then reloads the page in the host's frame, then hands off, Then the notice "Handed off 1 comment, agent notified" shows.

Given a human reviewer on a phone with a spec which a host serves at another address in a frame with no origin, When the reviewer opens the spec in the host, their browser goes offline, they save a comment on it, then reload the page in the host's frame with the service reachable, Then the comment appears as their draft.

Given a human reviewer with specs on two review services, which a host serves at other addresses in one frame with no origin, When the reviewer opens the first service’s spec in the host, their browser goes offline, they save a comment on it, then open the second service’s spec in the host’s frame with that service reachable, Then the page shows the second spec with no draft of that comment.

Given a human reviewer with specs on two review services, which a host serves at other addresses in one frame with no origin, When the reviewer opens the first service’s spec in the host, their browser goes offline, they save a comment on it, then open the second service’s spec in the host’s frame, then open the first service’s spec again with that service reachable, then hand off, Then the notice "Handed off 1 comment, agent notified" shows.

Given a human reviewer with specs on two review services, which a host serves at other addresses in one frame with no origin, When the reviewer opens the first service’s spec in the host, saves a comment on it, then opens the second service’s spec in the host’s frame and saves a comment there, then opens the first service’s spec again, then hands off, Then the notice "Handed off 1 comment, agent notified" shows.

Given a human reviewer with a spec which a host serves at another address in a frame with no origin, where the host names the frame and then clears its name once the page has opened, When the reviewer opens the spec in the host, their browser goes offline, they save a comment on it, then their browser goes back online, Then the comment appears as their draft.

Given a human reviewer with a spec which a host serves at another address in a frame with no origin, When the reviewer opens the spec in the host and opens the Review index back link, Then the host's frame shows the review index.

Given a human reviewer with a changed spec which a host serves at another address in a frame with no origin, When the reviewer opens the spec in the host and turns on focus on changes, Then the page shows the spec's changes against the chosen baseline.

Given a human reviewer on a spec page a host serves at another address, When the reviewer turns on focus on changes, Then the page leaves its location unchanged, proven by a unit test: no screen shows it.

Given a human reviewer on a spec page a host serves at another address, with a Jev mark whose target is a clause in another spec, When the reviewer opens that target, Then the page moves there by following a link to that spec's clause, which the host's link handling receives, proven by a unit test: no screen shows it.

Given a human reviewer on a spec page served directly, When the reviewer turns on focus on changes, Then the page's address names focus on changes and its baseline, proven by a unit test: no screen shows it.

Given a human reviewer on a spec page a host serves at another address in a frame with no origin, When the reviewer saves a comment, a review request that needs a preflight, Then the review service answers the preflight and the request so the page reads the answer and its version tag, proven by a unit test: no screen shows it.

Given a human reviewer on a spec page served directly, When the reviewer saves a comment on it, Then the review service's answers to the page's review requests carry no cross-origin permission, proven by a unit test: no screen shows it.

Given a reviewer on a private review service reached through their tunnel, a fixture must be added to provide it, When the reviewer opens another site that sends a review request to that service, Then the review service's answer grants that site no cross-origin read, proven by a unit test: no screen shows it.

Given a human reviewer on a private review service reached through their tunnel, a fixture must be added to provide it, When the reviewer opens another site that sends a review request to that service from a frame with no origin, Then the review service's answer grants that frame no cross-origin read, proven by a unit test: no screen shows it.

Given a Spec Chat contributor's change to any feature, When the contributor runs the review service with it, Then a public review service answers another origin only while it has no login and sets and reads no cookie, so a change that adds either also ends its answers to other origins (why), proven by a unit test: no screen shows it.

Modular boundaries

Each page the service serves takes everything it addresses from its own address, and the service answers a page of another origin or none; a host owns fetching the page, its base address, its frame, and its link handling. Caller-facing seam: the served page's base address, links the page follows, and the service's routes. Dependency direction: external-provider; a host depends on these rules, and Spec Chat names no host. Observable scope: spec pages and the review index served at another address, and the service's answers to a page of another origin or none.

Pages served at another address

A host may serve any page of the review service, a spec page or the review index, at another address: it fetches the page from the service and returns it with a base address naming the address it fetched, often into a frame sandboxed without same-origin access, so the page runs with no origin. A host may also load the comment layer into a page of its own, which then sends the layer's requests from that page's origin, another site's or none. Spec Chat names no host: every rule here holds for any host that does this, and a page served directly is the case where its base address is its location.

A page's own address is its document's base address, fragment aside; served directly, that is its location. Everything the page addresses comes from its own address, never from its location. Wherever a Spec Chat rule names a page's own address or origin, such as the new-tab click, it means this own address.

Kept placeKept per its path.
Review index back linkThe review index at its origin.

The anchor a page opens at and moves to is its location's fragment, so moves within the page stay in place wherever it is served.

A page rewrites its address, as when focus on changes or its baseline changes, only while its own address is its location, fragment aside. Served at another address, it leaves its location unchanged and changes only what it shows, so a reload opens the address the host served.

A page moves to another of the service's pages, as when a Jev mark's target is in another spec, by following a link to that page's address, never by setting its location, so a host's link handling applies to every move, as it does to the reviewer's own taps.

A page with no origin has no browser storage, so it keeps its fruit name, outbox, and drafts for as long as the host's frame lasts: across reloads and moves to the service's other pages in that frame, its unsent changes still send and its hand-off still lists the drafts it saved before them. Its kept place lasts only until the page reloads. What it keeps there is its own service’s: another service’s page in that frame never gets it, and once a page of another service writes there, the frame keeps of the first service only its reviewer, the browser id and fruit name, and its unsent changes, so when a page of that service opens in the frame again it is the same reviewer: its unsent changes send and its hand-off lists every draft it saved. Any later page in the frame can read the frame’s name, so it holds nothing past these rules. Once the host names its frame, the name is the host’s for the rest of the page’s life, even if the host clears it again: the page keeps nothing there, and its unsent changes still send from the page’s memory until it reloads.

A public service answers requests from any other origin, a page with no origin's Origin of null included, and their preflight, on every route a page or the comment layer requests, so such a page reads every answer it reads when served directly, its version tag included. An answer to a request with no Origin, or the service's own, carries no cross-origin permission.

Answering a page with no origin is safe because the service guards nothing by origin: it has no login, sets and reads no cookie, and its URL is not an authentication boundary (trust), as the review server's startup notice says. Whatever a page with no origin can send or read, anyone holding the URL can already send or read directly, and the browser sends such a page's requests with no credential. Agent events stay refused over HTTP whatever the origin (trust). Every origin is answered, since a host page of any site loads the comment layer, and Spec Chat names no host to list; it stays safe only by the no login, no cookie rule.

Only a public service, or one with a public base address, answers another origin; a private service answers every other origin, no origin included, with no cross-origin read. A private service is reached only through the reviewer's tunnel, yet any site the reviewer has open can send it requests, so answering them would let that site read the private service's review state. A page served at another address sends its requests from the reviewer's browser straight to its own address's origin, so it never reaches a private service anyway.

Proof

Served-address seam: the runtime's own address, given a document whose base address differs from its location and one with none, and the review server's answers to requests with and without an Origin of null.

First failing served-address test: a page whose base address names a spec other than its location's reads that spec's spool.
