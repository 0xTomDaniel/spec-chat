Jev review suggestions

docs / specs / jev-suggestions.spec.html

This spec owns Spec Chat's Jev contract, questions, and display; Every suggestion holds the rules every question follows. Jev questions read only specs and review threads, with no tracker or evidence dependency. Extends Git-derived focus and compared range.

User stories

As a reviewer in Git focus, I see which changed sections are scope or behavior changes and which are cosmetic, so I read the material ones first.

As a reviewer, an orphaned comment suggests where its passage moved, and one click moves it there.

As a reviewer, an open thread whose section was revised shows when the new text looks like it resolves my comment, so I resolve them all at once without rereading.

As a reviewer, a changed clause that contradicts or oversteps another clause in this or another spec is flagged with a link to it; following the link lands me on that clause, highlighted.

As a reviewer, a changed clause that contradicts or oversteps a clause another in-flight spec change makes is flagged on both specs' pages, each linking the other clause, so no spec quietly takes on another's responsibility.

As the owner shaping or delivering a spec, every cross-lane finding on my spec is an Important item in its /api/jev, so my compact Jev read lists it and I solve it before hand-off.

As a reviewer, a story no criterion verifies and a criterion no story backs are flagged while shaping.

As a reader, a reading view dims the internals in place, so the clauses written for me stand out and nothing moves or hides.

As a reviewer, when Jev is off, unsure, or failing, a one-word muted note names the question Jev could not answer, with the full sentence on hover, so I never mistake it for QA evidence, and the page otherwise works as today.

As a reviewer, Jev marks appear without a visible wait after the page renders, even while the box is busy.

As a reviewer, each actionable Jev note offers one button that drafts the comment it calls for, which I edit and send myself; with several notes of one kind on the page, one all (n) button handles them all.

As a reviewer, every Jev guess gives way to the real state once it settles, so a hint never outlives what it guessed.

As an agent reading /api/jev, every mark tells me its agent level, important or warning, beside the human level the reviewer sees as color.

As the operator, I can see for any suggestion which model, question set, and sources produced it, and with what confidence.

As a reviewer, a Contradicts or Oversteps flag points at a clause about the same thing as the flagged clause, so the flag is worth reading.

As a reviewer, headings, figures, examples, captions, TBD text, and preview blocks never draw a flag, and sibling rows of the same table never contradict each other, so I do not dismiss the same kinds of false flags repeatedly.

As a reviewer, each flag's popover quotes the flagged clause with its section heading and, for a table row, its column headers, so I understand the clause without navigating to it.

As the owner reading cross-lane findings on my spec, the findings are ranked by relevance like draft checks, not every pair of every changed clause, so I see the important conflicts first and irrelevant ones are not asked.

As the operator, I can see the before/after accuracy and flag counts on the audit's labelled cases, so I know the changes worked.

Acceptance criteria

When a spec change fixes a typo in one section and changes a rule in another, in Git focus, the rule's marker popover says Behavior and the typo's says Cosmetic, the typo is dimmed and readable, and neither section is tinted.

When a spec with change types, a Contradicts clause, a coverage gap, and several notes on one clause loads, each noted section or clause has exactly one margin marker, only the Contradicts and coverage-gap markers are colored, as mark levels fix, no text reflows or gains a tint, badge, or inline note, and hovering, focusing, or tapping a marker opens a popover listing all its notes.

When an answer is below threshold, fails twice, or there is no key, the item's popover shows its one-word question, such as story?, or Jev unavailable, muted, with the full sentence on hover, or the page shows one Jev off note, and review controls work unchanged.

When the reviewer changes the base, old labels disappear at once and the new base's labels replace them without a reload.

When a commented passage moves and its anchor is removed, its card shows Possibly moved to: that section with Go to; a deleted passage shows today's card.

When the reviewer clicks Move comment here, the orphaned thread is resolved and a draft comment at that section quotes the original, with no new event type.

When one open thread's section is revised to do what it asked and another's is revised unrelatedly, only the first shows Looks resolved, and both stay open.

When a thread shows Looks resolved, in light and dark theme, and is then resolved by any control, the tag is light green like the passed-evidence check, its text 4.5:1 readable, and once resolved the tag is gone and the thread shows its existing resolved indicator in its place, never a Jev label.

When a draft clause adds a behavior its own spec lists as a non-goal, and another restates a clause of another spec, the first shows Contradicts linking to that non-goal, and the second shows nothing.

When a lane changes a page header clause and a clause that another lane also serves a copy of, the header clause gets no question, and the clause is compared once, against main's copy, never against another lane's served copy; another lane's change reaches it only through cross-lane checks.

When slugs X and Y each change clauses against target main, Jev confidently says X's clause a contradicts Y's clause b and X's clause c oversteps Y's clause d, and another pair only overlaps, X's page shows Contradicts on a and Oversteps on c, Y's page shows Contradicts on b and Overstepped by on d, each note naming the other slug and linking its served clause with Ask agent to reconcile; a and b get the colored marker, c and d the grey dot; and the overlapping pair shows nothing on either page.

When X's and Y's /api/jev are read after those answers, and each owner runs the compact agent read, each response carries one lane item per finding on its own clause, with the label, its side, the other slug, and the other clause's served path and anchor as target, agent_level important for all four, and level important only for the contradictions; each agent read lists all four as Important; the board route lists each pair of paths once; and a question not yet answered counts as pending.

While cross-lane questions are unanswered, and when the same heads and target main are read again, both routes answer at once from held records, the missing questions are asked after answering, and a repeat read makes no provider call.

When a spec has a story no criterion verifies and a criterion no story backs, each shows its gap label, and adding the missing counterpart clears it on the next head.

When the reviewer turns reading view on, internals clauses are dimmed in place and readable, and no clause moves or hides.

When the reviewer clicks Ask agent to reconcile on a Contradicts clause, Ask for a criterion on a story gap, or Comment on this change on a Behavior section, from the marker popover, the comment composer opens at that element with the table's draft text, links to both clauses for reconcile, and nothing is written until the reviewer sends.

When the page shows n Important notes that carry Ask agent to reconcile, such as Contradicts, and m such Warning notes, such as Oversteps, with n at least 1 and n plus m at least 2, and the reviewer clicks Reconcile all (n) or the +m warnings link beside it in any of their popovers, the comment composer opens at that clause with one draft listing every Important such clause with its link, as the flags read, plus every Warning one only from the link; the link shows only when m is at least 1, sits on the button's line, a popover whose clause has several such notes shows the pair once, and nothing is written until the reviewer sends.

When the page shows two or more coverage gaps, stories with No criterion covers this and criteria with No story backs this, and the reviewer clicks Ask about all gaps (n) in any of their popovers, the comment composer opens at that clause with one draft listing every gap, as the batch table reads, and nothing is written until the reviewer sends; with one gap, only its own button shows.

When two or more open orphaned threads show Possibly moved to: and the reviewer clicks Move all (n) at the bottom of the thread list, each is moved exactly as its own Move comment here would, no other thread changes, and with one such thread the button is absent.

When a moved orphan is resolved, a coverage gap's counterpart is added, and a flagged conflict is reconciled on the next head, the moved thread shows only its resolved indicator, with no Possibly moved to:, Go to, or move button, and the gap and conflict marks are gone, each as settling fixes, with no Jev label left behind.

When the reviewer follows a conflict link to a clause in this or another spec, or clicks Go to on an orphan card, the page lands on that clause with the same outline an open TBD shows, and no other highlight style appears.

When a page's /api/jev and /api/evidence responses are read beside its markers and its agent read, each response carries the one levels table as levels, every item whose label is a mark kind carries level from its human column and agent_level from its agent column, each marker's color matches level, the agent read keys only on agent_level, and changing one cell changes the JSON and the one surface that reads it.

When n open threads show Looks resolved and the reviewer clicks Resolve all (n) at the bottom of the thread list, each of those threads is resolved with the existing resolve event, no other thread changes, no card shows its own Resolve thread button, and each card's own resolve control is unchanged; with none, the button is absent.

When a note is Cosmetic, Clarification, reading view, an unsure question, Jev unavailable, or Jev off, it shows no button, alone or in a batch.

When a criterion with a marker also has a thread pin, at 375px, 560px, and 1280px, the pin covers neither the marker nor any spec text, and a tap on each opens its own popover or thread.

Across a session with any suggestions and no note button click, spool, thread statuses, Finish eligibility, and spec bytes match Jev off, and every item stays present and 4.5:1 readable.

When the same page, base, and head load again, no Jev call is made and the same labels show.

Given a served spec whose questions are all answered in records, on a box whose load average exceeds its CPU count, GET /api/jev?path=<spec> answers in under 200 ms at the median of 10 sequential requests, measured before and after on the same box, with the same items, states, labels, and levels as before the change; a repeat read with an unchanged spec, spool, and served files parses no spec and runs no git process beyond resolving base, HEAD, and each repository's origin/main.

For every call, one record carries every record field and no source text, and no page, record, log, or response contains the key.

When a client sends text or parameters beyond path and base, the server ignores them.

When a spec has anchored headings (h1 to h6), figure, figcaption, pre, code, mock, and preview blocks, captions, elements with data-spec-tbd, and elements inside an anchor whose id contains source-issues, none of those anchors appear as a clause in draft-check questions, cross-lane questions, or as a candidate for any question, and the existing header and meta exclusions still apply.

When a leaf anchor's text is shorter than 20 characters, it is not a clause and not a candidate.

When two leaf clauses share the same parent table, list, or definition list, no draft-check or cross-lane question pairs them, and each is still paired with clauses outside its parent.

When a story and a criterion are in the same spec, no draft-check question pairs them; coverage owns that relationship.

When two slugs serve the same spec path and one clause from each is a draft-check or cross-lane candidate, a clause is compared once, against main's copy of that path, never against another slug's served copy of the same path.

When a clause sits inside a section with a heading, and when a clause is a table row, the question's state sends the section heading as section and, for a table row, its column headers as columns, alongside the clause text.

When a changed clause and a candidate are paired, a cheap yes/no about the same thing? question is asked first, and only pairs answered yes proceed to the contradicts/oversteps chain; a no answer records unrelated and shows nothing.

When the same clause text pair is asked about the same thing? again, the cached record is reused without a provider call, keyed by the same content hash as other question sets.

When a spec read builds 40 candidate pairs, the gate questions are asked in parallel, and a pair whose gate is no skips the contradicts/oversteps question entirely, so fewer provider calls are made than ungated pairs.

When two slugs each have 20 changed clauses, cross-lane pairs are ranked by the gate question and only the top 8 per clause that answer yes proceed to the lane question, instead of all 400 pairs.

When a slug's changed clauses include headings, figures, and TBD text, those are excluded from cross-lane questions by the same leaf filter as draft checks.

When a slug matches the pattern fx, lane, main, or ann followed by four or more digits (such as ann9200), its records are written to a separate test store, not the live records.jsonl, and its clauses are not candidates for any live slug's draft checks or cross-lane checks.

When the audit's labelled cases (270 wrong, 15 right, 2 missed) are run through the new pairing and leaf filter on the same question sets and provider, the wrong-flag count drops by at least 80% (at most 54 wrong), the 15 right flags are still shown, and the 2 missed real conflicts are still asked.

Modular boundaries

The review server's Jev seam owns questions, provider calls, one retry, thresholds, and records, which serve as the cache. It also owns the leaf filter, context builder, gate question, sibling and story-criterion skips, cross-lane ranking, and test-host dispatch. Caller-facing seam: GET /api/jev?path=<spec>&base=<id>[&view=reading], returning on or off, one state per item with its level and agent_level when its label is a mark kind, and the levels table. The gate's about question set is a new set in the same question-set directory. Dependency direction: calls OpenRouter as an external provider; reads local Git, served specs, and the spool; nothing calls back. The test store is a second JudgmentStore instance beside the live one. Observable scope: the JSON response and records (in live or test store), in single-root and registry modes.

The same seam owns cross-lane checks: which changed clauses of two slugs contradict or overstep, answered from its own registry, served files, local Git, and records. Caller-facing seam: lane items in each spec's /api/jev, and the parameterless GET /api/jev/board listing finding pairs of served paths for any reader. Dependency direction: self-contained within Spec Chat; readers depend on the routes, never the reverse; the seam knows slugs and specs, never lanes, owners, trackers, or what a reader shows. Observable scope: the two JSON answers and their records.

The browser runtime owns every marker, popover, reading view dim, and note button. Caller-facing seam: the rendered page; spool writes use existing events only. Dependency direction: self-contained within Spec Chat; consumes the seam route; no model, threshold, or key logic. Observable scope: what the reviewer sees.

Question sets own instructions, criteria, examples, and thresholds. Caller-facing seam: a set id and version. Dependency direction: self-contained data read by the seam. Observable scope: the version named in each record.

The anchor parser owns tag, parent, TBD, figure, and sibling detection; the leaf filter owns exclusion decisions from parsed anchors. Caller-facing seam: extract_anchors returns each anchor's tag, parent, children, and flags (tbd, figure, heading) used by the leaf filter. Dependency direction: self-contained; the parser reads HTML and returns data. Observable scope: the anchor dict and the questions the leaf filter produces.

The about question set owns the gate question's instructions, labels, examples, and threshold. Caller-facing seam: a set id and version, loaded by the existing load_question_sets. Dependency direction: self-contained data read by the seam. Observable scope: the version named in each record.

Fast reads

Every /api/jev read stays fresh: it builds its questions from the current spec, spool, Git, and served files, as today. What makes it fast is that a read never redoes work whose input has not changed since the last read. Kept results live only in the review server's memory, beside the records it already holds as its cache; nothing new is stored, and a restart starts empty.

Every suggestion

Only the review server calls Jev, OpenRouter typesafe/jev-1.13 through POST /api/alpha/decisions, with the jev provider file's key, read at each use (Providers); absent means Jev is off. The key never reaches the browser, a spec, spool, log, record, or pull request.

Every answer is a typed label with probabilities and a confidence. Deterministic code keeps owning facts, identity, workflow, and side effects; humans decide acceptance.

Every question is text within Jev's 32k token window; oversize state is withheld as neutral, never truncated.

The browser sends only the spec path and compared base. The server builds every question from its own served files, local Git, and the spool, so a public URL cannot submit text for classification.

No suggestion edits a spec, writes the spool, changes a thread, or affects Finish; only a human click on a note button writes, and only through existing events.

Nothing is hidden or reordered; dimmed text stays 4.5:1 readable; every note is text in a popover, and a colored marker also carries a glyph.

The page renders at once as today and labels arrive later; a base change drops all labels and asks again.

Every call appends one judgment record per question to JSONL in the server's state directory, outside spools and Git, with addresses but no source text or key, whether its label shows or not.

Moving an orphaned comment

Move comment here resolves the orphaned thread and starts a new draft comment at the suggested section that quotes the original, using only existing events; the agent answers it like any comment.

Markers

Jev adds no section tint, bar, inline badge, or inline note; the spec text keeps its layout, except that a block carrying both a marker and a thread pin reserves a right column for them so its text stays readable (pin clear of text). Git focus's own change highlight and the dims of cosmetic changes and reading view stay.

Each section or clause with any note gets one small marker in the right margin beside its first line, one per location however many notes it has.

Agent attention is much cheaper than human attention, so each mark kind has a level per audience: an agent gets the stricter one and must solve its Important marks before hand-off, and the human gets the quieter one. An agent level is never quieter than the human level.

The review server owns this table as its single source, as mark kind to a human and an agent level, each important or warning. It returns it as levels in /api/jev and /api/evidence, and puts level, the human column, and agent_level on each /api/jev item whose label is a mark kind. The browser colors every marker from the human column only: an item from its level, and a mark it derives, such as a coverage gap, evidence, or an unsure word, from the human column of levels; it holds no mapping of its own; the compact agent read (project rules) keys only on agent_level.

Both levels are fixed by mark kind, never by confidence. A marker is a colored ! when any of its notes is Important at the human level; else a small green check when its evidence is QA passed or QA passed · reworded, which has no level; else a quiet grey dot. The first that applies wins, and hover opens the popover for every kind. Both levels are advice only: color changes nothing else, with no folding, counts, or new UI. Overlaps still shows no mark (draft checks); its level applies only if it is shown.

Hover or keyboard focus opens its popover, a tap opens it on touch, and moving away, Escape, or a tap elsewhere closes it; the popover never covers review controls.

A popover lists, in this order, evidence (criterion evidence), conflicts, coverage, change type, and unsure questions or Jev unavailable, each note with its note button. Every note is one short line of a few words; the popover adds no box, rule, or heading between notes.

Draft checks

Only contradicts and oversteps show; overlaps is still answered and recorded but shows nothing, because restating a clause is normal in a spec set.

Clauses in the page header, such as title, source issues, and context, and in any section anchored as source issues, are neither asked nor compared against. The leaf filter further excludes headings, figures, examples, captions, TBD text, preview blocks, and anchors shorter than 20 characters.

Before the contradicts/oversteps chain, each candidate pair is asked the gate question; only pairs answered yes proceed. A no or unsure gate answer records unrelated and skips the chain.

Every question carries its clause text plus clause context: the section heading and, for table rows, column headers.

Two leaf clauses that share the same parent table, list, or definition list are siblings and are never paired in a draft check. A story and a criterion in the same spec are never paired; coverage owns that relationship.

Other specs are the lane's own served specs, those registered under the page's slug, as served, plus main's copy of every other spec path served by the registry, read from origin/main in that resource's root. Another lane's served copy is never a candidate, and each project and spec path is a candidate once. A path absent on main is skipped. In single-root mode, other specs are the root's other served specs.

Cross-lane checks

In registry mode, specs changing in flight are compared in full, so each keeps one contained responsibility and none creeps into another.

A slug's changed clauses are the leaf clauses of its served specs that differ from target main, each row root's origin/HEAD as last fetched, so shaping and delivering slugs alike are compared until they merge. The same leaf filter and header exclusions as draft checks apply.

For every two slugs, each changed clause of one slug is asked the gate question against every changed clause of every other slug. Only the top 8 per clause by gate confidence that answer yes proceed to the lane question, matching the draft-check candidate limit. Same slug pairs are the draft check's job. Clauses excluded by the leaf filter or same-path deduplication are dropped before any gate question is asked.

The pair question is its own versioned set, lane, with a directional answer: contradicts, which is symmetric; first oversteps second; second oversteps first; overlaps; or unrelated. One ask finds an overstep in either direction, so no pair is asked twice. The first clause is the lower slug's.

A confident contradicts or either overstep answer is a finding; overlaps, unrelated, unsure, unavailable, and off are none. A finding marks both clauses: each spec's /api/jev carries a lane item on its own clause with the label, its side, the other slug, and the other clause's served path and anchor, at the label's levels. An overstep reads Oversteps on the clause that oversteps and Overstepped by on the other. Every finding is Important for both owners; for the human, Contradicts is Important and an overstep a Warning.

The marks are the owners' to solve, as any mark Important at the agent level is before hand-off (project rules): a spec fix, a reason line in the spec, or a thread for the human. Ask agent to reconcile works on them as on draft checks, and a reconcile link opens the other slug's served clause.

The parameterless GET /api/jev/board keeps its answer shape and lists a pair of served paths once for any finding between them. What a reader of the board shows is the reader's own contract.

Both routes answer at once from held records and ask the missing questions after answering, as the board does today. On a page, each unanswered cross-lane question on its clauses counts as pending. In single-root mode there is one slug and no cross-lane check.

Test-host slugs are excluded: their clauses are not candidates for any live slug's cross-lane checks, and their records are kept in a separate store.

Clause pairing

A draft-check pair is a changed clause and a candidate clause. A cross-lane pair is a changed clause from one slug and a changed clause from another. Both use the same leaf filter, context, and gate question. The gate replaces the previous word-overlap ranking as the primary filter: candidates are enumerated, the gate drops unrelated pairs cheaply, and only related pairs proceed to the contradicts/oversteps chain.

Leaf clauses

A leaf clause is an anchor with no children, whose text is at least 20 characters, and that is not excluded by any of the following rules. The existing meta exclusion (corpus meta) is unchanged.

Excluded anchorHow detected
Heading (h1 to h6)Tag is h1 to h6

Pre, code, mock, previewTag is pre or code, or anchor id contains mock, preview, or example

An excluded anchor is excluded as both a clause (never asked) and a candidate (never compared against). The filter applies identically to draft checks, cross-lane checks, and the changed-clause builder.

Clause context

Every question carries its clause text plus structural context so the model reads the clause as a reviewer would. Context is derived from the parsed anchor tree, not generated.

Context fieldValuePresent when
sectionThe text of the nearest ancestor section's heading (h2 or h3)The clause has an ancestor section with a heading
columnsThe column header texts from the clause's table's thead, in orderThe clause's tag is tr, td, or th, or it is inside a table

Context fields appear in the question's state beside after and target. They are part of the cache key, so a clause under a renamed heading is re-asked.

Sibling skip

Two leaf clauses that share the same immediate table (table), list (ol, ul), or definition list (dl) parent are siblings. Neither draft-check nor cross-lane questions pair siblings: each sibling is paired only with clauses outside its parent container. Each sibling's question carries its column headers as context so the model reads each row in its table frame.

Story-criterion skip

A draft-check question never pairs a story (data-user-story) with a criterion (data-acceptance-criterion) in the same spec. Coverage owns that relationship.

Same-path deduplication

When two slugs serve the same spec path, a clause's candidates come from main's copy of that path, never from another slug's served copy. This is the existing behavior of corpus others, enforced at the seam: the served-specs builder de-duplicates by project and spec path, so the same file is a candidate once.

Gate question

Before asking contradicts or oversteps, each candidate pair is asked: Are these two clauses about the same thing? This is a yes/no Jev question using its own versioned question set, about. A yes answer means the clauses describe the same route, field, element, command, term, surface, or responsibility; the model sees the clause text, the context fields, and nothing else.

The gate precedes the yes/no contradicts/oversteps chain. The full sequence for a pair is: about? (yes) then contradicts? (no) then oversteps? A no or unsure (below threshold) gate answer records unrelated for the pair and skips the rest of the chain. The gate's record is keyed like any other question set, by the content hash of its inputs and set version.

Cross-lane checks use the same gate. For each clause of one slug, the gate is asked against every changed clause of every other slug, and only those answering yes proceed to the lane question. The top 8 per clause by gate confidence proceed, matching the draft-check candidate limit.

Gate questions are asked in parallel within one read, like other questions. A provider failure on the gate treats that pair as unrelated for this read and retries on the next read.

Test-host exclusion

Slugs whose name matches the pattern fx, lane, main, or ann followed by four or more digits are test or QA hosts. Their Jev records are written to a separate store file (records-test.jsonl) beside the live store, so test runs do not pollute live record lookups and do not grow the live file. Their clauses are not candidates for any live slug's draft checks or cross-lane checks.

Detection is by slug name at registration time. The review server holds one JudgmentStore for live and one for test; a read dispatches to the store matching its slug. The test store has no warm-up, no board contribution, and no onboarding effect.

Batch actions

Every per-item Jev button whose kind shows on two or more items of the page gets one all (n) batch, n the count; with one item, only its own button shows. A batch does what its per-item buttons would do, once, through the same draft or the same events; it adds no event, and a draft batch writes nothing until the reviewer sends.

A batch sits where its items' buttons sit: for popover notes, in each such note's popover on the button's line, as Reconcile all (n) does, once per popover however many of its notes carry it; for thread cards, at the bottom of the thread list beside Resolve all (n). Items are in page order.

Coverage

An item with no confident verifies is a gap; if any of its pairs is unsure, it shows criterion? on a story or story? on a criterion instead.

Reading view

A Reading view control on every HTTP-served spec is off by default and exclusive with Git focus.

for you is a clause that is user-facing or behavioral, what a user sees or what the result does, or architecture that is highly important: a hard-to-reverse boundary, a dependency direction, or a key interface. internals is everything else: implementation detail, mechanics, proofs, fixture or test detail, and minor structure.

Clauses in the User stories and Modular boundaries sections are for you by structure, with no Jev call. Each acceptance criterion is still asked; typical criteria are for you, and only criteria about proof or fixture mechanics are internals.

internals clauses are dimmed in place; for you, unsure, and failed clauses stay undimmed; comments and pins work unchanged.

Proof

First failing test: a fake provider answer below threshold returns unsure and appends an unsure record.

Levels per audience, first failing test: with the two-column levels from both routes, a coverage gap, evidence QA failed, and an unsure word keep their colors, read from the human column, and a cross-lane Oversteps item has level warning and agent_level important.

Batch first failing test: a page with two coverage gaps gives each gap's popover Ask about all gaps (2) drafting both lines in page order, and a page with one gives none.

Leaf filter first failing test: with a spec whose leaf anchors include a heading, a figure, and a TBD block, build_corpus_questions returns no question for any of them and no question targeting any of them.

Gate first failing test: with a fake provider answering no to the gate, build_corpus_questions returns no contradicts/oversteps question for that pair.

Sibling first failing test: with two leaf clauses under one table, build_corpus_questions returns no question pairing them.

Cross-lane first failing test: with 20 changed clauses per slug and a fake provider, the lane builder asks at most 8 lane questions per clause, not 400.

Test-host first failing test: a slug named ann9200 writes its record to the test store, not the live store.

Evidence: seam and runtime tests behind fakes for each filter, the gate, siblings, same-path, and test hosts; one live run per question set against real Jev; a QA bundle on a real spec change; and one run of the audit's labelled cases before and after.

Non-goals

Generated text of any kind, other providers, budget rules, specs outside the served collection, Jev questions beyond those listed here, semantic embeddings or vector similarity for pairing, LLM-generated context or summaries (context fields are parsed from HTML structure), and a new API route or response shape for pairing or the gate.
