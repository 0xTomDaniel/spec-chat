Jev review suggestions

docs / specs / jev-suggestions.spec.html

This spec owns Spec Chat's Jev contract, questions, and display; Every suggestion holds the rules every question follows. Jev questions read only specs and review threads, with no tracker or evidence dependency. Extends Git-derived focus and compared range.

User stories

As a reviewer in Git focus, I see which changed sections change behavior and which do not, so I read the material ones first.

As a reviewer, an orphaned comment suggests where its passage moved, and one click moves it there.

As a reviewer, an open thread whose section was revised shows when the new text looks like it resolves my comment, so I resolve them all at once without rereading.

As a reviewer, a changed clause that contradicts another clause in this spec, or contradicts, oversteps, or overlaps a clause in another spec, is flagged with a link to it; following the link lands me on that clause, highlighted.

As a reviewer, a changed clause that contradicts or oversteps a clause another in-flight spec change makes is flagged on both specs' pages, each linking the other clause, so no spec quietly takes on another's responsibility.

As the owner shaping or delivering a spec, every cross-lane finding on my spec is an Important item in its /api/jev, so my compact Jev read lists it and I solve it before hand-off.

As a reviewer, a story no criterion verifies and a criterion no story backs are flagged while shaping.

As a reader, a reading view dims the internals in place, so the clauses written for me stand out and nothing moves or hides.

As a reviewer, when Jev is off or failing, a muted note says so and names the question it could not answer, with the full sentence on hover, so I never mistake it for QA evidence, and the page otherwise works as it does with Jev off.

As a reviewer, Jev marks appear without a visible wait after the page renders, even while the box is busy.

As a reviewer, the shared review server keeps answering my pages and Jev reads after weeks of use, however large Jev's records grow.

As a reviewer, each actionable Jev note offers one button that drafts the comment it calls for, which I edit and send myself; with several notes of one kind on the page, one all (n) button handles them all.

As a reviewer, every Jev guess gives way to the real state once it settles, so a hint never outlives what it guessed.

As an agent reading /api/jev, every mark tells me its agent level, important or warning, beside the human level the reviewer sees as color; a neutral note carries neither.

As a reviewer, I never see a wall of conflict? marks: every Jev question is a yes or no, an unsure answer is settled by the general LLM, and Warning marks read light red, apart from grey neutral notes.

As the operator, I know each yes/no question's unsure rate and accuracy on this box's specs.

As the operator, I can see for any suggestion which model, question set, and sources produced it, and with what confidence.

As a reviewer, a Contradicts or Oversteps flag points at a clause about the same thing as the flagged clause, so the flag is worth reading.

As a reviewer, headings, figures, examples, captions, audit text, and preview blocks never draw a flag, so I do not dismiss the same kinds of false flags repeatedly.

As a reviewer, each flag's popover quotes the flagged clause with its surface, section heading, and, for a table row, its column headers, so I understand the clause without navigating to it.

As the owner reading cross-lane findings on my spec, the findings are filtered by relevance like draft checks, not every pair of every changed clause, so irrelevant pairs are not asked.

As the operator, I can see precision and recall on the eval set's labelled cases, so I know a Jev change worked.

Acceptance criteria

Given a reviewer in Git focus on a spec change that fixes a typo in one section, rewords a rule without changing it in a second, and changes a rule in a third, a fixture that must be added to provide it, When the reviewer opens each section's marker popover, Then the third's says Behavior, the first two say No behavior change and are dimmed and readable, and no section is tinted.

Given a reviewer on a spec with change types, a Contradicts clause, an Oversteps clause, an Overlaps clause, a coverage gap, and several notes on one clause, a fixture that must be added to provide it, When the reviewer opens the spec, Then each noted section or clause has exactly one margin marker, the Contradicts and coverage-gap markers show the Important color, the Oversteps and Overlaps markers are light red, and the rest are grey, as mark levels fix, and no text reflows or gains a tint, badge, or inline note.

Given a reviewer on a spec with several notes on one clause, a fixture that must be added to provide it, When the reviewer hovers that clause's marker, which needs a pointer that can hover, Then a popover opens listing all its notes.

Given a reviewer on a spec with several notes on one clause, a fixture that must be added to provide it, When the reviewer moves keyboard focus to that clause's marker, Then a popover opens listing all its notes.

Given a reviewer on a spec with several notes on one clause, a fixture that must be added to provide it, When the reviewer taps that clause's marker, which needs a touch screen, Then a popover opens listing all its notes.

Given a reviewer on a spec with Jev on, needs an induced failure: Jev and then the general LLM both fail on one question, When the reviewer opens that item's marker popover and hovers its note, which needs a pointer that can hover, Then the popover shows Jev unavailable, muted, with the full sentence naming the question on hover, and the reviewer can still comment and hand off.

Given a reviewer on a box with no Jev key, a fixture that must be added to provide it, When the reviewer opens a spec, Then the page shows one Jev off note, and the reviewer can still comment and hand off.

Given a reviewer in Git focus on a spec showing change-type labels, a fixture that must be added to provide it, When the reviewer changes the compared base, Then the old labels disappear at once and the new base's labels replace them without a reload.

Given a reviewer whose commented passage an edit moved to another section while removing its anchor, a fixture that must be added to provide it, When the reviewer opens that thread's card, Then the card shows Possibly moved to: that section with Go to.

Given a reviewer whose commented passage an edit deleted, a fixture that must be added to provide it, When the reviewer opens that thread's card, Then the card shows its orphaned thread with no Possibly moved to: and no Go to.

Given a reviewer whose orphaned thread's card shows Possibly moved to:, a fixture that must be added to provide it, When the reviewer clicks Move comment here, Then the orphaned thread shows as resolved, and a draft comment at that section quotes the original.

Given a reviewer with two open threads, one whose section an edit revised to do what it asked and one whose section an edit revised unrelatedly, a fixture that must be added to provide it, When the reviewer opens the thread list, Then only the first shows Looks resolved, and both stay open.

Given a reviewer whose open thread shows Looks resolved, a fixture that must be added to provide it, When the reviewer views the thread in light theme, Then the tag is light green like the passed-evidence check, and its text is 4.5:1 readable.

Given a reviewer whose open thread shows Looks resolved, a fixture that must be added to provide it, When the reviewer views the thread in dark theme, Then the tag is light green like the passed-evidence check, and its text is 4.5:1 readable.

Given a reviewer whose open thread shows Looks resolved, a fixture that must be added to provide it, When the reviewer resolves it with the card's own resolve control, Then the tag is gone, and the thread shows its existing resolved indicator in its place, never a Jev label.

Given a reviewer whose open thread shows Looks resolved, a fixture that must be added to provide it, When the reviewer clicks Resolve all (n) at the bottom of the thread list, Then the tag is gone, and the thread shows its existing resolved indicator in its place, never a Jev label.

Given a reviewer in Git focus on a draft whose first changed clause adds a behavior its own spec lists as a non-goal, whose second restates a clause of another spec, and whose third is unrelated to its best matches, a fixture that must be added to provide it, When the reviewer opens each clause's marker popover, Then the first shows Contradicts linking to that non-goal, the second shows a light-red Overlaps linking to that clause, and the third has no marker.

Given the operator on a box with Jev on, a fixture that must be added to provide it, When Jev answers a spec's draft-check, change-type, and rule-check questions, Then every record's labels are exactly yes and no, the other questions keep their two labels as the chains table lists, and a chain asks its next question only as its table says, proven by a unit test: no screen shows it.

Modular boundaries

The review server's Jev seam owns questions, provider calls, the retry pause, thresholds (including asymmetric show and verify cutoffs), the LLM verifier, and records, which serve as the cache. It also owns the candidate ranking, leaf filter, context builder, gate question, and test-store dispatch. Caller-facing seam: GET /api/jev?path=<spec>&base=<id>[&view=reading], returning on or off, one state per item with its level and agent_level when its label is a mark kind, and the levels table. The gate's about question set is a new set in the same question-set directory. Dependency direction: calls OpenRouter as an external provider for Jev decisions, and the box's Claude CLI as the general LLM for the verifier and non-draft-check fallback; reads local Git, served specs, and the spool; nothing calls back. A --test registration uses a second JudgmentStore instance beside the live one. A peer constructs JudgmentStore with a path in its own state; the path names that peer's store. Observable scope: the JSON response and records (live or test store), in single-root and registry modes.

The same seam owns cross-lane checks: which changed clauses of two slugs contradict or overstep, answered from its own registry, served files, local Git, and records. Caller-facing seam: lane items in each spec's /api/jev, and the parameterless GET /api/jev/board listing finding pairs of served paths for any reader. Dependency direction: self-contained within Spec Chat; readers depend on the routes, never the reverse; the seam knows slugs and specs, never lanes, owners, trackers, or what a reader shows. Observable scope: the two JSON answers and their records.

The browser runtime owns every marker, popover, reading view dim, and note button. Caller-facing seam: the rendered page; spool writes use existing events only. Dependency direction: self-contained within Spec Chat; consumes the seam route; no model, threshold, or key logic. Observable scope: what the reviewer sees.

Question sets own instructions, criteria, examples, and thresholds. Caller-facing seam: a set id and version. Dependency direction: self-contained data read by the seam. Observable scope: the version named in each record.

The anchor parser owns tag, parent, figure, and audit/history detection; the leaf filter owns exclusion decisions from parsed anchors. Caller-facing seam: extract_anchors returns each anchor's tag, parent, children, and flags (figure, heading, audit) used by the leaf filter, plus the spec title for the surface context. Dependency direction: self-contained; the parser reads HTML and returns data. Observable scope: the anchor dict and the questions the leaf filter produces.

The about question set owns the gate question's instructions, labels, examples, and threshold. Caller-facing seam: a set id and version, loaded by the existing load_question_sets. Dependency direction: self-contained data read by the seam. Observable scope: the version named in each record.

Fast reads

Every /api/jev read stays fresh: it builds its questions from the current spec, spool, Git, and served files. What makes it fast is that a read never redoes work whose input has not changed since the last read. Kept results live only in the review server's memory, beside the records it holds; nothing new is stored, and a restart starts empty.

A read answers only from records already recorded and never waits for Jev; a failed record answers until its pause ends: the same rule the /api/jev/board route follows, so there is no second mechanism. A question with no record comes back pending and is asked once, in the background; a later read while that ask is in flight does not ask it again. While any item is pending, the page asks /api/jev again every 2 seconds for the same base and shows each suggestion as its answer arrives, changing nothing else; it stops when nothing is pending, the base changes, or the page is hidden, and resumes when the page is shown.

The records are the cache: each is keyed by a hash of its question's inputs and set version, and a matching record is reused without calling Jev.

The records are plain JSONL files in the server's state directory on local disk, one line appended per record and no line ever rewritten, so they need no hosted service and any tool reads them line by line. They are split across files by cache key, so a lookup reads only the records that can hold its key, never the whole store.

The server holds in memory only the records its recent reads and writes used, up to a fixed bound that does not grow with the store, plus every rule dismissal, which stay few because only a human makes them. Starting the server reads no record.

No lock is held while a store file is read: a lookup that misses reads its file without making any other read or write wait, and a write is one append that waits for no read. The eval replay streams the files, holding one record at a time.

Each yes/no question has one versioned question set in this repository: instructions, yes and no criteria with examples, thresholds (show and verify cutoffs for draft checks, a single threshold for others), and whether it falls back to the general LLM. It is on whenever a key exists and is tuned from the eval set; any change is a new version.

Each question set carries 2 to 4 in-domain examples per label, drawn from the frozen eval set's train partition. The no criteria include near-miss exclusions: pairs that restate, extend, belong to another layer, are sibling rows of one table, or name a Jev label word. Each instruction is a single atomic judgment with no conditional branch; the non-goal check is a separate question set chosen by whether the candidate is a non-goal, not a conditional instruction within one set.

Asymmetric threshold

Each draft-check question set has two thresholds tuned from the eval set: a show cutoff and a verify cutoff, with verify below show.

P(yes)Draft-check action
At or above the show cutoffShow the mark directly
Between the verify and show cutoffsSend to the LLM verifier; show only if it confirms
Below the verify cutoffSilent no: the pair is recorded but nothing shows and nothing escalates

Both cutoffs are tuned per question on the eval set's train partition for precision at or above 80% at maximum recall, then reported on the test partition. Starting values: show 0.90, verify 0.70. A weak no never escalates to the general LLM and never shows an unsure mark; it is a silent no.

LLM verifier

When a draft-check answer falls in the verify band, the same pair goes once to the general LLM, the box's Claude CLI run the way the LLM fallback runs it, with the same llm_model. The verifier receives both clauses, their clause context, and must return a structured answer: yes with a quoted span from each clause that conflicts, or no. A mark shows only if the verifier answers yes and quotes a span from each clause. The verifier extends the existing general-LLM fallback mechanism with a stricter contract; it adds no new provider or endpoint.

The verifier's answer is one record: kind is the draft-check kind (contradicts, oversteps, overlaps), model is the LLM model, and the answer carries the label plus the quoted spans. A verifier answer of no records the silent no; a verifier call that fails records Jev unavailable and follows the one retry rule.

The verifier applies only to draft-check questions. Change type, scope, coverage, and reading view use the symmetric fallback; orphan and resolved show nothing when unsure.

Draft checks

Each changed clause and candidate pair is asked the draft-check chain; the first yes shows as Contradicts, Oversteps, or Overlaps, linking the candidate, and all no shows nothing. A non-goal candidate is asked only contradicts?.

Within a spec, only contradicts? is asked: a same-spec candidate, non-goal or not, stops after it, since a spec restates and extends its own clauses. Oversteps? and overlaps? run only against clauses of other specs and in cross-lane checks.

Clauses in the page header, such as title, source issues, and context, and in any section anchored as source issues, are neither asked nor compared against. The leaf filter further excludes headings, figures, examples, captions, audit and history text, and preview blocks.

Before the contradicts/oversteps chain, each candidate pair is asked the gate question; only pairs answered yes proceed. A no or unsure gate answer records unrelated and skips the chain.

Every question carries its clause text plus clause context: the surface, section heading and, for table rows, column headers.

Each changed clause is compared against the top 5 most relevant leaf clauses in the same spec, always including every non-goal, and the top 5 in other specs. Candidates are ranked by rarity-weighted word overlap: shared words weighted by inverse frequency across the spec collection, so domain-common words like spec or clause carry less weight than specific terms. Sibling rows of the same table, and stories paired with criteria in the same spec, remain eligible as candidates; the clause context (surface, section, column headers) lets the model tell complementary from contradictory.

Other specs are the lane's own served specs, those registered under the page's slug, as served, plus main's copy of every other spec path of the page's project served by the registry, read from origin/main in that resource's root; specs of another project are never candidates. Another lane's served copy is never a candidate, and each project and spec path is a candidate once. A path absent on main is skipped. In single-root mode, other specs are the root's other served specs.

Cross-lane checks

In registry mode, specs changing in flight are compared in full, so each keeps one contained responsibility and none creeps into another.

A slug's changed clauses are the leaf clauses of its served specs that differ from target main, each row root's origin/HEAD as last fetched, so shaping and delivering slugs alike are compared until they merge. The same leaf filter and header exclusions as draft checks apply.

For every two slugs of the same project, each changed clause of one slug is asked the gate question against every changed clause of every other slug; only pairs answered yes proceed to the lane question. Same slug pairs are the draft check's job. Clauses excluded by the leaf filter or same-path deduplication are dropped before any gate question is asked.

Each pair asks the yes/no questions: contradicts? once per pair, oversteps? once per direction, and overlaps? once only when every earlier answer is no. The first clause is the lower slug's.

A yes to contradicts? or to either oversteps? is a finding; overlaps, all no, unavailable, and off are none. A finding marks both clauses: each spec's /api/jev carries a lane item on its own clause with the label, its side, the other slug, and the other clause's served path and anchor, at the label's levels. An overstep reads Oversteps on the clause that oversteps and Overstepped by on the other. Every finding is Important for both owners; for the human, Contradicts is Important and an overstep a Warning.

The marks are the owners' to solve, as any mark Important at the agent level is before hand-off (project rules): a spec fix, a reason line in the spec, or a thread for the human. Ask agent to reconcile works on them as on draft checks, and a reconcile link opens the other slug's served clause.

The parameterless GET /api/jev/board keeps its answer shape and lists a pair of served paths once for any finding between them; slugs of different projects are never paired. What a reader of the board shows is the reader's own contract.

Each spec's /api/jev answers at once from held records and asks the missing questions after answering. The board answers at once with the last answer its background refresh computed, empty until the first refresh completes, and refreshes after answering. On a page, each unanswered cross-lane question on its clauses counts as pending. In single-root mode there is one slug and no cross-lane check.

Slugs registered with --test are excluded: their clauses are not candidates for any live slug's cross-lane checks, and their records are kept in a separate store.

Clause pairing

A draft-check pair is a changed clause and a candidate clause. A cross-lane pair is a changed clause from one slug and a changed clause from another. Both use the same leaf filter, context, and gate question. The goal is to compare every real claim with every related claim; the leaf filter drops non-claims and the gate drops unrelated pairs, so only related pairs proceed to the contradicts/oversteps chain. Context (surface, section, column headers) lets the model tell complementary from contradictory.

Same-path deduplication

When two slugs serve the same spec path, a clause's candidates come from main's copy of that path, never from another slug's served copy. This is the rule of corpus others, enforced at the seam: the served-specs builder de-duplicates by project and spec path, so the same file is a candidate once.

Candidate ranking

For each changed clause, candidates are ranked by rarity-weighted word overlap. Each word shared between the changed clause and a candidate contributes its inverse document frequency across the spec collection, so terms specific to a surface or concept rank higher than domain-common words. The top 5 same-spec candidates and top 5 cross-spec candidates proceed to the gate question. Non-goals are always included regardless of rank. A candidate that the gate rejects is not replaced; the chain runs only on gate-passed candidates.

Cross-lane pairs are not ranked: every pair of changed clauses, one from each slug, proceeds to the gate question, because both sides are changed and any conflict matters.

Gate question

Before asking contradicts or oversteps, each candidate pair is asked: Are these two clauses about the same thing? This is a yes/no Jev question using its own versioned question set, about. A yes answer means the clauses describe the same route, field, element, command, term, surface, or responsibility; the model sees the clause text, the context fields, and nothing else.

The gate precedes the yes/no contradicts/oversteps chain. The full sequence for a pair is: about? (yes) then contradicts? (no) then, for a candidate in another spec, oversteps? A no or unsure (below threshold) gate answer records unrelated for the pair and skips the rest of the chain. The gate's record is keyed like any other question set, by the content hash of its inputs and set version.

Cross-lane checks use the same gate. For each clause of one slug, the gate is asked against every changed clause of every other slug, and only those answering yes proceed to the lane question.

Gate questions are asked in parallel within one read, like other questions. A provider failure on the gate follows the one retry rule: the pair is unanswered until its pause ends, and the first read after the pause asks it again in the background. A failed gate is never recorded as unrelated.

Batch actions

Every per-item Jev button whose kind shows on two or more items of the page gets one all (n) batch, n the count; with one item, only its own button shows. A batch does what its per-item buttons would do, once, through the same draft or the same events; it adds no event, and a draft batch writes nothing until the reviewer sends.

A batch sits where its items' buttons sit: for popover notes, in each such note's popover on the button's line, as Reconcile all (n) does, once per popover however many of its notes carry it; for thread cards, at the bottom of the thread list beside Resolve all (n). Items are in page order.

Coverage

An item with no verifies is a gap; an unsure pair is settled by the LLM fallback first.

Reading view

A Reading view control on every HTTP-served spec is off by default and exclusive with Git focus.

for you is a clause that is user-facing or behavioral, what a user sees or what the result does, or architecture that is highly important: a hard-to-reverse boundary, a dependency direction, or a key interface. internals is everything else: implementation detail, mechanics, proofs, fixture or test detail, and minor structure.

Clauses in the User stories and Modular boundaries sections are for you by structure, with no Jev call. Each acceptance criterion is still asked; typical criteria are for you, and only criteria about proof or fixture mechanics are internals.

internals clauses are dimmed in place; for you and failed clauses stay undimmed; comments and pins work unchanged.

Measure

The data is a frozen, judged eval set: all known true positives from the audit plus a random sample of all asked pairs (not only flagged ones), each with clause and target text and a human-labelled ground truth. The set is split by spec into a train partition and a test partition. The eval set is frozen before any tuning; adding cases is a new version.

Live replay: the eval set's pairs are replayed through the current pipeline, including candidate ranking, gate, Jev questions, asymmetric threshold, and verifier. No simulated filter effects; each pair makes the calls the pipeline makes.

Each eval run reports per stage (candidate ranking, gate, Jev threshold, verifier) and per question: pairs asked, prevalence, TP, FP, FN, precision and recall of shown marks, with Wilson score intervals. Cutoffs are tuned on the train partition for precision at or above 80% at maximum recall, then reported unchanged on the test partition.

Every draft-check question that shows a mark reaches 80% precision on the test partition, with all known true positives kept. A question below 80% gets one more train-only tuning pass; if it is still below, its mark shows as a grey note with no level until it reaches 80%. Tuning runs in a separate correctness loop that uses this infrastructure.

The baseline is the first live replay of the frozen eval set through the current pipeline before any tuning. It reports the same per-stage metrics as tuning runs.

A human's rule decision, rule or not-a-rule, is a confirmed scope label at once. Every other resolution (fixed, dismissed, reason, thread) and silent-no records are unconfirmed until an independent agent audit labels them; an edit after a mark is not proof the mark was right. Confirmed labels accumulate in the existing records store; no dashboard, trend display, or running score is maintained. The score is computed by the eval replay when a Jev change is tested, nothing more.

When a Jev change (question set, threshold, pairing, verifier, model version) is tested, a separate reviewer agent (not the owner) labels a sample of unconfirmed fixes, dismissals, and silent-no pairs. The agent receives both full specs, the lane's spec diff, and the Jev record with its inputs and provenance, not just the two clauses. Its labels become confirmed. No human labeling step. The audit runs as part of the eval, not as a standing process.

Proof

First failing test: a fake provider answer below threshold returns unsure and appends an unsure record.

First failing chain test: with a fake provider answering yes to contradicts?, a draft check makes no second call and returns Contradicts; answering oversteps? with P(yes) below the verify cutoff, it makes no verifier or general LLM call and records a silent no.

Asymmetric threshold first failing test: with a fake Jev answering P(yes) = 0.95, the mark shows directly; at P(yes) = 0.80 (in the verify band), the verifier is called; at P(yes) = 0.50 (below verify), no mark shows and no verifier or fallback call is made.

Verifier first failing test: with a fake verifier returning yes and quoted spans from each clause, the mark shows with the label; with a fake verifier returning no, or yes without quoted spans, the mark does not show.

Top-k first failing test: with a changed clause and 20 candidate clauses, build_corpus_questions returns questions for at most 5 same-spec and 5 cross-spec candidates, always including non-goals.

Levels per audience, first failing test: with the two-column levels from both routes, a coverage gap and evidence QA failed keep their colors, read from the human column, and a cross-lane Oversteps item has level warning and agent_level important.

Batch first failing test: a page with two coverage gaps gives each gap's popover Ask about all gaps (2) drafting both lines in page order, and a page with one gives none.

Leaf filter first failing test: with a spec whose leaf anchors include a heading, a figure, and an audit block, build_corpus_questions returns no question for any of them and no question targeting any of them.

Gate first failing test: with a fake provider answering no to the gate, build_corpus_questions returns no contradicts/oversteps question for that pair.

Cross-lane first failing test: with 20 changed clauses per slug and a fake provider answering no to most gates, the lane builder asks only the lane question for pairs whose gate answered yes.

Test registration first failing test: a slug registered with --test writes its record to the test store, not the live store.

Provenance first failing test: a draft-check record written by a fake pipeline carries inputs with clause text and context, pairing with the ranking rule and rank, gate answer, and outcome with both cutoffs; when the verifier ran, the record carries the verifier answer and quoted spans.

Resolution first failing test: after a mark is dismissed with a reason, the record's resolution is dismissed (unconfirmed); after a spec fix clears the mark on the next head, the record's resolution is fixed, unconfirmed; after an audit labels it, the eval replay counts that confirmed label and excludes the unconfirmed dismissed one.

Record store first failing test: with a synthetic store of a million records, the server's peak memory after many reads and writes stays under a ceiling that does not change with store size, and a read of a held key answers while another lookup is reading its file.

Evidence: seam and runtime tests behind fakes for each filter, the gate, same-path, test hosts, asymmetric threshold, and verifier; one live run per question set against real Jev; the eval set replayed through the pipeline; and a QA bundle on a real spec change.

Non-goals

Generated text of any kind, other providers, budget rules, specs outside the served collection, Jev questions beyond those listed here, semantic embeddings or vector similarity for pairing, LLM-generated context or summaries (context fields are parsed from HTML structure), a new API route or response shape for pairing or the gate, pruning or expiring records, and QA pick improvements (those belong to jev-capture in AnnotateAnything).
