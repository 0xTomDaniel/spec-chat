Jev review suggestions

docs / specs / jev-suggestions.spec.html

Source issues: ANN-100.

Follows the shared Jev contract, annotateanything docs/specs/jev-seam.spec.html#contract (ANN-49, Jev agreement, at bf1a0e9, pairs pair-corpus, pair-audience, pair-thread): typed suggestions, unsure below threshold, Jev off note, errors show and retry, state changes only on a human click, one judgment record, cache per source revision, text only, server-side key. This spec owns Spec Chat's questions, criteria, and display, and does not use the contract's calibration gate (human, 2026-09-25: learn by doing); Spec Chat reads only specs and review threads, with no tracker or evidence dependency, and shares no code or data with annotateanything. Extends Git-derived focus and compared range.

User stories

As a reviewer in Git focus, I see which changed sections are scope or behavior changes and which are cosmetic, so I read the material ones first.

As a reviewer, an orphaned comment suggests where its passage probably moved, and one click moves it there; nothing moves unless I click.

As a reviewer, an open thread whose section was revised shows when the new text looks like it resolves my comment in spirit, so I can confirm and resolve it without rereading every thread.

As a reviewer, a changed clause that contradicts, overlaps, or oversteps a clause in another spec is flagged with a link to that clause, before anyone builds on it.

As a reader, a reading view puts the clauses written for me first and dims the internals, so I get what the spec means for me without losing anything.

As a reviewer, when Jev is off, unsure, or failing, a small note says so and the page otherwise works exactly as it does today.

As the operator, I can see for any suggestion which model, question set, and sources produced it, and with what confidence.

Where Jev runs

Only the review server calls Jev: OpenRouter model typesafe/jev-1.13 through POST /api/alpha/decisions. The browser never sees the key or the provider.

The server reads OPENROUTER_API_KEY from its environment, loaded from the box file at launch. The key never enters specs, spools, logs, judgment records, bundles, or pull requests.

With no key, the server reports Jev off: the page shows one small Jev off note in focus and is otherwise today's page.

The browser sends only the spec path, the compared base, and nothing else. The server builds every question from its own served file, local Git, and the spec's spool, so a public URL cannot submit arbitrary text for classification.

Change type in Git focus

Each changed root section of the current focus comparison gets one Choice question over its base text and current text: scope, behavioral, clarification, or cosmetic.

AnswerCriterionFocus treatment and badge
scope, confidentAdds, removes, or moves a capability, surface, or non-goalChanged highlight, strongest; badge Scope
behavioral, confidentAlters what the result does: a rule, interface, edge case, or criterionChanged highlight; badge Behavior
clarification, confidentSame behavior, meaning stated more preciselyChanged highlight, lighter; badge Clarification
cosmetic, confidentWording, typo, order, or style with no change in meaningDimmed, still 4.5:1 readable; badge Cosmetic
below thresholdNoneToday's changed highlight; small badge Unsure, never a best guess
oversize or offNoneToday's changed highlight; no badge
error or timeoutNoneToday's changed highlight; small marker Jev retrying, then Jev unavailable

On error or timeout the server retries automatically with bounded backoff, at most 3 retries at 2, 4, and 8 seconds; the page asks again while any item is retrying.

The marker clears when the answer lands; after the last retry it reads Jev unavailable until the next view. The same marker applies to an orphaned card.

Each question set states a moderate starting threshold, so labels show often and Unsure is the exception.

No label hides, collapses, or reorders a section; badges carry text, never color alone.

Focus renders at once as today; labels arrive later, and a slow or missing label never blocks or shifts review controls.

When the reviewer changes the base through the range bar, the page drops all labels at once, re-diffs as today, and asks again for the new base.

Unchanged sections and pages without focus=changes are never classified.

Orphaned comment location

A thread is orphaned when its anchor no longer exists in the current spec; today it keeps its sidebar card and stored quote and shows no pin.

The server picks up to 8 current anchors whose text best matches the stored quote, then asks one Choice question over the quote and candidate texts: one candidate, or none.

A confident candidate adds Possibly moved to: <section heading> to the orphaned thread's card, with Go to, which scrolls to and outlines that section, and Move comment here.

Clicking Move comment here appends one human move event naming the thread and the new anchor; the thread then pins to that section, keeping its messages, stored quote, and status.

The agent reads a move at the next hand-off as the thread's new anchor and owes it no reply.

Without that click the suggestion never re-attaches the thread, writes a spool event, or changes status.

A below-threshold answer adds a small Location unsure note; none, oversize, or off shows today's card only.

Open thread resolved in spirit

This is the contract's pair agree(revised spec text, open review comment): labels resolved in spirit, not addressed, or unsure.

A thread is asked when it is open, pending or acknowledged, its anchor exists, and its anchored section's text differs from the spec at the thread's newest human message.

The question receives the thread's human messages, the section's text at that message, and its current text; agent replies are left out, so Jev judges the text, not the claim.

A confident resolved in spirit adds a small Looks resolved label to the thread's card and pin; not addressed adds nothing, and below threshold adds unsure.

Resolving stays the existing human click; the label never resolves, reopens, or changes status, and never changes Finish eligibility.

A new head or base asks again; a new human reply makes the thread's comparison point move to that reply.

Draft against other specs

This is the contract's pair-corpus: labels contradicts, overlaps, oversteps, or unrelated, or unsure.

In Git focus, each changed clause or criterion, a changed anchored leaf block, is compared with clauses and criteria in the other specs of the served collection at head.

Deterministic code picks up to 8 other-spec clauses whose text best matches, always including any modular boundary that names the same surface; one question per pair.

Each confident flag adds a small label on the changed clause, such as Contradicts compared-range#bar-flow, linking to that clause; a clause may carry several, and below threshold adds unsure.

Flags never edit either spec, never block Finish, and never change thread state.

Reading view

This is the contract's pair-audience: each clause, an anchored leaf block, is labeled for you or internals for a reader who uses the result rather than builds it.

A Reading view control on every HTTP-served spec turns it on and off; it is off by default, and turning it on turns Git focus off, and back.

In reading view, within each section, for you clauses come first and internals follow, dimmed and still 4.5:1 readable; nothing is hidden and sections keep their order.

A clause below threshold shows a small unsure and stays in place undimmed, as do failed or oversize clauses; turning reading view off restores source order exactly.

Comments, pins, and threads work unchanged in reading view, anchored to the same blocks.

Cache and judgment records

Answers are cached per source revision, section anchor, thread id, or anchor pair, and question-set version. The revision is the compared base plus head, or the served bytes for a dirty working copy, so a new head or base classifies again and nothing else does.

A cached answer is reused without calling Jev again, so reload and repeat visits cost nothing.

Every call appends one judgment record in the contract's format, #record, including each failed attempt with its attempt number: addresses and revision, never source text or the key.

Records are append-only JSONL in the review server's state directory on the box, outside every spool and outside Git.

Question sets and learning by doing

The change-type, orphan-location, resolved-in-spirit, corpus, and audience question sets are versioned data in this repository: instructions, the criteria above with examples, and its stated threshold.

Every set is on whenever a key is configured; there is no labeled set, calibration command, or precision gate.

Criteria, examples, and thresholds are tuned from use: judgment records and what the reviewer does next, such as ignoring a label, resolving, or moving. Any change is a new question-set version, which classifies again.

Acceptance criteria

When a served spec change fixes a typo in one section and changes a rule in another, in Git focus with Jev on, the rule's section shows Behavior with the changed highlight and the typo's section shows Cosmetic, dimmed and still readable.

When a label is below threshold, there is no key, or the state is oversize, the section keeps today's changed highlight with, respectively, an Unsure badge, one page-level Jev off note, or nothing added, and review controls behave unchanged.

For any combination of labels, every changed and unchanged section stays present, in source order, and readable at 4.5:1 contrast.

When Jev errors or times out for a section, that section keeps today's highlight with a Jev retrying marker, the server retries at most 3 times at 2, 4, and 8 seconds, and the marker clears when the label lands or reads Jev unavailable after the last retry.

When the reviewer changes the base in the range bar, old labels disappear immediately and the new base's labels replace them without a reload.

When a commented passage moves to a new section and its anchor is removed, the orphaned thread's card shows Possibly moved to: that section, and Go to scrolls to and outlines it; a deleted passage shows today's card only.

When the reviewer clicks Move comment here, exactly one human move event is appended, the thread pins to the suggested section after reload with its messages, quote, and status unchanged, and the next hand-off needs no agent reply for it.

When one open thread's section was revised to do what its comment asked and another's was revised in an unrelated way, the first thread's card and pin show Looks resolved, the second shows nothing, and both stay open until the human resolves them.

When a draft clause states the opposite of a clause in another served spec, and another draft clause restates one, the first shows Contradicts and the second Overlaps, each linking to that other clause, and Finish stays available.

When the reviewer turns on reading view, within each section confident for you clauses come first and internals follow dimmed at 4.5:1 or better, every clause stays present, and turning it off restores the exact source order.

Across a review session with Jev on, any flags or reading view, and no human move click, the spool, thread statuses, Finish eligibility, and spec bytes match a session with Jev off.

When the same page, base, and head load a second time, no new Jev call is made and the same labels show.

For every shown or withheld answer, one judgment record carries every contract field, with no source text, and no page, record, log, or response contains the key.

When a client sends section text or any parameter beyond path and base, the server ignores it and classifies only its own served file, Git, and spool.

Modular boundaries

The review server's Jev seam owns questions, provider calls, thresholds, cache, and judgment records. Caller-facing seam: GET /api/jev?path=<spec>&base=<id> returns on or off, and per changed root anchor, changed clause, orphaned thread id, and revised open thread id a label, flags, or candidate, none, unsure, retrying, or unavailable; &view=reading returns per-clause audience labels. Dependency direction: calls Jev on OpenRouter as an external provider and reads local Git, the served collection's specs, and the spool; no tracker or evidence source; nothing calls back into the runtime. Observable scope: the JSON response and judgment records, in single-root and registry modes.

The browser runtime owns badges, focus treatments, corpus flags, reading view, error markers, orphan hints, Looks resolved labels, and the human move event. Caller-facing seam: the rendered Git focus, orphaned thread cards, and the move event in the spool schema. Dependency direction: self-contained within Spec Chat; consumes the seam route and holds no model, threshold, or key logic. Observable scope: what the reviewer sees in focus and on orphaned cards.

Question sets own instructions, criteria, examples, and thresholds. Caller-facing seam: a question-set id and version. Dependency direction: self-contained data read by the seam. Observable scope: the set version named in each judgment record.

Proof

Smallest first failing test: a fake provider answer below threshold returns no label and appends a withheld record.

Evidence: server tests behind a fake provider, runtime tests behind a fake route, one live smoke run per set against real Jev, and a QA bundle of Git focus and an orphaned card on a real spec change.

Non-goals

Generated text of any kind (ANN-96), other providers, or budget rules.

The contract's other pairs: stale proof and board flags (ANN-49). Comparing with specs outside the served collection.
