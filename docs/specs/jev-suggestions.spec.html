Jev review suggestions

docs / specs / jev-suggestions.spec.html

This spec owns Spec Chat's Jev contract, questions, and display; Every suggestion holds the rules every question follows. Jev questions read only specs and review threads, with no tracker or evidence dependency. Extends Git-derived focus and compared range.

User stories

As a reviewer in Git focus, I see which changed sections change behavior and which do not, so I read the material ones first.

As a reviewer, an orphaned comment suggests where its passage moved, and one click moves it there.

As a reviewer, an open thread whose section was revised shows when the new text looks like it resolves my comment, so I resolve them all at once without rereading.

As a reviewer, a changed clause that contradicts or oversteps another clause in this or another spec is flagged with a link to it; following the link lands me on that clause, highlighted.

As a reviewer, a changed clause that contradicts or oversteps a clause another in-flight spec change makes is flagged on both specs' pages, each linking the other clause, so no spec quietly takes on another's responsibility.

As the owner shaping or delivering a spec, every cross-lane finding on my spec is an Important item in its /api/jev, so my compact Jev read lists it and I solve it before hand-off.

As a reviewer, a story no criterion verifies and a criterion no story backs are flagged while shaping.

As a reader, a reading view dims the internals in place, so the clauses written for me stand out and nothing moves or hides.

As a reviewer, when Jev is off or failing, a muted note says so and names the question it could not answer, with the full sentence on hover, so I never mistake it for QA evidence, and the page otherwise works as today.

As a reviewer, Jev marks appear without a visible wait after the page renders, even while the box is busy.

As a reviewer, each actionable Jev note offers one button that drafts the comment it calls for, which I edit and send myself; with several conflicts on the page, one button drafts them all.

As an agent reading /api/jev, every mark tells me its agent level, important or warning, beside the human level the reviewer sees as color; a neutral note carries neither.

As a reviewer, I never see a wall of conflict? marks: every Jev question is a yes or no, an unsure answer is settled by the general LLM, and Warning marks read light red, apart from grey neutral notes.

As the operator, I know each yes/no question's unsure rate and accuracy on this box's specs, before and after the change.

As the operator, I can see for any suggestion which model, question set, and sources produced it, and with what confidence.

Acceptance criteria

When a spec change fixes a typo in one section, rewords a rule without changing it in a second, and changes a rule in a third, in Git focus, the third's marker popover says Behavior, the first two say No behavior change and are dimmed and readable, and no section is tinted.

When a spec with change types, a Contradicts clause, a coverage gap, and several notes on one clause loads, each noted section or clause has exactly one margin marker, the Contradicts and coverage-gap markers show the Important color, an Oversteps or Overlaps marker is light red, and the rest are grey, as mark levels fix, no text reflows or gains a tint, badge, or inline note, and hovering, focusing, or tapping a marker opens a popover listing all its notes.

When Jev and then the general LLM both fail twice on a question, or there is no key, the item's popover shows Jev unavailable, muted, with the full sentence naming the question on hover, or the page shows one Jev off note, and review controls work unchanged.

When the reviewer changes the base, old labels disappear at once and the new base's labels replace them without a reload.

When a commented passage moves and its anchor is removed, its card shows Possibly moved to: that section with Go to; a deleted passage shows today's card.

When the reviewer clicks Move comment here, the orphaned thread is resolved and a draft comment at that section quotes the original, with no new event type.

When one open thread's section is revised to do what it asked and another's is revised unrelatedly, only the first shows Looks resolved, and both stay open.

When a thread shows Looks resolved, in light and dark theme, and is then resolved by any control, the tag is light green like the passed-evidence check, its text 4.5:1 readable, and once resolved the tag is gone and the thread shows its existing resolved indicator in its place, never a Jev label.

When a draft clause adds a behavior its own spec lists as a non-goal, another restates a clause of another spec, and a third is unrelated to its best matches, the first shows Contradicts linking to that non-goal, the second shows a light-red Overlaps linking to that clause, and the third shows nothing.

When any Jev question is asked, and when Jev is below threshold on any question that shows a note, every record's labels are exactly yes and no, a chain asks its next question only as its table says, the unsure question goes once to the general LLM whose answer decides, and the page shows no unsure note such as conflict?, scope?, story?, or reader?; jev-read.py still counts each answer Jev was unsure of on its warnings line.

When a page shows an Important, a Warning, and a neutral marker, in light and dark theme, the Important marker keeps today's attention color and !, the Warning marker is a light red dot distinct from the grey neutral dot, each dot meets 3:1 against the page, and every popover text stays 4.5:1.

When the change ships, its pull request reports, for each yes/no question and for the old multi-way set it replaces, the unsure rate and the accuracy on a held-out test split of this box's served specs, as Measure defines.

When a lane changes a page header clause and a clause that another lane also serves a copy of, the header clause gets no question, and the clause is compared once, against main's copy, never against another lane's served copy; another lane's change reaches it only through cross-lane checks.

When slugs X and Y each change clauses against target main, Jev confidently says X's clause a contradicts Y's clause b and X's clause c oversteps Y's clause d, and another pair only overlaps, X's page shows Contradicts on a and Oversteps on c, Y's page shows Contradicts on b and Overstepped by on d, each note naming the other slug and linking its served clause with Ask agent to reconcile; a and b get the colored marker, c and d the light red dot; and the overlapping pair shows nothing on either page.

When X's and Y's /api/jev are read after those answers, and each owner runs the compact agent read, each response carries one lane item per finding on its own clause, with the label, its side, the other slug, and the other clause's served path and anchor as target, agent_level important for all four, and level important only for the contradictions; each agent read lists all four as Important; the board route lists each pair of paths once; and a question not yet answered counts as pending.

While cross-lane questions are unanswered, and when the same heads and target main are read again, both routes answer at once from held records, the missing questions are asked after answering, and a repeat read makes no provider call.

When a spec under shaping has a story no criterion verifies and a criterion no story backs, the story's marker popover shows No criterion covers this, the criterion's shows No story backs this, and adding the missing criterion or story clears each on the next head.

When the reviewer turns reading view on, internals clauses are dimmed in place and readable, and no clause moves or hides.

When the reviewer clicks Ask agent to reconcile on a Contradicts clause, Ask for a criterion on a story gap, or Comment on this change on a Behavior section, from the marker popover, the comment composer opens at that element with the table's draft text, links to both clauses for reconcile, and nothing is written until the reviewer sends.

When the page shows n Important notes that carry Ask agent to reconcile, such as Contradicts, and m such Warning notes, such as Oversteps, with n at least 1 and n plus m at least 2, and the reviewer clicks Reconcile all (n) or the +m warnings link beside it in any of their popovers, the comment composer opens at that clause with one draft listing every Important such clause with its link, as the flags read, plus every Warning one only from the link; the link shows only when m is at least 1, sits on the button's line, and nothing is written until the reviewer sends.

When the reviewer follows a conflict link to a clause in this or another spec, or clicks Go to on an orphan card, the page lands on that clause with the same outline an open TBD shows, and no other highlight style appears.

When a page's /api/jev and /api/evidence responses are read beside its markers and its agent read, each response carries the one levels table as levels, every item whose label is a mark kind carries level from its human column and agent_level from its agent column, each marker's color matches level, the agent read keys only on agent_level, and changing one cell changes the JSON and the one surface that reads it.

When n open threads show Looks resolved and the reviewer clicks Resolve all (n) at the bottom of the thread list, each of those threads is resolved with the existing resolve event, no other thread changes, no card shows its own Resolve thread button, and each card's own resolve control is unchanged; with none, the button is absent.

When a note is No behavior change, Overlaps, reading view, Jev unavailable, or Jev off, it shows no button.

When a criterion with a marker also has a thread pin, at 375px, 560px, and 1280px, the pin covers neither the marker nor any spec text, and a tap on each opens its own popover or thread.

Across a session with any suggestions and no note button click, spool, thread statuses, Finish eligibility, and spec bytes match Jev off, and every item stays present and 4.5:1 readable.

When the same page, base, and head load again, no Jev call is made and the same labels show.

Given a served spec whose questions are all answered in records, on a box whose load average exceeds its CPU count, GET /api/jev?path=<spec> answers in under 200 ms at the median of 10 sequential requests, measured before and after on the same box, with the same items, states, labels, and levels as before the change; a repeat read with an unchanged spec, spool, and served files parses no spec and runs no git process beyond resolving base, HEAD, and each repository's origin/main.

When the operator looks up the record of any shown or unsure suggestion, it names the model, the question-set id and version, the spec, anchor, and thread addresses with their revision, and the label with its probabilities and confidence, as the record fields list, with no source text, and no page, record, log, or response contains the key.

When a client sends text or parameters beyond path and base, the server ignores them.

Modular boundaries

The review server's Jev seam owns questions, provider calls, one retry, thresholds, and records, which serve as the cache. Caller-facing seam: GET /api/jev?path=<spec>&base=<id>[&view=reading], returning on or off, one state per item with its level and agent_level when its label is a mark kind, and the levels table. Dependency direction: calls OpenRouter as an external provider; reads local Git, served specs, and the spool; nothing calls back. Observable scope: the JSON response and records, in single-root and registry modes.

The same seam owns cross-lane checks: which changed clauses of two slugs contradict or overstep, answered from its own registry, served files, local Git, and records. Caller-facing seam: lane items in each spec's /api/jev, and the parameterless GET /api/jev/board listing finding pairs of served paths for any reader. Dependency direction: self-contained within Spec Chat; readers depend on the routes, never the reverse; the seam knows slugs and specs, never lanes, owners, trackers, or what a reader shows. Observable scope: the two JSON answers and their records.

The browser runtime owns every marker, popover, reading view dim, and note button. Caller-facing seam: the rendered page; spool writes use existing events only. Dependency direction: self-contained within Spec Chat; consumes the seam route; no model, threshold, or key logic. Observable scope: what the reviewer sees.

Question sets own instructions, criteria, examples, and thresholds. Caller-facing seam: a set id and version. Dependency direction: self-contained data read by the seam. Observable scope: the version named in each record.

Fast reads

Every /api/jev read stays fresh: it builds its questions from the current spec, spool, Git, and served files, as today. What makes it fast is that a read never redoes work whose input has not changed since the last read. Kept results live only in the review server's memory, beside the records it already holds as its cache; nothing new is stored, and a restart starts empty.

Every suggestion

Only the review server calls Jev, OpenRouter typesafe/jev-1.13 through POST /api/alpha/decisions, with the jev provider file's key, read at each use (Providers); absent means Jev is off. The key never reaches the browser, a spec, spool, log, record, or pull request.

Every answer is a typed label with probabilities and a confidence. Deterministic code keeps owning facts, identity, workflow, and side effects; humans decide acceptance.

Every question is text within Jev's 32k token window; oversize state is withheld as neutral, never truncated.

The browser sends only the spec path and compared base. The server builds every question from its own served files, local Git, and the spool, so a public URL cannot submit text for classification.

No suggestion edits a spec, writes the spool, changes a thread, or affects Finish; only a human click on a note button writes, and only through existing events.

Nothing is hidden or reordered; dimmed text stays 4.5:1 readable; every note is text in a popover, and a colored marker also carries a glyph.

The page renders at once as today and labels arrive later; a base change drops all labels and asks again.

Every call appends one judgment record per question to JSONL in the server's state directory, outside spools and Git, with addresses but no source text or key, whether its label shows or not.

The records are the cache: each is keyed by a hash of its question's inputs and set version, and a matching record is reused without calling Jev.

Each yes/no question has one versioned question set in this repository: instructions, yes and no criteria with examples, a moderate starting threshold, and whether it falls back to the general LLM. It is on whenever a key exists and is tuned from judgment records and what reviewers do next; any change is a new version.

Moving an orphaned comment

Move comment here resolves the orphaned thread and starts a new draft comment at the suggested section that quotes the original, using only existing events; the agent answers it like any comment.

Markers

Jev adds no section tint, bar, inline badge, or inline note; the spec text keeps its layout, except that a block carrying both a marker and a thread pin reserves a right column for them so its text stays readable (pin clear of text). Git focus's own change highlight and the dims of cosmetic changes and reading view stay.

Each section or clause with any note gets one small marker in the right margin beside its first line, one per location however many notes it has.

Agent attention is much cheaper than human attention, so each mark kind has a level per audience: an agent gets the stricter one and must solve its Important marks before hand-off, and the human gets the quieter one. An agent level is never quieter than the human level.

The review server owns this table as its single source, as mark kind to a human and an agent level, each important or warning. It returns it as levels in /api/jev and /api/evidence, and puts level, the human column, and agent_level on each /api/jev item whose label is a mark kind. The browser colors every marker from the human column only: an item from its level, and a mark it derives, such as a coverage gap or evidence, from the human column of levels; it holds no mapping of its own; the compact agent read (project rules) keys only on agent_level.

Both levels are fixed by mark kind, never by confidence. A marker is a colored ! when any of its notes is Important at the human level; else a small green check when its evidence is QA passed or QA passed · reworded, which has no level; else a light red dot when any note is Warning at the human level; else a quiet grey dot. The first that applies wins, and hover opens the popover for every kind. Both levels are advice only: color changes nothing else, with no folding, counts, or new UI.

The reviewer sees only the decided label; the agent read prints the count of answers Jev was unsure of, then settled by the LLM, as unsure N on its warnings line, so the agent sees it without acting on it.

Hover or keyboard focus opens its popover, a tap opens it on touch, and moving away, Escape, or a tap elsewhere closes it; the popover never covers review controls.

A popover lists, in this order, evidence (criterion evidence), conflicts, coverage, change type, and Jev unavailable, each note with its note button. Every note is one short line of a few words; the popover adds no box, rule, or heading between notes.

A one-word note is a short word or phrase with its full sentence on hover, and the sentence is its accessible name.

A Jev unavailable note is muted, so it reads as Jev and never as QA evidence, and its hover sentence names the question, e.g. Jev could not check which story this criterion verifies. Notes for different questions on one location each show once.

A conflict link or Go to that lands on a clause of this or another spec scrolls to it and gives it the open-TBD outline (TBD open) while that clause is the page address; it adds no highlight style of its own.

At 375px, markers sit at the content column's right edge without widening the page, and the popover opens as a sheet above the review controls.

A thread pin and a marker on the same block never cover each other or the spec text, at every width: the block reserves a right column for them, the marker beside its first line and the pin directly below the marker, and the block is at least tall enough to hold both, so neither reaches the next block.

Draft checks

Each changed clause and candidate pair is asked the draft-check chain; the first yes shows as Contradicts, Oversteps, or Overlaps, linking the candidate, and all no shows nothing. A non-goal candidate is asked only contradicts?.

Clauses in the page header, such as title, source issues, and context, and in any section anchored as source issues, are neither asked nor compared against.

Other specs are the lane's own served specs, those registered under the page's slug, as served, plus main's copy of every other spec path served by the registry, read from origin/main in that resource's root. Another lane's served copy is never a candidate, and each project and spec path is a candidate once. A path absent on main is skipped. In single-root mode, other specs are the root's other served specs.

Cross-lane checks

In registry mode, specs changing in flight are compared in full, so each keeps one contained responsibility and none creeps into another.

A slug's changed clauses are the leaf clauses of its served specs that differ from target main, each row root's origin/HEAD as last fetched, so shaping and delivering slugs alike are compared until they merge. Header clauses are excluded as in draft checks.

For every two slugs, every pair of changed clauses, one from each slug, in any file, is asked once, with no candidate cut. Same slug pairs are the draft check's job.

Each pair asks the draft-check yes/no questions: contradicts? once per pair, oversteps? once per direction, and overlaps? once only when every earlier answer is no. The first clause is the lower slug's.

A yes to contradicts? or to either oversteps? is a finding; overlaps, all no, unavailable, and off are none. A finding marks both clauses: each spec's /api/jev carries a lane item on its own clause with the label, its side, the other slug, and the other clause's served path and anchor, at the label's levels. An overstep reads Oversteps on the clause that oversteps and Overstepped by on the other. Every finding is Important for both owners; for the human, Contradicts is Important and an overstep a Warning.

The marks are the owners' to solve, as any mark Important at the agent level is before hand-off (project rules): a spec fix, a reason line in the spec, or a thread for the human. Ask agent to reconcile works on them as on draft checks, and a reconcile link opens the other slug's served clause.

The parameterless GET /api/jev/board keeps its answer shape and lists a pair of served paths once for any finding between them. What a reader of the board shows is the reader's own contract.

Both routes answer at once from held records and ask the missing questions after answering, as the board does today. On a page, each unanswered cross-lane question on its clauses counts as pending. In single-root mode there is one slug and no cross-lane check.

Draft text is fixed per button, never generated, and Jev never sends, resolves, or moves anything. A conflict label is a hint: reconcile drafts carry the flags as they read, and the shaping agent decides the direction.

Coverage

An item with no verifies is a gap; an unsure pair is settled by the LLM fallback first.

Reading view

A Reading view control on every HTTP-served spec is off by default and exclusive with Git focus.

for you is a clause that is user-facing or behavioral, what a user sees or what the result does, or architecture that is highly important: a hard-to-reverse boundary, a dependency direction, or a key interface. internals is everything else: implementation detail, mechanics, proofs, fixture or test detail, and minor structure.

Clauses in the User stories and Modular boundaries sections are for you by structure, with no Jev call. Each acceptance criterion is still asked; typical criteria are for you, and only criteria about proof or fixture mechanics are internals.

internals clauses are dimmed in place; for you and failed clauses stay undimmed; comments and pins work unchanged.

Measure

The data is the draft-check, change-type, and rule-check questions this box's served specs give today, split by spec into a train half and a test half, with a yes/no truth for every test question labelled by hand before either run.

One pass: the yes/no sets are written and tuned on the train half only, then the old multi-way sets and the new chains each answer the test half once, with no change after that run.

This spec's own first draft check is part of the data: the old multi-way set drew 27 Contradicts marks on it; the few that were real are fixed above, and the rest, such as the chain rows against the clauses they replace, are the false marks this change removes.

The pull request reports per question: unsure rate, the share of Jev answers below threshold before any fallback, and accuracy, the share of final answers matching the truth, with an old multi-way label read as the yes/no it implies.

Proof

First failing test: a fake provider answer below threshold returns unsure and appends an unsure record.

First failing chain test: with a fake provider answering yes to contradicts?, a draft check makes no second call and returns Contradicts; answering no below threshold to oversteps?, it makes one general LLM call and continues from its answer.

Levels per audience, first failing test: with the two-column levels from both routes, a coverage gap and evidence QA failed keep their colors, read from the human column, and a cross-lane Oversteps item has level warning and agent_level important.

Evidence: seam and runtime tests behind fakes, one live run per question set against real Jev, and a QA bundle on a real spec change.

Onboarding: not needed, this changes marker colors and note words only, with no new screen or step.

Non-goals

Generated text of any kind, other providers, budget rules, specs outside the served collection, and Jev questions beyond those listed here.
