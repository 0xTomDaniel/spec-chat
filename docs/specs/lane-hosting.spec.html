One lane slug across repositories

docs / specs / lane-hosting.spec.html

Extends skill/review-spec/SKILL.md, Remote hosting lifecycle. A spec lives in its repository and nowhere else. The lane slug is only a review-host name: it groups the specs one lane is changing, possibly in several repositories, under one review URL prefix and one index card while the lane is open, and teardown deletes it.

User stories

As a lane owner whose specs span repositories, I register every spec under the lane slug, so everything that reads the lane slug finds them all.

As a human reviewer, I open the review index and see specs grouped by lane and repository, each with its title, whether it changed since I last reviewed it, and how many of its comment threads are open and how many resolved, with the lanes and specs that need me first under In progress, and specs with no open lane out of the way in a collapsed Settled section at the bottom. From any spec page I can get back to it.

As a reviewer, a spec's review URL stays the same when the lane adds a spec from another repository.

Acceptance criteria

Given a lane owner whose lane already serves one project's specs from one repository. When they register a spec from a second project in another repository under the same lane slug. Then registration succeeds, the first project's specs keep their review URLs, and the new spec opens at a URL naming its project, with its own stylesheet and review controls.

Given a lane owner. When they register any spec. Then the registry row records as its path the URL path its spec is served at, without the leading slash, proven by a unit test: no screen shows it.

Given a lane owner whose spec is already registered. When they register it again under the same slug, project, and spec path from another root, such as a recreated worktree. Then registration succeeds, the spec keeps its review URL and is served from the new root and base, and no other spec's URL changes.

Given a lane owner with a spec row written before rows recorded a project. When they register that spec again at the same slug, root, and spec path. Then that same row gains the project and keeps its id and review URL, and no second row exists, proven by a unit test: no screen shows the registry.

Given a lane owner whose lane serves specs from two projects. When the first project's rows are removed. Then the second project's specs still open at their same review URLs.

Given a lane owner whose lane serves specs from two roots. When a human reviewer opens a spec from each root. Then each page shows its own threads and compares against its own base, and host baseline checks pass for both.

Given a human reviewer whose lanes hold specs that differ from their row base, match it, and are absent at it, on a fixture that must be added to provide them. When they open the review index. Then specs are grouped by lane and project in the index order, each spec row showing only its title link, status, and thread counts, with no served path or identifier text.

Given a human reviewer with specs under lane slugs, specs under a slug that is not a lane key, and specs served without a row, on a fixture that must be added to provide them. When they open the review index. Then the index shows one card per lane under an In progress heading, then one closed Settled (n) disclosure at the bottom holding every other spec, and a part with no specs is absent.

Given a human reviewer with changed, up-to-date, and settled specs, on a fixture that must be added to provide them. When they open the review index on a desktop screen and then on a phone screen. Then each spec status shows once, as the lane count or a Changed pill, with no “Up to date” on a spec row, text at 4.5:1 and stripes at 3:1, no sideways scrolling, and the index CSS has one ui tokens block with exactly the index tokens that its rules alone use.

Given a human reviewer on a served spec page on a narrow screen. When they open the review panel and then close it. Then the index link is hidden while the panel is open and shown again once it closes.

Given a human reviewer on a served spec page on a desktop screen. When they open the review panel. Then the index link stays visible beside the open panel.

Given a human reviewer whose lane holds a spec with draft, handed-off, replied, and resolved threads, on a fixture that must be added to provide those threads. When they open the review index. Then that spec\'s row shows two muted count pills, Open then Resolved, each reading its count and word, with the draft, handed-off, and replied threads all counted as open.

Given a human reviewer whose lane holds one spec with threads and one with none, on a fixture that must be added to provide them. When they open the review index. Then the spec with threads shows its count pills and the spec with none shows only its title, with no zero count.

Given a human reviewer with the review index open on a spec with one open thread, on a fixture that must be added to provide it. When they open that spec, resolve its thread, and go back to the review index. Then that row shows “1 Resolved” and no Open pill.

Given a human reviewer's spec whose spool holds comments, replies, edits, status changes, and hand-offs, including a hand-off that lists only some drafts. When the review index loads. Then the index counts each thread as resolved exactly when the spec page shows it resolved, and as open otherwise, proven by a unit test: no screen shows it.

Given a human reviewer whose system is set to dark appearance, on a fixture that must be added to provide a spec with threads in every status. When they open the review index. Then the index shows dark surfaces with light text, and every count pill and the Changed pill stay readable, text at 4.5:1 on its pill.

Onboarding: not needed, the review index and lane cards extend the review page with no new user surface.

Modular boundaries

The review host owns which root serves which path under a slug and records it as the row's path. Caller-facing seam: review-host register and the registry rows. Dependency direction: self-contained; the review server reads the rows and never decides paths itself. Observable scope: registry rows, served URLs, the review index, and registration errors.

Registry readers such as a worklane board own nothing here; they take each row's path as its served path. Caller-facing seam: the row's path. Dependency direction: external-provider; readers depend on the registry, never the reverse. Observable scope: links built from path.

The review server owns the index's thread counts: it folds each served spec's spool on index load and renders the counts in the index HTML; the counts need no script. Caller-facing seam: the index page at the server root. Dependency direction: external-provider; the index depends on the service fold over the spool, never the reverse, and writes nothing. Observable scope: count pills on index spec rows.

Served paths

A slug may hold several roots. A row's path is fixed when it is first registered: <slug>/<spec> while no other project holds rows under the slug, else <slug>/<project>/<spec>, spec pages and their relative assets alike, so the URL names the project only when needed.

RowServed path
New row while no other project holds rows under the slug<slug>/<spec>
New row while another project holds rows under the slug<slug>/<project>/<spec>

The project is the resource's PROJECT_ID as given at registration, recorded in the row as project.

Re-registering a row keeps its path. A new row gets the plain form only when no other project holds rows under the slug.

Each registry row records its served path as path. Readers use it rather than rebuilding a path from slug and spec.

Review index

The review index at the server root groups served specs by lane, then project, built only from the rows and the spec files it already serves. Lanes sit side by side where the width allows.

LevelShows, from existing data
Lane cardThe row slug written as an issue key (abc134 reads ABC-134) and a muted count over its specs with a status, “n of m changed” or “Up to date”, or “No status” when none has one; the card's left stripe is attention when any spec changed, else hairline.
Project labelThe row project, once per project in the lane.
Spec rowThe spec page's <title> as the link to its served path, and a “Changed” pill on the right when its status is changed; an up-to-date row shows no status, since the lane count says it.
Thread countsUnder the spec title, one count pill per thread status that has threads; nothing for a spec with no threads.
StatusChanged when the spec differs from its row base by the last reviewed version rule: in the row root, with GIT_OPTIONAL_LOCKS=0, git rev-parse <base>:<spec> differs from git hash-object <spec>, or the spec is absent at the base; otherwise up to date. None without a row or when the compare fails. The lane count and the Changed pill are its only words.

The index has two parts. “In progress” is a heading over the lane cards, one per open lane. A lane is open while rows exist under its lane key, a slug that reads as an issue key (abc230), since teardown deletes a lane's rows. “Settled (n)” is one native <details> at the bottom, closed by default, holding the n other specs: those under any other slug, such as the main collection registered as aa, and those served without a row. Settled groups them by project in the same spec row shape, a status shown where the row has one, and orders them as a lane's specs. A part with no specs is absent.

Order is a sort: lanes with any changed spec first, then the rest, each by issue number; projects by name; within a project, changed specs first, then by title. The served path, slug, row id, and base commit leave the index.

Design: the index CSS carries one named :root block, headed /* ui tokens */, holding the index tokens, and its rules use only those variables, no literal color, font, size, spacing, or radius. One heading “Review index” (h1); In progress and project labels are section labels; lane cards and Settled rows are surface with a border and the card radius; spec titles are card titles in link color, underlined on hover and focus; the lane stripe is attention when any spec changed, else border. Width up to 72rem. The index follows the system appearance: a prefers-color-scheme: dark block overrides the tokens with the dark values, the same ones the spec page chrome uses.

Thread counts

Each spec row shows how many of its comment threads are open and how many resolved, as at most two count pills on one line under its title, Open then Resolved. A thread is resolved when its status is resolved and open otherwise, whether draft, handed off, or replied. A pill reads its count then its word, such as “3 Open”, so color is never the only cue. A pill with no threads is absent; a spec with no threads shows its title alone. Pills are 12px, the count in weight 600 and the word in 400, on the status soft color, so they read quieter than the Changed pill.

Counts come from the spec's spool, folded by the service fold, the same statuses the spec page shows. No count is stored and no new file or route is added.

Counts are current at each index load; the counts need no script and the index does not poll for them. A reload re-renders it, and its ETag changes with the counts.

The counts are rendered by the review server itself, standard library only, so they show the same on a loopback server and on a hosted one.

Each spec row's title and status are kept per served spec file, keyed by the file's identity (device, inode, size, modification time) and, for status, the row base; the host records a row base as the commit it resolves to (registered base), so an unchanged key means an unchanged row. A row whose base is not a full commit id is compared on every load, uncached. Only a new or changed key rereads the title or reruns the git compare. Thread counts are kept per spool, keyed by the modification time of its human/ and agent/ directories, which change whenever an event file is added; only a changed key refolds the spool. Decided by the operator, 2026-09-26: the index loads warm in under 200 ms and renders exactly as uncached.

Every served spec page shows a fixed “Back to Spec Chat index” link to the review index. At phone width (640 px and narrower) the open review panel fills the screen, so the link is hidden while the panel is open and returns when it closes. At wider widths the panel sits beside the page and the link stays. Decided by the human, 2026-09-26.

Decided by the operator, 2026-09-26: the review index, every served spec page, and the unversioned .viz/runtime.js carry a strong ETag, the SHA-256 of the response body, keep Cache-Control: no-cache, and answer a matching If-None-Match with 304 and no body, since a spec or runtime changes in place. Files under .viz/vendor/ carry their version in the file name, so they carry Cache-Control: public, max-age=31536000, immutable. Errors and API routes keep today's headers.

The review server answers HTTP/1.1 with keep-alive: browsers send If-None-Match only for HTTP/1.1 responses, and one connection serves a page and its assets.
