One lane slug across repositories

docs / specs / lane-hosting.spec.html

Extends skill/review-spec/SKILL.md, Remote hosting lifecycle. A spec lives in its repository and nowhere else. The lane slug is only a review-host name: it groups the specs one lane is changing, possibly in several repositories, under one review URL prefix and one index lane while the lane is open, and teardown deletes it.

User stories

As a lane owner whose specs span repositories, I register every spec under the lane slug, so everything that reads the lane slug finds them all.

As a human reviewer, I open the review index and see first, under Needs you, the lanes with a spec waiting on me, each spec saying in one word what it waits on: a decision, a reply to read, a draft to send, or my acceptance; then the other open lanes, each spec saying whether it is with the agent, sent, or accepted, as its pull request records; and specs with no open lane out of the way in a collapsed Settled section at the bottom. Each spec shows its title, whether it changed since my last review, and its open and resolved thread counts, and each lane links its newest proof. From any spec page I can get back to it.

As a human reviewer, the review index reads like the evidence index beside it: quiet rows grouped by lane rather than boxed cards, each spec led by the status mark of its gate, its title never running under its gate word, the same type, colors, focus ring, and dark appearance, so the two indexes read as one tool.

As a reviewer, a spec's review URL stays the same when the lane adds a spec from another repository.

Modular boundaries

The review host owns which root serves which path under a slug and records it as the row's path. Caller-facing seam: review-host register and the registry rows. Dependency direction: self-contained; the review server reads the rows and never decides paths itself. Observable scope: registry rows, served URLs, the review index, and registration errors.

Registry readers such as a worklane board own nothing here; they take each row's path as its served path. Caller-facing seam: the row's path. Dependency direction: external-provider; readers depend on the registry, never the reverse. Observable scope: links built from path.

The review server owns the index's thread counts: it folds each served spec's spool on index load and renders the counts in the index HTML; the counts need no script. Caller-facing seam: the index page at the server root. Dependency direction: external-provider; the index depends on the service fold over the spool, never the reverse, and writes nothing. Observable scope: thread counts on index spec rows.

The review server owns each lane spec’s gate word and the index’s Needs you part: it reads the spec’s open decisions from the spec file, its threads and hand-offs from the same spool fold the thread counts use, and its acceptance and its lane’s proof from the evidence provider’s review facts. Caller-facing seam: the index page at the server root; to the provider, one GET <url>/review-facts per index load in the format review facts names. Dependency direction: external-provider for review facts, through the evidence provider file; Spec Chat names no provider product, and without a provider the index shows every gate it can read itself. Observable scope: gate words, the Needs you part, lane headers’ need counts and Proof links; the index writes nothing.

Served paths

A slug may hold several roots. A row's path is fixed when it is first registered: <slug>/<spec> while no other project holds rows under the slug, else <slug>/<project>/<spec>, spec pages and their relative assets alike, so the URL names the project only when needed.

RowServed path
New row while no other project holds rows under the slug<slug>/<spec>
New row while another project holds rows under the slug<slug>/<project>/<spec>

The project is the resource's PROJECT_ID as given at registration, recorded in the row as project.

Re-registering a row keeps its path. A new row gets the plain form only when no other project holds rows under the slug.

Each registry row records its served path as path. Readers use it rather than rebuilding a path from slug and spec.

Review index

The review index at the server root groups served specs by lane, then project, built only from the rows and the spec files it already serves. It is one column of rows, as the evidence index is: a lane is a group of rows under its header, never a boxed card.

Changed and Stale are its only words: the row base is the version of your last hand-off, so Changed says there is something new since you last reviewed, and nothing says up to date.

The index has three parts. “Needs you” is a heading over the open lanes with any spec whose gate needs you; “In progress” is a heading over the other open lanes; both show only when they hold a lane. A lane is open while rows exist under its lane key, a slug that reads as an issue key (abc230), since teardown deletes a lane's rows. “Settled (n)” is one native <details> at the bottom, closed by default, holding the n other specs: those under any other slug, such as the main collection registered as aa, and those served without a row. Settled groups them by project in the same spec row shape, a status shown where the row has one, and orders them as a lane's specs. A part with no specs is absent. The words are the ones the evidence index uses, and each index shows only its own gate: this one the spec review, the evidence index the merge ask.

Order is a sort: in each part, lanes by issue number; projects by name; within a project, specs that need you first, then changed specs, then by title. The served path, slug, row id, and base commit leave the index; a stale row shows only its spec path.

A gate word says what the spec waits on and who acts next, never how the file compares with a base. Accept spec sent is the instruction; Accepted is the record, read from the pull request’s receipt, never from the spool, so the index keeps no copy of an acceptance. Settled specs show no gate word.

Review facts: on each index load the server asks its evidence provider once, GET <url>/review-facts with one path parameter per lane spec’s served path, and reads {"specs": {"<path>": {"accepted": "<commit>", "proof": {"bundle": "<bundle id>", "url": "<bundle address>"}}}}, either key absent when the provider has none. A spec the answer leaves out has neither. Without a provider, or when the answer fails or does not come in time, the index renders at once with neither fact: Accepted never shows and Accept spec sent stays. A lane header’s Proof link opens url; framed by a host that asked for evidence opens, a click sends the evidence open with bundle instead.

Design: the index draws every color, type step, weight, space, radius, focus ring, status mark, and icon from the shared design set, the one the spec page chrome uses, and holds no value of its own. One title “Review index” (h1) at the title step with a muted count line beside it; Needs you and In progress are group headings with their counts; project labels are muted meta, never capitals. Spec rows are separated by hairlines, each led by its mark; a gate word is a quiet word in the meta step, in attention color when the gate needs you, else muted; spec titles are row titles in ink at medium weight, underlined on hover and focus. No card, border box, stripe, or pill. Width up to 48rem, one column. Under the set’s phone width the gate word moves under its title, and every row is a full-size touch target. The index follows the system appearance with the set’s dark values, and inside a host that passes its appearance, the host’s.

Thread counts

Each spec row shows how many of its comment threads are open and how many resolved, as one muted line under its title, open then resolved, such as “3 open · 5 resolved”. A thread is resolved when its status is resolved and open otherwise, whether draft, handed off, or replied. Each count reads its number then its word, so color is never the only cue. A status with no threads is absent; a spec with no threads shows no count line.

Counts come from the spec's spool, folded by the service fold, the same statuses the spec page shows. No count is stored and no new file or route is added.

Counts are current at each index load; the counts need no script and the index does not poll for them. A reload re-renders it, and its ETag changes with the counts.

The counts are rendered by the review server itself, standard library only, so they show the same on a loopback server and on a hosted one.

Each spec row's title and status are kept per served spec file, keyed by the file's identity (device, inode, size, modification time) and, for status, the row base; the host records a row base as the commit it resolves to (registered base), so an unchanged key means an unchanged row. A row whose base is not a full commit id is compared on every load, uncached. Only a new or changed key rereads the title, its open decisions, or reruns the git compare. Review facts are asked once per index load and never kept, since the pull request owns them. Thread counts are kept per spool, keyed by the modification time of its human/ and agent/ directories, which change whenever an event file is added; only a changed key refolds the spool. Decided by the operator, 2026-09-26: the index loads warm in under 200 ms and renders exactly as uncached.

Every served spec page shows a back link to the review index, a chevron and “Review index”, at the start of its fixed top line. At phone width (640 px and narrower) the open review panel fills the screen, so the link is hidden while the panel is open and returns when it closes. At wider widths the panel sits beside the page and the link stays. Decided by the human, 2026-09-26.

Decided by the operator, 2026-09-26: the review index, every served spec page, and the unversioned .viz/runtime.js carry a strong ETag, the SHA-256 of the response body, keep Cache-Control: no-cache, and answer a matching If-None-Match with 304 and no body, since a spec or runtime changes in place. Files under .viz/vendor/ carry their version in the file name, so they carry Cache-Control: public, max-age=31536000, immutable. Errors and API routes carry Cache-Control: no-cache and no ETag.

The review server answers HTTP/1.1 with keep-alive: browsers send If-None-Match only for HTTP/1.1 responses, and one connection serves a page and its assets.
