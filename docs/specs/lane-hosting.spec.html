One lane slug across repositories

docs / specs / lane-hosting.spec.html

Extends skill/review-spec/SKILL.md, Remote hosting lifecycle. A spec lives in its repository and nowhere else. The lane slug is only a review-host name: it groups the specs one lane is changing, possibly in several repositories, under one review URL prefix and one index card while the lane is open, and teardown deletes it.

User stories

As a lane owner whose specs span repositories, I register every spec under the lane slug, so everything that reads the lane slug finds them all.

As a human reviewer, I open the review index and see specs grouped by lane and repository, each with its title and whether it changed since I last reviewed it, with the lanes and specs that need me first under In progress, and specs with no open lane out of the way in a collapsed Settled section at the bottom. From any spec page I can get back to it.

As a reviewer, a spec's review URL stays the same when the lane adds a spec from another repository.

Acceptance criteria

Given slug ann45 with project aa registered from one repository, when project sc registers docs/specs/x.spec.html from another, registration succeeds, aa's specs keep ann45/<spec>, and x is served at ann45/sc/docs/specs/x.spec.html with its own stylesheet and runtime.

After any registration, every registry row carries path equal to the URL path its spec is served at, without the leading slash.

When a spec is registered again under the same slug, project, and spec path, at any root, for example from a recreated worktree, registration is an idempotent upsert: that one row is replaced with its new root and base, its path unchanged, nothing else moves, and no error is raised.

When a spec is registered at the same slug, root, and spec path as a row written before rows recorded a project, that row is the same row: it is upserted in place, gains the project, and keeps its id and path; no second row is created.

When aa's rows are removed and sc's remain, sc's specs keep ann45/sc/<spec>.

With two roots under one slug, each spec's spool, cursor, baseline, and last reviewed version belong to its own root, and host baseline checks pass for both.

Given registered rows whose specs differ from their row base, match it, and are absent at it, the index groups specs by lane and project in the index order, each spec row showing only its title link and status, with no served path or identifier text.

Given rows under lane slugs such as ann230, rows under another slug such as aa, and specs served without a row, the index shows one card per lane slug under an In progress heading, then one closed Settled (n) disclosure at the bottom holding every other spec; a part with no specs is absent.

At 1440 by 900 and 390 by 844, with changed, up-to-date, and settled specs, the index CSS has one ui tokens block with exactly the index tokens and its rules use only those variables, each spec status once as the lane count or a Changed pill, no “Up to date” on a spec row, text at 4.5:1 and stripes at 3:1, and no sideways drift.

On a served spec page at phone width, when the review panel opens and then closes, the index link is hidden while the panel is open and shown again once it closes; at desktop width it stays visible with the panel open.

Modular boundaries

The review host owns which root serves which path under a slug and records it as the row's path. Caller-facing seam: review-host register and the registry rows. Dependency direction: self-contained; the review server reads the rows and never decides paths itself. Observable scope: registry rows, served URLs, the review index, and registration errors.

Registry readers such as a worklane board own nothing here; they take each row's path as its served path. Caller-facing seam: the row's path. Dependency direction: external-provider; readers depend on the registry, never the reverse. Observable scope: links built from path.

Served paths

A slug may hold several roots. A row's path is fixed when it is first registered: <slug>/<spec> while no other project holds rows under the slug, else <slug>/<project>/<spec>, spec pages and their relative assets alike, so the URL names the project only when needed.

RowServed path
New row while no other project holds rows under the slug<slug>/<spec>
New row while another project holds rows under the slug<slug>/<project>/<spec>

The project is the resource's PROJECT_ID as given at registration, recorded in the row as project.

Re-registering a row keeps its path. A new row gets the plain form only when no other project holds rows under the slug.

Each registry row records its served path as path. Readers use it rather than rebuilding a path from slug and spec.

Review index

The review index at the server root groups served specs by lane, then project, built only from the rows and the spec files it already serves. Lanes sit side by side where the width allows.

LevelShows, from existing data
Lane cardThe row slug written as an issue key (ann134 reads ANN-134) and a muted count over its specs with a status, “n of m changed” or “Up to date”, or “No status” when none has one; the card's left stripe is attention when any spec changed, else hairline.
Project labelThe row project, once per project in the lane.
Spec rowThe spec page's <title> as the link to its served path, and a “Changed” pill on the right when its status is changed; an up-to-date row shows no status, since the lane count says it.
StatusChanged when the spec differs from its row base by the last reviewed version rule: in the row root, with GIT_OPTIONAL_LOCKS=0, git rev-parse <base>:<spec> differs from git hash-object <spec>, or the spec is absent at the base; otherwise up to date. None without a row or when the compare fails. The lane count and the Changed pill are its only words.

The index has two parts. “In progress” is a heading over the lane cards, one per open lane. A lane is open while rows exist under its lane key, a slug that reads as an issue key (ann230), since teardown deletes a lane's rows. “Settled (n)” is one native <details> at the bottom, closed by default, holding the n other specs: those under any other slug, such as the main collection registered as aa, and those served without a row. Settled groups them by project in the same spec row shape, a status shown where the row has one, and orders them as a lane's specs. A part with no specs is absent.

Order is a sort: lanes with any changed spec first, then the rest, each by issue number; projects by name; within a project, changed specs first, then by title. The served path, slug, row id, and base commit leave the index.

Design (ANN-301): the index CSS carries one named :root block, headed /* ui tokens */, holding the index tokens, and its rules use only those variables, no literal color, font, size, spacing, or radius. One heading “Review index” (h1); In progress and project labels are section labels; lane cards and Settled rows are surface with a border and the card radius; spec titles are card titles in link color, underlined on hover and focus; the lane stripe is attention when any spec changed, else border. Width up to 72rem. Light only; spec pages are unchanged.

Each spec row's title and status are kept per served spec file, keyed by the file's identity (device, inode, size, modification time) and, for status, the row base; the host records a row base as the commit it resolves to (registered base), so an unchanged key means an unchanged row. A row written before that rule whose base is not a full commit id is compared on every load, uncached. Only a new or changed key rereads the title or reruns the git compare. Decided by the operator, 2026-09-26 (ANN-178): the index loads warm in under 200 ms and renders exactly as uncached.

Every served spec page shows a fixed “Back to Spec Chat index” link to the review index. At phone width (640 px and narrower) the open review panel fills the screen, so the link is hidden while the panel is open and returns when it closes. At wider widths the panel sits beside the page and the link stays. Decided by the human, 2026-09-26 (ANN-277).

Decided by the operator, 2026-09-26 (ANN-178): the review index, every served spec page, and the unversioned .viz/runtime.js carry a strong ETag, the SHA-256 of the response body, keep Cache-Control: no-cache, and answer a matching If-None-Match with 304 and no body, since a spec or runtime changes in place. Files under .viz/vendor/ carry their version in the file name, so they carry Cache-Control: public, max-age=31536000, immutable. Errors and API routes keep today's headers.

The review server answers HTTP/1.1 with keep-alive: browsers send If-None-Match only for HTTP/1.1 responses, and one connection serves a page and its assets. Measured 2026-09-26 (ANN-188).
