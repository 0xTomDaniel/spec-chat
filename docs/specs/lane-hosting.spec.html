One lane slug across repositories

docs / specs / lane-hosting.spec.html

Extends skill/review-spec/SKILL.md, Remote hosting lifecycle. A spec lives in its repository and nowhere else. The lane slug is only a review-host name: it groups the specs one lane is changing, possibly in several repositories, under one review URL prefix and one index lane while the lane is open, and teardown deletes it.

User stories

As a lane owner whose specs span repositories, I register every spec under the lane slug, so everything that reads the lane slug finds them all.

As a reviewer, a spec's review URL stays the same when the lane adds a spec from another repository.

Acceptance criteria

Given a lane owner whose lane already serves one project's specs from one repository, a fixture must be added to provide it. When they register a spec from a second project in another repository under the same lane slug and open the new spec's review link. Then the new spec opens at a URL naming its project, with its own stylesheet and review controls.

Given a lane owner whose lane already serves one project's specs from one repository, a fixture must be added to provide it. When they register a spec from a second project in another repository under the same lane slug, then open one of the earlier project's specs at its review URL. Then that spec opens at the review URL it had before the second project was registered.

Given a lane owner. When they register any spec. Then the registry row records as its path the URL path its spec is served at, without the leading slash, proven by a unit test: no screen shows it.

Given a lane owner whose spec is already registered, a fixture must be added to provide it. When they register it again under the same slug, project, and spec path from another root, such as a recreated worktree, then open the spec's review URL. Then the spec opens at its same review URL, served from the new root and base.

Given a lane owner whose spec is already registered beside other registered specs, a fixture must be added to provide it. When they register it again under the same slug, project, and spec path from another root, such as a recreated worktree, then open another registered spec's review URL. Then that other spec opens at its same review URL.

Given a lane owner with a spec row that records no project. When they register that spec again at the same slug, root, and spec path. Then that same row gains the project and keeps its id and review URL, and no second row exists, proven by a unit test: no screen shows it.

Given a lane owner whose lane serves specs from two projects, a fixture must be added to provide it. When they remove one project's specs from the lane, then open a spec of the other project at its review URL. Then that spec still opens at its same review URL.

Given a lane owner whose lane serves specs from two roots, each spec with its own threads and base, a fixture must be added to provide it. When they open a spec from one root. Then the page shows that spec's own threads and compares against that root's base.

Given a lane owner whose lane serves specs from two roots, each spec with its own threads and base, a fixture must be added to provide it. When they open a spec from one root and then a spec from the other root. Then the page shows the other root's spec's own threads and compares against the other root's base.

Onboarding: not needed, a lane slug adds no user surface. Never strip proof clauses or rewrite unedited criteria: kept, each criterion here keeps its proof clause word for word, as the path field criterion does (shaping rule, repair rule). One hand-off control for desktop and phone: kept, a lane slug adds no page and no control; each spec it serves keeps its review panel’s one Hand off (phone rule, desktop rule). Any origin only without login or cookie: kept, a lane slug adds no login and no cookie (rule). Threads read as one conversation: kept, this spec shows no thread (rule). Every mockup at production fidelity: kept, this spec has no screen; the review index has its own spec, review index (rule).

Modular boundaries

The review host owns which root serves which path under a slug and records it as the row's path. Caller-facing seam: review-host register and the registry rows. Dependency direction: self-contained; the review server reads the rows and never decides paths itself. Observable scope: registry rows, served URLs, the review index, and registration errors.

Registry readers such as a worklane board own nothing here; they take each row's path as its served path. Caller-facing seam: the row's path. Dependency direction: external-provider; readers depend on the registry, never the reverse. Observable scope: links built from path.

Served paths

A slug may hold several roots. A row's path is fixed when it is first registered: <slug>/<spec> while no other project holds rows under the slug, else <slug>/<project>/<spec>, spec pages and their relative assets alike, so the URL names the project only when needed.

RowServed path
New row while no other project holds rows under the slug<slug>/<spec>
New row while another project holds rows under the slug<slug>/<project>/<spec>

The project is the resource's PROJECT_ID as given at registration, recorded in the row as project.

Re-registering a row keeps its path. A new row gets the plain form only when no other project holds rows under the slug.

Each registry row records its served path as path. Readers use it rather than rebuilding a path from slug and spec.
