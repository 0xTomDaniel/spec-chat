Shared review state

docs / specs / review-state.spec.html

One spec's review state is a conflict-free replicated set: several reviewers write it live, the agent edits the spec under it, and copies held offline merge without loss. The spool beside each spec is the one store; the decision and its tradeoff live in the review state CRDT ADR. The box service, its URL, and providers stay in Box review service and providers; owner wake stays in Review host wakes the owner pane.

User stories

As a human reviewer reviewing a spec with others, I see their comments, replies, edits, and resolutions on my open page as they save them, and nothing any of us saves is lost or overwritten.

As one of several reviewers, my hand-off sends my drafts and leaves another reviewer's unfinished drafts with them.

As a human reviewer, when the agent edits the spec during review, each of my marks stays on the text I marked, and the thread tells me when that text changed or is gone.

As a human reviewer on a laptop, I keep reviewing an open page when the connection drops, and everything I saved merges when it returns.

As a human reviewer, a comment or reply I typed and did not save is still there as my draft after I leave the page by any way and come back, kept wherever the page keeps my unsent changes, so leaving never loses what I wrote.

As the owning agent, I scan, reply, and keep my cursor by one contract however many reviewers write, and I read each mark at its current place in the spec I am editing.

Modular boundaries

The review service owns each spec's review state: storing events and spec versions idempotently, and resolving every mark to its place in the current spec. Caller-facing seam: /api/events, read with resolved places and written idempotently, and the spool directory beside the spec. Dependency direction: self-contained; it reads spec files and local Git and never writes repository state. Observable scope: spool files, version files, and /api/events responses.

The browser runtime owns showing shared state live, the browser's assigned fruit name, and the offline outbox of saved events not yet stored. Caller-facing seam: the page, and /api/events toward the service. Dependency direction: external-provider; the runtime depends on the service route, never the reverse. Observable scope: pins, threads, statuses, and the offline notice.

The review skill owns the agent side: zero-wait scan, batch processing, spec edits, replies, and cursor advance. Caller-facing seam: the scan's rows and the spool and cursor files. Dependency direction: self-contained on disk; it shares the service's resolver and needs no running service. Observable scope: scan output, agent events, and cursor contents.

Git owns spec text; the spec file in the worktree is the only live copy of it. Caller-facing seam: the spec file and its commits. Dependency direction: self-contained; review state points at spec versions by content hash, and Git never depends on review state. Observable scope: the spec file and its history.

Document model

Each spec's review state is two grow-only sets in its spool, plus values every reader derives the same way from them; a scope's hosted threads are a spool of the same shape with no spec, so the events part alone, and each mockup's is a spool of the same shape beside the mockup. Merging two copies is set union; nothing stored is ever changed or deleted.

Two folds exist, one per language, and give the same threads and statuses for the same events: the page's and the service's, which every service and agent reader uses, the review index and Jev among them. No third fold is added.

Every human event carries browser, a random id the page creates once and keeps in this browser, or, on a page with no storage whose address passes one, that id (phone shell), author, the fruit name assigned to that browser, and, when written on a spec page, version, the content hash of the spec text the page showed when it was written (served spec page).

A comment written on a host page through the comment layer also carries kind, label, and from from its anchor, and no version, so it resolves by anchor and quote; one on a subject that names no spec carries subject in place of a block anchor. A comment written on a spec page carries none of these.

A comment written on a mockup page with a walkthrough also carries step, the name of the step its frames showed (step threads); a comment on a video also carries moment, the video's time in seconds, and, when the reviewer drew one, box, its left, top, width, and height as fractions of the frame (video moment); a comment on a box may also carry picture, the file name of the picture its page made of the boxed spot (box picture).

Every message, a human's or the agent's, also carries stage, in words, the stage its lane was at when it was written, by the stage rule; a message with no lane, or written while its lane has no stage, carries none, and an edit carries none of its own. A comment with a lane also carries lane, the lane's review slug it took its stage from, which its thread's replies, the agent's included, take theirs from.

On first use, a browser is assigned one name at random from a fixed list and keeps it: Mango, Papaya, Lychee, Guava, Rambutan, Pineapple, Passion Fruit, Dragon Fruit, Durian, Jackfruit, Mangosteen, Starfruit, Soursop, Coconut, Banana, Tamarind, Longan, Feijoa, Cherimoya, Sapodilla, Kiwano, Pitanga, Jabuticaba, Salak. No name prompt appears. A page with no storage that takes its browser id from its address takes the name that browser's earlier events carry, and assigns one only when there are none.

Within one spec, browsers sharing a fruit name are numbered by their first event's file name: the first shows the name alone, the next adds 2, then 3. Every reader derives the same names, so authors stay distinct on every page.

File-name order breaks ties only between edits of one message; meaning follows references (respondsTo, threadId, supersedes), so a skewed clock changes at most which of two racing edits shows.

A message with more than one edit shows the effective text, and its thread history lists every edit with its author.

Live review

The page shows the review's new events within 2 seconds of their save, without reloading.

The page names each event before sending it, so a resend after a lost response stores nothing new.

A hand-off lists the event ids it hands off in events: its browser's drafts. Only those become pending; other reviewers' drafts stay drafts. A hand-off without events hands off every draft.

Accept spec is offered when every thread is resolved and no open TBD remains, whoever's thread it is, the threads of the spec's mockups included, and writes an empty hand-off, which for a spec with mockups names only each of its mockups, as acceptance of the set states. That hand-off is Spec Chat's only view of the acceptance: no registry row, file, or field copies it, and a caller that keeps acceptances quotes it in its own record.

The page shows no presence: no list of who is viewing and no live selections or cursors. Authors appear only on what they saved.

Marks through agent edits

The resolver finds a mark's source range in its event's version: the anchored block, then the target within it, the quote for a text target.

It maps that range through a character diff from that version to the current spec text, and reports the current block, range, and state below. The same inputs give the same answer on every reader.

An event with no version resolves by anchor and quote in the current spec.

The agent is the one writer of spec text. It edits the spec file in the worktree, Git stays the truth for that text, and marks follow by the diff mapping above. Reviewers change spec text only through comments and hand-offs that the agent applies; the page offers no direct text editing.

When the agent rewrites text a reviewer is commenting on, the edit lands and is never held back; the mark stays attached and shows changed or gone by the table above, including a comment saved from a page loaded before the edit.

Offline

The page keeps every event it saved and has not seen stored in browser storage for that page, and the events it last loaded.

While any saved event is not yet stored, the page shows Offline: n changes waiting, keeps every review action available, and sends the events in order as soon as the service answers.

A page opened later with waiting events sends them first, then reads.

Text typed in the comment box or a reply box and not yet saved is saved as a draft as the page is left, by a link, Previous or Next, an arrow key, Back, or closing the tab, so it waits in the outbox as any saved event does and shows as a draft when the page opens again; an Edit box left as it opened saves nothing. On a page with no origin it lasts as that page's outbox does, as long as its host's frame (served storage).

A waiting hand-off wakes the owner when the service stores it, by the wake rule.

Trust

The page has no login and its URL is not an authentication boundary. author is an assigned fruit name, not an identity, and is never checked.

Agent events are written only on disk; the service refuses an agent event over HTTP, so no page can speak as the agent.

The service never overwrites an event file; a write naming an existing file with different bytes is refused.

Proof

Seam: the resolver and the idempotent event write, tested over fixture spec versions and spool directories; the page through the runtime tests.

First failing test: an event resolved against a spec with a paragraph inserted above its quote reports state kept at the shifted range.
