User stories

As a product operator, I want a prompt to become clean durable issue and spec surfaces immediately so shaping survives a lost chat session.

As a reviewer away from the authoring machine, I want to comment and accept the spec from an ordinary mobile browser using one link so review requires no SSH or separate account.

As a feature author, I want every changed user-facing story to state whether the central guided journey extends so onboarding impact is explicit without forcing every feature into onboarding.

As a reviewer, I want TBDs marked for a later slice to leave spec acceptance available and each open TBD to be counted, highlighted, and reachable from the toolbar even while I have draft comments, so only real open questions stop spec acceptance and I always know how many remain.

As a human reviewer, I want sending my review and accepting the spec to have distinct names so no one mistakes a reviewed batch for approval to deliver.

As a reviewer on a keyboard or a browser agent, I want each block I can comment on to be a real button in comment mode so I can pick it without pointing at plain text.

As a reviewer answering a decision question in a spec, on a phone or a desktop, I want to press one of its answer buttons and have my answer saved as a draft comment on that question, so I answer without typing and the agent gets my answer like any comment.

As a reviewer, I read one short ADR per current decision, holding only its context, the decision, why, alternatives rejected, and consequences, and find each repo-wide rule as a spec criterion and each mechanic in code, so no review means reading a decision's history.

As a feature author, I want how my screens look and move to stay in the design system and its shared parts, out of my spec, and the validator to flag look and motion mechanics that creep in, so a change to a color or an animation never becomes a spec change, a review, and an acceptance.

As a QA capture program, I drive every acceptance criterion from its Given, When, and Then without guessing, take its concrete values from the target's qa.toml hint file, and read in plain words which gesture, timing, induced failure, or unit-test proof a criterion needs.

As a product reader, I read every criterion as a role in a situation and an outcome in product terms, with no fixture name, artifact path, or test harness in the spec, so the spec says what the product does and the target says how it is tested.

As a target repository whose QA and review gates read proof clauses in criteria, such as proven by a unit test: no screen shows it, I decide how my criteria are tested: shaping and repair never strip or reword those clauses, shaping never rewrites a criterion its change does not otherwise edit, and new criteria carry a clause where my project rules call for one.

As a feature author, when the spec my change lands in holds separate domains, I want shaping to propose splitting it as a question I answer on the review page, so my change lands in its own domain's spec and unrelated changes stop editing one file at once.

As a feature author whose change adds or changes a screen, I want shaping to draw each such screen as a mockup beside the spec, at desktop and phone, with real content and my repo's design tokens, so the reviewer decides on a picture as well as on the words.

As a feature author whose change adds or changes a screen, I want shaping's first round to show that screen's directions side by side, each with what it gives up, and its pick with a reason, and every later round only the direction kept, so the reviewer chooses between real options in the round they review anyway and review is no slower for it.

Modular boundaries

Every shaped spec includes one concise Modular boundaries section naming responsibility, caller-facing seam, dependency direction, and observable scope. On a single-module spec, the section defines that module's own boundaries.

The section stays architectural and omits classes, functions, files, and replaceable implementation detail.

A contract-bearing semantic diagram is the default when more than one meaningful module relationship exists.

The same stable responsibilities, interfaces or seams, and dependency direction remain current in the target-declared architecture source.

Issue-specific behavior and acceptance detail remain in the spec rather than being copied into architecture.

Guided-journey declarations do not invert runtime ownership: the central registry owns journey order, while feature modules own their targets and semantic success milestones.

The review runtime owns spec acceptance eligibility and open-TBD highlighting. The caller-facing seam is the spec markup: each data-spec-tbd marker and its value. Direction is self-contained: authoring writes markers, the runtime only reads them. Observable scope: the hand-off action label, the Next TBD button, their activation, and TBD block highlighting.

The review runtime owns answer buttons: saving each answer as a comment and showing the chosen mark. The caller-facing seam is the spec markup: a button's data-spec-choice value inside an anchored block. Direction is self-contained: a page declares its answers, the runtime reads them and writes the existing comment event, and agents read that event as any comment. Observable scope: the chosen mark, the draft thread, the drafts count, and the hand-off batch.

The structural validator owns the mechanics warning. The caller-facing seam is the spec markup: each clause's text and the same clause at the exact base. Direction is self-contained: the validator reads the spec file and its base offline, and the design system it points authors to is the target's, never read. Observable scope: one warning per warned clause, naming it and the words that raised it, with the validation result unchanged.

The structural validator owns the two-screen warning. The caller-facing seam is the spec markup: each criterion's Then, its data-one-screen reason, and the same criterion at the exact base. Direction is self-contained: authoring writes the reason, the validator only reads it. Observable scope: one warning per warned criterion, naming it and the words that raised it, with the validation result unchanged.

Outcome

Every new work unit begins with a plain-language feature prompt.

The workflow creates clean durable issue and spec surfaces immediately, then iterates on those surfaces instead of treating chat context as product truth.

The canonical HTML spec and its Spec Chat overlay are the only required human review surface for spec behavior.

Correctness survives agent, session, CLI, and host replacement through plain files and cold reconstruction.

Source ownership

The issue surface owns current high-level intent, desired outcome, non-goals, dependencies, and governing source links.

Implementation tickets, with their outcomes and blocker relations, are delivery's, outside Spec Chat.

The canonical spec owns current user stories, detailed behavior, constraints, edge cases, interaction contracts, and acceptance criteria.

Each changed user-facing story declares in canonical HTML whether it requires a guided-journey extension; no declaration is copied into lifecycle tracking or generated catalogs.

Linear carries issue lifecycle and governing links, not canonical story or guided-journey declaration text.

Markdown story catalogs remain generated downstream QA output.

An ADR owns one hard-to-reverse decision: its context, the decision, why, alternatives rejected, and consequences, kept short; it holds no policy section and no mechanics.

A repo-wide rule, a promise a later feature could break and never a design-system convention, lives once, in its home spec, as an acceptance criterion whose text says it applies to every feature and that its home spec marks as a project rule, so Jev checks it as a project-wide rule. An ADR may name a rule it decided on only by linking that criterion, as in see peer-seams#acceptance-ci, and never restates it: the why lives in the ADR, the what in the spec criterion, and the mechanics in code and the change request.

Implementation mechanics no caller depends on, such as storage tables, retry counts, internal keys, timeouts, and delivery details, live in code and the change request; neither a spec nor an ADR states them.

Look and motion mechanics, such as animation timings and their order, easing, colors, and spacing, belong to the design system, its design document and shared parts; a spec states what the user sees and links the design system for how it looks or moves, and neither a spec nor an ADR states them. A timing the user feels is an outcome and stays one, as the list shows within two seconds. The structural validator flags these mechanics where they creep in, as the mechanics warning states.

Specs carry no ticket or issue link; git history is the provenance record.

The evolving draft change request carries durable commits and history, but it is not a required human spec-review surface.

The actor-segregated review spool owns comments, replies, hand-offs, and their causal order.

The existing review context file carries only concise cold-recovery facts that have not yet become canonical behavior.

Conversation and model memory are evidence only and never override a durable current source.

Prompt-first shaping flow

The caller owns the issue; shaping never waits on it.

The caller keeps the issue always-most-recent and clean, replacing its content on later passes rather than retaining the raw prompt or accumulating summaries.

The agent creates the work branch, and that branch supplies the local Git comparison baseline.

The short seed pass lists every spec and ADR in the target, at least by title, and reads target instructions, the spec index, the specs and ADRs that own the behavior being changed, and directly relevant product or workflow docs.

The seed pass defers code, tests, configuration, and package inspection unless durable docs conflict or cannot identify the correct spec surface.

The issue retains links only to sources that actually govern the work, never a bibliography of everything inspected.

The agent writes one concise current spec seed before deeper grilling; the issue seed is the caller's.

When a relevant canonical spec exists, the agent edits it in place.

When no relevant spec exists, the agent creates a minimal durable capability or domain spec with only sections that contain real behavior.

When the spec a change lands in holds separate domains by the split check's signals, the change included, the agent writes an open TBD at the change proposing that split and naming each new spec, with answer buttons to split or keep one spec; size alone never raises it. On split, the split is made as the split check states, as its own commit before the change moves to its new spec.

When a change adds or changes a screen, the seed pass also writes or updates a mockup of each such screen in the spec's mockup set, at desktop and phone, at production fidelity (production fidelity): for a product that runs, the screen's mockup file naming its running prototype's route, regions, and steps, the prototype itself being the project's own frontend code, a route of its app or a harness page, written on the lane branch outside the shaping skill (prototype), and a drawn mockup only of chrome the project does not own, from that chrome's design source (drawn chrome); with a walkthrough for a screen that changes as its user acts or moves on its own (walkthrough), each part and step naming the spec anchors it illustrates, and commits it with the spec; a change with no screen writes none. A screen's first round shows its directions: two, or three when one differs in kind, each with the line saying what it gives up and the pick with its reason, each other direction another route of the same prototype or, for a drawn mockup, its own frames; the round after keeps the direction the reviewer picked, else the pick, and removes the rest, so later rounds and a change with no screen show none.

The spec carries no ticket or issue link; git history is the provenance record.

The first seed is committed locally, passes the structural validator, is hosted, and its review link is sent at once; the caller publishes the issue, branch, and draft change request in parallel.

After the link is sent, the agent inspects only relevant code, tests, configuration, and branch state before asking questions those sources can answer.

A contradiction between specs means one is out of date: shaping updates the out-of-date spec in the same change, and a real design choice goes to the human as an open TBD. Any other conflict between durable sources stops shaping visibly instead of being resolved from chat or model memory.

Shaping completeness

Every governing HTML spec contains explicit anchored user stories, and every user outcome created, changed, or retired by the work is current there.

Every changed user-facing story declares data-guided-journey="yes|no"; no requires no rationale and does not imply universal onboarding.

A yes declaration links one applicable guided-journey step and states passive or required; required also names the feature-owned semantic success milestone.

Shaping creates and maintains declarations, review evaluates their semantic correctness, and structural validation checks only presence and reference integrity on changed specs.

Each candidate acceptance criterion is classified as clear, gap, or not needed.

A clear criterion names an observable outcome and an identified governing spec rule.

A clear criterion stays at user-story level, what a person does and sees and never a click script, so a QA capture program can drive it without guessing; the rules below apply at shaping to each criterion the change adds or edits, and at repair to every criterion. Shaping never edits a criterion only to bring it to these rules: a criterion the change does not otherwise edit keeps its text word for word.

One scenario per criterion: no Given or When joins alternatives with or; each alternative becomes its own criterion.

Then names the observable outcome in product terms, what the user sees at the end, as in the account's cost page shows the generation under user-driven cost; it names no artifact path, capture file, command, or test output. When no screen shows the outcome, the no-screen recipe applies instead. A Then that states only an absence also names something visible that proves the end state was reached, and a Then never defers to other contracts, as in remains governed by existing contracts.

Every Given names who the user is as a role, such as a creator or an internal reviewer viewing a client account, and a situation that a fixture declared in the target repository provides; when none does, the Given says a fixture must be added to provide it. A Given never names a fixture identifier or fixture user; the target's qa.toml maps each role to its fixture user.

A Given holds only state a fixture can set, such as who the user is and what data exists, and the user's context, such as a phone, tablet, or desktop and light or dark appearance; a state the user reaches by a gesture is a When step, so Given a creator with the sidebar collapsed becomes Given a creator on the projects page, When the creator collapses the sidebar.

A When step is something the user does, such as opening, pressing, or typing; looking or reading is not a step, so what the user sees belongs in the Then: When the learner looks at the graph and the script control, Then the script control reads Zhuyin becomes When the learner opens the graph, Then its script control reads Zhuyin.

The Then is visible on the screen the last When step leaves: a When that ends by dismissing something, such as pressing Escape, also names what the user then sees, and the Then names it, never only that something closed.

When a Then compares what the screen shows before and after the When, as in stays where it was or no longer shows, the When joins its steps with then, as in opens the spec, then opens a criterion's popover, then clicks its bundle link; a comma never splits a step.

A Then reads from one screen or state; an outcome that needs two screens splits into one criterion per screen, each with its own When reaching that screen. A Then needs two screens when it reads past a navigation, such as to another tab, back to an earlier screen, or to another page, or reads two separate surfaces, as in the Transcript tab marks the hook and the overview card names it or the clip plays and Back returns to Discover. An outcome no screen shows follows the no-screen recipe instead.

A criterion names each thing by what it is, as in the lane with a QA bundle, never by screen position or order, as in the first card.

Shaping, review, and repair judge the criterion rules; the structural validator fails on none of them, because each is a judgment on meaning a markup check cannot make, and only warns on a Then that looks to span two screens. Its own checks of a criterion’s markup, a scenario holding a When and an observable outcome, run only on each criterion the change adds or edits: a criterion whose text is unchanged from the base passes as it is, so validation never leads shaping to edit it. It fails a change that drops a proof clause: each clause beginning proven by that a criterion at the base carries reads word for word in a criterion of the changed spec, and the failure names the base criterion and its clause. Repair's whole-spec check runs those markup checks, and the two-screen warning, on every criterion. It counts a base proof clause as kept when a criterion of any spec of the repository carries it word for word, so a criterion repair moves to its owning spec keeps its clause, and it fails a clause of a spec deleted since the base that no spec carries.

On each criterion the change adds or edits, the structural validator warns when its Then looks to span two screens: it names two different screens, tabs, pages, or routes, or joins two visible outcomes with a navigation step, such as opening another page or going back. A navigation step is the user moving to another screen, never focus moving within one, as in focus returns to the Save button; a Then whose only outcome before the move is something closing, as in the menu closes and the user returns to the list, reads from the screen the move reaches. The warning names the criterion and the words that raised it, and the validation still passes. A criterion whose Then reads from one screen despite those words carries the reason as data-one-screen="<reason>" and raises no warning; an empty reason counts as none. The reason sits on the criterion because the validator reads only the spec file and its base, offline. A criterion whose Then says no screen shows it, and a criterion whose text is unchanged from the base, raise no warning. Shaping answers each warning by splitting that criterion as the one-screen rule states or by writing its reason; no warning leads shaping or repair to edit a criterion the change does not otherwise edit.

On each clause the change adds or edits, the structural validator warns when it states look or motion mechanics: a color value, such as a hex, rgb, or hsl color; an easing curve, such as a cubic Bézier or a named CSS easing; or a motion timeline, two or more durations under a second in one clause or across the rows of one table, as a choreography table holds. The warning names the clause and the words that raised it, and the validation still passes. One duration in a clause, as a press held for a set time or an answer within a set time, raises no warning: it is a timing the user feels. Shaping answers each warning by moving the mechanics to the design system and linking it, or by stating the outcome the user feels; a clause whose text is unchanged from the base raises no warning, so no warning leads shaping to edit a clause the change does not otherwise edit. Repair's whole-spec check runs the warning on every clause.

When no screen shows the outcome, as for an analytics event or a stored record, or the outcome lies outside the page, as for a sound, the browser tab title or icon, an operating system dialog, or a live third-party page, the Then states the outcome in product terms, as in Then the funnel step is recorded once. This is Spec Chat's whole recipe for such a criterion: shaping does not add a capture file, readback command, or stub to make it drivable, and the target, not the spec, names any artifact.

How a criterion is tested belongs to the target repository, so Spec Chat's criterion rules neither add nor remove a test level, proof method, or proving test, as in proven by a unit test: no screen shows it. Shaping writes such a clause where a target project rule calls for one, and shaping and repair keep every one a criterion carries, word for word.

QA harness setup is not product behavior: stubs, capture files, readback tooling, and fixture extensions never appear in a product spec; they belong to the target's qa.toml or QA docs.

No hidden steps: when reaching the Then needs something the user must do, such as finishing a re-run setup after a handle change, the When says so in user terms; no step the Then depends on is left implied.

Concrete values, selectors, and paths stay out of the spec: the When says what the user types or picks in user terms, as in types a folder name, and the target's qa.toml hint file carries the exact value.

A gesture or timing is its own explicit step with its target or duration, such as press and hold 500ms or drag to the Ideas tile, and the criterion says in plain words that it needs that gesture or timing, so a QA program without it can report the criterion unsupported instead of failed. Spec Chat keeps no list of QA capabilities; the plain words are the whole contract.

A state that cannot occur live is marked needs an induced failure: <what fails>, as in needs an induced failure: provider timeout; the spec does not say how the target induces it.

Given, When, and Then open their clauses capitalized as written here, the same way throughout a spec, with no label before them such as a number or Scenario:; a criterion in a table cell keeps each Given, When, and Then a readable clause of its own.

A gap remains visible in an anchored data-spec-tbd block until resolved.

A criterion that is not needed is removed rather than retained as historical prose.

An ADR is created only when a decision is hard to reverse, surprising to a future maintainer, and carries a real tradeoff.

An ADR is immutable once committed to the base branch: a changed decision is a new ADR that names the ADR it supersedes, the old ADR gains only the line Superseded by ADR NNNN (date), and git holds the history. Where a repo's ADRs carry no number, the line names the new ADR by a link to its file.

Multi-module behavior is reconciled with the target-declared architecture source at the stable modular level.

Implementation ticket graph

Any implementation ticket derives from the accepted spec, after spec acceptance.

The spec owns the stories and acceptance criteria a ticket delivers; cutting them into tickets is delivery's.

Every contract-bearing clause and criterion keeps its stable anchor, so a ticket can link the exact spec anchors that govern it.

The spec states no delivery order, in prose or by numbering; the dependency direction between tickets is delivery's.

Which ticket is ready to start is delivery's: Spec Chat neither reads nor decides it.

Shaping does not invent dependencies merely to serialize delivery.

Shaping creates no tickets, so review batches never reconcile ticket scope.

Shaping never marks ticket state, such as implementation work In Progress or Done; ticket state is delivery's.

Spec Chat makes no ticket graph mutation, so it depends on no tracker or orchestrator.

Issue surface

Each target repository selects its own issue surface through a separate concise issue skill.

External repositories may select a different issue surface without changing Spec Chat's shaping or review contract.

The core Spec Chat shaping skill calls no issue operation; creating and editing the issue are the caller's.

The Spec Chat browser runtime, review server, and event protocol contain no tracker client or tracker-specific behavior.

Missing access to the repository-selected issue surface is the caller's blocker and never blocks shaping.

The caller keeps the issue current: resolved decisions replace prior issue prose, and resolved material TBDs are removed immediately.

In-spec grilling

After the seed opens, shaping conversation occurs inside Spec Chat by default.

The agent may expose a small batch of internally orthogonal material questions so review stays dynamic and fast.

Questions whose answers could materially redirect one another remain sequential, and the agent never dumps the complete grill at once.

Each question appears as a temporary anchored TBD block marked with data-spec-tbd so spec acceptance cannot become eligible while material questions remain; only a question deliberately deferred to a later slice uses data-spec-tbd="later".

The human answers with an ordinary comment on that block.

A question whose answer is one of a few options, such as a decision or a call to check, offers each option as an answer button in its TBD block, the recommended option's button text ending in (recommended), so the human answers with one press; an answer no button offers takes an ordinary comment on that block.

A question about how a screen looks or behaves is asked on that screen's mockup, at the part and step it is about (mockup questions), and the page's open questions read as the agent's messages in its conversation (questions).

The agent immediately replaces the TBD with the resulting current rule or removes it when no rule is needed.

When an answer changes the issue's high-level scope or criteria, keeping the issue current is the caller's; the agent never edits it.

Agent questions require no agent-created root thread, new event type, or side channel.

Terminal chat is only a fallback when the browser review surface is unavailable.

Thread lifecycle

Resolved threads remain in history and collapse by default.

Selecting a resolved thread opens its complete conversation, focused (focused thread).

An expanded resolved thread whose latest message is from the agent shows Reply and reopen.

Saving that reply writes the existing human reply event and naturally derives draft status.

There is no separate reopen status, state-only Reopen action, or new event schema.

The reopened draft follows the ordinary Hand off flow.

Truthful browser status

The browser displays only event-backed facts it can know.

After hand-off it shows Handed off, waiting for agent.

After a matching agent reply it shows the acknowledged thread state.

When no matching reply appears within the existing timeout, it reports that automatic wake did not occur and instructs the human to send a new chat message to resume.

The browser never claims that an agent is attached based only on old agent-event recency.

Browser status adds no heartbeat, sentinel, lease, connection monitor, or periodic presence write.

Human spec review and spec acceptance

Human spec review: the human reviews changes and sends them from the page. Every sent hand-off, a comment batch or spec acceptance, is a human spec review and sets the last reviewed version.

Spec acceptance: the human approval that permits delivery under the reviewed canonical spec. It is the no-draft action, formerly called Finish review.

The spec acceptance action is labelled Accept spec.

The split is wording only in Spec Chat: events, fields, anchors, and gates are unchanged, and historical receipts keep their recorded text.

When no draft, pending, acknowledged, or unresolved work remains, the hand-off action becomes spec acceptance. If only open TBD work remains, it reads TBD open, and each activation scrolls to and focuses the next open TBD in document order, wrapping after the last.

While open TBDs remain and the action is Hand off, a secondary Next TBD button sits left of it and steps through the same open-TBD sequence as TBD open; there is one next-TBD position, shared by both. Hand off keeps its ordinary draft batch and leaves every TBD open. When the action becomes TBD open, Next TBD disappears, since the action itself does the same step.

TBD open and Next TBD carry the open TBD count only when two or more open TBDs remain, as TBD open (n) and Next TBD (n); with one open TBD they carry no number.

Every block holding an open TBD is visibly highlighted whenever open TBDs remain, whichever button offers the step.

A data-spec-tbd marker is open unless its value is later. data-spec-tbd="later" marks a TBD deliberately left for a later slice: it stays visible text but neither blocks spec acceptance nor is highlighted.

Spec acceptance writes the existing hand-off event with an empty batch.

The spec, applicable ADRs, user stories, acceptance criteria, and architecture must describe the same current behavior before spec acceptance is eligible; the caller keeps the issue matching them.

Absent ADRs and single-module work are valid only when their stated conditions hold.

Spec acceptance means the human accepts the reviewed canonical spec, the applicable durable surfaces agree, and delivery may start under it.

Spec acceptance is not human acceptance of delivered software, tracker lifecycle transition, merge approval, or deployment approval.

Comment targets

While comment mode is on, every anchored block that holds no other anchored block is a button: it has the button role, sits in the Tab order, and is named by its own text.

Enter or Space on a focused block opens the comment composer on that block, exactly as a click on the block outside any inner element does.

Text selection inside a block keeps working in comment mode and still comments on the selected text.

Turning comment mode off returns every block to its own role and Tab order, so reading view adds no buttons and no Tab stops.

The block button is the existing comment-mode targeting made reachable; it adds no second picker or composer path.

Answer buttons

A page offers an answer to a decision question as a button carrying data-spec-choice, whose value is the answer's text, inside the question's anchored block; the page needs no script.

Pressing an answer button outside comment mode saves a draft comment through the existing comment save: its anchor is the nearest enclosing anchored block, its target is that button, and its text is the button's answer.

The save opens no composer, panel, or full-viewport sheet, so the reviewer stays where they were on a phone as on a desktop; the existing saved-as-draft notice confirms it.

An answer button shows as chosen, pressed and marked by more than color, while the newest answer comment saved in its block is on that button.

The chosen mark derives from the review state, so it survives a reload and shows on every reviewer's page.

Pressing another answer button of the same block saves a new comment and moves the chosen mark to it; pressing the chosen button again saves nothing.

In comment mode an answer button is an ordinary comment target: pressing it opens the composer on that button, so a reviewer who wants to add words to an answer types them there.

An answer comment is an ordinary comment: it counts as a draft and is handed off, replied to, and resolved like any other, so agents read it with no change.

A button whose data-spec-choice value is empty, or that sits outside every anchored block, is not an answer button and keeps its own behavior.

Answer buttons extend the existing comment save and hand-off; they add no event, field, endpoint, or composer path.

Mobile review

Prompt-first shaping uses HTTP transport so the same review works on phones, tablets, and desktops.

Comment mode remains target-first on narrow screens: opening comment mode exposes the document, and selecting a target opens the full-viewport composer.

Review controls keep at least 44 pixel touch targets, 16 pixel textarea text, dynamic viewport height, safe-area padding, and reduced-motion behavior.

On a narrow screen the review panel's own hand-off bar, its drafts note, Next TBD, and Hand off with its spec acceptance and TBD open transitions, is the page's one hand-off control: it sits in the bottom toolbar whether the panel is open or closed, and no second Hand off or Next TBD shows. Its labels, count, and enabled state come from the same review state as on a desktop and change as soon as a comment is saved, handed off, or resolved; Next TBD shows under the same rule as on a desktop; its hand-off writes the same event and wakes the owner as on a desktop; each of its controls is at least 44 pixels tall. Every feature keeps one hand-off control for desktop and phone (phone rule, desktop rule).

A spec page held by a shell at an origin the box names (held) shows no hand-off control of its own: the shell's comment UI page holds the one; under any other parent the page keeps its own (review actions when held).

Public review access

Prompt-first shaping hands off a review link on its Herdr session's one review service; once the box owner has made that service public, the link opens from any ordinary browser without SSH, VPN, or a separate account login.

The link is not an authentication boundary: the page has no login.

The shaping skill tells the human to treat the link as a secret and never publishes it into the issue or change request.

The public server exposes only the declared review collection and its event routes, never the repository root.

A review collection needs no Git repository: outside one, the served directory itself is the collection boundary, comments, replies, and hand-offs work over its spools, and the baseline, compared range, and issue focus report unavailable.

Without consulting Git, the server refuses a filesystem or volume root, a top-level system or shared temporary directory, the home directory or any ancestor of it, the home Desktop, Documents, and Downloads folders, any path inside Git metadata, and a directory outside Git that contains a repository; inside a repository it also refuses the repository root.

A single-directory collection accepts the review spool of any HTML page it serves, while a registered resource accepts only its declared spec.

A public review service binds directly to an approved ingress port, with no relay or tunnel; the service owns its bind and port (one service per session).

Lane teardown removes the lane's registered rows, so their review links stop serving (lane hosting); spec acceptance leaves them registered, and the lane's session's review service keeps serving other lanes.

Visual generation doctrine

The shaping reference states the canonical runtime boundary and selects renderers from the information being expressed.

Canonical specs use editable HTML, the shared stylesheet, and the committed offline Spec Chat runtime.

Only the artifact renderer needed by the contract belongs in the page; no application framework catalog is a shaping prerequisite.

Canonical spec documents remain non-React HTML so the source stays directly editable and canonical.

React applies to existing applications reviewed through embed mode and to explicitly requested noncanonical throwaway prototypes.

A target application using React does not turn its canonical spec into React or introduce a Vite source-to-HTML synchronization loop.

Offline fidelity, local vendoring, semantic-island, and small-runtime principles hold.

Visual quality contract

The governing objective is maximum contract-bearing information per unit of reader attention and page space, constrained by high readability.

Before authoring prose, the agent classifies every behavior cluster as a required, valuable, or unsuitable visual opportunity and establishes the hierarchy connecting its artifacts.

The agent realizes every visual opportunity that increases information density without reducing comprehension, scanability, or annotation precision.

Visual richness is suitable-opportunity coverage and explanatory depth rather than a fixed artifact count, so a simple contract may remain simple while a relationship-dense contract produces many artifacts.

One behavior receives complementary artifacts when no single view preserves all material dimensions, such as time path plus state-versus-input or desktop plus mobile placement.

Unrelated relationships remain in separate legible artifacts rather than being compressed into one crowded diagram to reduce count.

Each rule has one authoritative expression, and diagrams replace strings of relational prose rather than duplicating them.

Adjacent prose is limited to the context, caveat, or one-line gloss needed to read an artifact correctly.

Lists are retained only when item independence or literal order is itself the information shape, never as a fallback for topology, state, causality, spatial relations, or cross-product logic.

Every spec uses one coherent visual system defining hierarchy, typography, palette, spacing, geometry, metadata, responsive behavior, annotation affordance, and focus treatment.

The bundled crisp editorial language is one tested fallback visual system, not the required aesthetic identity of every spec.

A target visual language may vary, but every decorative treatment must support its hierarchy and content instead of weakening contrast or competing with contract-bearing artifacts.

Normal text and diagram labels meet at least 4.5 to 1 contrast, while large text and meaningful graphic boundaries meet at least 3 to 1.

Color distinguishes semantic categories, states, warnings, or ownership and never substitutes for labels, line shape, or position.

System, state, lifecycle, spatial, and cyclic relationships use purpose-fit diagrams with collision-free labels rather than default chart layouts.

ECharts is reserved for quantitative relationships whose scales and values matter; topology alone does not justify a chart.

A material spec uses only an unchanged shared stylesheet present at its exact Git base, otherwise the byte-identical bundled high-contrast editorial stylesheet becomes its shared fallback.

A canonical spec contains no page-level style block; inline styling is limited to artifact-local geometry and semantic marks absent from the shared system.

Before presenting a new or materially revised draft for review, a deterministic check rejects missing style provenance, newly invented shared themes, changed established themes, and spec-local page styling.

The human reviewer is the visual gate: the agent runs no browser screenshot pass before a handoff or a batch reply.

Runtime and shared-style regressions are caught by Spec Chat's own tests and preflight, not by each shaping lane.

Corrections are grouped before rechecking, and evidence matches the checks performed.

The base palette and focus treatment are evaluated together so changed material leads clearly while unchanged context remains readable rather than disappearing into an already weak page.

Skill ownership

The automatically discoverable spec-chat-shape skill owns prompt intake, short docs discovery, first spec seed, Git focus launch, in-spec grilling, batch publication, and review completion.

The spec-chat-review skill is the sole owner of spool reading, thread folding, reply emission, cursor safety, watcher attachment, mobile review, and cold recovery.

Review-only ends when a batch changes behavior or information architecture, at which point the review skill retains the spool transaction while the shaping skill becomes the required material-authoring co-skill.

The shaping skill hands into the review skill without copying its event protocol, while both skills encode the same spec contract invariants.

One repository-selected issue skill owns tracker-specific operations outside the Spec Chat runtime.

One required authoring reference contains information shape, shared markup examples, visual quality, and canonical runtime constraints.

No parallel instruction file restates any part of that authoring contract.

Every skill is short, specific, clear, and human-readable by default.

Skill instructions preserve contract invariants while leaving room for context-sensitive tactics and visual variation.

Conditional authoring detail lives in the single reference so the entry skill remains concise.

Evaluation fixtures live with repository tests and are not installed as agent instructions.

No Spec Chat skill depends on an orchestrator or another workflow package.

Other workflows may consume Spec Chat skills as downstream callers without becoming required by Spec Chat.

Burden budget

Every new mechanism must replace complexity or answer an observed failure that existing files and protocol cannot answer.

The implementation keeps shaping, review, rendering, transport, and optional wake adaptation in focused self-contained pieces.

It reuses the current spec dialect, review spools, event schema, cursor commit point, watcher scripts, reply emitter, HTTP server, and context file.

It adds no database, job ledger, capsule file, daemon, generic supervisor, heartbeat, presence sentinel, lease system, fencing system, tracker adapter registry, new event protocol, copied task context, or background infrastructure.

Portability comes from plain durable files and reconstructible current sources, not from a universal resident process.

Implementation and proof contract

A fresh agent scenario proves the shaping skill writes the prompt-first spec seed and review hand-off and keeps the agreed burden boundary.

The same scenario calls no issue operation and adds no excluded machinery.

Skill validation proves the shaping skill states the ADR ownership and supersede rule of source ownership and shaping completeness, and the repair skill lists the ADR repair.

Changed-spec validation accepts complete no, passive, and required declarations while rejecting missing binary decisions, invalid modes, missing required milestones, and broken step anchors.
