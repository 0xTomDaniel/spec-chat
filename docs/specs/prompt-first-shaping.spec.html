Prompt-first shaping and portable handoffs

docs / specs / prompt-first-shaping.spec.html

User stories

As a product operator, I want a prompt to become clean durable issue and spec surfaces immediately so shaping survives a lost chat session.

As a reviewer, I want additions to remain clear while existing context recedes so the canonical spec itself explains the current issue-scoped change.

As a reviewer away from the authoring machine, I want to comment and accept the spec from an ordinary mobile browser using one secret link so review requires no SSH or separate account.

As an authoring agent, I want hand-offs to wake the active shaping turn and durable files to support cold recovery so processing remains portable without a resident supervisor.

As a reviewer, I want the same required review capabilities in every repository so an old vendored runtime cannot silently remove controls, focus, or visuals.

As a feature author, I want every changed user-facing story to state whether the central guided journey extends so onboarding impact is explicit without forcing every feature into onboarding.

As a reviewer, I want TBDs marked for a later slice to leave spec acceptance available and each open TBD to be counted, highlighted, and reachable from the toolbar even while I have draft comments, so only real open questions stop spec acceptance and I always know how many remain.

As a human reviewer, I want sending my review and accepting the spec to have distinct names so no one mistakes a reviewed batch for approval to deliver.

As a reviewer on a keyboard or a browser agent, I want each block I can comment on to be a real button in comment mode so I can pick it without pointing at plain text.

As a QA capture program, I drive every acceptance criterion from its Given, When, and Then without guessing, take its concrete values from the target's qa.toml hint file, and read in plain words which gesture, timing, or induced failure a criterion needs.

Modular boundaries

A spec that spans multiple modules includes a concise Modular boundaries section naming responsibility, interface or seam, and dependency direction.

The section stays architectural and omits classes, functions, files, and replaceable implementation detail.

A contract-bearing semantic diagram is the default when more than one meaningful module relationship exists.

The same stable responsibilities, interfaces or seams, and dependency direction remain current in the target-declared architecture source.

Issue-specific behavior and acceptance detail remain in the spec rather than being copied into architecture.

Guided-journey declarations do not invert runtime ownership: the central registry owns journey order, while feature modules own their targets and semantic success milestones.

The review runtime owns spec acceptance eligibility and open-TBD highlighting. The caller-facing seam is the spec markup: each data-spec-tbd marker and its value. Direction is self-contained: authoring writes markers, the runtime only reads them. Observable scope: the hand-off action label, the Next TBD button, their activation, and TBD block highlighting.

Outcome

Every new work unit begins with a plain-language feature prompt.

The workflow creates clean durable issue and spec surfaces immediately, then iterates on those surfaces instead of treating chat context as product truth.

The canonical HTML spec and its Spec Chat overlay are the only required human review surface for spec behavior.

Correctness survives agent, session, CLI, and host replacement through plain files and cold reconstruction.

Source ownership

The issue surface owns current high-level intent, desired outcome, acceptance criteria, non-goals, dependencies, and governing source links.

Linked implementation tickets own bounded independently assignable code outcomes and explicit blocker relations.

The canonical spec owns current user stories, detailed behavior, constraints, edge cases, and interaction contracts.

Each changed user-facing story declares in canonical HTML whether it requires a guided-journey extension; no declaration is copied into lifecycle tracking or generated catalogs.

Linear carries issue lifecycle and governing links, not canonical story or guided-journey declaration text.

Markdown story catalogs remain generated downstream QA output.

Specs carry no ticket or issue link; git history is the provenance record.

The evolving draft change request carries durable commits and history, but it is not a required human spec-review surface.

The actor-segregated review spool owns comments, replies, hand-offs, and their causal order.

The existing review context file carries only concise cold-recovery facts that have not yet become canonical behavior.

Conversation and model memory are evidence only and never override a durable current source.

Prompt-first shaping flow

The caller names the issue for the spec to link; shaping never waits on it.

The issue is always-most-recent and clean, so later passes replace its content rather than retaining the raw prompt or accumulating summaries.

The agent creates the work branch, and that branch supplies the local Git comparison baseline.

The short seed pass reads only target instructions, the spec index, clearly related specs and ADRs, and directly relevant product or workflow docs.

The seed pass defers code, tests, configuration, and package inspection unless durable docs conflict or cannot identify the correct spec surface.

The issue retains links only to sources that actually govern the work, never a bibliography of everything inspected.

The agent writes one concise current issue seed and one concise current spec seed before deeper grilling.

When a relevant canonical spec exists, the agent edits it in place.

When no relevant spec exists, the agent creates a minimal durable capability or domain spec with only sections that contain real behavior.

The spec carries no ticket or issue link; git history is the provenance record.

The first seed is committed locally, passes the structural validator, is hosted, and its review link is sent at once; the caller publishes the issue, branch, and draft change request in parallel.

After the link is sent, the agent inspects only relevant code, tests, configuration, and branch state before asking questions those sources can answer.

A conflict between durable sources stops shaping visibly instead of being resolved from chat or model memory.

Shaping completeness

Every governing HTML spec contains explicit anchored user stories, and every user outcome created, changed, or retired by the work is current there.

Every changed user-facing story declares data-guided-journey="yes|no"; no requires no rationale and does not imply universal onboarding.

A yes declaration links one applicable guided-journey step and states passive or required; required also names the feature-owned semantic success milestone.

Shaping creates and maintains declarations, review evaluates their semantic correctness, and structural validation checks only presence and reference integrity on changed specs.

Each candidate acceptance criterion is classified as clear, gap, or not needed.

A clear criterion names an observable outcome and an identified governing spec rule.

A clear criterion stays at user-story level, what a person does and sees and never a click script, so a QA capture program can drive it without guessing; the rules below apply at shaping and at repair.

One scenario per criterion: no Given or When joins alternatives with or; each alternative becomes its own criterion.

Then names what is visible at the end: on screen, or for a feature with no screen, in its terminal output or a named file. A Then that states only an absence also names something visible that proves the end state was reached, and a Then never defers to other contracts, as in remains governed by existing contracts.

Every Given names who the user is, such as a creator or an internal reviewer viewing a client account, and a state that a fixture declared in the target repository provides; when none does, the Given says a fixture must be added to provide it.

No hidden steps: when reaching the Then needs something the user must do, such as finishing a re-run setup after a handle change, the When says so in user terms; no step the Then depends on is left implied.

Concrete values, selectors, and paths stay out of the spec: the When says what the user types or picks in user terms, as in types a folder name, and the target's qa.toml hint file carries the exact value.

A gesture or timing is its own explicit step with its target or duration, such as press and hold 500ms or drag to the Ideas tile, and the criterion says in plain words that it needs that gesture or timing, so a QA program without it can report the criterion unsupported instead of failed. Spec Chat keeps no list of QA capabilities; the plain words are the whole contract.

A state that cannot occur live is marked needs an induced failure: <what fails>, as in needs an induced failure: provider timeout, so the target proves the criterion with a unit test instead of driving it.

Given, When, and Then open their clauses capitalized as written here, the same way throughout a spec, with no label before them such as a number or Scenario:; a criterion in a table cell keeps each Given, When, and Then a readable clause of its own.

A gap remains visible in an anchored data-spec-tbd block until resolved.

A criterion that is not needed is removed rather than retained as historical prose.

An ADR is created or updated only when a decision is hard to reverse, surprising to a future maintainer, and carries a real tradeoff.

A behavior change names a deep-module seam in the spec, the smallest first failing test at that seam, and observable acceptance evidence.

Docs-only work skips the TDD contract.

When the smallest failing test is genuinely unsuitable, the issue and spec record one narrow waiver and its alternative proof.

Multi-module behavior is reconciled with the target-declared architecture source at the stable modular level.

Each ticket owns one bounded independently assignable code outcome.

Each ticket links exact governing spec anchors and names observable completion evidence.

Tracker blocking relations express real dependency direction instead of prose ordering or ticket numbering.

Every incomplete ticket with no incomplete blocker belongs to the ready frontier.

Shaping does not invent dependencies merely to serialize delivery.

Delivery keeps ticket state truthful; shaping never marks implementation work In Progress or Done.

Tracker-specific graph mutations remain behind the repository-selected issue skill, so Spec Chat depends on no tracker or orchestrator.

Issue surface

Each target repository selects its own issue surface through a separate concise issue skill.

External repositories may select a different issue surface without changing Spec Chat's shaping or review contract.

The core Spec Chat shaping skill depends only on the issue skill's create, read, replace-current-content, and link operations.

The Spec Chat browser runtime, review server, and event protocol contain no tracker client or tracker-specific behavior.

Missing access to the repository-selected issue surface is a visible shaping blocker.

Resolved decisions replace prior issue prose, and resolved material TBDs are removed immediately.

Git-derived focus is the diff viewer

The highlighted current spec is the complete required human diff-review surface.

Every current block added or modified by the work branch remains fully clear.

The runtime marks each outermost added or modified block with an unmistakable focus boundary that remains visible across custom spec styles without outlining every changed descendant.

Every unchanged current block recedes visually so the issue-scoped additions hold attention.

A new spec is entirely clear.

Opening the spec without issue focus renders the whole current document at normal clarity.

Focus is derived from Git and never maintained through embedded issue metadata, sidecars, anchor lists, or hand-authored change markers.

The shaping skill commits and pushes every accepted spec change before presenting the refreshed focus view, so the Git-derived review state remains durable and reproducible.

Prompt-first shaping uses the existing HTTP review transport on desktop and mobile because a browser file page cannot inspect Git.

The review server reads only the current local repository and never fetches, checks out, stages, commits, or writes Git state.

No focus behavior imports, invokes, expects, or mentions an orchestrator.

An explicit review base resolves to the exact selected local commit, including a previously reviewed sibling branch, while automatic discovery alone uses a merge base.

The baseline response retains the selected commit in base; a file absent from the selected base is entirely new and returns null for both htmlBase and html.

If Git comparison cannot be calculated, focus mode fails visibly and renders the complete current spec without stale highlighting.

A removed behavior must be expressed by the resulting current rule or constraint, because a silent deletion with no current replacement cannot be reviewed in the current-spec highlighting model.

The first version requires no side-by-side viewer, removed-content tray, deletion ghost, or pull-request review.

The contract leaves room for optional richer in-spec diff views when real use justifies them.

In-spec grilling

After the seed opens, shaping conversation occurs inside Spec Chat by default.

The agent may expose a small batch of internally orthogonal material questions so review stays dynamic and fast.

Questions whose answers could materially redirect one another remain sequential, and the agent never dumps the complete grill at once.

Each question appears as a temporary anchored TBD block marked with data-spec-tbd so spec acceptance cannot become eligible while material questions remain; only a question deliberately deferred to a later slice uses data-spec-tbd="later".

The human answers with an ordinary comment on that block.

The agent immediately replaces the TBD with the resulting current rule or removes it when no rule is needed.

The clean current issue is updated in the same batch when the answer changes its high-level scope or criteria.

Agent questions require no agent-created root thread, new event type, or side channel.

Terminal chat is only a fallback when the browser review surface is unavailable.

Thread lifecycle

Resolved threads remain in history and collapse by default.

Selecting a resolved thread expands its complete conversation.

An expanded resolved thread whose latest message is from the agent shows Reply and reopen.

Saving that reply writes the existing human reply event and naturally derives draft status.

There is no separate reopen status, state-only Reopen action, or new event schema.

The reopened draft follows the ordinary Hand off flow.

Active review attachment

In turn-yielded state, the authoring agent keeps its current turn open and parks through the review-control wrapper.

The agent never returns a final response while turn-yielded state remains active.

A browser hand-off completes the wait, re-enters the same authoring turn, and delivers the exact ready batch.

After the batch settles, the same turn reconciles remaining backlog and parks a fresh watcher.

A watcher timeout or watcher error while the turn remains active wakes the same agent, which reconciles and reparks automatically.

A host-stopped, completed, or lost turn cannot reactivate itself.

Hosts may display the authoring turn as working throughout active browser review.

Review wake ownership

Every open review is in exactly one terminal control state: turn-yielded, host-wake, or manual-resume.

Control stateWake ownerFinal responseReviewer promise
turn-yieldedThe open authoring turn through a verified same-turn yieldForbiddenHandoff re-enters this turn
host-wakeThe review host, bound to the registry row owner paneAllowedHandoff prompts the owning pane
manual-resumeThe humanAllowedSend a new chat message to drain queued work

A raw shell watcher is detection-only and never establishes turn-yielded or host-wake state.

The review host observes complete handoffs per registered resource without advancing the processing cursor and wakes that row's owner pane once per unchanged batch, as defined by Review host wakes the owner pane.

A local kernel-held lock permits one turn-yielded control owner for each canonical collection root and cursor name, and a second owner fails visibly into manual resume.

The lock uses one user-owned absolute runtime namespace independent of shell environment variables so multiplexer panes and ordinary shells contend on the same identity.

The ownership lock is released automatically with its foreground process and introduces no lease, heartbeat, fencing protocol, or persistent coordinator.

Host wake owns only reactivation and never reads comments, edits the spec, emits replies, advances cursors, or invokes detached agent processing.

Host wake uses only the registered wake provider (Providers); review-host register reports wake=verified only when its check resolves the owner pane.

Without a wake provider, registration reports wake=unavailable and the owner selects manual-resume rather than false active status.

Hand-off batch transaction

The hand-off event defines the exact batch cutoff.

The agent folds edits and replies, then rechecks that each newest human message still needs an answer.

Before editing, the agent classifies whether the batch changes behavior or information architecture.

Questions and atomic corrections remain review-only, while a material batch loads the shaping skill and its complete authoring quality contract before the first file edit.

An existing or old spec receives no exemption from the current information-shape or visual-quality rules when a material batch changes it.

When the current page cannot carry new material with readable visual density, the agent restructures the affected page rather than appending prose, cards, or one catch-all diagram.

The agent completes each coherent batch of behavior, acceptance, and necessary layout changes before its replies.

The agent updates the clean current issue when high-level truth changed.

The agent commits and pushes every accepted spec change before the browser presents its refreshed Git-derived focus view.

The agent emits one reply to each newest human message after the durable spec write succeeds.

Only after every prior action succeeds does the agent append the exact processed filenames to its cursor.

A partial or failed batch leaves the cursor unchanged so the next processor reconstructs and completes the same work.

One active writer owns a mutable review collection at a time.

Leases, fencing, and distributed claims remain deferred until observed concurrent processors prove a real race.

Portable recovery

The durable guarantee is one accepted batch outcome, not resumption of a particular worker session.

Processing allows at-least-once attempts and accepts one complete current outcome.

Same-thread continuation and CLI session resume are performance and context optimizations only.

Any later compatible agent can cold-start from the current spec, review spool, existing context, repository instructions, current issue, and current change request.

The portable work capsule is derived at processing time from those existing sources and is never copied into a job file or ledger.

When no agent process exists, handed-off events remain durably queued and no claim of active processing is made.

When an agent later enters the repository, its first action is a zero-wait collection scan that drains every completed unprocessed hand-off before new work.

A completely closed host session cannot self-wake without a host trigger or another local process capable of invoking an agent.

The implementation adds no generic supervisor or agent-launching server.

The review host may detect a complete handoff and prompt the registered owner pane, but it never launches a second processor.

Truthful browser status

The browser displays only event-backed facts it can know.

After hand-off it shows Handed off, waiting for agent.

After a matching agent reply it shows the acknowledged thread state.

When no matching reply appears within the existing timeout, it reports that automatic wake did not occur and instructs the human to send a new chat message to resume.

The browser never claims that an agent is attached based only on old agent-event recency.

The first implementation adds no heartbeat, sentinel, lease, connection monitor, or periodic presence write.

Human spec review and spec acceptance

Human spec review: the human reviews changes and sends them from the page. Every sent hand-off, a comment batch or spec acceptance, is a human spec review and sets the last reviewed version.

Spec acceptance: the human approval that permits delivery under the reviewed canonical spec. It is the no-draft action, formerly called Finish review.

The spec acceptance action is labelled Accept spec.

The split is wording only in Spec Chat: events, fields, anchors, and gates are unchanged, and historical receipts keep their recorded text.

When no draft, pending, acknowledged, or unresolved work remains, the hand-off action becomes spec acceptance. If only open TBD work remains, it reads TBD open, and each activation scrolls to and focuses the next open TBD in document order, wrapping after the last.

While open TBDs remain and the action is Hand off, a secondary Next TBD button sits left of it and steps through the same open-TBD sequence as TBD open; there is one next-TBD position, shared by both. Hand off keeps its ordinary draft batch and leaves every TBD open. When the action becomes TBD open, Next TBD disappears, since the action itself does the same step.

TBD open and Next TBD carry the open TBD count only when two or more open TBDs remain, as TBD open (n) and Next TBD (n); with one open TBD they carry no number.

Every block holding an open TBD is visibly highlighted whenever open TBDs remain, whichever button offers the step.

A data-spec-tbd marker is open unless its value is later. data-spec-tbd="later" marks a TBD deliberately left for a later slice: it stays visible text but neither blocks spec acceptance nor is highlighted.

Spec acceptance writes the existing hand-off event with an empty batch.

The parked agent interprets that empty hand-off as explicit completion of the browser review window.

The agent reconciles issue and spec, commits and pushes any final changes, advances the cursor, and closes the active wait.

The issue, spec, applicable ADRs, user stories, acceptance criteria, architecture, and TDD contract must describe the same current behavior before spec acceptance is eligible.

Absent ADRs, single-module work, docs-only work, and recorded test waivers are valid only when their stated conditions hold.

Spec acceptance means the human accepts the reviewed canonical spec, the applicable durable surfaces agree, and delivery may start under it.

Spec acceptance is not human acceptance of delivered software, tracker lifecycle transition, merge approval, or deployment approval.

Comment targets

While comment mode is on, every anchored block that holds no other anchored block is a button: it has the button role, sits in the Tab order, and is named by its own text.

Enter or Space on a focused block opens the comment composer on that block, exactly as a click on the block outside any inner element does.

Text selection inside a block keeps working in comment mode and still comments on the selected text.

Turning comment mode off returns every block to its own role and Tab order, so reading view adds no buttons and no Tab stops.

The block button is the existing comment-mode targeting made reachable; it adds no second picker or composer path.

Comment mode remains target-first on narrow screens: opening comment mode exposes the document, and selecting a target opens the full-viewport composer.

Public review access

Prompt-first shaping publishes an HTTPS review link that opens from any ordinary browser without SSH, VPN, or a separate account login.

The unguessable link is a bearer capability, and possession of that link is the only review authentication.

The shaping skill tells the human to treat the link as a secret and never publishes it into the issue or change request.

The public server exposes only the declared review collection and its event routes, never the repository root.

The review server binds directly to an approved ingress port through the approved-port launcher, with no relay or tunnel.

Spec acceptance or explicitly ending review closes the public transport and invalidates the capability URL.

Review surface compatibility

The review-surface preflight is the single seam that verifies a target spec, browser runtime, and local transport before review opens.

Compatibility is checked for the target runtime only, from explicit capabilities required by the current bundled runtime rather than global skill freshness, file age, or an external registry.

When the target runtime lacks a required capability, preflight replaces it from the current self-contained skill bundle before the server starts; the review server is always the skill's own bundled assets/review-serve.py, so it is never copied into the target.

A target asset declaring every required capability remains untouched even when its implementation or pin differs from the bundle.

Git focus needs both the bundled server's read-only baseline route and the target runtime's browser behavior.

A migrated running server is restarted on the same approved port before review continues.

Before a review handoff, the agent verifies served runtime capabilities and uses the read-only verifier to compare served spec bytes and baseline HTML with local files and Git, including new-file baselines.

Every semantic visual island has a render target in the same parent, and a missing target blocks publication rather than silently producing prose-only output.

A failed migration or preflight is a visible review blocker.

Preflight adds no service, registry, package dependency, background updater, or cross-repository control plane.

Visual generation doctrine

The shaping reference states the canonical runtime boundary and selects renderers from the information being expressed.

Canonical specs use editable HTML, the shared stylesheet, and the committed offline Spec Chat runtime.

Only the artifact renderer needed by the contract belongs in the page; no application framework catalog is a shaping prerequisite.

Canonical spec documents remain non-React HTML so the source stays directly editable and canonical.

React applies to existing applications reviewed through embed mode and to explicitly requested noncanonical throwaway prototypes.

A target application using React does not turn its canonical spec into React or introduce a Vite source-to-HTML synchronization loop.

Existing offline fidelity, local vendoring, semantic-island, and small-runtime principles remain in force.

Visual quality contract

The governing objective is maximum contract-bearing information per unit of reader attention and page space, constrained by high readability.

Before authoring prose, the agent classifies every behavior cluster as a required, valuable, or unsuitable visual opportunity and establishes the hierarchy connecting its artifacts.

The agent realizes every visual opportunity that increases information density without reducing comprehension, scanability, or annotation precision.

Visual richness is suitable-opportunity coverage and explanatory depth rather than a fixed artifact count, so a simple contract may remain simple while a relationship-dense contract produces many artifacts.

One behavior receives complementary artifacts when no single view preserves all material dimensions, such as time path plus state-versus-input or desktop plus mobile placement.

Unrelated relationships remain in separate legible artifacts rather than being compressed into one crowded diagram to reduce count.

Each rule has one authoritative expression, and diagrams replace strings of relational prose rather than duplicating them.

Adjacent prose is limited to the context, caveat, or one-line gloss needed to read an artifact correctly.

Lists are retained only when item independence or literal order is itself the information shape, never as a fallback for topology, state, causality, spatial relations, or cross-product logic.

Every spec uses one coherent visual system defining hierarchy, typography, palette, spacing, geometry, metadata, responsive behavior, annotation affordance, and focus treatment.

The bundled crisp editorial language is one tested fallback visual system, not the required aesthetic identity of every spec.

A target visual language may vary, but every decorative treatment must support its hierarchy and content instead of weakening contrast or competing with contract-bearing artifacts.

Normal text and diagram labels meet at least 4.5 to 1 contrast, while large text and meaningful graphic boundaries meet at least 3 to 1.

Color distinguishes semantic categories, states, warnings, or ownership and never substitutes for labels, line shape, or position.

System, state, lifecycle, spatial, and cyclic relationships use purpose-fit diagrams with collision-free labels rather than default chart layouts.

ECharts is reserved for quantitative relationships whose scales and values matter; topology alone does not justify a chart.

A material spec uses only an unchanged shared stylesheet present at its exact Git base, otherwise the byte-identical bundled high-contrast editorial stylesheet becomes its shared fallback.

A canonical spec contains no page-level style block; inline styling is limited to artifact-local geometry and semantic marks absent from the shared system.

Before presenting a new or materially revised draft for review, a deterministic check rejects missing style provenance, newly invented shared themes, changed established themes, and spec-local page styling.

The human reviewer is the visual gate: the agent runs no browser screenshot pass before a handoff or a batch reply.

Runtime and shared-style regressions are caught by Spec Chat's own tests and preflight, not by each shaping lane.

Corrections are grouped before rechecking, and evidence matches the checks performed without regenerating every full page, tile, and contact sheet after each small edit.

The base palette and focus treatment are evaluated together so changed material leads clearly while unchanged context remains readable rather than disappearing into an already weak page.

Information-shape doctrine

The organizing question is: what shape is this information, and what medium loses the least of it?

A visual element is preferred whenever it materially improves comprehension, comparison, error detection, memory, or review of contract-bearing structure, and prose remains primary only when it is equally or more legible.

Everything contract-bearing is addressable through stable section, clause, figure, table-row, and acceptance identifiers so reviewers name the rule rather than describe its location.

Visuals are load-bearing: changing a contract diagram changes the contract, and a visual removable without information loss is decoration.

Repetition is allowed only when it presents the same rule at different useful resolutions, never when two forms become competing authorities.

Each form is selected to expose its likely error: sequence mistakes in ordinals, missing cases in empty cells, precedence mistakes in predicate order, layout violations in proportional drawings, and false confidence beside provenance.

Skill ownership

A new automatically discoverable spec-chat-shape skill owns prompt intake, issue creation, short docs discovery, first issue and spec seed, Git focus launch, in-spec grilling, batch publication, and review completion.

The existing spec-chat-review skill remains the sole owner of spool reading, thread folding, reply emission, cursor safety, watcher attachment, mobile review, and cold recovery.

Review-only ends when a batch changes behavior or information architecture, at which point the review skill retains the spool transaction while the shaping skill becomes the required material-authoring co-skill.

The shaping skill hands into the review skill without copying its event protocol, while both skills encode the same spec contract invariants.

One repository-selected issue skill owns tracker-specific operations outside the Spec Chat runtime.

One required authoring reference contains information shape, shared markup examples, visual quality, proportional browser proof, and canonical runtime constraints.

No parallel instruction file restates any part of that authoring contract.

Every skill is short, specific, clear, and human-readable by default.

Skill instructions preserve contract invariants while leaving room for context-sensitive tactics and visual variation.

Conditional authoring detail lives in the single reference so the entry skill remains concise.

Evaluation fixtures live with repository tests and are not installed as agent instructions.

No Spec Chat skill depends on an orchestrator or another workflow package.

Other workflows may consume Spec Chat skills as downstream callers without becoming required by Spec Chat.

Burden budget

Every new mechanism must replace complexity or answer an observed failure that existing files and protocol cannot answer.

The implementation keeps shaping, review, rendering, transport, and optional wake adaptation in focused self-contained pieces.

It reuses the current spec dialect, review spools, event schema, cursor commit point, watcher scripts, reply emitter, HTTP server, and context file.

It adds no database, job ledger, capsule file, daemon, generic supervisor, heartbeat, presence sentinel, lease system, fencing system, tracker adapter registry, new event protocol, copied task context, or background infrastructure.

Portability comes from plain durable files and reconstructible current sources, not from a universal resident process.

Implementation and proof contract

Before changing shaping instructions, a fresh agent scenario must show that the current skills do not create the prompt-first issue and spec seed or maintain the agreed burden boundary.

A different fresh agent scenario must run the same request against the new skill and produce the current issue, spec seed, and review handoff without adding excluded machinery.

A runtime test must first fail because current Spec Chat cannot classify current anchored blocks against a Git baseline or render focus solely from that classification.

A regression requests both the ref and commit of a sibling snapshot and verifies exact baseline bytes; source-verifier tests cover substituted baselines, wrong served pages, absent-at-base new specs, and uncommitted new files.

The focus test passes for added, modified, unchanged, new-file, normal-view, and unavailable-baseline cases.

The runtime test proves only outermost changed blocks receive the explicit focus boundary and that the new runtime capability migrates stale repository copies.

Skill validation proves review-only is limited to questions and atomic corrections and material batches are routed through the complete shaping quality contract before editing.

Style-provenance tests accept unchanged established styling and the exact fallback while rejecting local style blocks, new custom themes, and changed established themes.

Changed-spec validation accepts complete no, passive, and required declarations while rejecting missing binary decisions, invalid modes, missing required milestones, and broken step anchors.

A thread-model test must first fail because the current UI withholds reply from a resolved thread.

The same test passes when a resolved thread offers Reply and reopen and the existing human reply event derives draft status.

A runtime test must first fail because the current no-draft hand-off remains disabled and cannot signal review completion.

The acceptance test passes when a clean review emits the existing empty hand-off and an ineligible review cannot reach spec acceptance.

A watcher attachment scenario must first demonstrate that returning a final response strands a later browser hand-off until another agent turn begins.

The same scenario passes when turn-yielded keeps the turn open, host-wake prompts the registered owner pane, or manual-resume explicitly requires a new human message.

Existing mobile, FSA, thread-model, and review-script suites remain green.

A runtime test must first fail because a block in comment mode has no button role or Tab stop, then pass when comment mode gives leaf anchored blocks the button role and a Tab stop, Enter and Space open the composer on that block, and leaving comment mode restores each block's own role and Tab order.

Browser evidence must verify focus readability, mobile target-first commenting, resolved-thread reopen, hand-off waiting state, and spec acceptance on a real rendered spec.

Non-goals

The first version does not guarantee processing while no compatible agent process exists.

It does not guarantee resurrection of a closed host session or preservation of hidden conversational state.

It does not build a distributed scheduler, exactly-once execution system, multi-writer coordinator, or cross-host presence service.

It does not require humans to inspect GitHub or another change-request UI to understand the spec change.

It does not install an application framework catalog into every shaping context or add a source-to-HTML build loop.
