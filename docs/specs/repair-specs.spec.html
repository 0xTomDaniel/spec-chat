Repair specs

docs / specs / repair-specs.spec.html

One Spec Chat skill that brings a repo's existing specs and ADRs to the current shaping contract. Runnable any time and optionally as onboarding catch-up. The skill reads Spec Chat's own onboarding status, the repo's specs and ADRs, and for the drift check the repo's code and Git history; project rules found by Jev drive criterion repairs generically. Extends project-wide rules: its warm-up, detection, and reconcile offer are unchanged; this spec owns the bulk editing that the offer or a direct invocation triggers.

User stories

As the shaping agent, I run one skill and every spec in a repo is brought to the shaping contract: non-target text removed, behavior in its owning spec, contradictions resolved, criteria meeting the shaping contract's criterion rules and project rules.

As the shaping agent, I run the same skill and every ADR in a repo is brought to the ADR model: its rules move to spec criteria, its mechanics leave, and an ADR carrying amendments, rules, or mechanics is superseded by one short ADR.

As the shaping agent, I run the same skill and every spec page is brought to the shaping contract's visual quality contract: shared stylesheet and current runtime, consistent headings, tables, and callouts, and figures that show the real mechanism the spec text states, while every behavior sentence stays as it was.

As a reviewer, I review the repairs on the review page with Git focus showing what changed in each spec.

As a project new to Spec Chat, the repairs run as part of onboarding catch-up when warm-up finds specs to reconcile, and I review the result.

As the human running repair, the skill checks each spec against its code, presents me one suggestion per drift saying which side to change and why, and makes only the spec edits I choose, so specs catch up with their code without anything being written behind my back.

As the shaping agent, the skill drives criterion repairs from Jev project rules without hardcoding any project's rule wording or format.

Acceptance criteria

Given the shaping agent on a repo whose spec has an audit section and a ticket link in its header, When the agent runs repair, Then the committed spec shows neither the section nor the link, and every behavior clause, acceptance criterion, and modular boundary remains.

Given the shaping agent on a repo where spec A holds a behavior clause that spec B already owns per its title, boundaries, and stories, When the agent runs repair, Then the committed spec B shows the clause and spec A no longer does.

Given the shaping agent on a repo with a spec named after a lane whose behavior belongs in an existing owning spec, When the agent runs repair, Then the committed owning spec shows that behavior and the lane-named file is deleted.

Given the shaping agent on a repo with two specs whose clauses contradict and one side is out of date, When the agent runs repair, Then the committed out-of-date side matches the current side.

Given the shaping agent on a repo with two specs whose clauses contradict as a real design choice, When the agent runs repair, Then the committed spec shows an open TBD at the clause.

Given the shaping agent on a repo with Jev on, a Jev project rule from another spec, and a spec whose acceptance criteria miss that rule, When the agent runs repair, Then the committed criteria satisfy the rule using its wording, and the skill names no project's rules and applies whatever Jev found.

Given the shaping agent that made a repair edit on a clause, When that edit raises a new contradiction on the same clause, Then the committed spec shows an open TBD at that clause, written instead of editing again.

Given the shaping agent that made a repair edit on a clause, When that edit raises a new rule miss on the same clause, Then the committed spec shows an open TBD at that clause, written instead of editing again.

Given a reviewer on a repo the shaping agent repaired, When repairs complete and the reviewer opens a changed spec on the review page, Then each changed spec is committed on the current branch and registered with the review server, and the page shows what changed with Git focus.

Given the shaping agent running the repair skill, When the skill reads its inputs, Then it reads Spec Chat's onboarding status, the repo's specs and ADRs, and for the drift check the repo's code and Git history, and names no peer status file or peer, proven by a unit test: no screen shows it.

Given the shaping agent on a project new to Spec Chat whose onboarding status shows specs to reconcile, When the agent invokes the skill, Then it runs all six repair types and the drift check on that project's specs and updates the project's onboarding status when done.

Given the shaping agent on a repo with Jev off, When the agent runs repair, Then the committed specs and ADRs show clean, home, contradiction, ADR, criterion-rule, and presentation repairs, and only Jev project-rule repairs are skipped.

Given the shaping agent on a repo whose criterion's When joins two places with or, When the agent runs repair, Then the committed spec shows one criterion per place, the first keeps the original anchor, each new one has a new stable anchor, and each meets every criterion rule of the shaping contract.

Given the shaping agent on a repo with a criterion whose When skips a step to its Then that the specs do not state, When the agent runs repair, Then the committed spec shows an open TBD at that criterion naming the missing step, and repair invents no step.

Given the shaping agent on a repo with a criterion whose visible end state cannot be read from the specs, When the agent runs repair, Then the committed spec shows an open TBD at that criterion naming the missing end state, and repair invents no end state.

Given the shaping agent on a repo with a criterion whose providing fixture cannot be read from the specs, When the agent runs repair, Then the committed spec shows an open TBD at that criterion naming the missing fixture, and repair invents no fixture.

Given the shaping agent on a repo whose criterion has the user type an exact quoted value into a named field, When the agent runs repair, Then the committed criterion says in user terms what the user types, the spec no longer shows the value, and the repair commit message lists the value for the target's qa.toml hint file.

Given the shaping agent on a repo whose criterion's Given names a fixture user and whose specs say which role that user is, When the agent runs repair, Then the committed Given names that role, the spec no longer shows the fixture user, and the repair commit message lists the fixture user as that role's fixture user for the target's qa.toml.

Given the shaping agent on a repo whose criterion's Then names a capture file holding an event that no screen shows, When the agent runs repair, Then the committed Then states in product terms what is recorded and reads proven by a unit test: no screen shows it, the spec no longer shows the file, and the repair commit message lists it for the target's qa.toml.

Given the shaping agent on a repo whose product spec has a section describing a provider stub and its capture file, When the agent runs repair, Then the committed spec shows neither the stub nor the capture file, every behavior clause remains, and the repair commit message lists the removed harness setup for the target's QA docs.

Given the shaping agent on a repo with a criterion whose Given does not say who the user is and whose specs do not say it either, When the agent runs repair, Then the committed spec shows an open TBD at that criterion asking who the user is, and repair invents no user.

Given the shaping agent on a repo whose ADR has a policy section stating a rule every feature must follow, When the agent runs repair, Then the rule's home spec shows it as an acceptance criterion that says it applies to every feature, a new ADR states the decision and why, links that criterion, and names the ADR it supersedes, and the old ADR's only change is one added line reading Superseded by ADR NNNN (date).

Given the shaping agent on a repo whose ADR restates a rule a spec already states, When the agent runs repair, Then the superseding ADR links that spec's clause instead of restating it, and the rule's wording appears only in the spec.

Given the shaping agent on a repo whose ADR states a retry count and a storage table, When the agent runs repair, Then the superseding ADR names neither, and the repair commit message lists both for the code and the change request.

Given the shaping agent on a repo whose ADR carries two dated amendment blocks, When the agent runs repair, Then one new ADR states the current decision and names the ADR it supersedes, and the old ADR's only change is one added line reading Superseded by ADR NNNN (date).

Given the shaping agent on a repo whose ADR holds only context, decision, why, alternatives rejected, and consequences, with no amendment, restated rule, or mechanics, When the agent runs repair, Then the ADR is unchanged.

Given the shaping agent on a repo whose spec draws a figure as ASCII art in a preformatted block, When the agent runs repair, Then the committed spec shows that figure as a purpose-fit diagram of the same mechanism with a caption and stable anchor, and every behavior sentence is unchanged.

Given the shaping agent on a repo whose spec holds a placeholder figure in place of a mockup, When the agent runs repair, Then the committed spec shows a figure of the real mechanism or screen its adjacent text states, and every behavior sentence is unchanged.

Given the shaping agent on a repo whose spec has a diagram that contradicts its text, When the agent runs repair, Then the committed diagram matches the text and the text is unchanged.

Given the shaping agent on a repo whose spec diagram paints its own fixed colors, When the agent runs repair and a reader opens the page in the light and then the dark color scheme, Then the diagram takes its colors from the shared stylesheet, and its labels and edges read clearly at the contract's contrast in both.

Given the shaping agent on a repo whose spec carries a page-level style block of its own, When the agent runs repair, Then the committed spec has no page-level style block, links the repo's shared spec stylesheet, and passes the structural validator.

Given the shaping agent on a repo whose spec skips a heading level, leaves a wide table unwrapped, and marks a callout with ad hoc styling, When the agent runs repair, Then the committed spec shows headings in order, the table scrolling inside the page, and the callout in the shared stylesheet's markup, with every behavior sentence unchanged.

Given the shaping agent on a repo whose spec runtime lacks a capability the bundled runtime requires, When the agent runs repair, Then the runtime is replaced by the review preflight as its own commit touching only the shared runtime assets, and the reviewer's page has every required capability.

Given a reviewer on a repo where only presentation repair changed a spec, When the reviewer opens that spec on the review page with Git focus, Then the changed blocks are figures, headings, tables, callouts, and markup only, and no behavior sentence, acceptance criterion, or boundary reads differently.

Given the human running repair on a repo whose code does a criterion's behavior differently in a way that makes sense and fits the spirit of the spec, When the run reaches the drift check, Then the skill presents a suggestion to update the spec, which is behind the code, naming the spec anchor, the code location, and the mismatch, and asks the human to decide.

Given the human running repair on a repo whose code does a criterion's behavior differently in a way that looks broken or against the spirit of the spec, When the run reaches the drift check, Then the skill presents a suggestion to fix the code and says why, naming the spec anchor, the code location, and the mismatch, and asks the human to decide.

Given the human running repair on a repo whose code has a behavior that no criterion of its spec states, When the run reaches the drift check, Then the skill presents a suggestion to add a criterion for it to the owning spec, naming the code location and the behavior, and asks the human to decide.

Given the human running repair on a repo with code that no spec links or was committed with, whose behavior falls within one spec's scope in spirit and that no criterion states, When the run reaches the drift check, Then the skill presents a suggestion to add a criterion for it to that spec, naming the code location and the behavior, and asks the human to decide.

Given the human settling a drift suggestion, When the human chooses to adjust the spec and says how, Then the committed spec shows that edit and no other change for that suggestion.

Given the human settling a drift suggestion, When the human chooses to fix the code later, Then neither the spec nor the code has changed, and the code fix stays a recommendation to the human.

Given the human settling a drift suggestion, When the human chooses to leave it, Then neither the spec nor the code has changed.

Given the human running repair with one drift suggestion not yet settled, When the human asks whether the run is done, Then the skill answers that the drift check is waiting on that suggestion and reports no completion.

Given a reviewer on a spec the drift check found drift in, When the reviewer opens that spec on the review page after the drift check is settled, Then the page shows no TBD, note, or finding from the drift check, and the only drift-driven changes are the edits the human chose.

Given the shaping agent on a repo whose spec links no code but was committed together with its code, When the agent runs repair, Then the drift check reads the code from those shared commits and no spec-to-code index is written, proven by a unit test: no screen shows it.

Given the shaping agent on a repo whose spec has no code the drift check can find, When the agent runs repair, Then the skill tells the human that spec was not checked against code, and the spec has not changed.

CI: the repair-specs test runs in CI with no other tool of the box installed and no provider file.

Modular boundaries

The repair skill reads all specs and ADRs in a repo, identifies repairs using the six types and Jev project rules, edits specs in place, checks each spec against its code for drift, commits, and registers for review. Caller-facing seam: the skill invocation; the caller names the repo and optionally the project for onboarding context. Dependency direction: self-contained within Spec Chat; reads Jev as an existing external provider when available; uses the review page for human review. Observable scope: changed spec and ADR files, commits, the review page, and the drift suggestions the skill presents to the human; it reads code and never edits it.

Repair types

TypeTriggerAction
CleanNon-target text: audit sections, before/after comparisons, history, status, source-issue links, ticket links, QA harness setup (stubs, capture files, readback tooling)Remove; preserve every behavior clause, criterion, and boundary; list removed harness setup in the commit message for the target's qa.toml or QA docs
HomeBehavior in a spec that does not own it, or a spec named after a changeMove clauses to the owning spec; delete a change-named spec once empty
ContradictTwo specs' clauses disagreeUpdate the out-of-date side; real design choice becomes an open TBD
ADRAn ADR beyond the ADR model: a policy or rules section, a restated rule, mechanics, or amendments such as superseded blocks, dated amendments, or a decision logMove each rule into its home spec as an acceptance criterion that says it applies to every feature, unless a spec already states it; write one new short ADR holding the current decision and why, linking those criteria without restating them and naming every ADR it supersedes; add only Superseded by ADR NNNN (date) to each superseded ADR; list removed mechanics in the commit message for the code and the change request
CriteriaAcceptance criteria break a criterion rule of the shaping contract, or miss a Jev project ruleRewrite to the criterion rules, listing each concrete value, fixture user, and artifact path moved out in the commit message for the target's qa.toml hint file; rewrite to satisfy a missed project rule using its own wording
PresentationA spec page beyond the visual quality contract or the authoring figure and layout rules: an ASCII, placeholder, or stale figure; a figure that contradicts the spec text; a figure with fixed colors of its own; a page-level style block; skipped heading levels, unwrapped wide tables, or ad hoc callouts; a runtime lacking a required capabilityRedraw each figure as a purpose-fit diagram of the mechanism the text states, colored from the shared stylesheet; make a contradicting figure match the text; link the shared stylesheet and remove spec-local page styling; bring headings, tables, and callouts to the shared markup; replace the runtime through the review preflight; change no behavior sentence

Presentation repair changes how a spec page reads, never what it says: every behavior sentence, acceptance criterion, and boundary keeps its wording, and the text governs any figure that disagrees with it. Presentation repair applies to specs; Markdown ADRs have no figures or page styling to repair. The review chrome is the runtime's, owned by spec page design, and reaches a spec only through preflight.

Every edit follows the authoring contract: one sentence per line, stable data-anchor on every block, pretty-printed semantic islands.

Drift check

After the six repairs, the skill checks each spec against the code that implements it. Drift is a criterion whose behavior the code does differently, or a code behavior no criterion of the owning spec states, including code no pointer connects to the spec whose behavior the spec should cover in spirit.

Drift, as the skill judges itSuggestion
Code does a criterion's behavior differently, and the behavior makes sense and fits the spirit of the spec; the common case, a spec behind its codeUpdate the spec to match the code (default)
Code does a criterion's behavior differently, and the behavior looks broken or against the spirit of the specFix the code, saying why; stays a recommendation
Code has a behavior no criterion states, whether the spec points to that code or only covers it in spiritAdd a criterion for it to the owning spec

For each drift the skill judges whether the code's behavior makes sense and fits the spirit of the spec, and presents the human one suggestion naming the spec anchor, the code location, the mismatch, and which side to change. The human settles each suggestion: adjust the spec, fix the code later, or leave it. The skill makes only the spec edits the human chose and commits them; it never edits code, so a code fix stays a recommendation to the human. Nothing about drift is written into a spec as a finding, note, or TBD; a spec changes only by the edits the human chose. The drift check, and so the run, is not done until the human has settled every suggestion. A spec whose code the check cannot find gets no suggestion, and the skill tells the human it was not checked against code.

One retry rule

If a repair edit raises a new contradiction or rule miss on the same clause, the skill writes an open TBD at that clause (data-spec-tbd) instead of editing again. The TBD blocks spec acceptance until the human settles it. Same rule as the shaping agent's fix-raises-new-mark.

Proof

First failing test: given a spec with an audit section and a ticket link, after repair neither is present and every acceptance criterion remains.

Evidence: one repair run on a real repo with all six repair types producing a reviewed PR.

Non-goals

Reading a peer's status file or naming a peer; hardcoding project rules; creating specs; changing the warm-up, detection, or reconcile offer in project-wide rules; running without the repo's specs present; automated merging or promotion; turning relational prose into new figures, which changes behavior text and belongs to shaping.

Onboarding: not needed, the reviewer sees repairs through the existing review page and catch-up offer.
