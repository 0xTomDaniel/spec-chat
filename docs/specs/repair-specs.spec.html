Repair specs

docs / specs / repair-specs.spec.html

One Spec Chat skill that brings a repo's existing specs to the current shaping contract. Runnable any time and optionally as onboarding catch-up. The skill reads only Spec Chat's own onboarding status and the repo's specs; project rules found by Jev drive criterion repairs generically. Extends project-wide rules: its warm-up, detection, and reconcile offer are unchanged; this spec owns the bulk editing that the offer or a direct invocation triggers.

User stories

As the shaping agent, I run one skill and every spec in a repo is brought to the shaping contract: non-target text removed, behavior in its owning spec, contradictions resolved, criteria meeting the shaping contract's criterion rules and project rules.

As a reviewer, I review the repairs on the review page with Git focus showing what changed in each spec.

As a project new to Spec Chat, the repairs run as part of onboarding catch-up when warm-up finds specs to reconcile, and I review the result.

As the shaping agent, the skill drives criterion repairs from Jev project rules without hardcoding any project's rule wording or format.

Acceptance criteria

Given a spec with an audit section and a ticket link in its header, When repair runs, Then the committed spec shows neither the section nor the link, and every behavior clause, acceptance criterion, and modular boundary remains.

Given a behavior clause in spec A that spec B already owns per its title, boundaries, and stories, When repair runs, Then the committed spec B shows the clause and spec A no longer does.

Given a spec named after a lane whose behavior belongs in an existing owning spec, When repair runs, Then the committed owning spec shows that behavior and the lane-named file is deleted.

Given two specs whose clauses contradict and one side is out of date, When repair runs, Then the committed out-of-date side matches the current side.

Given two specs whose clauses contradict as a real design choice, When repair runs, Then the committed spec shows an open TBD at the clause.

Given a Jev project rule from another spec and a spec whose acceptance criteria miss that rule, When repair runs, Then the committed criteria satisfy the rule using its wording, and the skill names no project's rules and applies whatever Jev found.

When a repair edit raises a new contradiction or rule miss on the same clause, an open TBD is written at that clause instead of editing again.

When repairs complete, each changed spec is committed on the current branch and registered with the review server; the reviewer sees changes with Git focus.

When the skill's code and instructions are read, it reads only Spec Chat's onboarding.toml and the repo's specs; no peer status file or peer name appears.

When Spec Chat's onboarding.toml shows specs to reconcile for a project and the skill is invoked, it runs all four repair types on that project's specs and updates the project's table when done.

Given Jev is off, When repair runs, Then the committed specs show clean, home, contradiction, and criterion-rule repairs, and only Jev project-rule repairs are skipped.

Given a spec whose criterion reads When the user views a script card at the root or inside a drilled folder, When repair runs, Then the committed spec shows one criterion for the root and one for the drilled folder, the first keeps the original anchor, and each meets every criterion rule of the shaping contract.

Given a criterion whose visible end state or providing fixture cannot be read from the specs, When repair runs, Then the committed spec shows an open TBD at that criterion naming what is missing, and repair invents no end state and no fixture.

Modular boundaries

The repair skill reads all specs in a repo, identifies repairs using the four types and Jev project rules, edits specs in place, commits, and registers for review. Caller-facing seam: the skill invocation; the caller names the repo and optionally the project for onboarding context. Dependency direction: self-contained within Spec Chat; reads Jev as an existing external provider when available; uses the review page for human review. Observable scope: changed spec files, commits, and the review page.

Repair types

TypeTriggerAction
CleanNon-target text: audit sections, before/after comparisons, history, status, source-issue links, ticket linksRemove; preserve every behavior clause, criterion, and boundary
HomeBehavior in a spec that does not own it, or a spec named after a changeMove clauses to the owning spec; delete a change-named spec once empty
ContradictTwo specs' clauses disagreeUpdate the out-of-date side; real design choice becomes an open TBD
CriteriaAcceptance criteria break a criterion rule of the shaping contract, or miss a Jev project ruleRewrite to the criterion rules; rewrite to satisfy a missed project rule using its own wording

Repairs run in this order: clean, home, contradict, criteria. Each type reads the spec as the previous type left it.

Every edit follows the authoring contract: one sentence per line, stable data-anchor on every block, pretty-printed semantic islands.

One retry rule

If a repair edit raises a new contradiction or rule miss on the same clause, the skill writes an open TBD at that clause (data-spec-tbd) instead of editing again. The TBD blocks spec acceptance until the human settles it. Same rule as the shaping agent's fix-raises-new-mark.

Proof

First failing test: given a spec with an audit section and a ticket link, after repair neither is present and every acceptance criterion remains.

Evidence: one repair run on a real repo with all four repair types producing a reviewed PR.

Non-goals

Reading a peer's status file or naming a peer; hardcoding project rules; creating specs; changing the warm-up, detection, or reconcile offer in project-wide rules; running without the repo's specs present; automated merging or promotion.

Onboarding: not needed, the reviewer sees repairs through the existing review page and catch-up offer.
