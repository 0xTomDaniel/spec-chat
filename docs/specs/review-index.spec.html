Review index

docs / specs / review-index.spec.html

The review index at the review service’s root lists every spec the service serves, grouped by lane and project, each saying what it waits on. A lane is the specs registered under one lane slug, as lane hosting defines it.

User stories

As a human reviewer, I open the review index and see first, under Needs you, the lanes with a spec waiting on me, each spec saying in one word what it waits on: a decision, a reply to read, a draft to send, or my acceptance; then the other open lanes, each spec saying whether it is with the agent, sent, or accepted, as its pull request records; and specs with no open lane out of the way in a collapsed Settled section at the bottom. Each spec shows its title, whether it changed since my last review, and its open and resolved thread counts, and each lane links its newest proof. From any spec page I can get back to it.

As a human reviewer, the review index reads like the evidence index beside it: quiet rows grouped by lane rather than boxed cards, each spec led by the status mark of its gate, its title never running under its gate word, the same type, colors, focus ring, and dark appearance, so the two indexes read as one tool.

As a human reviewer, I find a spec on the review index by typing a word of its title, its spec name, or its lane’s issue key into Find, settled specs included, the same Find the evidence index has, so I never scroll the whole index or ask an agent where a spec is.

Modular boundaries

The review server owns the index's thread counts: it folds each served spec's spool on index load and renders the counts in the index HTML; the counts need no script. Caller-facing seam: the index page at the server root. Dependency direction: external-provider; the index depends on the service fold over the spool, never the reverse, and writes nothing. Observable scope: thread counts on index spec rows.

The review server owns each lane spec’s gate word and the index’s Needs you part: it reads the spec’s open decisions from the spec file, its threads and hand-offs from the same spool fold the thread counts use, and its acceptance and its lane’s proof from the evidence provider’s review facts. Caller-facing seam: the index page at the server root; to the provider, one GET <url>/review-facts per index load in the format review facts names. Dependency direction: external-provider for review facts, through the evidence provider file; Spec Chat names no provider product, and without a provider the index shows every gate it can read itself. Observable scope: gate words, the Needs you part, lane headers’ need counts and Proof links; the index writes nothing.

The review server owns what Find matches each row by: it writes each spec row’s title, spec name, and lane key into the index HTML; the design set’s Find script shows and hides the rows in the page. Caller-facing seam: the index page at the server root. Dependency direction: external package, the shared design set’s Find field at the version Spec Chat pins, built in; Find fetches nothing, writes nothing, and names no peer. Observable scope: which rows, lanes, parts, and Settled show while Find holds text.

Review index

The review index at the server root groups served specs by lane, then project, built only from the rows and the spec files it already serves. It is one column of rows, as the evidence index is: a lane is a group of rows under its header, never a boxed card.

Changed and Stale are its only words: the row base is the version of your last hand-off, so Changed says there is something new since you last reviewed, and nothing says up to date.

The index has three parts. “Needs you” is a heading over the open lanes with any spec whose gate needs you; “In progress” is a heading over the other open lanes; both show only when they hold a lane. A lane is open while rows exist under its lane key, a slug that reads as an issue key (abc230), since teardown deletes a lane's rows. “Settled (n)” is one native <details> at the bottom, closed by default, holding the n other specs: those under any other slug, such as the main collection registered as aa, and those served without a row. Settled groups them by project in the same spec row shape, a status shown where the row has one, and orders them as a lane's specs. A part with no specs is absent. The words are the ones the evidence index uses, and each index shows only its own gate: this one the spec review, the evidence index the merge ask.

Order is a sort: in each part, lanes by issue number; projects by name; within a project, specs that need you first, then changed specs, then by title. The served path, slug, row id, and base commit leave the index; a stale row shows only its spec path.

Find: one field under the title line, above the parts, filters the index as you type, case aside, to the spec rows whose title, spec name, or lane holds what is typed, in every part, Settled included. A spec’s name is its file name without .spec.html, as the evidence index names a spec; its lane is its lane header’s issue key; a settled spec has no lane, and a stale row is matched by its spec path’s name and its lane. A lane, project, or part left with no row hides; each part’s heading count reads the lanes the filter leaves it, and Settled opens while it holds a match, its count reading the matches; when nothing matches, the index shows “No spec matches” under Find. Clearing the field, or Escape, restores the page as it opened. Find filters what the page already holds and fetches nothing; the page keeps no filter across loads. It is the shared design set’s Find field, the one the evidence index uses, so the two look and work the same.

A gate word says what the spec waits on and who acts next, never how the file compares with a base. Accept spec sent is the instruction; Accepted is the record, read from the pull request’s receipt, never from the spool, so the index keeps no copy of an acceptance. Settled specs show no gate word.

A lane spec with a mockup set is read with it: its thread counts and every gate word that reads the spool fold take the spec’s and its mockups’ threads as one, so a mockup’s open thread or waiting reply shows on its spec’s row, and the index shows no row of its own for a mockup.

Review facts: on each index load the server asks its evidence provider once, GET <url>/review-facts with one path parameter per lane spec’s served path and one lane parameter per lane’s slug, and reads {"specs": {"<path>": {"accepted": "<commit>", "proof": {"bundle": "<bundle id>", "url": "<bundle address>"}}}, "lanes": {"<slug>": {"stage": "<words>"}}}, any key absent when the provider has none. The server asks the same review facts for a lane’s stage when a page of that lane reads its events, and tells the page that stage with them (stage tag); a lane the answer leaves out has no stage. A spec the answer leaves out has neither. Without a provider, or when the answer fails or does not come in time, the index renders at once with neither fact: Accepted never shows and Accept spec sent stays. A lane header’s Proof link opens url; framed by a host that asked for evidence opens, a click sends the evidence open with bundle instead.

Design: the index draws every color, type step, weight, space, radius, focus ring, status mark, and icon from the shared design set, the one the spec page chrome uses, and holds no value of its own. One title “Review index” (h1) at the title step with a muted count line beside it; Needs you and In progress are group headings with their counts; project labels are muted meta, never capitals. Spec rows are separated by hairlines, each led by its mark; a gate word is a quiet word in the meta step, in attention color when the gate needs you, else muted; spec titles are row titles in ink at medium weight, underlined on hover and focus. No card, border box, stripe, or pill. Width up to 48rem, one column. Find spans the column under the title line, its label beside its field. Under the set’s phone width the gate word moves under its title, and every row and Find are full-size touch targets. The index follows the system appearance with the set’s dark values, and inside a host that passes its appearance, the host’s.

Shared design set: the index and the spec page chrome take their values from one design set, a small package each consumer builds in at the version it pins, never fetched from a peer at run time; Spec Chat pins it and serves the index, the runtime, and the spec stylesheet with that version. Its names are the --ui-* names: page, surface, ink, muted, border, link, action, focus, and pass, fail, attention, and muted with their soft fills, each in light and dark; the font and monospace font; the type steps and three weights; spaces and radii; motion; the five status marks and the line icons; and the Find field. A peer shows the set’s Find once it pins a version holding it, and until then its index keeps what it had, so each index moves to it with its own pin, in any order, and neither waits on the other. Spec Chat keeps no copy of a value in its own code: a new value arrives only with a new pin.

The design set’s Find field

The index’s Find takes from the design set one seam, the Find field: its markup, its style, and its filter script, built in at the pinned version like the rest of the set. The set names no page: a page marks what Find filters, and the set’s script does the rest, so every index that pins it finds the same way.

The review index marks each spec row an item, its words its title, spec name, and lane key; each project, lane, and part a group, a part’s count counting its lanes; Settled a disclosure, its count counting its specs; and its no-match line “No spec matches”.

Thread counts

Each spec row shows how many of its comment threads are open and how many resolved, as one muted line under its title, open then resolved, such as “3 open · 5 resolved”. A thread is resolved when its status is resolved and open otherwise, whether draft, handed off, or replied. Each count reads its number then its word, so color is never the only cue. A status with no threads is absent; a spec with no threads shows no count line.

Counts come from the spec's spool and its mockups' spools, folded by the service fold, the same statuses the spec page shows. No count is stored and no new file or route is added.

Counts are current at each index load; the counts need no script and the index does not poll for them. A reload re-renders it, and its ETag changes with the counts.

The counts are rendered by the review server itself, so they show the same on a loopback server and on a hosted one.

The index renders exactly as it would with nothing kept between loads, and a warm load answers in under 200 ms. Review facts are asked once per index load and never kept, since the pull request owns them.

Every served spec page shows a back link to the review index, a chevron and “Review index”, at the start of its fixed top line. At phone width (640 px and narrower) the open review panel fills the screen, so the link is hidden while the panel is open and returns when it closes. At wider widths the panel sits beside the page and the link stays.
