Review surface compatibility

docs / specs / review-preflight.spec.html

Before review opens, one preflight checks a target’s runtime against the bundled runtime’s capabilities and migrates it in its own commit.

User stories

As a reviewer, I want the same required review capabilities in every repository so an old vendored runtime cannot silently remove controls, focus, or visuals.

Acceptance criteria

Given a feature author whose target's review runtime lacks a capability the bundled runtime requires, a fixture must be added to provide it, When the author opens review, Then the reviewer's page has every required capability, the runtime replaced from the bundle before the server started.

Given a feature author whose target repository holds its own copy of a review server, a fixture must be added to provide it, When the author opens review, Then the reviewer's page is served by Spec Chat's own bundled server with every required capability, and the target's copy is unchanged.

Given a feature author whose target's review assets declare every required capability, a fixture must be added to provide it, When the author opens review, Then the page opens with the target's own assets, left untouched.

Given a feature author whose target's review runtime lacks a required capability, a fixture must be added to provide it, When the author opens review and preflight fails, which needs an induced failure: preflight replacement, Then the failed preflight shows as a review blocker.

Given a feature author shaping a feature in a target whose review runtime lacks a required capability, a fixture must be added to provide it, When shaping opens review, Then the migration shows as its own commit touching only the shared runtime assets, the hand-off names that commit, it ships inside the feature's change with no separate change or earlier merge to main, and no feature spec commit contains runtime files.

Onboarding: not needed, preflight adds no user surface. CI: the preflight tests run in CI with no other tool of the box installed and no provider file (CI rule). One hand-off control for desktop and phone: not affected, preflight adds no hand-off control (phone rule, desktop rule). Never strip proof clauses or rewrite unedited criteria: not affected, no criterion here carries a proof clause (shaping rule, repair rule). Every mockup at production fidelity: not affected, preflight changes no screen (rule).

Modular boundaries

Preflight owns the capability check and migration. Caller-facing seam: the runtime’s spec-chat-capabilities line and scripts/preflight.py’s result line. Dependency direction: self-contained; reads the bundle and the target, commits only the shared runtime assets. Observable scope: the migration commit and a visible blocker.

Review surface compatibility

The review-surface preflight is the single seam that verifies a target spec, browser runtime, and local transport before review opens.

Compatibility is checked for the target runtime only, from explicit capabilities required by the current bundled runtime rather than global skill freshness, file age, or an external registry.

When the target runtime lacks a required capability, preflight replaces it from the current self-contained skill bundle before the server starts; the review server is always the skill's own bundled assets/review-serve.py, so it is never copied into the target.

A committed target asset declaring every required capability remains untouched even when its implementation or pin differs from the bundle. In a Git target, a runtime that declares them only in uncommitted changes is replaced and committed as a migration.

Git focus needs both the bundled server's read-only baseline route and the target runtime's browser behavior.

In a Git target, a migration of the shared review runtime is its own commit, never mixed into a feature commit: preflight commits it alone, touching only the shared runtime assets, and the hand-off names that commit; it ships inside the same change as the feature, never as a separate change or an earlier merge to the target's main branch. In a plain directory outside Git, preflight replaces the runtime in place with no commit.

A running review server serves the migrated runtime on its next request, with no restart.

Before a review handoff, the agent verifies served runtime capabilities and uses the read-only verifier to compare served spec bytes with the local file plus the meta the service adds (served spec page), and baseline HTML with local files and Git, including new-file baselines, as the service's own proof checks them before register reports a link.

Every semantic visual island has a render target in the same parent, and a missing target blocks publication rather than silently producing prose-only output.

A failed migration or preflight is a visible review blocker.

Preflight adds no service, registry, package dependency, background updater, or cross-repository control plane.
