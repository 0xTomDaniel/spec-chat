Right pairs and explicit project rules

docs / specs / right-pairs.spec.html

The Jev suggestions draft checks and cross-lane checks produce too many wrong flags: 270 confirmed wrong out of 2082 window pairs, 15 right. Most wrong flags come from pairing clauses that share words but are about different things, and from asking clauses that are not behavioral text. This spec rewrites the pairing and leaf rules in those sections, adds an about the same thing? gate question, makes project rules explicit in the criterion text, and updates onboarding to use the explicit rule. Extends Jev review suggestions and project-wide rules at shaping; depends on yes/no chains (PR #91).

User stories

As a reviewer, a Contradicts or Oversteps flag points at a clause about the same thing as the flagged clause, so the flag is worth reading.

As a reviewer, headings, figures, examples, captions, TBD text, and preview blocks never draw a flag, and sibling rows of the same table never contradict each other, so I do not dismiss the same kinds of false flags repeatedly.

As a reviewer, each flag's popover quotes the flagged clause with its section heading and, for a table row, its column headers, so I understand the clause without navigating to it.

As the owner reading cross-lane findings on my spec, the findings are ranked by relevance like draft checks, not every pair of every changed clause, so I see the important conflicts first and irrelevant ones are not asked.

As a spec author, a criterion counts as a project-wide rule only when its own text says it applies to every feature, so I control which criteria become rules by including or omitting that wording.

As a reviewer on a project new to Spec Chat, the first-run warm-up and reconcile offer find only the criteria whose text says every feature, and onboarding docs say how to write a project rule.

As the operator, I can see the before/after accuracy and flag counts on the audit's labelled cases, so I know the changes worked.

Acceptance criteria

When a spec has anchored headings (h1 to h6), figure, figcaption, pre, code, mock, and preview blocks, captions, elements with data-spec-tbd, and elements inside an anchor whose id contains source-issues, none of those anchors appear as a clause in draft-check questions, cross-lane questions, or as a candidate for any question, and the existing header and meta exclusions still apply.

When a leaf anchor's text is shorter than 20 characters, it is not a clause and not a candidate.

When two leaf clauses share the same parent table, list, or definition list, no draft-check or cross-lane question pairs them, and each is still paired with clauses outside its parent.

When a story and a criterion are in the same spec, no draft-check question pairs them; coverage owns that relationship.

When two slugs serve the same spec path and one clause from each is a draft-check or cross-lane candidate, a clause is compared once, against main's copy of that path, never against another slug's served copy of the same path.

When a clause sits inside a section with a heading, and when a clause is a table row, the question's state sends the section heading as section and, for a table row, its column headers as columns, alongside the clause text.

When a changed clause and a candidate are paired, a cheap yes/no about the same thing? question is asked first, and only pairs answered yes proceed to the contradicts/oversteps chain; a no answer records unrelated and shows nothing.

When the same clause text pair is asked about the same thing? again, the cached record is reused without a provider call, keyed by the same content hash as other question sets.

When a spec read builds 40 candidate pairs, the gate questions are asked in parallel, and a pair whose gate is no skips the contradicts/oversteps question entirely, so fewer provider calls are made than today's ungated pairs.

When two slugs each have 20 changed clauses, cross-lane pairs are ranked by the gate question and only the top 8 per clause that answer yes proceed to the lane question, instead of all 400 pairs.

When a slug's changed clauses include headings, figures, and TBD text, those are excluded from cross-lane questions by the same leaf filter as draft checks.

When a slug matches the pattern fx, lane, main, or ann followed by four or more digits (such as ann9200), its records are written to a separate test store, not the live records.jsonl, and its clauses are not candidates for any live slug's draft checks or cross-lane checks.

When a criterion's text says every feature, every change, any change, or equivalent every-feature wording, the scope question still asks Jev, and Jev's answer decides, as today; the explicit wording makes Jev's answer reliable, not a new mechanism.

When a criterion describes how one feature behaves and does not say it applies to every feature, Jev answers this feature and it is never a project rule.

After the sweep rewrites real project-wide rules with explicit every-feature wording in their home specs and drops false rules, the scope question produces no false rules on the rewritten specs, measured on the audit's 9 wrong and 2 real rule records.

When the first-run warm-up classifies every criterion, it uses the same scope question and Jev answer as any other rule check; criteria without explicit every-feature wording are classified this feature and produce no rule, no offer, and no miss mark.

When a reviewer reads the onboarding docs, one section says how to write a project rule: include explicit every-feature wording in the criterion text, such as When any change adds a screen, it ships with its help center article.

When the audit's labelled cases (270 wrong, 15 right, 2 missed) are run through the new pairing and leaf filter on the same question sets and provider, the wrong-flag count drops by at least 80% (at most 54 wrong), the 15 right flags are still shown, and the 2 missed real conflicts are still asked.

Modular boundaries

The review server's Jev seam owns the leaf filter, context builder, gate question, sibling and story-criterion skips, same-path dedup, cross-lane ranking, and test-host dispatch. It extends the existing seam; no new route or response shape is added. Caller-facing seam: the existing GET /api/jev response, with the same item shapes and levels; the gate's about question set is a new set in the same question-set directory. Dependency direction: external-provider; calls Jev through OpenRouter as before; reads local Git, served specs, and the spool; nothing calls back. The test store is a second JudgmentStore instance beside the live one. Observable scope: the JSON response (fewer and more accurate items), records (in live or test store), and the question count per read.

The anchor parser owns tag, parent, TBD, figure, and sibling detection; the leaf filter owns exclusion decisions from parsed anchors. Caller-facing seam: extract_anchors returns each anchor's tag, parent, children, and new flags (tbd, figure, heading) used by the leaf filter. Dependency direction: self-contained; the parser reads HTML and returns data. Observable scope: the anchor dict and the questions the leaf filter produces.

The about question set owns the gate question's instructions, labels, examples, and threshold. Caller-facing seam: a set id and version, loaded by the existing load_question_sets. Dependency direction: self-contained data read by the seam. Observable scope: the version named in each record.

The sweep rewrites criterion text in spec files across three repos. Caller-facing seam: per-repo PRs changing only spec HTML files. Dependency direction: self-contained text changes; no code or configuration. Observable scope: the rewritten criterion text and Jev's scope answers on it.

Pairing

A draft-check pair is a changed clause and a candidate clause. A cross-lane pair is a changed clause from one slug and a changed clause from another. Both use the same leaf filter, context, and gate question. The gate replaces the previous word-overlap ranking as the primary filter: candidates are enumerated, the gate drops unrelated pairs cheaply, and only related pairs proceed to the contradicts/oversteps chain.

Leaf clauses

A leaf clause is an anchor with no children, whose text is at least 20 characters, and that is not excluded by any of the following rules. The existing meta exclusion (corpus meta) is unchanged.

Clause context

Every question carries its clause text plus structural context so the model reads the clause as a reviewer would. Context is derived from the parsed anchor tree, not generated.

Context fieldValuePresent when

Context fields appear in the question's state beside after and target. They are part of the cache key, so a clause under a renamed heading is re-asked.

Sibling skip

Two leaf clauses that share the same immediate table (table), list (ol, ul), or definition list (dl) parent are siblings. Neither draft-check nor cross-lane questions pair siblings: each sibling is paired only with clauses outside its parent container. Each sibling's question carries its column headers as context so the model reads each row in its table frame.

Audit class: 228 window pairs, 73 judged wrong. Example: surface-toast vs surface-error under one table, both describing per-surface rules that are alternatives, not contradictions.

Story-criterion skip

A draft-check question never pairs a story (data-user-story) with a criterion (data-acceptance-criterion) in the same spec. Coverage owns that relationship. Audit class: 49 window pairs, 9 judged wrong.

Same-path deduplication

When two slugs serve the same spec path, a clause's candidates come from main's copy of that path, never from another slug's served copy. This is the existing behavior of corpus others, enforced at the seam: the served-specs builder de-duplicates by project and spec path, so the same file is a candidate once. Audit class: 398 window pairs (stale or parallel copies).

Gate question

Before asking contradicts or oversteps, each candidate pair is asked: Are these two clauses about the same thing? This is a yes/no Jev question using its own versioned question set, about. A yes answer means the clauses describe the same route, field, element, command, term, surface, or responsibility; the model sees the clause text, the context fields, and nothing else.

The gate precedes the yes/no contradicts/oversteps chain from PR #91. The full sequence for a pair is: about? (yes) then contradicts? (no) then oversteps? A no or unsure (below threshold) gate answer records unrelated for the pair and skips the rest of the chain. The gate's record is keyed like any other question set, by the content hash of its inputs and set version. The threshold is tuned from the audit's labelled cases.

Cross-lane checks use the same gate. For each clause of one slug, the gate is asked against every changed clause of every other slug, and only those answering yes proceed to the lane question. The top 8 per clause by gate confidence proceed, matching the draft-check candidate limit. This replaces the previous all-pairs approach; clauses filtered out by the leaf filter or same-path deduplication are excluded before any gate question is asked.

Gate questions are asked in parallel within one read, like other questions. A provider failure on the gate treats that pair as unrelated for this read and retries on the next read.

Test-host exclusion

Slugs whose name matches the pattern fx, lane, main, or ann followed by four or more digits are test or QA hosts. Their Jev records are written to a separate store file (records-test.jsonl) beside the live store, so test runs do not pollute live record lookups and do not grow the live file. Their clauses are not candidates for any live slug's draft checks or cross-lane checks.

Detection is by slug name at registration time. The review server holds one JudgmentStore for live and one for test; a read dispatches to the store matching its slug. The test store has no warm-up, no board contribution, and no onboarding effect.

Explicit project rules

A criterion counts as a project-wide rule only when Jev, reading its text, answers every feature. The mechanism is unchanged: the existing scope question and its fallback decide. What changes is the input: every real project-wide rule is rewritten in its home spec with explicit every-feature wording, and false rules (criteria that describe one feature's behavior but were ambiguously worded) are rewritten to say this feature clearly. The rewrite is a sweep across all three repos' specs, delivered as per-repo PRs.

No new mechanism is added. The scope question set, the Jev fallback, the rule-check question, records, and caching are unchanged. The improvement is in the criterion text, not the code.

Sweep

Every acceptance criterion in every spec across spec-chat, annotateanything, and octo-lite is checked: does its text say it applies to every feature? Real project-wide rules get explicit every-feature wording added. False rules (criteria that Jev previously classified as every feature but that describe one feature's behavior) are reworded to make their single-feature scope clear.

The sweep is delivered as one PR per repo, separate from the pairing changes. Each PR changes only criterion text in spec files, adding or clarifying every-feature wording. No code changes.

The audit identified 9 wrong rule records and 2 real ones. After the sweep, the scope question produces no false rules on the rewritten specs.

Onboarding

The first-run warm-up and reconcile offer use the same scope question as any other rule check. With the explicit wording in place, criteria without every-feature wording are classified this feature reliably, producing no false rules, no spurious offers, and no spurious miss marks.

Onboarding docs (the README.md or a docs section in each repo) include one section saying how to write a project rule: include explicit every-feature wording in the criterion text. Example: When any change adds a screen or alters what a user can do, the change ships with its help center article.

Changes to existing specs

In jev-suggestions.spec.html: the Draft checks section gains the leaf filter, sibling skip, story-criterion skip, context fields, and the gate question before the contradicts/oversteps chain. The Cross-lane checks section gains the leaf filter, gate-based ranking (top 8 per clause), and test-host exclusion. Corpus meta is extended to cover TBD, figure, and example anchors.

In project-rules.spec.html: no mechanism change. The scope question and its fallback are unchanged. The sweep rewrites criterion text so Jev answers reliably. The onboarding warm-up and reconcile offer produce no false rules after the sweep.

Proof

First failing test: with a spec whose leaf anchors include a heading, a figure, and a TBD block, build_corpus_questions returns no question for any of them and no question targeting any of them.

Gate first failing test: with a fake provider answering no to the gate, build_corpus_questions returns no contradicts/oversteps question for that pair.

Sibling first failing test: with two leaf clauses under one table, build_corpus_questions returns no question pairing them.

Cross-lane first failing test: with 20 changed clauses per slug and a fake provider, the lane builder asks at most 8 lane questions per clause, not 400.

Test-host first failing test: a slug named ann9200 writes its record to the test store, not the live store.

Evidence: seam tests behind fakes for each filter, the gate, siblings, same-path, and test hosts; one live run of the audit's labelled cases before and after.

Non-goals

Semantic embeddings or vector similarity for pairing; a new question set for contradicts or oversteps (the existing yes/no chains from PR #91 are unchanged); LLM-generated context or summaries (the context fields are parsed from the HTML structure, not generated); a new API route or response shape; rules from outside the served specs; changes to the scope question set's instructions, labels, or threshold; any change to the browser runtime, markers, popovers, or note buttons.
