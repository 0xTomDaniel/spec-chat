Box review service and providers

docs / specs / review-service.spec.html

Spec Chat works completely alone. A box has one review service per Herdr session, and every lane of a session joins its session's service; a box without Herdr is its one default session. Each service owns its bind, port, and URL. Anything else plugs in only through Spec Chat's state: each service publishes facts in its own state for readers, and every service reads the box's optional providers from one place. Spec Chat names no reader and no provider product; why the session scopes the service is in the ADR.

User stories

As a human reviewer, every lane of one Herdr session hands me a link on that session's one review service, so a page I can open once I can open for every lane of the session.

As a lane owner, my lane's prototype runs on my session's review service at an origin of its own, at its root as my product ships, so any product runs as a prototype unchanged and shares nothing with the review pages or another lane.

As an operator running several Herdr sessions on one box, each session's lanes register, get woken, and are torn down on that session's own review service, so no session sees, wakes, or removes another's specs, and a box with one session needs no session setup: its one service is the default session's.

As a Spec Chat user with nothing else installed, review works end to end: private by default, public when I say so once, and no capability I lack shows an error.

As a box operator, the review service's log keeps everything the running service wrote, whatever starts it and whatever later start fails, so I can find why something went wrong.

As another tool, I find the review service and plug an optional capability into it through its state alone, with no launch flag, environment variable, path, or port set by hand, and Spec Chat never learns my name.

As a box operator, the review service holds steady memory and CPU however long it runs and however many specs, pages, and Jev reads it serves, and one route tells me so, so no watchdog has to restart it and drop open pages and wakes.

As a box operator, when a host fast-forwards my Spec Chat clone, it runs the one after-pull step Spec Chat publishes, and the review service then runs the pulled code, so I never restart it by hand after an update.

As a box operator, a host tells me when my Spec Chat install is older than its pulled clone, from the commit Spec Chat’s onboarding file records, so a pull no after-pull step followed never goes unnoticed.

As a box operator, a host runs the one setup check Spec Chat publishes and shows me each problem with how my box has Spec Chat set up, each with the step that fixes it, so a skill link lost, an onboarding file out of date, or a review service left on older code never goes unnoticed, and the check itself changes nothing.

As a box operator, every store Spec Chat writes on the box says whether it is safe to delete and which writer ends it, so nothing piles up and no fact is kept twice.

As a human reviewer, I scrub any video the review service serves me, a round’s video or one a reviewed page or prototype shows, to any moment without waiting for it to load whole.

Modular boundaries

The review service owns its bind, port, proof host, public base address, unit, and URL, recorded in its own state; the HTTPS front that proxies to it is the box's, not Spec Chat's. Caller-facing seam: review-host register, which returns the URL. Dependency direction: external-provider for its session alone, read from the session key Herdr exports, never from another tool's code; otherwise self-contained, and no lane, skill, or brief picks a port. Observable scope: the printed URL, [process], the status route, and the stores it writes.

Readers own nothing in the service state; they read what the service publishes. Caller-facing seam: the published files and routes. Dependency direction: external-provider; readers depend on Spec Chat, never the reverse, find a session's service state from the same session key, and never write into its state. Observable scope: the published fields.

Each provider owns exactly its own file under the box's providers/; Spec Chat owns each file's format and reads it. Caller-facing seam: the provider files. Dependency direction: external-provider; providers depend on Spec Chat's format, Spec Chat names no provider product. Observable scope: a capability on while its file is valid, off otherwise.

One service per session

The Herdr session is the isolation unit: each session has its own review service, with its own registry, server, port, log, review index, and box setup, and a lane joins only its own session's service. The session key is the Herdr session name, read from Herdr alone as ${HERDR_SESSION:-default}: Herdr exports HERDR_SESSION to every pane of a named session, a pane of the default session has none, and a process outside any pane is in the session its environment names, the default session when it names none. A box without Herdr is its default session.

A session's review service lives at its service state, $XDG_STATE_HOME/spec-chat/hosting/<key> (~/.local/state when XDG_STATE_HOME is unset), so the default session's is hosting/default. Every review-host command without --state-dir acts on its caller's session's service; register joins it, and if it is live, the rows are added and its URL is returned unchanged.

Herdr pane ids are unique only within a session, so a row's owner and checker are pane ids of its service's session, and rows name no session. A service runs in its session: register starts it from its caller's session, and the box user service runs outside any pane, in the default session. Its wake checks and sends run in that same session, so a wake reaches only a pane of the service's session.

A new service is private on loopback. --public <host> makes it public; --private returns it to loopback. --public-base <address> gives it a public base address, such as an HTTPS front's https://spec.<a-b-c-d>.sslip.io: its published url and every review link it reports start with that address, while its box-side proof checks the service's own listener; an empty address clears it. The choices, and the proof host used for a wildcard bind, are recorded, so every later register and restart keeps them. Choosing them is the box owner's act, not each lane's.

An HTTPS public base address (one starting https://) means the box serves the page through its HTTPS front, which proxies to the loopback listener in [process]. While one is recorded, the service listens on loopback only, whatever visibility is recorded, so the front is the only way in from outside the box; the recorded visibility and proof host are kept, and clearing the address, or replacing it with one that is not HTTPS, returns the service to them. Giving or clearing an HTTPS address moves a live service at once, keeping its port while free, through its unit when one is recorded; any other change to the address needs no restart. Every start takes the listener from the recorded setup. A loopback listener is private, so the port rules for a private service apply. The box owner sets the front to proxy to the loopback listener before the service moves; a wildcard listener already answers on loopback, so the front reaches the service before, during, and after the move.

Before register reports a spec's review link, its box-side proof checks the spec's row over HTTP at the service's own listener, its proof host and port. It opens the spec's review link with focus on changes against the row's base commit and checks that the page is the spec file plus the meta the service adds (served spec page), then asks the page's baseline and checks that it names that commit and holds the spec as Git holds it there, or none for a spec absent at that commit. A private service, and one an HTTPS public base address holds on loopback, is proved on loopback. A failed proof fails the registration, which leaves the registry as it was. A scope row serves no page, so it has no proof.

A dead service restarts on its recorded bind, public base address, and recorded port while that port is free; otherwise it takes another free port by its own rule (an approved ingress port when public). With a recorded unit, the restart goes through the unit's service manager.

Box setup's --service runs the service as a box user service: spec-chat-review.service under ~/.config/systemd/user, enabled, with lingering on. It starts at boot without a login, starts again after the process dies, and stays stopped after a clean stop, which is never a failure. The unit runs review-host serve from the clone that installed it, so after a pull it runs that clone's code from its next start. serve starts the server in the foreground on the recorded setup and records itself in [process], including unit. While a unit is recorded, register starts, restarts, or moves the service only through that unit, a live service started otherwise is handed to it, and stop is the unit's clean stop. A recorded unit that no longer exists is dropped, and the service starts without one.

A service's log is server.log in its service state, and it holds everything the service prints, the wake lines included. Each line starts with the UTC instant it began, to the millisecond, ending in Z, as a Jev record’s time. Every start appends to it, a start through the unit included, and nothing empties it, so a start that fails, such as one whose port is taken, leaves every line the running service wrote.

Each /api/jev read writes one line to it as it ends: the spec and base it read, how long it took in milliseconds, how many items it answered and how many of them are pending, and the asks waiting and running in the ask queue. A read whose reader left before its answer was sent says so on that line, in place of an error.

After a pull: the installer publishes after_pull in its onboarding file, the step a host runs, after fast-forwarding this clone, to bring the box onto the pulled code: install-spec-chat --after-pull from this clone. It first writes the onboarding file’s published fields as this clone’s installer publishes them, its commit this clone’s current one, keeping the file’s status and its [installed] record, so a field the pulled code publishes reaches the box with no installer run. It then restarts each session's live review service onto the clone's code, each in its own session, through its unit when one is recorded, else by a clean stop and a start on its recorded setup; a service that is not running stays stopped, since its next start runs the clone's code. It exits successfully once each restarted service's status route answers with an uptime shorter than the step has run, and otherwise exits non-zero, the last line of its error output naming why, such as that the service did not answer on the pulled code. It names no host and asks nothing.

Setup check: the installer publishes check in its onboarding file beside after_pull, the step a host runs, with no shell and no input, to read how the box has Spec Chat set up: install-spec-chat --check from this clone, which takes no other flag. It changes nothing: it writes, starts, and stops nothing, and a check run twice reports the same. It reports every problem it finds, never stopping at the first, each as one line of its error output naming the problem and the step that fixes it, and exits non-zero when it finds any, else zero with nothing on its error output. Its problems are Spec Chat’s own setup alone: no onboarding file, fixed by running the installer; an onboarding file whose published fields, its commit aside, differ from what this clone’s installer publishes, fixed by running the installer again; a Spec Chat skill not linked, or its link not leading to that skill in this clone or in another clone of this repository, the installer’s adoption, in a repository the installer recorded installing into, in each skill folder it linked there, fixed by running the installer again for that repository, once whatever else holds the link’s place is removed; a box user service the installer recorded whose unit is gone or not enabled, fixed by box setup’s --service, a masked unit unmasked first; and a session’s running review service that is not on this clone’s current commit, as its commit reads, fixed by the after-pull step. A stopped service is no problem, since its next start runs this clone’s code; nor is an onboarding file’s commit other than this clone’s, which its readers compare with the clone’s own; nor is a unit it cannot ask the box’s user service manager about, as when that manager cannot be reached, which it says on its standard output as not checked. It names no host, and nothing of any other tool.

A row whose worktree, collection, or spec file cannot be reached is stale. A stale row affects only itself: every start, restart, and registration of the service goes on, serves every other row, and reports each stale row by its id and reason, and the row stays registered untouched until its owner removes it. The service serves no page for it and the review index marks it stale. A registry that is unreadable or structurally invalid, such as a duplicate id, two rows at one path, a reserved slug, or a missing field, still stops the service, since no row can be trusted.

A lane runs only review-host register --slug <lane-key> --owner <pane> <spec path>, repeating the spec path for more specs. It names no exposure: the service already owns it, so a lane command never reads as opening ingress. Its one optional address, --prototype <address>, names where the lane's running prototype answers at its root, often on loopback, for the specs' prototype mockups; registering a spec again with it sets or changes it on the existing row and keeps its review. It refuses a slug whose prototype origin's first label, <slug>-prototype, would pass 63 characters, the most a host name's label holds.

The service serves a lane's prototype at the lane's prototype origin, its own address with <slug>-prototype. before its host name, at the root and the route, from the address its rows last named: https://<slug>-prototype.spec.<a-b-c-d>.sslip.io for a service at https://spec.<a-b-c-d>.sslip.io, and http://<slug>-prototype.localhost:<port> for one private on loopback. So a product runs at its root as it ships, on an origin no review page and no other lane shares, and a prototype on loopback is reached wherever the service is, public or private. The service tells a request for a prototype from one for its own pages by the host it names. A service whose address names its host by an IP address off loopback has no prototype origin, so its prototype mockups read Prototype not running until the box owner gives it a public base address with a host name (box setup). It forwards only reads, GET and HEAD, forwards no cookie either way, and adds the comment layer's script to each HTML page it forwards that runs no Spec Chat runtime of its own; a page that runs one, such as Spec Chat's own pages run as a lane's prototype, is held by it, so the page runs the runtime once. On each page it adds the layer to, it changes the page's own policy only as far as the layer needs to run there and the review pages need to frame it: it lets the layer's script in, by the service's address, or by a nonce of that answer's own where the policy trusts scripts by nonce, hash, or 'strict-dynamic', and it names the service's origins and the box's shell origins as the ancestors that may frame the page, in place of any X-Frame-Options, which it drops; it loosens nothing else. A shell whose frames have no origin cannot be named, so under it a page whose own policy limits its ancestors is not framed and its mockup reads Prototype not running. The prototype reads only data that is safe to show, as the lane's shaping keeps it.

Through an HTTPS front, the box's front answers each lane's prototype origin as it answers the service's own address, proxying to the loopback listener with the request's host kept; a front that issues a certificate for each host as it is first asked may ask the service first, GET /api/prototype-host?domain=<host>, the query name such a front asks with, answered 200 for a lane's prototype origin while a row names its slug and 404 for any other host. A front that does not answer the prototype origins leaves every other page served as before, its prototype mockups reading Prototype not running.

register rejects a row without an owner, so every hosted spec has one. With no spec path it registers a scope row.

A plain spec path infers the rest from Git: root is the worktree top; project is the last path part of origin without .git, or the top directory's name without an origin; base is the merge base of HEAD with the default branch (origin/HEAD, else main), or --base <ref>. The PROJECT_ID=ROOT:SPEC_PATH@BASE form is also accepted.

Spec Chat has one install and onboarding entry point, scripts/install-spec-chat: it links its skills into the target repo's .agents/skills and links each from .claude/skills and .codex/skills relatively (with --agents-only, only .agents/skills), never under the home directory, installs the page runtime and style into a named spec folder, sets up the default session's review service, whatever session it runs in, since the box user service it installs runs in the default session, and writes its one onboarding file, onboarding.toml, which also records what it added; a rerun from a clone at the same commit changes nothing. When a target path is already occupied, the installer classifies it: a symlink resolving into a different clone of this repository, one with the same origin, is adopted and reported; any other existing file or symlink is skipped and reported; the installer never overwrites, never fails on an occupied path, and continues with the remaining items. --undo removes only what that file records it added, then the file: it stops any review server process it started, disables and removes the box user service unit it installed (lingering, shared with other user services, stays on), removes its skill links and registered review resources, and deletes the runtime assets (.viz, .style) only when they are unmodified and not tracked by git. Any other tool reaches Spec Chat's install only through it.

Box setup, by the box owner and outside any lane: --public <host>, --private, --proof-host, --public-base <address>, --shell <origin>, which names an origin that may hold the service's pages as a shell and may be given again for more (shell setting), and the installer's --service (review-host register --unit <name>), each once. Each review-host flag sets up its caller's session's service, so a named session's service, private on loopback until then, is set up from that session; the installer's --service sets up the default session's service, as its onboarding does. Without --proof-host, the proof host is SPEC_CHAT_PROOF_HOST (or REVIEW_PROOF_HOST) when set, else the public bind address, else the address the box routes outward from. The approved ingress port list is SPEC_CHAT_APPROVED_INGRESS_PORTS (or REVIEW_APPROVED_INGRESS_PORTS) when set, else, for a public service, the TCP ports the firewall allows (ufw status); every start reads it again.

--state-dir names a separate, isolated service for tests or deliberate isolation; lanes do not pass it.

The review server answers HTTP/1.1 with keep-alive: browsers send If-None-Match only for HTTP/1.1 responses, and one connection serves a page and its assets.

A video or audio file the service serves, under a row’s root or as one of a round’s files, its captions included, answers a Range request for one byte range with 206 and that range’s Content-Range, so a reviewer’s player seeks to any moment without loading the file whole (video rail). Each answer for it carries Accept-Ranges: bytes and an ETag naming the file’s version; several ranges, or a range asked If-Range of another version, answer the whole file, and a range past its end answers 416. A lane’s prototype forwards a read’s Range when it asks one byte range, with its If-Range, and passes on the prototype’s answer, so a video on its route seeks as the prototype serves it. A page it adds the comment layer’s script to is not the prototype’s bytes, so it is answered whole whatever range is asked.

The registry and routes are each session's own, published in its service state; the onboarding file and the providers belong to the box.

Readers never write into the service state; a reader keeps its own records in its own state.

Providers

Providers are the box's: an optional capability is on while providers/<name>.toml in the default session's service state is valid, and off otherwise, silently. Every session's service reads them there, so a provider plugs in once per box; a service named by --state-dir reads its own providers/. A provider writes its file atomically and deletes it to unplug. The server reads the file at each use, so plugging needs no restart.

Steady service

What the service holds in memory has a fixed bound that does not grow with its uptime, its requests, the pages ever opened, or the size of its stores: every value it keeps is bounded in count or bytes, and nothing is kept for a request or a page after its answer.

With no page open and no hand-off waiting, the service's only work is noticing a new hand-off, at a cost that does not grow with review history; it reads no spec, folds no spool, and asks Jev nothing until a page or a read asks.

The service closes a connection that carries no request for a short while, so its open connections follow the pages open now, never the pages ever opened.

The status route, /api/status, answers at once and reads no store: rss_bytes, the service's resident memory; uptime_seconds, whole seconds since the service started; connections, its open connections, the one asking included; and jev, with waiting and running, its Jev asks in the ask queue, and, while the provider refuses Jev's key, paused_until and status, the pause's end and the provider's status. A reader such as a box watchdog reads it instead of a process tool, and sees memory growth as rss_bytes over uptime_seconds. Like every route, it has no login and shows nothing the URL does not already reach.

Stores

Every file or folder Spec Chat writes on the box, each with one lifetime and the writer that ends it. A Log is appended to, or rewritten only by its one writer, and is never deleted automatically; it ends with what holds it or by its owner's hand. A Cache may be deleted any time, and its own writer rebuilds what it needs on its next run. No store keeps a copy of a fact another store owns. A path no row names is no store of Spec Chat: provider files are the box owner's configuration, and the lock beside the registry holds nothing. What the installer adds, its skill links, the page runtime and style it copies into a spec folder, and the box user service unit, is its install, recorded in the onboarding file and removed by its --undo; a file Spec Chat writes into a target repository, such as a replaced page runtime, is that repository's, in Git; a lock or temporary file a command removes when it ends holds nothing.

Proof

Seam: review-host register and the review server's provider read; the box user service at its service manager.

First failing test: a live service's registry.toml gains [process] url equal to the printed URL.

First failing session test: register with a named session key in its environment writes its row to that session's service state, and the default session's registry is unchanged.

Steady-service seam: the review server's status route, sampled while pages poll and close and Jev reads run; the idle criterion at the server's spec, spool, and Jev record reads.

First failing steady test: the status route reports rss_bytes, connections, and jev waiting and running.

Ranges seam: the review server’s answers to Range requests for a round’s video, a video under a row’s root, and a video on a lane’s prototype route, over fixture worktrees and a fixture prototype. First failing ranges test: a Range read of a video through a lane’s prototype answers 206 with the prototype’s Content-Range.
