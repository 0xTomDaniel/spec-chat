Box review service and providers

docs / specs / review-service.spec.html

Spec Chat works completely alone. A box has one review service per Herdr session, and every lane of a session joins its session's service; a box without Herdr is its one default session. Each service owns its bind, port, and URL. Anything else plugs in only through Spec Chat's state: each service publishes facts in its own state for readers, and every service reads the box's optional providers from one place. Spec Chat names no reader and no provider product; why the session scopes the service is in the ADR.

User stories

As a human reviewer, every lane of one Herdr session hands me a link on that session's one review service, so a page I can open once I can open for every lane of the session.

As an operator running several Herdr sessions on one box, each session's lanes register, get woken, and are torn down on that session's own review service, so no session sees, wakes, or removes another's specs, and a box with one session works as it always has.

As a Spec Chat user with nothing else installed, review works end to end: private by default, public when I say so once, and no capability I lack shows an error.

As a human reviewer on a Spec Chat page that a host serves at another address, in a frame with no origin, I review as on the page served directly: I see its threads, comment, hand off, and move to other specs and the review index, all in the host's frame; served directly, the page works unchanged.

As a box operator, the review service's log keeps everything the running service wrote, whatever starts it and whatever later start fails, so I can find why something went wrong.

As another tool, I find the review service and plug an optional capability into it through its state alone, with no launch flag, environment variable, path, or port set by hand, and Spec Chat never learns my name.

As a box operator, the review service holds steady memory and CPU however long it runs and however many specs, pages, and Jev reads it serves, and one route tells me so, so no watchdog has to restart it and drop open pages and wakes.

As a box operator, every store Spec Chat writes on the box says whether it is safe to delete and which writer ends it, so nothing piles up and no fact is kept twice.

Modular boundaries

The review service owns its bind, port, proof host, public base address, unit, and URL, recorded in its own state; the HTTPS front that proxies to it is the box's, not Spec Chat's. Caller-facing seam: review-host register, which returns the URL. Dependency direction: external-provider for its session alone, read from the session key Herdr exports, never from another tool's code; otherwise self-contained, and no lane, skill, or brief picks a port. Observable scope: the printed URL, [process], the status route, and the stores it writes.

Readers own nothing in the service state; they read what the service publishes. Caller-facing seam: the published files and routes. Dependency direction: external-provider; readers depend on Spec Chat, never the reverse, find a session's service state from the same session key, and never write into its state. Observable scope: the published fields.

Each provider owns exactly its own file under the box's providers/; Spec Chat owns each file's format and reads it. Caller-facing seam: the provider files. Dependency direction: external-provider; providers depend on Spec Chat's format, Spec Chat names no provider product. Observable scope: a capability on while its file is valid, off otherwise.

Each page the service serves takes everything it addresses from its own address, and the service answers a page of another origin or none; a host owns fetching the page, its base address, its frame, and its link handling. Caller-facing seam: the served page's base address, links the page follows, and the service's routes. Dependency direction: external-provider; a host depends on these rules, and Spec Chat names no host. Observable scope: spec pages and the review index served at another address, and the service's answers to a page of another origin or none.

One service per session

The Herdr session is the isolation unit: each session has its own review service, with its own registry, server, port, log, review index, and box setup, and a lane joins only its own session's service. The session key is the Herdr session name, read from Herdr alone as ${HERDR_SESSION:-default}: Herdr exports HERDR_SESSION to every pane of a named session, a pane of the default session has none, and a process outside any pane is in the session its environment names, the default session when it names none. A box without Herdr is its default session.

A session's review service lives at its service state, $XDG_STATE_HOME/spec-chat/hosting/<key> (~/.local/state when XDG_STATE_HOME is unset), so the default session's is hosting/default. Every review-host command without --state-dir acts on its caller's session's service; register joins it, and if it is live, the rows are added and its URL is returned unchanged.

Herdr pane ids are unique only within a session, so a row's owner and checker are pane ids of its service's session, and rows name no session. A service runs in its session: register starts it from its caller's session, and the box user service runs outside any pane, in the default session. Its wake checks and sends run in that same session, so a wake reaches only a pane of the service's session.

A new service is private on loopback. --public <host> makes it public; --private returns it to loopback. --public-base <address> gives it a public base address, such as an HTTPS front's https://spec.<a-b-c-d>.sslip.io: its published url and every review link it reports start with that address, while its box-side proof checks the service's own listener; an empty address clears it. The choices, and the proof host used for a wildcard bind, are recorded, so every later register and restart keeps them. Choosing them is the box owner's act, not each lane's.

An HTTPS public base address (one starting https://) means the box serves the page through its HTTPS front, which proxies to the loopback listener in [process]. While one is recorded, the service listens on loopback only, whatever visibility is recorded, so the front is the only way in from outside the box; the recorded visibility and proof host are kept, and clearing the address, or replacing it with one that is not HTTPS, returns the service to them. Giving or clearing an HTTPS address moves a live service at once, keeping its port while free, through its unit when one is recorded; any other change to the address needs no restart. Every start takes the listener from the recorded setup, so a box that already records an HTTPS address moves to loopback at its next start after an update. A loopback listener is private, so the port rules for a private service apply. The box owner sets the front to proxy to the loopback listener before the service moves; a wildcard listener already answers on loopback, so the front reaches the service before, during, and after the move.

A dead service restarts on its recorded bind, public base address, and recorded port while that port is free; otherwise it takes another free port by its own rule (an approved ingress port when public). With a recorded unit, the restart goes through the unit's service manager.

Box setup's --service runs the service as a box user service: spec-chat-review.service under ~/.config/systemd/user, enabled, with lingering on. It starts at boot without a login, starts again after the process dies, and stays stopped after a clean stop, which is never a failure. The unit runs review-host serve from the clone that installed it, so after a pull it runs that clone's code from its next start. serve starts the server in the foreground on the recorded setup and records itself in [process], including unit. While a unit is recorded, register starts, restarts, or moves the service only through that unit, a live service started otherwise is handed to it, and stop is the unit's clean stop. A recorded unit that no longer exists is dropped, and the service starts as before.

A service's log is server.log in its service state, and it holds everything the service prints, the wake lines included. Every start appends to it, a start through the unit included, and nothing empties it, so a start that fails, such as one whose port is taken, leaves every line the running service wrote.

A row whose worktree, collection, or spec file cannot be reached is stale. A stale row affects only itself: every start, restart, and registration of the service goes on, serves every other row, and reports each stale row by its id and reason, and the row stays registered untouched until its owner removes it. The service serves no page for it and the review index marks it stale. A registry that is unreadable or structurally invalid, such as a duplicate id, two rows at one path, a reserved slug, or a missing field, still stops the service, since no row can be trusted.

A lane runs only review-host register --slug <lane-key> --owner <pane> <spec path>, repeating the spec path for more specs. It names no exposure: the service already owns it, so a lane command never reads as opening ingress. register rejects a row without an owner, so every hosted spec has one. With no spec path it registers a scope row.

A plain spec path infers the rest from Git: root is the worktree top; project is the last path part of origin without .git, or the top directory's name without an origin; base is the merge base of HEAD with the default branch (origin/HEAD, else main), or --base <ref>. The PROJECT_ID=ROOT:SPEC_PATH@BASE form is also accepted.

Spec Chat has one install and onboarding entry point, scripts/install-spec-chat: it links its skills into the target repo's .agents/skills and links each from .claude/skills and .codex/skills relatively (with --agents-only, only .agents/skills), never under the home directory, installs the page runtime and style into a named spec folder, sets up the default session's review service, whatever session it runs in, since the box user service it installs runs in the default session, and writes its one onboarding file, onboarding.toml, which also records what it added; a rerun changes nothing. When a target path is already occupied, the installer classifies it: a symlink resolving into a different clone of this repository (matched by git remote get-url origin) is adopted and reported; any other existing file or symlink is skipped and reported; the installer never overwrites, never fails on an occupied path, and continues with the remaining items. --undo removes only what that file records it added, then the file: it stops any review server process it started, disables and removes the box user service unit it installed (lingering, shared with other user services, stays on), removes its skill links and registered review resources, and deletes the runtime assets (.viz, .style) only when they are unmodified and not tracked by git. Any other tool reaches Spec Chat's install only through it.

Box setup, by the box owner and outside any lane: --public <host>, --private, --proof-host, --public-base <address>, and the installer's --service (review-host register --unit <name>), each once. Each flag sets up its caller's session's service, so a named session's service, private on loopback until then, is set up from that session. Without --proof-host, the proof host is SPEC_CHAT_PROOF_HOST (or the older REVIEW_PROOF_HOST) when set, else the public bind address, else the address the box routes outward from.

--state-dir names a separate, isolated service for tests or deliberate isolation; lanes do not pass it.

What the service publishes

ReadHolds
registry.toml [process]pid, bind, port, host (proof host), url, the public base address when one is recorded, else the URL the service printed, and, when set, public_base and unit. While an HTTPS public base address holds the service on loopback, bind and host name the loopback listener, and public_bind and public_host keep the recorded public bind and proof host.
registry.toml [[resource]]One row per registered spec: id, slug, project, path, spec, root, narrow_root, base, owner, checker, cursor_name, test, registered_at, and updated_at (lane hosting); a scope row names no spec, so it holds no project, path, spec, root, narrow_root, or base.
$XDG_STATE_HOME/spec-chat/onboarding.tomlstatus, pending or done, and doc, a link to Spec Chat's own install and first-run steps, which Spec Chat alone owns. Its [installed] section is the installer's own record of what it added (links, copies, resources, units); readers ignore it. Spec Chat keeps no other onboarding or install file.
Routes under urlSpec pages, the review index, /api/jev/board, the status route, /api/status, and the comment layer, /static/comment-layer.js.

A spec page is served as its file with any missing description, og:type, og:title, and og:description meta added at the end of its head: og:type is article, the others the page title. Some reviewers' browsers read them as the page loads and fail without them, so a spec from any repository opens on every client with no edit to its file. The page's ETag and stored version name that served page.

The registry and routes are each session's own, published in its service state; the onboarding file and the providers belong to the box.

Readers never write into the service state; a reader keeps its own records in its own state.

Providers

Providers are the box's: an optional capability is on while providers/<name>.toml in the default session's service state is valid, and off otherwise, silently. Every session's service reads them there, so a provider plugs in once per box; a service named by --state-dir reads its own providers/. A provider writes its file atomically and deletes it to unplug. The server reads the file at each use, so plugging needs no restart.

Steady service

What the service holds in memory has a fixed bound that does not grow with its uptime, its requests, the pages ever opened, or the size of its stores: every value it keeps is bounded in count or bytes, and nothing is kept for a request or a page after its answer.

With no page open and no hand-off waiting, the service's only work is noticing a new hand-off, at a cost that does not grow with review history; it reads no spec, folds no spool, and asks Jev nothing until a page or a read asks.

The service closes a connection that carries no request for a short while, so its open connections follow the pages open now, never the pages ever opened.

The status route, /api/status, answers at once and reads no store: rss_bytes, the service's resident memory; connections, its open connections, the one asking included; and jev, with waiting and running, its Jev asks in the ask queue. A reader such as a box watchdog reads it instead of a process tool. Like every route, it has no login and shows nothing the URL does not already reach.

Stores

Every file or folder Spec Chat writes on the box, each with one lifetime and the writer that ends it. A Log is appended to, or rewritten only by its one writer, and is never deleted automatically; it ends with what holds it or by its owner's hand. A Cache may be deleted any time, and its own writer rebuilds what it needs on its next run. No store keeps a copy of a fact another store owns. A path no row names is no store of Spec Chat: provider files are the box owner's configuration, and the lock beside the registry holds nothing. What the installer adds, its skill links, the page runtime and style it copies into a spec folder, and the box user service unit, is its install, recorded in the onboarding file and removed by its --undo; a file Spec Chat writes into a target repository, such as a replaced page runtime, is that repository's, in Git; a lock or temporary file a command removes when it ends holds nothing.

Pages served at another address

A host may serve any page of the review service, a spec page or the review index, at another address: it fetches the page from the service and returns it with a base address naming the address it fetched, often into a frame sandboxed without same-origin access, so the page runs with no origin. A host may also load the comment layer into a page of its own, which then sends the layer's requests from that page's origin, another site's or none. Spec Chat names no host: every rule here holds for any host that does this, and a page served directly is the case where its base address is its location.

A page's own address is its document's base address, fragment aside; served directly, that is its location. Everything the page addresses comes from its own address, never from its location. Wherever a Spec Chat rule names a page's own address or origin, such as the new-tab click, it means this own address.

The anchor a page opens at and moves to is its location's fragment, so moves within the page stay in place wherever it is served.

A page rewrites its address, as when focus on changes or its baseline changes, only while its own address is its location, fragment aside. Served at another address, it leaves its location unchanged and changes only what it shows, so a reload opens the address the host served.

A page moves to another of the service's pages, as when a Jev mark's target is in another spec, by following a link to that page's address, never by setting its location, so a host's link handling applies to every move, as it does to the reviewer's own taps.

A page with no origin has no browser storage, so its fruit name, outbox, and kept place last only until the page reloads, and so do its drafts: after a reload, its hand-off (review-state) lists none saved before it.

A public service answers requests from any other origin, a page with no origin's Origin of null included, and their preflight, on every route a page or the comment layer requests, so such a page reads every answer it reads when served directly, its version tag included. An answer to a request with no Origin, or the service's own, carries no cross-origin permission.

Answering a page with no origin is safe because the service guards nothing by origin: it has no login, sets and reads no cookie, and its URL is not an authentication boundary (trust), as the review server's startup notice says. Whatever a page with no origin can send or read, anyone holding the URL can already send or read directly, and the browser sends such a page's requests with no credential. Agent events stay refused over HTTP whatever the origin (trust). Every origin is answered, since a host page of any site loads the comment layer, and Spec Chat names no host to list; it stays safe only by the no login, no cookie rule.

Only a public service, or one with a public base address, answers another origin; a private service answers every other origin, no origin included, with no cross-origin read. A private service is reached only through the reviewer's tunnel, yet any site the reviewer has open can send it requests, so answering them would let that site read the private service's review state. A page served at another address sends its requests from the reviewer's browser straight to its own address's origin, so it never reaches a private service anyway.

Served-address seam: the runtime's own address, given a document whose base address differs from its location and one with none, and the review server's answers to requests with and without an Origin of null; the screen criteria through a test host that serves a spec with a base address into a frame sandboxed without same-origin access.

First failing served-address test: a page whose base address names a spec other than its location's reads that spec's spool.
