Pages a shell holds

docs / specs / shell.spec.html

A shell, such as a workbench framing many pages, holds Spec Chat’s pages and places one comment UI page beside them; held pages publish and pick, the comment UI page holds every thread. Extends Comment layer: a held host page is one the layer loads on.

User stories

As a human in a shell that frames many pages, I comment on any of them through the one comment UI the shell places beside them, read each page's conversation there, and hand off or accept a spec from it, while each page draws its own pins, on a desktop or a phone.

As a shell author, I frame Spec Chat's comment UI page once per window, say hello to each page I frame, and relay the shell messages between them; I write no comment code and keep no thread.

As a box owner, I name the origins that may act as a shell, so no other site can hide a page's comment UI or receive the picks made on it.

Acceptance criteria

Given a human on a desktop in a shell at an origin the box names, framing a lane's spec page that holds a thread, When the human opens that spec page in the shell, Then the spec page shows the thread's pin and no review panel, Comment, or Hand off of its own, and the shell's comment UI shows the spec's conversation with Hand off.

Given a human on a desktop with a lane's spec page that holds a thread, When the human opens that spec page in a plain browser tab, then opens its review panel, Then the page shows its own review panel with Hand off, its own Comment, and the thread's pin.

Given a human on a desktop with a host at an origin the box does not name as a shell, framing a lane's spec page and saying hello with comments, When the human opens that host page, then opens the framed spec page's review panel, Then the framed spec page shows its own review panel, Comment, and Hand off.

Given a human on a desktop in a shell framing a held spec page with no thread, When the human presses Comment in the shell's comment UI, then clicks a block in the spec page, then types a comment in the comment UI and saves it, Then the comment's bubble shows as the comment UI conversation's newest thread, its receipt reading Draft and its chip naming that block, and the block in the spec page shows a pin.

Given a shell author's shell at an origin the box names, framing a spec page that holds one open TBD question, When the shell author opens that spec page in the shell, Then the shell receives the page's publish naming its address, the version it shows, and that question with its answers.

Given a human on a desktop in a shell framing a held spec page with no thread, When the human clicks in the spec page, then presses C, then clicks a block in the spec page, Then the shell's comment UI shows its composer on that block.

Given a human on a desktop in a shell framing a held spec page holding a thread on a block far below the top of the page, When the human presses that thread's chip in the shell's comment UI, Then the spec page shows that block in view and ringed.

Given a human on a desktop in a shell framing a held spec page holding a thread on a block, When the human presses that block's pin in the spec page, Then the shell's comment UI shows that thread focused.

Given a human in a shell framing a held spec page with one draft comment, When the human presses Hand off in the shell's comment UI, Then the comment UI shows the notice Handed off 1 comment, agent notified, and the receipt under the comment's bubble reads Sent.

Given a human in a shell framing a held spec page whose lane owner's pane the wake provider finds, When the human presses Comment in the shell's comment UI, then clicks a block in the spec page, then types a comment and saves it, then presses Hand off there, Then the owner's pane receives a wake prompt for that hand-off naming the spec.

Given a human in a shell framing a held spec page whose threads are all resolved, with no open TBD, When the human opens the shell's comment UI, Then the comment UI offers Accept spec, and the spec page shows no Accept spec of its own.

Given a human in a shell framing a held spec page whose threads are all resolved and which holds one open TBD question, When the human opens the shell's comment UI, Then the comment UI offers no Accept spec, and its conversation ends with that question as the agent's bubble with its answer buttons.

Given a human in a shell framing a held spec page holding an open TBD question offering two answers, When the human presses one answer button in the question's block in the spec page, Then the shell's comment UI shows the human's answer under the question as a draft, and the button in the spec page shows as chosen.

Given a human on a desktop in a shell framing a held spec page with Jev marks, When the human opens that spec page in the shell, Then the spec page shows its Jev marks and its compared range in its own top line.

Given a human on a desktop in a shell framing a held mockup page holding a thread on a card at its walkthrough's second step, When the human opens the mockup page at its first step, then presses that thread's chip in the shell's comment UI, Then the mockup page shows both frames at the second step with the card ringed.

Given a human on a desktop in a shell framing a page that speaks the shell messages without Spec Chat's script and publishes a thing with no page element holding one thread, When the human presses that thing's comment control in the page, Then the shell's comment UI shows that thing's conversation with the thread's first message, and the page shows the thread's pin on the thing.

Given a human on a desktop in a shell framing a held host page with an anchored item holding two threads, When the human presses that item's comment control in the host page, Then the shell's comment UI shows the item's conversation with both threads' first messages, and the host page shows no comment box of its own.

Given a human on a desktop in a shell framing a held spec page with the shell's comment UI open, When the human presses the comment UI's close control, Then the shell shows the spec page with its pins and no comment UI.

Given a human on a phone in a shell framing a held spec page, When the human taps Comment in the shell's comment UI, then taps a block in the spec page, then types a comment and saves it, Then the comment UI shows within the screen's width as a sheet over the lower part of the screen, the comment's bubble as a draft in it, and the one Hand off under it.

Given a human on a phone in a shell whose frames have no origin, framing a held spec page, When the human taps Comment in the shell's comment UI, then taps a block in the spec page, then types a comment and saves it, then reloads the shell, then taps the comment's bubble, then types a reply and saves it, Then the focused thread shows the comment and the reply under the same fruit name as their author.

One hand-off control for desktop and phone: kept, in a shell, a held page shows none and the comment UI page shows the one (held, phone) (phone rule, desktop rule). Any origin only without login or cookie: kept, the comment UI page adds no login and no cookie (rule). Never strip proof clauses or rewrite unedited criteria: not affected, no criterion here carries a proof clause (shaping rule, repair rule). Every mockup at production fidelity: kept, the comment UI’s mockup is drawn from the runtime’s chrome and design set tokens: its screen is review chrome a mockup page shows, and the page that frames a prototype cannot frame itself (drawn mockup, rule). Threads read as one conversation: kept, the comment UI page draws the conversation (rule).

Modular boundaries

A shell, such as a workbench framing many pages, owns framing pages and the comment UI page, saying hello, relaying the shell messages by source window, and placing the comment UI page. Caller-facing seam: the shell messages on the existing bridge, the comment UI page's address, and the box's shell setting. Dependency direction: external-provider; a shell depends on Spec Chat's messages and page, and Spec Chat names no shell. Observable scope: none in Spec Chat beyond the messages a page and the comment UI page send and take.

The review service owns the comment UI page at /comments: the conversation, composer, and one hand-off control for held pages. Caller-facing seam: its address and the shell messages. Dependency direction: self-contained within Spec Chat; it reads and writes threads only by review state’s events. Observable scope: what the comment UI page shows and writes.

Pages a shell holds

A shell is a host that frames several pages in one window, such as a workbench, and draws one comment UI for all of them: Spec Chat's comment UI page, framed once per window.

One script, two roles

A page that runs Spec Chat's script, a spec page, a mockup page, or a host page loading the layer, is alone until a shell holds it: alone, it draws its own comment UI, exactly as a page outside any shell does.

A page is held once its parent says hello with comments among the hello's opens (bridge hello), from an origin the box names as a shell (shell setting), by the existing sender check. Held, it draws no comment UI, no review panel, toolbar Comment, composer, thread, or hand-off control; it publishes what it shows, draws its own pins, waiting dots, question marks, and quote marks in its own content, so they move with it, and runs pointing for the shell. On a held host page, each item keeps its comment control and pins in their corner row (placement), and pressing either sends a pick.

A hello that reaches a page after it drew its own comment UI saves any text typed in its composer as a draft, then removes its comment UI and becomes held; its saved drafts stay drafts, read by the comment UI page.

A held spec page keeps what reads the spec rather than talks about it: its top line with its compared range and Change base, Jev marks, evidence notes, and focus on changes; a held mockup page keeps its step bar and Before and After.

A receiver ignores a field it does not know, and an absent field means none, so a page and a shell of different versions still speak.

The shell relays a page's publish and pick to the comment UI page naming the frame they came from in frame, a string the shell picks for each frame it holds, and the comment UI page's point, show, and marks to the frame their frame names, the comment UI page echoing it; the comment UI page's conversation is the context of the page whose publish the shell relayed last (context).

Keys and clicks in a frame stay the page's: it runs pointing itself, and its own C starts it, as the toolbar's Comment does alone.

Every message is plain data: none carries markup to draw or an address the receiver loads; a from address shows only as a link the human may follow.

A mockup page holds the prototype frames it shows, each at the lane's prototype origin, as a shell holds a page, by these messages sent straight to each frame and never relayed. Its hello also carries frame, the viewport that frame shows, and regions, each {anchor, select} as the mockup file lists them (prototype file), and three messages more pass between them. The hello also carries id, a string the page picks for each frame it holds, which the route sends back as id in every message it sends the page; the page takes a message from the lane's prototype origin as from the frame its id names, since a message the route sends as its document leaves, such as a press whose link loads the next step's page, can reach the page with no source window. Size, spec-chat-size, from the route on hello and whenever its content's height changes, carries past, the CSS pixels its content runs past its viewport, and the page sizes the frame from it. Act, spec-chat-act, from the page, carries actions, the step actions to do in order, each {press} or {type, text} with its selector, and next, the actions that reach the next step; the route does each action after the motion before it ends, then answers spec-chat-acted with done, the number it did (steps). Pressed, spec-chat-pressed, from the route on a reviewer's press or typing with pointing off, carries reached: true when that did the next step's actions, so the page moves the step bar to it, and false otherwise.

Any page may speak the page side of these messages natively, without Spec Chat's script, such as a page that draws on a canvas: its publish names things with no page element by the same fields, subject, scope, kind, label, from, and starters, its picks name them, and it draws its own marks from marks; the comment UI page treats its messages as any held page's.

A page that says nothing after hello runs no Spec Chat script; what a shell does for it is the shell's.

The comment UI page

The review service serves the comment UI page at /comments on its own address: the conversation (threads), its focused threads, the composer, and the one hand-off control, for whatever a shell relays to it.

It alone reads and writes the threads, hand-offs, and Accept spec of the pages a shell holds, through the review service, by review state's events (review state); a held page reads and writes no thread. It reads a held page's text, for the names its chips and questions show, at that page's address on its own review service, as it reads the page's threads there; it loads no address a message names outside its own service (plain data).

A shell frames it once per window, at the review service's own address, and places it beside a page, under another pane, or as a sheet on a phone; placing it never reloads it, so its drafts, outbox, and fruit name last as long as the window.

It takes shell messages only from its parent window at an origin the box names as a shell, and shows nothing until it has one.

Review actions when held

For a held spec page, Hand off and Accept spec sit in the comment UI page under its conversation: Accept spec is offered there by the same rule as on the spec page, from the open TBDs the page publishes and the threads of the spec and its mockups (acceptance covers the set), and writes the same hand-off.

Next TBD there sends show for the next open question, which a held spec page brings into view and a held mockup page shows at its step.

A spec page alone keeps all of them on itself.

Who may be a shell

The box names the origins that may act as a shell, by box setup's --shell <origin>, recorded with its other choices (box setup); the review service tells every page it serves and the comment layer those origins.

A page and the comment UI page obey only their parent, and only at a named origin; under any other parent, a page stays alone with its own comment UI, so no other site can hide it or receive the picks made on it.

The review service's own origin is a shell for the prototype routes it serves at each lane's prototype origin, under their mockup pages (prototype route).

With no origin named, no page other than a prototype route under its mockup page is ever held.

A phone shell's frames

A shell whose frames have no origin, so no storage, may pass the comment UI page a browser id in its address fragment, as #browser=<id>, the id up to 64 letters, digits, hyphens, and underscores; with no storage, the page takes that id as its browser, and the fruit name that browser's earlier events carry, so the name lasts across reloads (review state). Without one, its name and drafts last until reload, as on a phone spec page in such a frame.

Proof

Proof: the held role and the comment UI page through a fixture shell framing a spec page, a mockup page, a host page, and the comment UI page, at a named origin and at another, on a desktop and a phone.
