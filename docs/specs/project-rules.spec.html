Project-wide rules at shaping

docs / specs / project-rules.spec.html

Source issues: ANN-272.

Status: shaping; direction agreed with the human in ANN-272 (2026-09-26).

Some acceptance criteria apply to every feature, such as every change to what a user sees or does adds its onboarding section. They live in one spec that shaping never reads, so they get missed. This spec lets Jev find them and check a spec under shaping against them. Extends Jev review suggestions: its seam, records, cache, markers, popovers, and note buttons apply unchanged, and marks are one-word notes as its one-word questions and unsure note style define (ANN-258, in review).

User stories

As a spec author, I write a rule that applies to every feature once, in plain words, in its home spec, and Spec Chat treats it as project-wide with nothing else to maintain.

As a spec author, a criterion whose scope is too vague to tell shows as unsure on its home spec, so I sharpen its wording.

As a reviewer of a spec under shaping, a project-wide rule the spec triggers but does not cover shows one compact mark linking the rule, which I resolve by adding a criterion or by a thread saying why it does not apply.

As the shaping agent, I read every Jev check on my spec as JSON without a browser, and resolve what I can before the human sees the review link.

Acceptance criteria

When one served spec has a criterion that applies to every feature and another that applies only to its own feature, Jev treats only the first as a project-wide rule, and no tag, list, side file, or Spec Chat state names it.

When a rule's criterion is reworded to apply to one feature, or deleted, on the next load no spec shows a mark for it.

When a criterion's text is unchanged across heads, lanes, and specs that read it, its scope question is asked once and its record reused.

When Jev is below threshold on whether a criterion applies to every feature, that criterion on its home spec shows the unsure note rule? with the sentence Jev is unsure whether this applies to every feature, and no other spec shows a mark for it.

When a spec under shaping adds a change to what a user sees and has no onboarding criterion, while onboarding.spec.html holds the onboarding rule, its Acceptance criteria heading shows one marker whose popover lists onboarding? linking that rule, with Ask to cover.

When the spec then adds a criterion that covers the rule, or a thread linking the rule is resolved, the onboarding? note is gone on the next load; a spec that does not trigger the rule never shows it.

When the reviewer clicks Ask to cover, the comment composer opens at the Acceptance criteria heading with the draft Cover <link to rule> with a criterion, or say why it does not apply., and nothing is written until the reviewer sends.

When the shaping agent reads its spec's Jev checks from the box, one command prints the same items the page gets as JSON: conflicts, coverage gaps, unsure notes, and rule misses, each with its anchor and link, or off.

When the shaping skill registers a spec for review, it reads the Jev checks, resolves each it can per the reconcile rule, commits, and only then hands the review link to the human.

Modular boundaries

The review server's Jev seam owns the scope and rule-check questions, their records, and the cache. Caller-facing seam: the existing GET /api/jev response, gaining items of kind scope and rule. Dependency direction: external-provider; calls Jev and reads the served specs as the draft checks do; nothing calls back. Observable scope: the JSON response and records.

The browser runtime owns the rule? and <word>? notes and the Ask to cover button. Caller-facing seam: the rendered page; writes only through the existing comment composer. Dependency direction: self-contained; consumes the seam route. Observable scope: what the reviewer sees.

The shaping skill owns reading and resolving the checks before handing off the link. Caller-facing seam: one read command over the running review server. Dependency direction: self-contained; the skill calls the server, and the server never calls the skill. Observable scope: commits and threads before the review link is sent.

A spec without data-acceptance-criterion clauses holds no rules.

Muted notes and hover sentences follow the unsure note style; a missed note uses the same one-word form.

The word is the home spec's file name without .spec.html, e.g. onboarding?; fixed, never generated.

Rule notes list after coverage in the popover order, one per rule, and the marker stays neutral.

A resolved thread on the spec whose messages link the rule's anchor clears its note; an open one does not.

Agent read

The read returns the /api/jev response for the spec and base the review link serves, from the running server, so the agent and the page see one answer from one cache.

The shaping skill step runs after review-host register and before the link is sent: read, resolve per the reconcile rule in shape-spec, commit, read again, then send the link with what is left.

With Jev off, the read says off and the skill sends the link at once.

Proof

First failing test: with a fake provider answering every feature for one criterion of spec A and missed for spec B, /api/jev for B returns one rule item targeting A's criterion.

Evidence: seam and runtime tests behind fakes, one live run per new question set, and a QA bundle on a real spec with a real project-wide rule.

Non-goals

Tags, rule lists, side files, or Spec Chat state holding project knowledge; rules from outside the served specs; generated mark text; checking a spec that is not under shaping.
