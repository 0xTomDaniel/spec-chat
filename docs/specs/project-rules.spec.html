Some acceptance criteria apply to every feature, such as every change to what a user sees or does adds its onboarding section. They live in one spec that shaping never reads, so they get missed. This spec lets Jev find them and check a spec under shaping against them. Extends Jev review suggestions: its seam, records, cache, markers, popovers, and note buttons apply unchanged, and marks are one-word notes as its one-word questions and unsure note style define (ANN-258, in review).

User stories

As a spec author, I write a rule that applies to every feature once, in plain words, in its home spec, and Spec Chat treats it as project-wide with nothing else to maintain or remember.

As a reviewer of a spec under shaping, a project-wide rule the spec triggers but does not cover shows one compact mark linking the rule, and it clears once the spec either covers the rule or says in one line why it does not apply.

As the shaping agent, I read every Jev check on my spec as JSON without a browser, resolve what I can, and hand off the review link naming the rules checked.

As a reviewer on a project new to Spec Chat, I am offered once to reconcile the existing specs that miss project rules.

Acceptance criteria

When one served spec has a criterion that applies to every feature and another that applies only to its own feature, only the first is a project-wide rule, and no tag, list, side file, or Spec Chat state names it.

When a rule's criterion is reworded to apply to one feature, or deleted, on the next load no spec shows a mark for it.

When a criterion's text is unchanged across heads, lanes, and specs that read it, and when the records are deleted, its scope is asked once and reused, and after deletion the same rules are rebuilt from the specs alone.

When Jev is below threshold on a criterion's scope, or on whether a spec misses a rule, the same question goes once to the general LLM, its answer decides and is recorded and reused, and the page shows only a clear missed note or nothing, never an unsure rule or scope mark.

When a spec under shaping adds a change to what a user sees and has no onboarding criterion, while onboarding.spec.html holds the onboarding rule, its Acceptance criteria heading shows one marker whose popover lists onboarding? linking that rule, with Ask to cover.

When a rule check, its LLM fallback, or a scope answer it depends on is still running, or the warm-up has not finished, the spot where the mark would appear shows a small rotating wheel with checking onboarding… on hover, or checking project rules… while rules are not yet known; it becomes the onboarding? note or nothing without a reload, and with reduced motion the wheel does not rotate.

When the spec then adds a criterion that covers the rule, or one plain line such as Onboarding: not needed, this changes no screen, the onboarding? note is gone on the next load; a thread alone never clears it, and a spec that does not trigger the rule never shows it.

When the reviewer clicks Ask to cover, the comment composer opens at the Acceptance criteria heading with the draft Cover <link to rule> with a criterion, or add one line saying why it does not apply., and nothing is written until the reviewer sends.

When the shaping agent reads its spec's Jev checks from the box, one command prints the same items the page gets as JSON, conflicts, coverage gaps, unsure notes, rule misses, and pending checks, each with its anchor and link, plus the list of rules checked, or off.

When the shaping skill registers a spec for review, it reads the Jev checks, resolves each it can per the reconcile rule, commits, and only then hands off the review link, with one line naming the rules checked.

When a project is registered with the review service for the first time, with no other tool installed, register returns without waiting, a background warm-up classifies every criterion and checks every spec in parallel, and later pages reuse its records without new calls, and the onboarding status file shows the rules classified and N specs to reconcile.

When the warm-up finds N existing specs that miss a rule, and the reviewer opens a page of that project, the page shows N existing specs miss project rules: reconcile? once; Reconcile opens the composer with one draft listing each spec and its missed rules with links, nothing is written until the reviewer sends, and after it is sent or dismissed it never shows again for that project.

Modular boundaries

The review server's Jev seam owns the scope and rule-check questions, the general LLM fallback, the warm-up, the onboarding status, their records, and the cache. Caller-facing seam: the existing GET /api/jev response, gaining items of kind rule, a pending state, the rules checked, and the one-time offer; the onboarding status file for readers outside Spec Chat. Dependency direction: external-provider; calls Jev and the general LLM through OpenRouter, and reads the served specs as the draft checks do; nothing calls back. Observable scope: the JSON response, records, and status file.

The browser runtime owns the <word>? notes, the pending wheel, the Ask to cover button, and the one-time offer. Caller-facing seam: the rendered page; writes only through the existing comment composer. Dependency direction: self-contained; consumes the seam route. Observable scope: what the reviewer sees.

The shaping skill owns reading and resolving the checks before handing off the link. Caller-facing seam: one read command over the running review server. Dependency direction: self-contained; the skill calls the server, and the server never calls the skill. Observable scope: commits and the hand-off message.

Two questions

Both are Jev questions under the Every suggestion rules: one question set each, one record per call, records as cache.
QuestionAsked forSeesLabelsCache key

Rule check: does this spec trigger the rule and not cover it?Each project-wide rule from another spec, on a spec that differs from its compared base, and on every spec at warm-upThe rule text and the spec's textmissed, covered, not triggeredRule text, spec text, and set version

An answer below threshold, to either question, sends the same question once to a general LLM through OpenRouter, the model named in that question set; its answer decides and is recorded with the same key. If that call fails, the item shows Jev unavailable as every suggestion defines, and is asked again on the next load.

A project-wide rule is a criterion whose decided scope is every feature. A spec is never checked against its own criteria.

A spec without data-acceptance-criterion clauses holds no rules.

The records are derived and disposable: they hold no project knowledge, and deleting them costs only recomputation from the specs.

A missed note is one word with its sentence on hover as its accessible name, as the one-word note style defines, but not muted; it is a clear miss.

Pending

Pending never looks like no miss: until every rule check for the spec is answered, its spot shows the wheel in the marker's place, the same size and calm neutral color, with no text beside it.

While any item is pending, the page asks /api/jev again and swaps the wheel for the answer in place; the spec text never moves.

With reduced motion, the wheel is a still glyph; the hover sentence is its accessible name.

Every Spec Chat Jev mark whose question escalates to the LLM shows this wheel while pending.

The word is the home spec's file name without .spec.html, e.g. onboarding?; fixed, never generated.

Rule notes list after coverage in the popover order, one per rule, and the marker stays neutral.

A miss is answered in the spec: a criterion that covers the rule, or one plain line saying why it does not apply. The next rule check reads it and the note clears; threads play no part.

Agent read

The read returns the /api/jev response for the spec and base the review link serves, from the running server, so the agent and the page see one answer from one cache.

The shaping skill step runs after review-host register and before the link is sent: read, resolve per the reconcile rule in shape-spec, commit, read again, then send the link with what is left; a read with pending items is repeated until none remain.

The hand-off message names the rules checked, as home spec and anchor, for visibility only; it asks nothing of the human.

With Jev off, the read says off and the skill sends the link at once.

Bootstrap

WhenScope asked forRule check asked forShown
First registration of a project, in the backgroundEvery criterion of main's copy of every spec in its collection, in parallelEvery such specOne offer, once
AfterwardsNew or changed criterion text only, since records answer the restSpecs under review onlyRule notes on those specs

The offer is one page note on that project's next review page after warm-up; Reconcile drafts one comment through the existing reconcile flow, Reconcile each spec with its missed rules: then one line per spec, <spec> <word>? <rule link>; the agent answers it per the reconcile rule.

The bootstrap is part of Spec Chat's onboarding, its own first run: the first review-host register of a project starts it, and Spec Chat alone runs it end to end. No peer's setup starts, waits for, or completes it.

Spec Chat publishes its onboarding status per project as one JSON file in the server's state directory: warm-up state, criteria classified, rules found, N specs to reconcile, and whether the offer was sent or dismissed. Anyone may read it; it names no peer and is derived like the records.

Sending or dismissing the offer is recorded in that file; with N zero, or Jev off, no offer shows.

Proof

First failing test: with a fake provider answering every feature for one criterion of spec A and missed for spec B, /api/jev for B returns one rule item targeting A's criterion.

Evidence: seam and runtime tests behind fakes, one live run per new question set, and a QA bundle on a real spec with a real project-wide rule, including a first registration.

Non-goals

Tags, rule lists, side files, or Spec Chat state holding project knowledge; rules from outside the served specs; generated mark text; a scope mark or an unsure rule mark; clearing a miss by thread; checking specs not under review after bootstrap; any bootstrap step in a peer's setup.
