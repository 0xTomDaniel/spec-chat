Project-wide rules at shaping

docs / specs / project-rules.spec.html

Some acceptance criteria apply to every feature, such as every change to what a user sees or does adds its onboarding section. They live in one spec that shaping never reads, so they get missed. This spec lets Jev find them and check a spec under shaping against them. Extends Jev review suggestions: its seam, records, cache, markers, popovers, and note buttons apply unchanged, and every note about a rule is one readable rule card.

User stories

As a spec author, I write a rule that applies to every feature once, in plain words, in its home spec, and Spec Chat treats it as project-wide with nothing else to maintain or remember.

As a reviewer of a spec under shaping, a project-wide rule the spec triggers but does not cover shows one readable card that names the rule in plain words, quotes it in full, and links its source, so I can judge it at a glance, and it clears once the spec either covers the rule or says in one line why it does not apply.

As a reviewer, every note about a project rule, whether a missed rule, an important mark citing a rule, a candidate rule, or a reconcile row, looks and reads the same, so I learn one card and never decode a cryptic label.

As the shaping agent, I read every Jev check on my spec as compact text without a browser, solve every important mark, and hand off the review link naming the rules checked and listing the warnings I did not act on.

As a reviewer who judges a rule mark wrong, I answer it with one clearly labelled click: Not for this spec when the rule does not apply to this spec, or Not a project rule when the criterion is not a project-wide rule at all, and it stays dismissed on every later load and edit, until the rule itself changes.

As a reviewer, a rule that several specs restate as linked copies shows as one rule, its home, so I judge and dismiss it once.

As a reviewer on a box that serves several projects, a spec is checked only against its own project's rules, so no mark of any kind, rule, contradiction, overstep, overlap, or cross-lane, ever cites another project's spec.

As a reviewer on a project new to Spec Chat, I am offered once to reconcile the existing specs that miss project rules, as a readable list with one line per spec naming the rule it misses.

As a reviewer, a criterion Jev reads as project-wide is only a candidate until I confirm it, so no spec is checked against, or edited to cover, a rule nobody agreed is a rule.

As the operator, every rule confirmation or rejection a human makes becomes a labeled example for Jev's scope question, and a mark an agent merely edited around is never counted as proven right.

As a Spec Chat user without the review service, shaping and the spec page work fully without it: cards, candidates, and the offer exist only where the review service runs Jev.

As a spec author, a criterion counts as a project-wide rule only when its own text says it applies to every feature, so I control which criteria become rules by including or omitting that wording.

Modular boundaries

The review server's Jev seam owns the scope and rule-check questions, the general LLM fallback, the warm-up, the onboarding status, their records, and the cache. Caller-facing seam: the existing GET /api/jev response, gaining items of kind rule and candidate carrying their rule's criterion text, name, and home, a pending state, a level on every mark, the rules checked, and the one-time offer; the existing Jev record route, taking either rule dismissal, a rule confirmation, and both offers; the project's table in onboarding.toml for readers outside Spec Chat. Dependency direction: external-provider; calls Jev through OpenRouter with the Jev provider's key, and the general LLM through the box's Claude CLI with the provider's model, and reads the served specs as the draft checks do; nothing calls back. Observable scope: the JSON response, records, and onboarding.toml.

The browser runtime owns the one rule card and every place it renders, the pending wheel, the card buttons, and the one-time candidate and reconcile offers. Caller-facing seam: the rendered page; writes only through the existing comment composer and the existing Jev record route the offer already uses. Dependency direction: self-contained; consumes the seam route. Observable scope: what the reviewer sees.

The shaping skill owns reading and resolving the checks before handing off the link. Caller-facing seam: one read command over the running review server, printing compact text, with --anchor for one anchor's detail. Dependency direction: self-contained; the skill calls the server, and the server never calls the skill. Observable scope: commits and the hand-off message.

Spec Chat's core, the shaping skill, validator, spec format, and spec page runtime without a review service, owns nothing in this spec. Caller-facing seam: none new; the runtime renders cards only from a /api/jev answer, and the shaping skill's Jev read already says off when there is none. Dependency direction: self-contained; the review service depends on the core, never the reverse, and no core step calls, waits on, or stores rule approval. Observable scope: a spec page and a shaping run with no review service show no rule card, candidate, offer, or error.

Two questions

Both are Jev questions under the Every suggestion rules: one question set each, one record per call, records as cache.
QuestionAsked forSeesLabelsCache key
Scope: does this apply to every feature?Every acceptance criterion of every served spec of the project, and of main's copy of every other spec path of the project, as the draft checks choose other specsThe criterion text onlyevery feature, this featureCriterion text and set version
Rule check: does this spec trigger the rule? then, only if yes, does it cover it? (yes/no chain)Each confirmed project-wide rule from another spec, on a spec that differs from its compared base, and on every spec at warm-upThe rule text and the spec's textyes, no; triggered and not covered is missedRule text, spec text, and set version

An answer below threshold, to either question, sends the same question once to a general LLM, when its question set allows fallback. The general LLM is the box's Claude CLI, run once per question isolated from user instructions and hooks, and authenticated by the box's own Claude settings rather than the Jev key. The model id is the box's one LLM name, llm_model in the Jev provider file beside its key, as review service providers define; unset, the CLI's own default model answers; question sets name no model, and nothing is read from the environment; its answer decides and is recorded with the same key. If that call fails, the item shows Jev unavailable and is asked again after a pause, by the one retry rule every Jev question follows.

A criterion whose decided scope is every feature is a candidate rule; it becomes a project-wide rule only when a human confirms it, as rule approval defines. Only confirmed rules are checked. A spec is never checked against its own criteria.

A spec is checked only against rules from its own project, the project its registry row names. The other specs both questions read are the corpus others, which hold only the page's project; a box serving several projects never mixes their rules, candidates, confirmations, or dismissals. The same holds for every other mark kind, as one project per mark defines.

A rule criterion that links a criterion of another spec in the same project, which is itself a rule, is a copy of that home rule; links are followed to the criterion that links no further rule. Copies are instances of one global rule: there is one rule per home, checked with the home's text, listed once in the rules checked, and shown as one note naming and linking the home. Confirm rule, Not for this spec, and Not a project rule on that card apply to the home, and so to every copy; a copy is never a candidate of its own.

A criterion that narrows or diverges from a rule should not link it; it then stays its own rule and is checked, shown, and dismissed on its own.

A spec without data-acceptance-criterion clauses holds no rules.

The records are derived and disposable: they hold no project knowledge, and deleting them costs only recomputation from the specs, plus forgetting the human's dismissals and confirmations, which are judgments of Jev's answers, not project knowledge; the rule itself always lives in its home spec's text. After deletion, confirmed rules are candidates again.

Pending

Only an escalated question waiting on the LLM shows the wheel, in the marker's place, the same size and calm neutral color, with no text beside it; plain Jev questions are fast and show nothing while pending, so the page stays clean.

A pending item says whether it has escalated. While any item is pending, the page asks /api/jev again and swaps the wheel for the answer in place; the spec text never moves.

With reduced motion, the wheel is a still glyph; the hover sentence is its accessible name.

Every Spec Chat Jev mark whose question escalates to the LLM shows this wheel while pending.

The agent read names a rule by its home spec and anchor, e.g. onboarding.spec.html#acceptance-onboarding; the page names it by its plain-words name.

Rule cards list after coverage in the popover order, one per rule. A rule miss's level comes from one row in the mark levels table, important, like every other mark; this spec keeps no level of its own.

A miss is answered in the spec: a criterion that covers the rule, or one plain line saying why it does not apply. The next rule check reads it and the note clears; threads play no part.

Dismiss

Two buttons sit left of the primary on every rule card; each is the human's one-click answer that Jev is wrong, adds no line to the spec, and removes the note at once.

ButtonHuman saysHolds forResolution, on which recordEffect
Not for this specThe rule does not apply to this specOne project, one spec path, one rule's criterion textdismissed, on the note's rule-check recordNo note for that rule on that spec path; other specs unaffected
Not a project ruleThe criterion is not a project-wide ruleOne project, one rule's criterion text, every spec, and every copy of that rulenot-a-rule, on the rule's scope recordThe criterion is no rule and no candidate, drives no card, is not listed in the rules checked, and counts toward no reconcile offer in that project

Both write through the existing Jev record route the offer uses, as record resolution defines, into the one records store; there is no other dismissal store, and deleting the records forgets dismissals, as it forgets answers. The resolution names the project, since one record may serve several projects with the same text.

A later check finds a dismissal by what it holds for, the project, spec path, and rule text for Not for this spec, or the project and rule text for Not a project rule, never by the record's cache key, which also hashes the spec text. So a dismissal survives reloads, edits, and new heads; a change to the rule's text is a new rule, and its miss shows again.

Neither takes a reason. Not for this spec stays unconfirmed, like an owner's dismissal, until the agent audit labels it; Not a project rule is a confirmed scope label, as rule approval defines. The two resolutions keep wrong for this spec, a rule-check label, apart from not a rule, a scope label, as labeled data for Jev's precision work.

A dismissed miss is absent from /api/jev, so the agent read neither lists nor counts it.

Jev's scope answer proposes rules; a human disposes. Nothing is checked against a rule, and no spec is edited to cover one, until a human confirms it.

A decision holds for the project and the rule's criterion text at its home, the same key a dismissal uses, and writes through the same Jev record route into the one records store; there is no rule list. A change to the home's text is a new candidate.

A human's Confirm rule and Not a project rule are confirmed labels for the scope question the moment they are recorded, since a human judged the rule; they feed Jev's eval set as confirmed labels define. Not for this spec judges one rule check and stays unconfirmed until audited.

The agent never confirms or rejects a rule. The agent read lists candidates on their own line, and the hand-off message names them as awaiting the human, for visibility only; a candidate needs no agent action and blocks nothing.

Agent read

The command reads the /api/jev response for the spec and base the review link serves, from the running server, so the agent and the page see one answer from one cache, and prints only a compact summary so the agent's context stays small.

important  acceptance       rule        important  onboarding.spec.html#acceptance-onboarding
important  save-rule        contradicts important  #non-goal-offline
warnings   corpus 2, unsure 1
rules      onboarding.spec.html#acceptance-onboarding
candidates peer-seams.spec.html#acceptance-ci

The shaping skill step runs after review-host register and before the link is sent: wait until no item is pending, read, solve every important mark, commit, and read again after each fix; then send the link.

  1. The agent keys on each item's level field, important or warning, set from the single mark levels table that also colors the page; it keeps no list of kinds of its own. A rule miss is important.
  2. Each important mark ends in exactly one of: fixed in the spec; a reason line in the spec, such as Onboarding: not needed, this changes no screen; or, when it is bigger than a simple edit, an open TBD the agent writes at the clause (data-spec-tbd), which blocks Accept spec until the human settles it; the TBD counts as solved for hand-off. A mark the human dismissed is absent from the read and needs nothing.
  3. Fixes follow the reconcile rule in shape-spec.
  4. The pass stops naturally, with no cap: if a fix raises a new important mark on the same clause, the agent writes an open TBD at that clause instead of fixing again.
  5. Warnings are read, not acted on, and never hidden: the hand-off message starts with N warnings not acted on: and the read's counts by kind, e.g. 3 warnings not acted on: corpus 2, unsure 1.
  6. For the human, marks are advice: none blocks Accept spec, and the agent never edits a spec just to raise Jev's confidence.

The hand-off message names the rules checked, as home spec and anchor, for visibility only; it asks nothing of the human.

With Jev off, the read says off and the skill sends the link at once.

The candidate offer comes first: one page note, N possible project rules: confirm?, collapsed by default, that expands to one candidate card per candidate rule. It shows on that project's next review page after warm-up, until every candidate is decided or the note is dismissed; an undecided candidate still shows its card on its home spec.

The reconcile offer counts confirmed rules only, and shows once no warm-up candidate is undecided or the candidate offer was dismissed: one page note, N existing specs miss project rules, collapsed by default, reusing the existing disclosure button pattern. Expanded, it is a readable list, one line per spec: the spec's name linking to the spec, then misses and the plain-words name of each rule it misses. Each line expands in place to that rule's card, one per missed rule. Reconcile drafts one comment through the existing reconcile flow, Reconcile each spec with its missed rules: then one line per spec, <spec> misses <rule name> <rule link>; the agent answers it per the reconcile rule.

The bootstrap is part of Spec Chat's onboarding, its own first run: the first review-host register of a project starts it, and Spec Chat alone runs it end to end. No peer's setup starts, waits for, or completes it.

Spec Chat publishes warm-up status through its one onboarding.toml in its own state, as the review service defines, with one table per project: warm-up state, criteria classified, candidates, confirmed rules, N specs to reconcile, whether each offer was sent or dismissed, and the warm-up definition it ran under. There is no separate status file. Anyone may read it; it names no peer and is derived like the records.

Sending or dismissing either offer is recorded in that project's table; with N zero, or Jev off, that offer does not show. A done warm-up is not redone while its warm-up definition, what the warm-up asks and publishes, is unchanged. When Spec Chat changes that definition, every project whose done status ran under an earlier one warms again, and the rerun keeps every human decision: confirmed and dismissed rules, and whether each offer was sent or dismissed.

Explicit rule wording

A criterion counts as a project-wide rule only when Jev, reading its text, answers every feature. The scope question and its fallback decide. A real project-wide rule is written in its home spec with explicit every-feature wording so Jev's answer is reliable. A criterion that describes how one feature behaves and does not say it applies to every feature is answered this feature and is never a rule.

Explicit wording adds no mechanism: the scope question set, the Jev fallback, the rule-check question, records, and caching stay the ones above. Reliability comes from the criterion text alone.

Proof

First failing test: with a fake provider answering every feature for one criterion of spec A and missed for spec B, /api/jev for B returns one rule item targeting A's criterion.

Dismiss first failing test: with a fake provider answering missed for spec B, resolving that rule-check record dismissed removes the item from B's /api/jev, and it stays absent after B's text changes, then returns when the rule's criterion text changes; resolving the rule's scope record not-a-rule for B's project removes the rule from every spec's items, rules checked, and offer in that project, and not in another project; with a fake answering every feature for a home and two criteria linking it, B's items and rules checked name only the home.

Approval first failing test: with a fake provider answering every feature for spec A's criterion and missed for spec B, B's /api/jev has a candidate item for A's criterion and no rule item; after a rule resolution for that project and text, it has the rule item, the rule is in the rules checked, and the scope record's label is confirmed.

Card first failing test: the runtime renders a rule item as one card with label, name, full quote, source link, and the three buttons in order, and a candidate item with Not a project rule and Confirm rule.

Own-project first failing test: with mounts of two projects each holding an every feature criterion, /api/jev for a spec of the first project lists only the first project's rule as checked.

Evidence: seam and runtime tests behind fakes, one live run per new question set, and a QA bundle on a real spec with a real project-wide rule, including a first registration.

Non-goals

Tags, rule lists, side files, or Spec Chat state holding project knowledge (a dismissal or a confirmation judges Jev's answer and is not project knowledge); rules from outside the served specs; generated mark text other than the rule name; a scope mark or an unsure rule mark; clearing a miss by thread; checking specs not under review after bootstrap; any bootstrap step in a peer's setup; changes to the scope question set's instructions, labels, or threshold; a reason prompt or undo for either dismissal or a confirmation; a standing rules page apart from the two one-time offers and the cards; an agent confirming a rule.
