Project-wide rules at shaping

docs / specs / project-rules.spec.html

Some acceptance criteria apply to every feature, such as every change to what a user sees or does adds its onboarding section. They live in one spec that shaping never reads, so they get missed. A spec author declares such a criterion a project rule where it lives, and Jev checks a spec under shaping against the declared rules. Jev also flags a criterion that reads as project-wide but is not marked, so no rule slips in unmarked. Extends Jev review suggestions: its seam, records, cache, markers, popovers, and note buttons apply unchanged, and every note about a rule is one readable rule card. One check finds such criteria at three points: the shaping agent asks the human while authoring, the review page and the agent read flag them, and onboarding catch-up runs it over every spec.

User stories

As a spec author, I declare a rule that applies to every feature once, by marking its criterion in its home spec with a short name, and Spec Chat treats it as project-wide with nothing else to maintain or remember.

As a spec author, only promises a later feature could break become project rules, what the product does for its users or how the project builds and ships it, while each design-system convention stays in the design system and the code check that enforces it, so the rules stay few and no rule question comes up for each new shared part.

As a spec author, a criterion is a project rule exactly while its home spec marks it, so the rule set changes only by editing specs, and no click anywhere makes, unmakes, or brings back a rule.

As a reviewer, a criterion that reads as project-wide but is not marked is flagged as a possible project rule, so a rule never slips in unmarked; Mark as rule hands it to the owning agent, and Not a project rule settles it for good.

As the shaping agent, when a criterion I add or change reads as project-wide, I ask the human whether it is a repo-wide rule while shaping, mark it on yes, and record Not a project rule on no, so the question is settled before review.

As the operator, every candidate a human settles or passes over, at any entry point, leaves its outcome beside the Jev answer that raised it, so I can measure the scope question's precision and recall from real outcomes.

As a reviewer of a spec under shaping, a project-wide rule the spec triggers but does not cover shows one readable card that names the rule, quotes it in full, and names its source, linked where my lane serves it, so I can judge it at a glance, and it clears once the spec either covers the rule or says in one line why it does not apply.

As a reviewer, every note about a project rule, a missed rule or an important mark citing a rule, looks and reads the same, so I learn one card and never decode a cryptic label.

As the shaping agent, I read every Jev check on my spec as compact text without a browser, solve every important mark, and hand off the review link naming the rules checked and listing the warnings I did not act on.

As a reviewer who judges a rule mark wrong for this spec, I answer it with one clearly labelled click, Not for this spec, and it stays dismissed on every later load and edit of that spec.

As a Spec Chat user without the review service, shaping and the spec page work fully without it: rule cards exist only where the review service runs Jev.

Modular boundaries

The review server's Jev seam owns the scope and rule-check questions, the general LLM fallback, its records, and the cache; it reads the declared rules from the marks of the project's specs, as the rule source reads them. Caller-facing seam: the existing GET /api/jev response, with items of kind rule and candidate carrying their rule's criterion text, name, and home, a pending state, a level on every mark, and the rules checked; the existing Jev record route, taking Not for this spec and Not a project rule. Dependency direction: external-provider; calls Jev through OpenRouter with the Jev provider's key, and the general LLM through the box's Claude CLI with the provider's model, and reads the served specs, and main's copies from git, as the draft checks do; nothing calls back. Observable scope: the JSON response, records, and the warning ledger.

The browser runtime owns the one rule card and every place it renders, the pending wheel, and the card buttons, including Mark as rule's draft. Caller-facing seam: the rendered page; writes only through the existing comment composer and the existing Jev record route. Dependency direction: self-contained; consumes the seam route. Observable scope: what the reviewer sees.

The shaping skill owns reading and resolving the checks before handing off the link. Caller-facing seam: one read command over the running review server, printing compact text, with --anchor for one anchor's detail. Dependency direction: self-contained; the skill calls the server, and the server never calls the skill. Observable scope: commits and the hand-off message.

Spec Chat's core, the shaping skill, validator, spec format, and spec page runtime without a review service, owns the rule mark as spec markup and nothing else in this spec. Caller-facing seam: the rule mark on an acceptance criterion; the runtime renders cards only from a /api/jev answer, and the shaping skill's Jev read already says off when there is none. Dependency direction: self-contained; the review service depends on the core, never the reverse, and no core step calls or waits on Jev. Observable scope: a spec page and a shaping run with no review service show no rule card or error.

Declaring a rule

A project rule is an acceptance criterion its home spec marks as one: the criterion carries data-project-rule, whose value is the rule's short plain-words name. The mark is the whole declaration: marked is a rule, unmarked is not.

A project rule is a promise a later feature could break: what the product does for its users, as every tab keeps its place until reload, or how the project builds and ships it, as CI covers every acceptance criterion. A design-system convention, how the interface looks or moves or which shared part draws a kind of thing, as every loading state uses the shared skeleton, is no project rule and is never marked: it lives in the design system, its design document and shared parts, where a code check rejects a hand-rolled version exactly, as Jev reading prose cannot. A project keeps at most one project rule for its design system, the umbrella the interface uses the design system's shared parts, whose text links the design system; a spec that adds a shared part or a convention raises no candidate, since the umbrella covers it.

A marked criterion says in its own text that it applies to every feature, so a reader of the home spec sees why it is a rule; the validator rejects a mark with an empty name or on anything but an acceptance criterion.

The rule set changes only by editing specs: marking a criterion adds a rule, removing the mark or the criterion retires it, and rewording it changes it. Spec Chat keeps no rule list and no state that adds, removes, or restores a rule; Not a project rule only stops a candidate flag.

One check, the scope question below, finds unmarked criteria that read as project-wide, at three entry points: the shaping agent asks the human at authoring time (agent ask), the review page and the agent read flag a candidate as a backstop warning, and onboarding catch-up runs it over every spec of a project in one batch. Each settles a candidate the same two ways: marked in the spec, or Not a project rule in the warning ledger; a settled criterion is never proposed again by any of them.

An answer Jev is unsure of, its confidence below the question set's threshold, to the scope question, sends the same question once to a general LLM, when its question set allows fallback. The general LLM is the box's Claude CLI, run once per question isolated from user instructions and hooks, and authenticated by the box's own Claude settings rather than the Jev key. If that call fails, the item shows Jev unavailable and is asked again after a pause, by the one retry rule every Jev question follows.

The rule check goes to that general LLM, never to Jev: one call asks about every rule the spec's text has no record for, and its answer decides each rule, recorded one record per rule, so a spec's rule check costs one LLM run per spec text however many rules its project marks, and a rule marked later asks only about that rule. Jev is no first pass for it, since a judgment about a rule over a whole spec is one Jev mostly leaves unsure. A failed call follows the same retry rule.

The scope question answers every feature only for a promise, as a project rule is; a design-system convention answers this feature, so it never becomes a candidate.

An unmarked criterion whose scope answer is every feature is a candidate until it is marked or answered Not a project rule; a candidate is flagged and never checked.

Only marked rules are checked. A spec is never checked against its own criteria. The rules checked are the rules the rule check has answered for the spec's text; a rule still waiting on its answer, or whose call failed, is never listed as checked, and while it waits it counts as pending.

The rules a spec is checked against are every rule its project marks: the marks of every spec its collection holds on the project's main, origin/main in the page's root, found as the review index finds a collection's specs. A spec the page's lane changes, its copy in the lane's root differing from its copy where the lane's branch left main, is read from the lane's root instead, so a rule the lane adds, rewords, or unmarks counts as the lane has it, and a spec the lane deletes holds no rules. Each spec path is read once and another lane's copy never, so the rules checked never depend on which other lanes are open; another lane's change to a rule reaches the check once it merges. In single-root mode, the rules are those of the root's other served specs. These are not the draft checks' corpus others, the specs some lane serves: a rule binds every feature whether or not its home spec is under review.

A spec is checked only against rules from its own project, the project its registry row names, read as the rule source says; a box serving several projects never mixes their rules or dismissals. The same holds for every other mark kind, as one project per mark defines.

A spec without data-acceptance-criterion clauses holds no rules.

The records are a disposable cache: they hold no project knowledge, and deleting them costs only recomputation. Rules live in their home specs' marks, and dismissals in the warning ledger.

Pending

Only a question waiting on the LLM, a rule check or an escalated scope question, shows the wheel, in the marker's place, the same size and calm neutral color, with no text beside it; plain Jev questions are fast and show nothing while pending, so the page stays clean.

A pending item says whether it has escalated. While any item is pending, the page asks /api/jev again and swaps the wheel for the answer in place; the spec text never moves.

With reduced motion, the wheel is a still glyph; the hover sentence is its accessible name.

The agent read names a rule by its home spec and anchor, e.g. onboarding.spec.html#acceptance-onboarding; the page names it by its plain-words name.

Rule cards list after coverage in the popover order, one per rule. A rule miss's level comes from one row in the mark levels table, important, like every other mark; this spec keeps no level of its own.

A miss is answered in the spec: a criterion that covers the rule, or one plain line saying why it does not apply. The next rule check reads it and the note clears; threads play no part.

Dismiss

One button sits left of the primary on every rule card: Not for this spec, the human's one-click answer that the rule does not apply to this spec. It adds no line to the spec and removes the note at once.

It is recorded once in the warning ledger, by the project, the spec path, and the rule's home spec and anchor; the note for that rule stays gone on that spec path through reloads, edits, and new heads, and other specs are unaffected.

It takes no reason and stays unconfirmed, like an owner's dismissal, until the agent audit labels it.

Not a project rule on a candidate card records not-a-rule once in the warning ledger, by the project, the criterion's spec path, and its anchor; that criterion is never flagged again by any entry point, through rewording too, and marking it later still makes it a rule. A marked rule is retired only by removing its mark in its home spec, which a review of that spec settles; no card button does it.

Every candidate outcome is a trace for Jev's accuracy: the warning ledger line names the spec path and anchor, the outcome, and the id of the scope record that raised it, whose inputs, label, and probabilities live in the record. not-a-rule comes from the card, the shaping ask, or catch-up; marked when a served spec first marks a criterion, citing the scope record for its text whatever it answered, so a mark on a this feature answer counts as a miss; ignored when a spec is accepted with a candidate still unsettled, or catch-up passes one over. The scope question's precision and recall are an eval read over these lines, as measure feedback defines.

A dismissed miss is absent from /api/jev, so the agent read neither lists nor counts it.

On a mark citing a rule, Not for this spec records dismissed in the warning ledger for that spec path, the flagged clause, and the rule, and the mark is gone.

Mark as rule is a hand-off, not a decision: it drafts a comment at the criterion asking its owner to mark it as a project rule with a short name; the owning agent adds the mark in the spec, and the rule exists for its own lane at once and for every other lane once that spec merges, as the rule source reads.

Agent read

The command reads the /api/jev response for the spec and base the review link serves, from the running server, so the agent and the page see one answer from one cache, and prints only a compact summary so the agent's context stays small.

important  acceptance       rule        important  onboarding.spec.html#acceptance-onboarding  judgment-4f1c9a
important  save-rule        contradicts important  sync.spec.html#non-goal-offline           judgment-b27e05
warnings   corpus 2, unsure 1
rules      onboarding.spec.html#acceptance-onboarding
candidates save.spec.html#acceptance-backup
pending    0

The shaping skill step runs after review-host register and before the link is sent: wait until no item is pending, read, solve every important mark, commit, and read again after each fix; then send the link.

  1. The agent keys on each item's level field, important or warning, set from the single mark levels table that also colors the page; it keeps no list of kinds of its own. A rule miss is important.
  2. Each important mark ends in exactly one of the owner outcomes the warning ledger records. A reason line reads like Onboarding: not needed, this changes no screen. A mark bigger than a simple edit gets an open TBD the agent writes at the clause (data-spec-tbd), never a thread; it is recorded as fixed, blocks Accept spec until the human settles it, and counts as solved for hand-off. A mark Jev got wrong is dismissed by the owner with a reason; a mark the owner or the human resolved is absent from the read and needs nothing.
  3. Fixes follow the reconcile rule in shape-spec.
  4. The pass stops naturally, with no cap: if a fix raises a new important mark on the same clause, the agent writes an open TBD at that clause instead of fixing again.
  5. Warnings are read, not acted on, and never hidden: the hand-off message starts with N warnings not acted on: and the read's counts by kind, e.g. 3 warnings not acted on: corpus 2, unsure 1.
  6. For the human, marks are advice: none blocks Accept spec, and the agent never edits a spec just to raise Jev's confidence.

The hand-off message names the rules checked, as home spec and anchor, for visibility only; it asks nothing of the human.

While shaping, before the link is sent, the agent asks the human, for each candidate on its own spec, whether it is a repo-wide rule: on yes it marks the criterion with a short name and commits; on no it records Not a project rule through the agent read. Candidates on other specs are only listed. The agent never decides a candidate itself.

With Jev off, the read says off and the skill sends the link at once.

While the provider refuses Jev's key, the read says paused with the pause's end and the provider's status, waits for nothing, and the skill sends the link at once, as with Jev off.

Proof

First failing test: with spec A marking one criterion as a project rule and a fake provider answering missed for spec B, /api/jev for B returns one rule item targeting A's criterion under the mark's name; with the mark removed, it returns none and asks nothing.

Dismiss first failing test: with a fake provider answering missed for spec B, recording Not for this spec removes the item from B's /api/jev, it stays absent after B's text changes, and the warning ledger holds one line for B and the rule.

Candidate first failing test: with a fake provider answering every feature for an unmarked criterion of spec A, A's /api/jev has a candidate item and no spec is checked against it; after Not a project rule for A and that anchor, A has no candidate item and the scope question is not asked again, even with the criterion reworded.

Card first failing test: the runtime renders a rule item as one card with label, name, full quote, source link, and its two buttons in order, a rule item whose home the page's lane does not serve with that source as plain text, and a candidate item with Not a project rule and Mark as rule.

Own-project first failing test: with mounts of two projects each marking a rule, /api/jev for a spec of the first project lists only the first project's rule as checked.

Rule source first failing test: with the project's main marking a rule in a spec no row serves, and another lane serving a copy of a second home spec that rewords its rule, /api/jev for a lane's spec lists both rules as checked by home spec and anchor, and its one rule-check ask quotes main's text of each; with the lane rewording the second rule in its own root, the ask quotes the lane's text.

Evidence: seam and runtime tests behind fakes, the validator's mark check, and a QA bundle on a real spec with a real marked rule.

Non-goals

Rule lists, side files, or Spec Chat state that add, remove, or restore a rule; a button that makes, unmakes, or renames a rule; an agent deciding a candidate; generated rule names; rules from another project, from another lane's copy, or from outside the project's collection; an unsure scope or rule mark; clearing a miss by thread; checking specs not under review; any rule step in a peer's setup; a reason prompt or undo for a dismissal; a standing rules page; a project rule per design-system convention; Spec Chat checking a target's design-system conventions, which the target's own code check does.
