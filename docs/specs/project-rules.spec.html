Project-wide rules at shaping

docs / specs / project-rules.spec.html

Some acceptance criteria apply to every feature, such as every change to what a user sees or does adds its onboarding section. They live in one spec that shaping never reads, so they get missed. This spec lets Jev find them and check a spec under shaping against them. Extends Jev review suggestions: its seam, records, cache, markers, popovers, and note buttons apply unchanged, and marks are one-word notes as its one-word note style defines.

User stories

As a spec author, I write a rule that applies to every feature once, in plain words, in its home spec, and Spec Chat treats it as project-wide with nothing else to maintain or remember.

As a reviewer of a spec under shaping, a project-wide rule the spec triggers but does not cover shows one compact mark that links the rule and states the rule's own text, so I can judge it at a glance, and it clears once the spec either covers the rule or says in one line why it does not apply.

As the shaping agent, I read every Jev check on my spec as compact text without a browser, solve every important mark, and hand off the review link naming the rules checked and listing the warnings I did not act on.

As a reviewer who judges a rule mark wrong, I answer it with one click: Not here when the rule does not apply to this spec, or Dismiss rule when the criterion is not a project-wide rule at all, and it stays dismissed on every later load and edit, until the rule itself changes.

As a reviewer on a box that serves several projects, a spec is checked only against its own project's rules, so a mark never cites another project's spec.

As a reviewer on a project new to Spec Chat, I am offered once to reconcile the existing specs that miss project rules.

As a spec author, a criterion counts as a project-wide rule only when its own text says it applies to every feature, so I control which criteria become rules by including or omitting that wording.

Acceptance criteria

When one served spec has a criterion that applies to every feature and another that applies only to its own feature, only the first is a project-wide rule, and no tag, list, side file, or Spec Chat state names it.

When a rule's criterion is reworded to apply to one feature, or deleted, on the next load no spec shows a mark for it.

When a criterion's text is unchanged across heads, lanes, and specs that read it, and when the records are deleted, its scope is asked once and reused, and after deletion the same rules are rebuilt from the specs alone.

When Jev is below threshold on a criterion's scope, or on whether a spec misses a rule, the same question goes once to the general LLM, its answer decides and is recorded and reused, and the page shows only a clear missed note or nothing, never an unsure rule or scope mark.

When a spec under shaping adds a change to what a user sees and has no onboarding criterion, while onboarding.spec.html holds the onboarding rule, its Acceptance criteria heading shows one marker whose popover lists onboarding? linking that rule, then the rule's own criterion text in full, with Ask to cover, Not here, and Dismiss rule.

Given that onboarding? note, When the reviewer clicks Not here, then reloads, then edits and commits the spec, the note is gone at once without a reload and stays gone on every later load and head of that spec path while the rule's criterion text is unchanged; the agent read no longer lists it; the note still shows on another spec that misses the same rule; and the rule-check record carries resolution dismissed, unconfirmed.

Given onboarding? notes on specs B and C and a warm-up offer listing the onboarding rule, When the reviewer clicks Dismiss rule on B's note, then reloads B, C, and a page showing the offer, both notes are gone and stay gone on every spec of that project while the rule's criterion text is unchanged; the rules checked no longer list it; the offer no longer lists it and counts no spec whose only misses are dismissed rules; another project holding the same criterion text is unaffected; and the rule's scope record carries resolution not-a-rule, unconfirmed.

Given a dismissed onboarding? note, When the rule's criterion text in onboarding.spec.html changes and the rule check still answers missed, the note shows again with the new rule text and both dismiss buttons; the same holds after Dismiss rule.

Given one review server serving lanes of project A and project B, each with a spec holding a project-wide rule, When a spec under shaping in project A is read, its /api/jev rules checked, rule notes, and corpus candidates come only from project A's specs, and the agent read names no project B spec.

When a rule check, or the scope of a rule it needs, has escalated from Jev to the LLM and the LLM has not answered, the spot where the mark would appear shows a small rotating wheel with checking onboarding… on hover, which becomes the onboarding? note or nothing without a reload; while only plain Jev checks are pending the spot shows nothing; with reduced motion the wheel does not rotate.

When the spec then adds a criterion that covers the rule, or one plain line such as Onboarding: not needed, this changes no screen, the onboarding? note is gone on the next load; a thread alone never clears it, and a spec that does not trigger the rule never shows it.

When the reviewer clicks Ask to cover, the comment composer opens at the Acceptance criteria heading with the draft Cover <link to rule> with a criterion, or add one line saying why it does not apply., and nothing is written until the reviewer sends.

When the shaping agent reads its spec's Jev checks from the box, one command prints compact text, not raw JSON: one line per important mark with anchor, kind, level, and link target; one line of warning counts by kind; the rules checked; pending count; or off. With --anchor <id> it prints full detail for that anchor only.

When the shaping skill registers a spec for review, it hands off the review link only once every important mark ends in exactly one of a spec fix, a reason line in the spec, or an open TBD the agent writes at the clause (data-spec-tbd), which blocks Accept spec until the human settles it, and the hand-off message names the rules checked and starts with N warnings not acted on: and the same counts by kind the read prints.

When the agent's fix for an important mark raises a new important mark on the same clause, the agent writes an open TBD at that clause instead of editing it again, and Accept spec stays blocked until the human settles it.

When a spec still has Jev marks, including a missed note, as the human reviews it, Accept spec proceeds unchanged, and no spec edit exists only to change a Jev answer or its confidence.

When a project is registered with the review service for the first time, with no other tool installed, register returns without waiting, a background warm-up classifies every criterion and checks every spec in parallel, and later pages reuse its records without new calls, and onboarding.toml shows the rules classified and N specs to reconcile for that project.

When the warm-up finds N existing specs that miss a rule, and the reviewer opens a page of that project, the page shows N existing specs miss project rules: reconcile? once with a disclosure toggle collapsed by default; expanding it lists each spec with its missed rules, the spec name linking to the spec and each rule word linking to the rule's home clause; Reconcile opens the composer with one draft listing each spec and its missed rules with links, nothing is written until the reviewer sends, and after it is sent or dismissed it never shows again for that project.

When a criterion's text says every feature, every change, any change, or equivalent every-feature wording, the scope question still asks Jev, and Jev's answer decides, as today; the explicit wording makes Jev's answer reliable, not a new mechanism.

When a criterion describes how one feature behaves and does not say it applies to every feature, Jev answers this feature and it is never a project rule.

When the first-run warm-up classifies every criterion, it uses the same scope question and Jev answer as any other rule check; criteria without explicit every-feature wording are classified this feature and produce no rule, no offer, and no miss mark.

When a reviewer reads Spec Chat's onboarding documentation, one section says how to write a project rule: include explicit every-feature wording in the criterion text, such as When any change adds a screen, it ships with its help center article.

CI: the scope and rule-check tests run in CI with no Jev provider installed and no provider file; fake provider answers are the contract tests.

Modular boundaries

The review server's Jev seam owns the scope and rule-check questions, the general LLM fallback, the warm-up, the onboarding status, their records, and the cache. Caller-facing seam: the existing GET /api/jev response, gaining items of kind rule carrying their rule's criterion text, a pending state, a level on every mark, the rules checked, and the one-time offer; the existing Jev record route, taking either rule dismissal as well as the offer; the project's table in onboarding.toml for readers outside Spec Chat. Dependency direction: external-provider; calls Jev and the general LLM through OpenRouter with the Jev provider's key and model, and reads the served specs as the draft checks do; nothing calls back. Observable scope: the JSON response, records, and onboarding.toml.

The browser runtime owns the <word>? notes with their rule text, the pending wheel, the Ask to cover, Not here, and Dismiss rule buttons, and the one-time offer. Caller-facing seam: the rendered page; writes only through the existing comment composer and the existing Jev record route the offer already uses. Dependency direction: self-contained; consumes the seam route. Observable scope: what the reviewer sees.

The shaping skill owns reading and resolving the checks before handing off the link. Caller-facing seam: one read command over the running review server, printing compact text, with --anchor for one anchor's detail. Dependency direction: self-contained; the skill calls the server, and the server never calls the skill. Observable scope: commits and the hand-off message.

Two questions

Both are Jev questions under the Every suggestion rules: one question set each, one record per call, records as cache.
QuestionAsked forSeesLabelsCache key
Scope: does this apply to every feature?Every acceptance criterion of every served spec, and of main's copy of every other spec path, as the draft checks choose other specsThe criterion text onlyevery feature, this featureCriterion text and set version
Rule check: does this spec trigger the rule? then, only if yes, does it cover it? An answer below threshold, to either question, sends the same question once to a general LLM through OpenRouter, when its question set allows fallback. The model id is the box's one LLM name, llm_model in the Jev provider file beside its key, as review service providers define, default anthropic/claude-sonnet-5; question sets name no model, and nothing is read from the environment; its answer decides and is recorded with the same key. If that call fails, the item shows Jev unavailable and is asked again after a pause, by the one retry rule every Jev question follows.

A project-wide rule is a criterion whose decided scope is every feature. A spec is never checked against its own criteria.

A spec is checked only against rules from its own project, the project its registry row names. The other specs both questions read are the corpus others, which hold only the page's project; a box serving several projects never mixes their rules.

A spec without data-acceptance-criterion clauses holds no rules.

The records are derived and disposable: they hold no project knowledge, and deleting them costs only recomputation from the specs, plus forgetting the human's dismissals, which are judgments of Jev, not project knowledge.

A missed note is one word with its sentence on hover as its accessible name, as the one-word note style defines, but not muted; it is a clear miss.

In the popover, the rule's own criterion text follows the word in full, as plain quoted text, so the reviewer judges the rule without opening its home spec. The text comes from the served rule clause the scope question read; it is never generated or shortened.

Pending

Only an escalated question waiting on the LLM shows the wheel, in the marker's place, the same size and calm neutral color, with no text beside it; plain Jev questions are fast and show nothing while pending, so the page stays clean.

A pending item says whether it has escalated. While any item is pending, the page asks /api/jev again and swaps the wheel for the answer in place; the spec text never moves.

With reduced motion, the wheel is a still glyph; the hover sentence is its accessible name.

Every Spec Chat Jev mark whose question escalates to the LLM shows this wheel while pending.

The word is the home spec's file name without .spec.html, e.g. onboarding?; fixed, never generated.

Rule notes list after coverage in the popover order, one per rule. A rule miss's level comes from one row in the mark levels table, important, like every other mark; this spec keeps no level of its own.

A miss is answered in the spec: a criterion that covers the rule, or one plain line saying why it does not apply. The next rule check reads it and the note clears; threads play no part.

Dismiss

Two buttons sit beside Ask to cover on every missed note; each is the human's one-click answer that Jev is wrong, adds no line to the spec, and removes the note at once.

ButtonHuman saysHolds forResolution, on which recordEffect
Not hereThe rule does not apply to this specOne project, one spec path, one rule's criterion textdismissed, on the note's rule-check recordNo note for that rule on that spec path; other specs unaffected
Dismiss ruleThe criterion is not a project-wide ruleOne project, one rule's criterion text, every specnot-a-rule, on the rule's scope recordThe criterion drives no rule note, is not listed in the rules checked, and counts toward no reconcile offer in that project

Both write through the existing Jev record route the offer uses, as record resolution defines, into the one records store; there is no other dismissal store, and deleting the records forgets dismissals, as it forgets answers. The resolution names the project, since one record may serve several projects with the same text.

A later check finds a dismissal by what it holds for, the project, spec path, and rule text for Not here, or the project and rule text for Dismiss rule, never by the record's cache key, which also hashes the spec text. So a dismissal survives reloads, edits, and new heads; a change to the rule's text is a new rule, and its miss shows again.

Neither takes a reason, and both stay unconfirmed, like an owner's dismissal, until the agent audit labels them. The two resolutions keep wrong for this spec, a rule-check label, apart from not a rule, a scope label, as labeled data for Jev's precision work.

A dismissed miss is absent from /api/jev, so the agent read neither lists nor counts it.

Agent read

The command reads the /api/jev response for the spec and base the review link serves, from the running server, so the agent and the page see one answer from one cache, and prints only a compact summary so the agent's context stays small.

important  acceptance       rule        important  onboarding.spec.html#acceptance-onboarding
important  save-rule        contradicts important  #non-goal-offline
warnings   type 3, reader 2
rules      onboarding.spec.html#acceptance-onboarding
pending    0

The shaping skill step runs after review-host register and before the link is sent: wait until no item is pending, read, solve every important mark, commit, and read again after each fix; then send the link.

  1. The agent keys on each item's level field, important or warning, set from the single mark levels table that also colors the page; it keeps no list of kinds of its own. A rule miss is important.
  2. Each important mark ends in exactly one of: fixed in the spec; a reason line in the spec, such as Onboarding: not needed, this changes no screen; or, when it is bigger than a simple edit, an open TBD the agent writes at the clause (data-spec-tbd), which blocks Accept spec until the human settles it; the TBD counts as solved for hand-off. A mark the human dismissed is absent from the read and needs nothing.
  3. Fixes follow the reconcile rule in shape-spec.
  4. The pass stops naturally, with no cap: if a fix raises a new important mark on the same clause, the agent writes an open TBD at that clause instead of fixing again.
  5. Warnings are read, not acted on, and never hidden: the hand-off message starts with N warnings not acted on: and the read's counts by kind, e.g. 5 warnings not acted on: type 3, reader 2.
  6. For the human, marks are advice: none blocks Accept spec, and the agent never edits a spec just to raise Jev's confidence.

The hand-off message names the rules checked, as home spec and anchor, for visibility only; it asks nothing of the human.

With Jev off, the read says off and the skill sends the link at once.

The offer is one page note on that project's next review page after warm-up, with a disclosure toggle (collapsed by default) that lists each spec and its missed rules: the spec name links to the spec, and each rule word links to the rule's home clause, reusing the existing disclosure button pattern. Reconcile drafts one comment through the existing reconcile flow, Reconcile each spec with its missed rules: then one line per spec, <spec> <word>? <rule link>; the agent answers it per the reconcile rule.

The bootstrap is part of Spec Chat's onboarding, its own first run: the first review-host register of a project starts it, and Spec Chat alone runs it end to end. No peer's setup starts, waits for, or completes it.

Spec Chat publishes warm-up status through its one onboarding.toml in its own state, as the review service defines, with one table per project: warm-up state, criteria classified, rules found, N specs to reconcile, and whether the offer was sent or dismissed. There is no separate status file. Anyone may read it; it names no peer and is derived like the records.

Sending or dismissing the offer is recorded in that project's table; with N zero, or Jev off, no offer shows.

Explicit rule wording

A criterion counts as a project-wide rule only when Jev, reading its text, answers every feature. The mechanism is unchanged: the existing scope question and its fallback decide. A real project-wide rule is written in its home spec with explicit every-feature wording so Jev's answer is reliable. A criterion that describes how one feature behaves and does not say it applies to every feature is answered this feature and is never a rule.

No new mechanism is added. The scope question set, the Jev fallback, the rule-check question, records, and caching are unchanged. The improvement is in the criterion text, not the code.

Proof

First failing test: with a fake provider answering every feature for one criterion of spec A and missed for spec B, /api/jev for B returns one rule item targeting A's criterion.

Dismiss first failing test: with a fake provider answering missed for spec B, resolving that rule-check record dismissed removes the item from B's /api/jev, and it stays absent after B's text changes, then returns when the rule's criterion text changes; resolving the rule's scope record not-a-rule for B's project removes the rule from every spec's items, rules checked, and offer in that project, and not in another project.

Own-project first failing test: with mounts of two projects each holding an every feature criterion, /api/jev for a spec of the first project lists only the first project's rule as checked.

Evidence: seam and runtime tests behind fakes, one live run per new question set, and a QA bundle on a real spec with a real project-wide rule, including a first registration.

Non-goals

Tags, rule lists, side files, or Spec Chat state holding project knowledge (a dismissal judges Jev and is not project knowledge); rules from outside the served specs; generated mark text; a scope mark or an unsure rule mark; clearing a miss by thread; checking specs not under review after bootstrap; any bootstrap step in a peer's setup; changes to the scope question set's instructions, labels, or threshold; a reason prompt or undo for either dismissal; asking the human to confirm each rule before any mark.
