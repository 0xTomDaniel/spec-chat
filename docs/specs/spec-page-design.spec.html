Spec page design

The spec page chrome uses the Spec Chat index design values: one button system, one color palette, consistent placement. The spec document's own content keeps its own styles, which the shared spec stylesheet sets from the same design set (the document).

Scope
runtime.js chrome styles, and the dark mode chrome of its document rules

01

User stories

One reviewer, one page, consistent chrome.

As a spec reviewer, I see one coherent visual system across every button, pill, pin, panel, popover, toolbar, and bar on a spec page, so I never wonder whether two differently styled controls do the same thing.

As a contributor editing runtime.js, every chrome color, font size, weight, radius, and spacing value is a named token from one block, so I never invent an ad hoc value or guess which grey to use.

As a spec reviewer, the spec page is one calm surface, as a Notion page is: the document, its compared range, the toolbar, and the review panel share one page color and ink, light or dark as my system or host sets it, and the document opens on its own title at reading size, not a poster in a box.

As a spec reviewer, every icon on the page is from one line set, the one Proof shows, status words read in sentence case, and no button label carries a key: I find each key in its tooltip, and on a phone none shows.

As a spec reviewer, an error the page meets shows once, with how often it came, and never hides the screen I review or its controls.

02

Acceptance criteria

Given a contributor editing the review runtime, When they open its chrome styles, Then every chrome color, font size, weight, radius, and spacing value is a named token in the one token block, which holds the shared design set’s tokens at the version Spec Chat pins plus the token additions, and every chrome style uses those tokens, with literal values only for the pin teardrop radius, stacking order, transitions, animations, and positions, proven by a unit test: no screen shows it.

Given a spec reviewer on a desktop screen on a spec page, When they open it, Then every chrome button matches one of the four button variants (primary, secondary, icon, text-link) with its shared properties, and no button has a shape, size, radius, font, or color outside the system.

Given a spec reviewer on a phone on a spec page, When they open it, Then every chrome button matches one of the four button variants (primary, secondary, icon, text-link) with its shared properties, and no button has a shape, size, radius, font, or color outside the system.

Given a spec reviewer on a desktop screen on a spec page with draft, acknowledged, and resolved threads, When they open the review panel, Then every pin and every receipt in the conversation for the same status shows the same color, and no two statuses share a color.

Given a spec reviewer on a spec with Jev markers at important, neutral, and passed levels, When they open the spec, Then the markers show the important, neutral, and passed colors of the marker tokens, each in its level's marker shape and size.

Given a spec reviewer on a spec with a Jev marker whose notes are all Warning level, a fixture must be added to provide it, When they open the spec, Then the marker shows as a light red dot in the warning marker color, distinct from the important, neutral, and passed markers.

Given a spec reviewer on a spec page, When they open it, Then every chrome text meets 4.5:1 contrast and meaningful non-text chrome boundaries (status pill borders, active thread borders, pin outlines) meet 3:1.

Given a spec reviewer on a desktop screen on a spec that uses the shared stylesheet, When they open it, Then the spec content (headings, prose, tables, figures, code blocks, section borders, page background) takes its look from the shared stylesheet and the runtime's document rules alone, and no chrome token restyles it.

Given a spec reviewer on a phone on a spec that uses the shared stylesheet, When they open it, Then the spec content (headings, prose, tables, figures, code blocks, section borders, page background) takes its look from the shared stylesheet and the runtime's document rules alone, and no chrome token restyles it.

Given a spec reviewer whose system is set to dark mode, When they open a spec page, Then all chrome surfaces, text, and borders show the dark token values, and no light-mode chrome color shows.

Given a spec reviewer on a desktop screen with a spec served with a compared range, When they open the spec page, Then the page’s top line reads the back link, the compared range, and Change base on the page color with a hairline under it and no tinted box, the document header shows the spec’s title with no box or rule around it, and the document, top line, and toolbar share one background.

Given a spec reviewer on a phone with a spec served with a compared range, When they open the spec page, Then the first screen shows the top line, the spec’s title, and the start of its first section, on one background, without horizontal scrolling.

Given a spec reviewer whose system is set to dark appearance, with a spec that uses the shared stylesheet holding a table and a figure, When they open the spec page, Then the document and its chrome both show light text on one dark page, and the table and figure read clearly on it.

Given a spec reviewer on a desktop screen on a spec page, When they point at the toolbar’s Comment button, which needs a pointer that can hover, then wait for its tooltip, Then the tooltip names the C key, and the button itself reads only Comment.

Given a spec reviewer on a phone on a spec page, When they open it, Then every toolbar button reads its name alone, Comment and Reading view among them, with no key in any label.

Given a spec reviewer on a desktop screen on a spec page with threads, When they open the review panel, then press a thread's first message, Then the panel toggle, the gear, and the focused thread's Back are line icons of one size and stroke weight.

Given a spec reviewer on a desktop screen on a spec page with threads, When they open the review panel, Then every receipt in the conversation reads in sentence case.

Given a spec reviewer on a desktop screen on a spec page with threads, When they open the spec page with its review panel closed, Then the thread dock shows a thin line icon, drawn as an outline, not a filled glyph or a text character.

Given a spec reviewer at a keyboard on a spec page whose threads are all resolved, When they press Tab until Accept spec has focus, Then Accept spec shows the design set’s focus ring.

Given a spec reviewer on a desktop with a spec page under review, needs an induced failure: the same error on every refresh, When they open the spec, then wait 6 seconds, Then the error overlay under the top line shows that error once, with a count of the times it came.

Given a spec reviewer on a phone with a spec page under review, needs an induced failure: an error as the page opens, When they open the spec, Then the error overlay shows under the top line, and the bottom toolbar shows its Hand off control in full.

Onboarding: not needed, the chrome’s design adds no user surface of its own. CI: the CI rule covers the runtime style tests; they use no provider. One hand-off control for desktop and phone: kept, the chrome draws the review panel’s one hand-off control on both, and the error overlay never covers it (phone rule, desktop rule). Never strip proof clauses or rewrite unedited criteria: kept, each criterion here keeps its proof clause word for word, as the token block criterion does (shaping rule, repair rule). Threads read as one conversation: kept, the panel’s surface rule draws the conversation (thread panel, rule). Every mockup at production fidelity: kept, its mockups are drawn from the runtime’s chrome and the design set’s tokens: their screens are review chrome a mockup page shows, and the page that frames a prototype cannot frame itself (drawn mockup, rule).

03

Modular boundaries

Self-contained chrome styling.

The chrome styles in runtime.js own all spec page chrome styling: layout, color, typography, and responsive rules for the annotation overlay (toolbar, panel, dock, pins, pills, popovers, toasts, banners, badges, error overlay, range bar, index link, Screens index, Jev notes, orphan hints, composer, settings). The caller-facing seam is the chrome the runtime draws on every spec page, in the design set’s token names, and the appearance a host passes to the frame as its preferred color scheme (dark mode); the top line holds the range bar and the index link in one line. External package, pinned: the shared design set at the version Spec Chat pins, built into runtime.js, the review index, and the shared spec stylesheet; nothing is fetched at run time and no peer is named. Observable scope: every chrome element on a spec page uses the unified token set, and the shared spec stylesheet sets the document's look from the same set (the document).

04

Design

One token block, one button system, one color per meaning.

Token block

The spec page chrome styles in runtime.js open with the shared design set’s stylesheet at the version Spec Chat pins, then one :root block holding only the additions in the table below. Every chrome rule uses only these variables. No literal color, font size, weight, spacing, or radius value appears in a chrome rule. The spec document's own content styling (the runtime’s article.spec rules and spec.css) keeps its own --spec-* names, each set from the design set as the document states.

Button system

Every chrome button is one of four variants. The button system consumes tokens from the token block; it does not redefine them. Badges and pills are not buttons and use their own radius (--ui-radius-pill). All buttons share: font-family: var(--ui-font), font-size: var(--ui-text-xs) (12px), font-weight: 600, border-radius: var(--ui-radius-sm) (6px), min-height: 32px desktop / 44px mobile, padding: var(--ui-space-2) var(--ui-space-3) (8px 12px). Focus: outline: 2px solid var(--ui-focus); outline-offset: 2px.

Placement rule: a bar, panel footer, or popover action row puts the primary action rightmost and a cancel or secondary action left of it. Each state shows one primary action: while a composer is open, its send is the primary and Hand off shows as secondary. A single primary action fills available width on mobile. Icon buttons are always square (var(--ui-space-6) desktop, 44px mobile).

Typography

Chrome text uses only the design set’s type steps. var(--ui-text-xs) 12px: pills, badges, captions, toolbar status, note meta, popover text, dock threads, Jev note. var(--ui-text-sm) 14px: panel body, thread messages, composer textarea, range bar text. var(--ui-text-md) 16px: mobile composer textarea (iOS zoom prevention). var(--ui-text-lg) 20px: panel toggle glyph. Weights: the set’s three, 400 body, 500 row titles, 600 emphasis and buttons, never 700 or 750. Status pills and badges read in sentence case, never capitals.

Spacing and geometry

Chrome spacing uses only the design set’s spacing scale: 4, 8, 12, 16, 24, 32px. Border radii: var(--ui-radius) 8px for containers (panel, toolbar, dock, popover, toast), var(--ui-radius-sm) 6px for buttons and inputs, var(--ui-radius-pill) 999px for pills and badges. Pin border-radius keeps its teardrop shape.

Shared design set

Every value the chrome, the review index, and the document use comes from one shared design set: a small package Spec Chat builds in at the version it pins, never fetched from a peer at run time, so a page served without any other tool looks complete. It carries the --ui-* colors in light and dark, one accent for action, focus, links, and acknowledged, the type steps from 12px to a 30px display step, three weights, spaces, radii, motion, the five status marks, the line icons, and the Find field the review index filters by. A new value reaches Spec Chat only with a new pin.

One surface

Top line: one fixed line across the top of the page, on the page color with a hairline under it: at its start the back link, a chevron and “Review index”; then the compared range as muted meta, worded as the compared range states it; at its end Change base as a text button. The page has no floating index button and no tinted range box.

The document, the top line, the toolbar, and the review panel share the page color and ink; the toolbar and an open popover alone lift on the set’s shadow. The panel is the same page color, separated by a hairline.

The document

The shared spec stylesheet, the one Spec Chat bundles for spec content, sets every --spec-* value from the design set, in light and dark: the page paper is the set’s page color; the header is unboxed, its title at the display step, its breadcrumb meta, its lede one step over body; section headings sit at the heading step under a hairline; body text reads at 15px with a reading line length; tables and figures use hairlines and the soft surface, never heavy rules. A repository takes a new stylesheet by replacing its copy, as it took the first.

Keys and icons

No button label carries a key: Comment reads Comment, and its tooltip and any menu item name C beside it; on a phone neither tooltip nor label shows a key.

Every chrome icon, the panel toggle, gear, dock, thread, and disclosure, is the design set’s line icon at one size and stroke weight, the same icons Proof shows.

The error overlay lists the errors the page meets, one line per distinct error: an error that comes again stays on its line, which counts its times, as in rejection: TypeError: loadedEvents().concat is not a function (×12), so an error on a timer never grows it. It sits at the top of the page, under the top line when the page shows one, on every width, so the toolbar, the hand-off control, and a phone’s bottom sheet stay in view; it is at most a fifth of the screen tall, its lines scrolling within it.
