Spec page design

The spec page chrome uses the Spec Chat index design values: one button system, one color palette, consistent placement. The spec document's own content styling is outside this design.

Scope
runtime.js CSS const blocks (CSS, DOC_CSS dark mode chrome only)
Tokens
Index token block
01

User stories

One reviewer, one page, consistent chrome.

As a spec reviewer, I see one coherent visual system across every button, pill, pin, panel, popover, toolbar, and bar on a spec page, so I never wonder whether two differently styled controls do the same thing.

As a contributor editing runtime.js, every chrome color, font size, weight, radius, and spacing value is a named token from one block, so I never invent an ad hoc value or guess which grey to use.

02

Acceptance criteria

Given a contributor editing runtime.js, When they look up a chrome color, font size, weight, radius, or spacing value, Then they find it as a named token in the one token block, which holds the index tokens plus the token additions, and every chrome style uses those tokens, with literal values only for the pin teardrop radius, stacking order, transitions, animations, and positions, proven by a unit test: no screen shows it.

Given a spec reviewer on a spec page, When they view it at desktop and at phone width, Then every chrome button matches one of the four button variants (primary, secondary, icon, text-link) with its shared properties, and no button has a shape, size, radius, font, or color outside the system.

Given a spec reviewer on a spec page with draft, acknowledged, and resolved threads, a fixture that must be added to provide it, When they view it at desktop width, Then every pin, pill, dock thread, and thread card border for the same status shows the same color on the same soft background, and no two statuses share a color.

Given a spec reviewer on a spec with Jev markers at important, neutral, and passed levels, When they view the markers, Then the markers show the important, neutral, and passed colors of the marker tokens, each in its level's marker shape and size.

Given a spec reviewer on a spec with a Jev marker whose notes are all Warning level, a fixture that must be added to provide it, When they view the marker, Then it shows as a light red dot in the warning marker color, distinct from the important, neutral, and passed markers.

Given a spec reviewer on a spec page, When they read every chrome text and control, Then normal text meets 4.5:1 contrast and meaningful non-text boundaries (status pill borders, active thread borders, pin outlines) meet 3:1.

Given a spec reviewer on a spec that uses the shared stylesheet, When they view it at desktop and at phone width, Then the spec content (headings, prose, tables, figures, code blocks, section borders, page background) takes its look from the shared stylesheet and the runtime's document rules alone, and no chrome token restyles it.

Given a spec reviewer whose system is set to dark mode, When they open a spec page, Then all chrome surfaces, text, and borders show the dark token values, and no light-mode chrome color shows.

Onboarding: not needed, the design pass restyles existing chrome with no new user surface. CI: the CI rule covers the runtime style tests; they use no provider.

03

Modular boundaries

Self-contained chrome styling.

The CSS const strings in runtime.js own all spec page chrome styling: layout, color, typography, and responsive rules for the annotation overlay (toolbar, panel, dock, pins, pills, popovers, toasts, banners, badges, error overlay, range bar, index link, Jev notes, orphan hints, composer, settings). The caller-facing seam is the set of CSS class names and data attributes already used in mountUI() and render functions. No class name changes; the same selectors get new property values from tokens. Self-contained: no new external dependency. The token block is a CSS custom property declaration within the same file. Observable scope: every chrome element on a spec page uses the unified token set. The spec document's own content styling is outside this boundary.

04

Design

One token block, one button system, one color per meaning.

Token block

The spec page chrome CSS const (the CSS string in runtime.js) opens with one :root block headed /* ui tokens */, holding exactly the index tokens plus the additions in the table below. Every chrome rule uses only these variables. No literal color, font size, weight, spacing, or radius value appears in a chrome rule. The spec document's own content styling (DOC_CSS article.spec rules and spec.css) keeps its own --spec-* tokens and is outside this design.

Button system

Every chrome button is one of four variants. The button system consumes tokens from the token block; it does not redefine them. Badges and pills are not buttons and use their own radius (--ui-radius-pill). All buttons share: font-family: var(--ui-font), font-size: var(--ui-text-xs) (12px), font-weight: 600, border-radius: var(--ui-radius-sm) (6px), min-height: 32px desktop / 44px mobile, padding: var(--ui-space-2) var(--ui-space-3) (8px 12px). Focus: outline: 2px solid var(--ui-focus); outline-offset: 2px.

Typography

Chrome text uses only the index type scale. var(--ui-text-xs) 12px: pills, badges, captions, toolbar status, note meta, popover text, dock threads. var(--ui-text-sm) 14px: panel body, thread messages, composer textarea, range bar text, Jev note. var(--ui-text-md) 16px: mobile composer textarea (iOS zoom prevention). var(--ui-text-lg) 20px: panel toggle glyph. Weights: 400 body, 600 emphasis and buttons, never 700 or 750.

Spacing and geometry

Chrome spacing uses only the index spacing scale: 4, 8, 12, 16, 24, 32px. Border radii: var(--ui-radius) 8px for containers (panel, toolbar, dock, popover, toast), var(--ui-radius-sm) 6px for buttons and inputs, var(--ui-radius-pill) 999px for pills and badges. Pin border-radius keeps its teardrop shape.
