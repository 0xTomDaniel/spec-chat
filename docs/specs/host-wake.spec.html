Review host wakes the owner pane

docs / specs / host-wake.spec.html

Replaces the per-lane external monitor in Review wake ownership. The one long-lived review host already knows each resource's owner pane from its registry, so it wakes that pane itself, only through the registered wake provider (Providers).

User stories

As a human reviewer, when I hand off a batch, the owning agent wakes without anyone having started a monitor for that lane.

As a human reviewer, when the owner pane is gone, the page tells me wake failed so I resume by chat instead of waiting.

As a lane owner, registering my spec with my pane id is the whole wake setup; I may end my turn and the next hand-off prompts my pane.

As a human reviewer on a host without a wake provider, review works as before and the page keeps its existing timeout message.

Acceptance criteria

Given a lane owner whose spec is registered with an idle owner pane and a wake provider, on a fixture that must be added to provide them. When a human reviewer completes a hand-off. Then the host runs the wake provider's send for that owner pane exactly once for that batch, within a few seconds, and never again while the batch is unchanged.

Given a lane owner already woken for one batch, on a fixture that must be added to provide it. When a human reviewer completes a later hand-off with new events. Then the host wakes the owner once for the new batch.

Given a human reviewer's completed hand-off, needs an induced failure: the wake provider's send exits 75 because the owner is working. When the host polls. Then the host sends nothing now and retries on each poll until one delivery succeeds.

Given a human reviewer's completed hand-off, needs an induced failure: the wake provider's check fails for the owner pane. When the host polls. Then the page shows wake failed; send a new chat message to resume, and the host keeps retrying so a re-registered owner is woken.

Given a lane owner on a service state with no valid providers/wake.toml. When the lane owner registers a spec. Then the host sends nothing on hand-off, register prints wake=unavailable, and the page keeps the existing timeout message.

Given a lane owner with a wake provider. When review-host register succeeds. Then it prints wake=verified owner=<pane> only when the wake provider's check exits 0 for that owner pane, and wake=unavailable owner=<pane> otherwise; registration never fails on wake.

Given a lane owner reading the review skill. When they list its scripts and instructions. Then review-control.sh external, the per-lane wake adapter script, the adapter environment contract, and the monitor instructions no longer exist; yielded and manual are unchanged.

Onboarding: not needed, wake status extends the review page with no new user surface.

Modular boundaries

The review host owns detecting a complete hand-off batch per registered resource and waking that row's owner once per batch. Caller-facing seam: registry rows (owner, cursor_name, spec) in, one wake provider send per batch out, and the wake state on /api/events. Dependency direction: external-provider; the host runs the registered provider's commands anonymously, by slot name, and never names the provider. Observable scope: delivered prompts, register output, and the page wake message.

The woken owner owns everything after wake: zero-wait scan, batch transaction, replies, and cursor advance. Caller-facing seam: the wake prompt text and the existing spool and cursor files. Dependency direction: self-contained; the host never reads comments, edits specs, writes the spool, or advances cursors. Observable scope: agent replies and cursor contents.

Wake rule

The host polls every registered resource's spool every 3 seconds, in one background thread of the running review server.

A batch is the resource's handed-off events not in its cursor: each hand-off not in the cursor and the events it lists (Shared review state), exactly as the zero-wait scan reports it. Its identity is that list of file names.

Delivered batch identities live only in memory. After a host restart, a still-unprocessed batch is woken once more; a duplicate wake is harmless because the owner starts with a zero-wait scan.

The prompt names the spec path, collection root, cursor name, and event count, and tells the owner to run the zero-wait scan, process the batch, and park.

Control states

The external-wake state becomes host-wake: the resource is registered with the owner's pane id and register printed wake=verified. A final response is allowed.

Turn-yielded and manual-resume are unchanged. A registration that printed wake=unavailable selects manual-resume.

The row's owner is the lane record owner pane id, never an agent or tab name.
