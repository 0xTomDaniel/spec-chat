Review host wakes the owner pane

docs / specs / host-wake.spec.html

Owns the host-wake state of Review wake ownership. The one long-lived review host knows each resource's owner pane from its registry, so it wakes that pane itself, only through the registered wake provider (Providers).

User stories

As a human reviewer, when I hand off a batch, the owning agent wakes without anyone having started a monitor for that lane.

As a human reviewer, when the owner pane is gone, the page tells me wake failed so I resume by chat instead of waiting.

As a lane owner, registering my spec with my pane id is the whole wake setup; I may end my turn and the next hand-off prompts my pane.

As a human reviewer on a host without a wake provider, review works without wake and the page shows the waiting-for-agent timeout message.

Acceptance criteria

Given a lane owner whose spec is registered with their idle pane on a box with a wake provider, a fixture that must be added to provide it, When a human reviewer completes a hand-off, Then the owner's pane receives one wake prompt for that batch within a few seconds, and no second prompt while the batch is unchanged.

Given a lane owner already woken for one batch, a fixture that must be added to provide it, When a human reviewer completes a later hand-off with new comments, Then the owner's pane receives one wake prompt for the new batch.

Given a human reviewer's completed hand-off whose owner pane is busy working, needs an induced failure: the wake provider reports the owner busy, When the host polls, Then the owner's pane receives no prompt while busy and receives exactly one wake prompt once delivery succeeds on a later poll.

Given a human reviewer's completed hand-off whose owner pane is gone, needs an induced failure: the wake provider cannot find the owner pane, When the host polls, Then the page shows wake failed; send a new chat message to resume.

Given a hand-off whose page shows wake failed, needs an induced failure: the wake provider cannot find the owner pane, When the lane owner re-registers the spec with a live pane, Then that pane receives the wake prompt for the waiting batch.

Given a lane owner on a box with no wake provider plugged in, When the lane owner registers a spec and a human reviewer then completes a hand-off, Then the registration reports wake as unavailable, no pane receives a wake prompt, and the page shows the waiting-for-agent timeout message.

Given a lane owner on a box whose wake provider finds their pane, a fixture that must be added to provide it, When the lane owner registers a spec with their pane, Then registration succeeds and reports wake as verified for that pane.

Given a lane owner on a box whose wake provider cannot find the pane they name, a fixture that must be added to provide it, When the lane owner registers a spec with that pane, Then registration still succeeds and reports wake as unavailable for that pane.

Given a lane owner reading the review skill, When they look up how to be woken for review, Then the skill names registering with their pane as the whole wake setup, beside the turn-yielded and manual-resume modes, and offers no external wake mode, per-lane wake adapter, adapter environment, or monitor to start.

Onboarding: not needed, wake status extends the review page with no new user surface. CI: the CI rule covers wake; its contract test is the wake provider: file present, capability appears; file absent, capability quietly absent.

Modular boundaries

The review host owns detecting a complete hand-off batch per registered resource and waking that row's owner once per batch. Caller-facing seam: registry rows (owner, cursor_name, spec) in, one wake provider send per batch out, and the wake state on /api/events. Dependency direction: external-provider; the host runs the registered provider's commands anonymously, by slot name, and never names the provider. Observable scope: delivered prompts, register output, and the page wake message.

The woken owner owns everything after wake: zero-wait scan, batch transaction, replies, and cursor advance. Caller-facing seam: the wake prompt text and the existing spool and cursor files. Dependency direction: self-contained; the host never reads comments, edits specs, writes the spool, or advances cursors. Observable scope: agent replies and cursor contents.

Wake rule

The host polls every registered resource's spool every 3 seconds, in one background thread of the running review server.

A batch is the resource's handed-off events not in its cursor: each hand-off not in the cursor and the events it lists (Shared review state), exactly as the zero-wait scan reports it. Its identity is that list of file names.

Delivered batch identities live only in memory. After a host restart, a still-unprocessed batch is woken once more; a duplicate wake is harmless because the owner starts with a zero-wait scan.

The prompt names the spec path, collection root, cursor name, and event count, and tells the owner to run the zero-wait scan, process the batch, and park.

Control states

Host-wake: the resource is registered with the owner's pane id and register printed wake=verified. A final response is allowed.

Turn-yielded and manual-resume are unchanged. A registration that printed wake=unavailable selects manual-resume.

The row's owner is the lane record owner pane id, never an agent or tab name.
