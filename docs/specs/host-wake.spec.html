Review host wakes the owner pane

docs / specs / host-wake.spec.html

Owns the host-wake state of Review wake ownership. Each Herdr session's one long-lived review host knows each resource's owner pane from its registry, a pane of its own session, so it wakes that pane itself, only through the registered wake provider (Providers).

User stories

As a human reviewer, when I hand off a batch, the owning agent wakes without anyone having started a monitor for that lane.

As a human reviewer, when the host cannot wake the owner pane, the page tells me wake failed and why, so I resume by chat instead of waiting.

As a human reviewer, a wake that fails is retried, so the page asks me for a chat message only once retries keep failing, and a wake that lands later needs nothing from me.

As a lane owner, registering my spec with my pane id is the whole wake setup; registration reports wake verified only when the review service itself reaches my pane, so I may end my turn and the next hand-off prompts my pane.

As a box operator, the review service's log holds every wake send and every failed check with its exit code and the wake provider's error output, so I can find why a wake failed.

As a human reviewer on a host without a wake provider, review works without wake and the page shows the waiting-for-agent timeout message.

Acceptance criteria

Given a lane owner whose spec is registered with their idle pane on a box with a wake provider, a fixture that must be added to provide it, When a human reviewer completes a hand-off, Then the owner's pane receives one wake prompt for that batch within a few seconds, and no second prompt while the batch is unchanged, proven by a unit test: no screen shows it.

Given a lane owner whose spec is registered with their idle pane on a box with a wake provider, a fixture that must be added to provide it, When a human reviewer completes a hand-off, the owner is woken for that batch, and the reviewer then completes a later hand-off with new comments, Then the owner's pane receives one wake prompt for the new batch, proven by a unit test: no screen shows it.

Given a lane owner whose registered pane is busy working, needs an induced failure: the wake provider reports the owner busy, When a human reviewer completes a hand-off and the host polls, Then the owner's pane receives no prompt while busy and receives exactly one wake prompt once delivery succeeds on a later poll, proven by a unit test: no screen shows it.

Given a human reviewer on a registered spec whose owner pane is gone, needs an induced failure: the wake provider cannot find the owner pane and says why in its error output, When the reviewer completes a hand-off, then waits while the host retries the wake, Then the page shows wake failed, the reason the wake provider gave, and send a new chat message to resume.

Given a human reviewer on a registered spec whose owner pane is gone, needs an induced failure: the wake provider cannot find the owner pane and writes no error output, When the reviewer completes a hand-off, then waits while the host retries the wake, Then the page shows wake failed, that the owner pane was not found with the check's exit code, and send a new chat message to resume.

Given a human reviewer on a registered spec whose owner's first wake attempt fails, needs an induced failure: the first wake attempt fails, When the reviewer completes a hand-off, Then the page shows handed off, waiting for agent, not wake failed.

Given a lane owner whose registered idle pane the wake provider fails to reach on the first attempt, needs an induced failure: the first wake attempt fails, When a human reviewer completes a hand-off, Then the owner's pane receives one wake prompt for that batch from a later attempt, proven by a unit test: no screen shows it.

Given a lane owner whose registered pane the wake provider cannot reach until it recovers, needs an induced failure: the wake provider fails for longer than the host's retries, then recovers, When a human reviewer completes a hand-off, Then the owner's pane receives one wake prompt for that batch once the provider recovers, proven by a unit test: no screen shows it.

Given a lane owner whose registered spec's owner pane is gone, needs an induced failure: the wake provider cannot find the owner pane, When a human reviewer completes a hand-off, the page shows wake failed, and the lane owner re-registers the spec with a live pane, Then that pane receives the wake prompt for the waiting batch, proven by a unit test: no screen shows it.

Given a lane owner on a box with no wake provider plugged in, When the lane owner registers a spec and a human reviewer then completes a hand-off, Then the page shows the waiting-for-agent timeout message.

Given a lane owner on a box with no wake provider plugged in, When the lane owner registers a spec and a human reviewer then completes a hand-off, Then the registration reports wake as unavailable and no pane receives a wake prompt, proven by a unit test: no screen shows it.

Given a lane owner on a box whose wake provider finds their pane, a fixture that must be added to provide it, When the lane owner registers a spec with their pane, Then registration succeeds and reports wake as verified for that pane, proven by a unit test: no screen shows it.

Given a lane owner on a box whose wake provider cannot find the pane they name, a fixture that must be added to provide it, When the lane owner registers a spec with that pane, Then registration still succeeds and reports wake as unavailable for that pane, proven by a unit test: no screen shows it.

Given a lane owner on a box whose wake provider finds their pane from the lane owner's own shell but not from the review service, needs an induced failure: the wake provider's check fails only in the review service's environment, When the lane owner registers a spec with their pane, Then registration reports wake as unavailable for that pane, proven by a unit test: no screen shows it.

Given a box operator on a box whose wake provider reaches the owner pane, a fixture that must be added to provide it, When a human reviewer completes a hand-off, Then the review service's log holds one line for that wake send naming the spec, the owner, and the exit code, proven by a unit test: no screen shows it.

Given a box operator on a box whose wake provider fails to send, needs an induced failure: the wake send exits with an error and writes error output, When a human reviewer completes a hand-off, Then the review service's log holds a line for each failed send naming the spec, the owner, the exit code, and the provider's error output, proven by a unit test: no screen shows it.

Given a box operator on a box whose wake provider cannot find the owner pane, needs an induced failure: the wake check exits with an error, When a human reviewer completes a hand-off, Then the review service's log holds a line for each failed check naming the spec, the owner, the exit code, and any error output the provider wrote, proven by a unit test: no screen shows it.

Given a lane owner reading the review skill, When they look up how to be woken for review, Then the skill names registering with their pane as the whole wake setup, beside the turn-yielded and manual-resume modes, and offers no external wake mode, per-lane wake adapter, adapter environment, or monitor to start, proven by a unit test: no screen shows it.

Onboarding: not needed, wake status extends the review page with no new user surface. CI: the CI rule covers wake; its contract test is the wake provider: file present, capability appears; file absent, capability quietly absent.

Modular boundaries

The review host owns detecting a complete hand-off batch per registered resource and waking that row's owner once per batch. Caller-facing seam: registry rows (owner, cursor_name, spec) in, one delivered wake provider send per batch out, retried while it fails, the wake state and its reason on /api/events, and one service log line per send and failed check. Dependency direction: external-provider; the host runs the registered provider's commands anonymously, by slot name, and never names the provider. Observable scope: delivered prompts, register output, the page wake message, and the service log.

The woken owner owns everything after wake: zero-wait scan, batch transaction, replies, and cursor advance. Caller-facing seam: the wake prompt text and the existing spool and cursor files. Dependency direction: self-contained; the host never reads comments, edits specs, writes the spool, or advances cursors. Observable scope: agent replies and cursor contents.

Wake rule

The host polls every registered resource's spool every 3 seconds, in one background thread of the running review server.

A batch is the resource's handed-off events not in its cursor: each hand-off not in the cursor and the events it lists (Shared review state), exactly as the zero-wait scan reports it. Its identity is that list of file names.

Delivered batch identities live only in memory. After a host restart, a still-unprocessed batch is woken once more; a duplicate wake is harmless because the owner starts with a zero-wait scan.

The prompt names the spec path, collection root, cursor name, and event count, and tells the owner to run the zero-wait scan, process the batch, and park.

A failed attempt is retried at each poll while its batch waits. The state turns failed only after a few attempts in a row have failed; until then it is retrying. A later attempt that sends returns it to sent, so a wake that lands after the page showed wake failed needs nothing from the reviewer.

A failed state carries the reason from its latest attempt: the last line of the wake provider's error output; with none, owner pane not found for a check or send failed for a send, with its exit code; or that the command could not start or timed out.

Every send, and every check that does not exit 0, writes one line to the service log naming the spec, owner, step, exit code, and the wake provider's error output. A send deferred again for the same batch writes no second line.

register runs the wake provider's check in the running service's environment, the one its wake attempts run in, whatever started the service, so wake=verified means the service itself reaches the pane.

Control states

Host-wake: the resource is registered with the owner's pane id and register printed wake=verified. A final response is allowed.

Turn-yielded and manual-resume are unchanged. A registration that printed wake=unavailable selects manual-resume.

The row's owner is the lane record owner pane id, never an agent or tab name, registered from the owner's own session.
