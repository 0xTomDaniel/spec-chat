Git-derived focus

docs / specs / git-focus.spec.html

Every HTTP-served spec highlights what its branch changed against a base, derived from Git alone; Compared commit range extends it.

User stories

As a reviewer, I want additions to remain clear while existing context recedes so the canonical spec itself explains the current issue-scoped change.

Acceptance criteria

Given a reviewer on a spec that adds and changes blocks against its base, When the reviewer opens it with focus against that base, Then every outermost added or modified block is clear with a visible focus boundary and every unchanged block recedes.

Given a reviewer on a desktop on a spec that adds and changes blocks against its base, When the reviewer opens it with focus against that base, then opens Display settings, then sets Diff visibility to 0%, then reloads the page, then opens Display settings again, Then Diff visibility reads 0%, and every block, unchanged ones included, reads at normal clarity.

Given a reviewer on a spec absent from its base, When the reviewer opens it with focus against that base, Then the whole spec is clear and no block recedes.

Given a reviewer on a spec whose Git comparison cannot be calculated, which needs an induced failure: Git comparison, When the reviewer opens it with focus, Then focus mode shows its failure visibly and the complete current spec renders without stale highlighting.

Onboarding: not needed, focus extends the review page with no new user surface. CI: the focus tests run in CI with no other tool of the box installed and no provider file (CI rule). One hand-off control for desktop and phone: not affected, focus adds no hand-off control (phone rule, desktop rule). Never strip proof clauses or rewrite unedited criteria: not affected, no criterion here carries a proof clause (shaping rule, repair rule). Any origin only without login or cookie: kept, focus reads the review service’s baseline and adds no login and no cookie (rule). Every mockup at production fidelity: kept, the focus view’s mockup is drawn from the runtime’s chrome and design set tokens: its screen is review chrome a mockup page shows, and the page that frames a prototype cannot frame itself (drawn mockup, rule).

Modular boundaries

The browser runtime owns classifying current anchored blocks against the base and drawing focus. Caller-facing seam: GET /api/baseline base, htmlBase, html. Dependency direction: self-contained; the server reads local Git only. Observable scope: clear blocks with a focus boundary, receded blocks, the failure notice.

Git-derived focus is the diff viewer

The highlighted current spec is the complete required human diff-review surface.

Every current block added or modified by the work branch remains fully clear.

The runtime marks each outermost added or modified block with an unmistakable focus boundary that remains visible across custom spec styles without outlining every changed descendant.

Every unchanged current block recedes visually so the issue-scoped additions hold attention.

A new spec is entirely clear.

A spec with no change against its compared base renders the whole current document at normal clarity; from any entry, a spec with changes shows them highlighted, as compared range states.

Focus is derived from Git and never maintained through embedded issue metadata, sidecars, anchor lists, or hand-authored change markers.

The shaping skill commits every accepted spec change locally before presenting the refreshed focus view, so the Git-derived review state remains durable and reproducible.

Prompt-first shaping uses the existing HTTP review transport on desktop and mobile because a browser file page cannot inspect Git.

The review server reads only the current local repository and never fetches, checks out, stages, commits, or writes Git state.

No focus behavior imports, invokes, expects, or mentions an orchestrator.

An explicit review base resolves to the exact selected local commit, including a previously reviewed sibling branch, while automatic discovery alone uses a merge base.

The baseline response retains the selected commit in base; a file absent from the selected base is entirely new and returns null for both htmlBase and html.

If Git comparison cannot be calculated, focus mode fails visibly and renders the complete current spec without stale highlighting.

A removed behavior must be expressed by the resulting current rule or constraint, because a silent deletion with no current replacement cannot be reviewed in the current-spec highlighting model.

Focus requires no side-by-side viewer, removed-content tray, deletion ghost, or pull-request review.

The contract leaves room for optional richer in-spec diff views when real use justifies them.

Mobile review

Issue focus and receded context remain legible and operable on narrow screens without shifting the spec sideways.

Implementation and proof contract

A runtime test proves the runtime classifies current anchored blocks against a Git baseline and renders focus solely from that classification.

A regression requests both the ref and commit of a sibling snapshot and verifies exact baseline bytes; source-verifier tests cover substituted baselines, wrong served pages, absent-at-base new specs, and uncommitted new files.

The focus test passes for added, modified, unchanged, new-file, normal-view, and unavailable-baseline cases.

The runtime test proves only outermost changed blocks receive the explicit focus boundary and that the focus capability migrates stale repository copies.

Non-goals

Git-derived focus does not require humans to inspect GitHub or another change-request UI to understand the spec change.
