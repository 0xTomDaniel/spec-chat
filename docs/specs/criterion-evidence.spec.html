Evidence per criterion

docs / specs / criterion-evidence.spec.html

Each acceptance criterion on the spec page shows what its newest evidence proves about the text being read. The evidence read is owned by the evidence provider, the service named in the evidence provider file (Providers); Spec Chat holds no provider code and only renders the answer.

In spec-driven development behavior changes only with a spec change, so a text-matched QA passed is proof of what the spec promises now, and QA stale on an unchanged-looking spec exposes unspecced behavior change.

User stories

As a reviewer, each acceptance criterion tells me whether its newest evidence proves the text I am reading, so I know what is actually proven.

As a reviewer, one click on the evidence label in a criterion's marker popover opens its evidence, and a small link opens the whole bundle.

As a reviewer on a lane worktree or on main, evidence notes judge the text of the tree I am viewing.

As a reviewer, a QA stale or reworded criterion shows me what changed between the proven text and the text I am reading, so I judge the gap without opening anything.

As a reviewer, a QA stale criterion offers one button that drafts a re-proof request, and several offer one button that drafts one request for them all; the request reaches the spec's owner, who acts on it, and once new evidence lands it replaces QA stale.

As a reviewer inside the BB plugin, evidence links open in the plugin's Proof page instead of a browser.

As a reviewer inside a host that offers tabs, a new-tab click on a link to another Spec Chat page, on a spec page or the review index, opens it in the host's own tab instead of a browser, while plain clicks and links to other sites keep the browser's own behavior.

As a reviewer, when a spec page reloads, including after I go to Proof and back with Spec alone in BB, it returns me to where I was reading.

As a reviewer, when the evidence service is down or not configured, the page works with no evidence notes and no error.

Modular boundaries

The review server owns one evidence read per page: it names the spec and the tree being viewed, marks uncommitted criteria, and makes links absolute. Caller-facing seam: GET /api/evidence?path=<spec>, returning one entry per criterion anchor, or none, plus the levels table as levels. Dependency direction: calls the evidence service as an external provider over HTTP; reads local Git and served specs; imports no provider code. Observable scope: the JSON response, in single-root and registry modes.

The browser runtime owns each evidence note's label, context, and links inside the marker popover that jev-suggestions defines. Caller-facing seam: the rendered evidence notes. Dependency direction: self-contained within Spec Chat; consumes the server route; holds no matching, Jev, or Git logic. Observable scope: what the reviewer sees.

A framing host, such as a BB plugin, owns what it opens on an open request or a tab request; Spec Chat owns only the bridge messages and which of its own link clicks are new-tab clicks. Caller-facing seam: the plugin bridge messages. Dependency direction: external; the host frames Spec Chat and answers its requests; Spec Chat imports no host code and works unframed. Observable scope: the page the host opens.

The evidence provider owns which evidence is picked, text matching, the Jev judgment, and on main. Caller-facing seam: GET /criteria?spec=project/<project-id>::<spec path>&commit=<viewed commit>, returning criteria keyed by anchor, each with match, verdict, judgment, PR, capture time, on main, artifact, bundle, proven text, and view link (One read per page). Dependency direction: external provider; it never calls Spec Chat. Observable scope: its JSON response.

Evidence note

Every data-acceptance-criterion on an HTTP-served spec gets an evidence note, listed first in its marker popover, once evidence loads; a criterion with no other note gets a marker for it.

An evidence note is a state label in words, a muted context line, and a small bundle link.

The criterion's marker follows its evidence: QA passed and QA passed · reworded show a small green check, since it passed and only wording changed, QA failed, QA failed · reworded, and QA stale the colored ! (Important, since it failed), and No QA yet stays the quiet grey dot. Check and ! are glyph shapes, so state never rests on color alone, and each mark meets 3:1 against the page in light and dark themes. Precedence across a marker's notes is in markers.

Matching text, passedNot askedQA passed
Matching text, failedNot askedQA failed

Newest, text differs, or criterion edited but uncommittedmaterial, unsure, off, or unavailableQA stale

Every evidence label names QA, so it never reads as a Jev note in the same popover; labels stay one short line with no added box, rule, or heading.

Every label but No QA yet has context #<PR> · <age>, plus not on main when so; the label opens the bundle page at that criterion with its artifact open, through the view link /criteria returns, and bundle opens the bundle page at its top. No QA yet has neither.

Age is the capture time relative to now: minutes, hours, or days, as 5 m, 3 h, 2 d.

A picked evidence with no valid artifact still links its label; the bundle page then lands on the criterion with nothing opened.

A QA stale or reworded note adds one inline diff line: the proven text from the evidence against the criterion text as read, word by word, removed words on a light red tinted background and added words on a light green tinted background (design tokens --ui-fail-soft and --ui-pass-soft), each with 4.5:1 text contrast in light and dark themes, no underline or strikethrough. Where a diff appears, a tiny removed / added legend precedes the diff line. The diff wraps inside the popover and never widens the page.

Evidence notes never change a spec, the spool, a thread, or spec acceptance eligibility, and never hide or reorder content.

Ask for re-proof

Only a QA stale note gets a note button, Ask for re-proof; it opens the comment composer at the criterion and writes nothing until the reviewer sends.

Draft text, fixed: <criterion anchor> changed since its evidence (#<PR>, <capture date>): please recapture it.

With two or more QA stale notes on the page, each also gets Re-proof all stale (n), a batch action. Its draft, fixed: Re-proof each criterion, changed since its evidence: then one line per stale criterion in page order, <criterion anchor> (#<PR>, <capture date>). Sent, it is one request, so the owner runs one recapture for them all.

QA stale is Jev's guess that the text changed materially; once evidence of the current text lands, the next read shows that evidence's label and the stale note, its diff, and its buttons are gone.

A sent request is an ordinary comment: the hand-off wakes the host row's owner through host wake, and that owner runs a narrow Jev recapture of that criterion.

A spec on main, outside any lane, is registered with the operator as owner, so its request reaches the operator, who starts a small re-proof lane.

Every hosted spec has an owner, as the lane command requires. A lane spec's owner is the lane owner; a main spec's is the operator. So a request always reaches someone, and the page shows no watcher state.

Opening in the plugin

StepFromMessage
1Plugin, to the framed page on load{type: "spec-chat-host", opens: ["evidence"]}
2Page, to that sender's origin on a label or bundle click{type: "spec-chat-open-evidence", bundle, criterion}; criterion only for the label
3PluginOpens its Proof page on that bundle, and that criterion when given, through toPluginPanel
4Page, to that sender's origin, on a hello whose opens contains "tab"{type: "spec-chat-title", title}; title the document title as a string
5Page, to that same window and origin, on a new-tab click on a link to the page's own origin, after step 4{type: "spec-chat-open-tab", href}; href the link's absolute address as a string

Only after step 1 does the page turn an evidence click into step 2 instead of following the link; before it, and in any unframed page, links keep the browser's own behavior.

The page takes a hello only when event.source is its parent window and event.origin is a real origin, not null, and answers to event.source at event.origin. opens must be an array; "evidence" and "tab" each turn on only their own steps.

A new-tab click is a Cmd+click on macOS, a Ctrl+click elsewhere, or a middle-click, on a link whose resolved address has the page's own origin. On it the page cancels the click's default and sends step 5. A plain click, a click on a link to another origin, and any click before a tab hello keep the browser's own behavior, and a page that is not framed sends nothing.

Spec pages and the review index both speak steps 4 and 5. One mechanism: the tab steps extend the existing hello listener and its sender check, and the index runs the same bridge code as spec pages, not a second copy; the index loads nothing else from the runtime.

Proof: the deep-module seam is the page's message and click handling given a parent window, a hello, and a click; the first failing test sends spec-chat-open-tab for a Cmd+click on a same-origin link after a tab hello and sends nothing for a plain click or before the hello.

bundle and criterion are the evidence service's bundle ID and criterion ID, not URLs, so the plugin opens only its own Proof page.

Keeping the reader's place

The runtime remembers, per spec path, the nearest section anchor at the top of the viewport and the scroll offset from it, in the browser's local storage, updated as the reader scrolls and when the page hides.

On load, once the page has rendered, it scrolls back to that anchor plus the offset; an anchor in the address wins, and a missing anchor or no record leaves the page at the top.

Every storage read and write is wrapped so a sandboxed frame, a full quota, or disabled storage never breaks the page; the place is then simply not kept.

This makes Spec alone in BB keep its place across an evidence open and Back, where BB reloads the frame.

One read per page

The review server reads the evidence service's public base URL, at each read, from the evidence provider file's url (Providers); absent means no read and no evidence notes.

The criterion ID is branch-free, project/<project-id>::<spec path>#<anchor>, as evidence records it; the project ID is the last path part of the served root's origin URL without .git, such as spec-chat.

The viewed commit is the serving root's head, so a lane worktree and main each judge their own text.

A criterion whose served bytes differ from its bytes at head is marked uncommitted and shows QA stale, because the evidence service judges committed text only.

Each entry passes through the picked evidence's proven text and view link from /criteria; the diff compares that text with the criterion as served.

The service's relative artifact and bundle paths are joined to that provider URL before they reach the browser.

A timeout, error, or non-JSON answer returns no entries; the server does not retry, and the next page load asks again.

Proof

First failing test: the review server, given a fake evidence service answering one matching pass and one material mismatch, returns QA passed and QA stale entries with absolute links.

Evidence: server and runtime tests behind a fake evidence service, and a QA bundle driven by the Jev driver on a real spec served with the real evidence service.

Non-goals

Coverage totals per spec are later work.

Recapturing, re-reviewing, or accepting from the page itself (Ask for re-proof only drafts a comment); evidence on stories; tracker reads; opening other links in the plugin.
