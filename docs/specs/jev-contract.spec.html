Jev contract

docs / specs / jev-contract.spec.html

The one written contract for asking Jev: the question-set format, the request sent, the cache key, the judgment record, the outcome names, and the retry rule, plus conformance cases any program that asks Jev runs on its own. Spec Chat's Jev review suggestions conform to it; why it is data and not shared code is in the ADR.

User stories

As a maintainer of a program that asks Jev, I read one contract for every format and rule, and build my own small adapter without importing Spec Chat's code or calling its server.

As a maintainer of a program that asks Jev, I run the conformance cases against my adapter and see which case my request, key, or record breaks.

As the operator, the same question asked by any conforming program sends the same request, gets the same cache key, and writes a record with the same fields and outcome names, so a question set tuned once works everywhere.

As the operator, a failed Jev ask in any conforming program waits the same pause before it is asked again, never retried in a loop.

Acceptance criteria

Given a Spec Chat contributor's change, When the test suite runs, Then Spec Chat's Jev seam passes every conformance case: the request it sends, the cache key it computes, and the record it writes match each case, proven by a unit test: no screen shows it.

Given a maintainer of another program with a Spec Chat checkout on the box and no Spec Chat server running or package installed, When the maintainer's test reads the conformance cases, Then every case is a plain JSON file holding its own question set, question, provider reply, and expected request, key, and record, so it runs with no Spec Chat code, proven by a unit test: no screen shows it.

Given a Spec Chat contributor whose change makes the Jev seam send a request one case does not expect, When the test suite runs, Then the suite fails naming that case and the field that differs, proven by a unit test: no screen shows it.

Given a Spec Chat contributor who adds a question set whose version is not a whole number, When the test suite runs, Then the suite fails naming that question-set file, proven by a unit test: no screen shows it.

Given the operator of a box with Jev on, When the same question is asked once with its state fields in one order and once in another, Then both asks have the same cache key and only the first calls Jev, proven by a unit test: no screen shows it.

Given the operator of a box with Jev on and a record for a question, When the question's set gains a new version and the question is asked again, Then the ask has a new cache key and calls Jev once, proven by a unit test: no screen shows it.

Given the operator of a box with Jev on, which needs an induced failure: Jev rate-limits with a given wait, When a question is asked, Then its record is unavailable and holds the instant the given wait ends, and an ask of the same question before that instant calls nothing, proven by a unit test: no screen shows it.

Given the operator of a box with Jev on, which needs an induced failure: Jev fails with no given wait, When a question is asked, Then its record is unavailable and holds the instant 60 seconds later, proven by a unit test: no screen shows it.

Given the operator of a box with Jev on and an unavailable record whose pause has ended, When the same question is asked, Then Jev is called once and the new record is the question's answer, proven by a unit test: no screen shows it.

Given the operator of a box with Jev on, When any question is asked, Then its record's outcome is one of the outcome names and the record holds no provider key, proven by a unit test: no screen shows it.

Onboarding: not needed, the contract adds no user surface. CI: the CI rule covers the conformance cases; they use a recorded provider reply and no provider file.

Modular boundaries

The contract owns the question-set format, the request, the cache key, the record's core fields, the outcome names, and the retry rule, and its conformance cases are the executable form of those rules. Caller-facing seam: this spec and the case files in the conformance cases directory, read as plain JSON. Dependency direction: self-contained data; Spec Chat's Jev seam and any other program read it, and it names no program that reads it. Observable scope: the case files and each conforming program's test result.

Each program that asks Jev owns its own adapter: loading sets, building the request, calling Jev, and writing its records in its own store. Caller-facing seam: its own; the contract fixes only what crosses into Jev and into a record. Dependency direction: the adapter reads the contract; it imports no other program's code and calls no other program's server. Observable scope: its requests, its records, and its run of the cases.

A feature that asks Jev owns the record fields it adds beyond the core, and their meaning. Caller-facing seam: the feature's own spec, as draft-check provenance is. Dependency direction: the feature extends the core record; the contract never depends on a feature. Observable scope: the added fields on that feature's records.

Question sets

A question set is one JSON file. Its id and whole-number version name it everywhere; any change to the file is a new version.

FieldHoldsRequired
idThe question's name; it is also the question's key in the requestyes
versionA whole number, raised on every changeyes
instructionsOne atomic judgment, as textyes
labelsA list of labels, each a name, a description, and examples: each an input object in the question's state shape and the label it deservesyes
thresholdThe confidence at or above which a label is shown, between 0 and 1yes
fallbackTrue when an answer below threshold goes to the asking program's general LLM; sets name no modelno, false
show_cutoff, verify_cutoffAn asymmetric threshold on the yes probability in place of threshold, as draft checks use itno

A program ignores a set field it does not use, so a feature may add one in its own spec, as the verifier levels are.

Request

Every ask is one call to Jev decisions, POST https://openrouter.ai/api/alpha/decisions with model typesafe/jev-1.13, asking one question about one state.

Request fieldHolds
modeltypesafe/jev-1.13
questions.<id>type choice, the set's instructions, and criteria
criteria.<label>The label's description and its examples, each input and label: examples ride with the label they illustrate, never folded into the instructions text
question-supplied labelsWhen a question supplies its own labels, such as candidate anchors, criteria holds those labels' descriptions and instructions becomes question (the set's instructions) plus the set's examples
stateThe question's inputs as one JSON object

The reply's answers.<id> gives the choice, the probabilities per label, and the confidence; its model is the model version Jev reports.

A request whose canonical JSON length, divided by 4 and rounded up, exceeds 32,000 tokens is never sent and never truncated: its outcome is oversize.

The provider key travels only in the request's authorization header; no record, log, case, or reply holds it.

Cache key

key = "sha256:" + hex(sha256(canonical({state, criteria, question_set: {id, version}})))

The key hashes the question's content and set version only, so the same text asked at any revision, head, or lane reuses one record; criteria is the question-supplied labels, or empty when the set's own labels are asked.

Canonical JSON is UTF-8 with object keys sorted, no whitespace between tokens, and non-ASCII characters written as themselves.

A record whose key matches and whose outcome is final is reused without calling Jev; a key's record is its latest line.

Judgment record

Every ask appends one judgment record, one JSON line, whether its label shows or not. A record is never amended; what a person decides about it lives elsewhere and cites its id.

FieldHolds
record_idjudgment- plus a unique id
cache_keyThe cache key
modelThe model version Jev reports, or the general LLM's model when source is llm
question_setThe set's id and version
sourcejev, or llm when the general LLM answered
sourcesThe addresses the inputs were read from and the revision they were read at; addresses only, no source text
answerlabel, probabilities per label, and confidence; all empty when nothing answered
thresholdThe threshold used
outcomeOne of the outcome names
retry_atOnly on unavailable: the UTC instant the pause ends
timeThe UTC instant of the ask, to the millisecond, ending in Z

A feature may add fields its own spec defines, such as the inputs it sent; a reader ignores fields it does not know.

Records are a cache: deleting them costs only asking again, so no record is the only copy of anything a person decided.

Outcome names

These are the only outcome names. A final outcome is never asked again; a waiting outcome is replaced by the next ask's record.

OutcomeMeansKind
shownConfidence at or above threshold, or yes probability at or above the show cutofffinal
unsureBelow threshold, and the set has no fallbackfinal
silent-noYes probability below the verify cutofffinal
escalatedBelow threshold with fallback, or in the verify band: the general LLM or verifier answers nextwaiting
verifiedThe verifier confirmed a verify-band answerfinal
verifier-rejectedThe verifier did not confirm itfinal
oversizeThe request is over the token limit and was not sentfinal
offNo provider key; asked again on the next read once a key existswaiting
unavailableThe call failed; asked again after its pausewaiting

Retry rule

An ask makes one call and never waits inside it. A failed call writes an unavailable record whose retry_at is the end of the pause.

The pause is the wait the provider gives, such as a rate-limit Retry-After in seconds or as a date; otherwise 60 seconds.

Before retry_at, an ask of the same key answers from its unavailable record and calls nothing; the first ask after it calls Jev once.

No program retries in a loop, backs off by doubling, or holds a failed ask open.

Conformance cases

The cases are JSON files in skill/review-spec/assets/jev/cases/ in this repository, one case per file. A program runs them from a Spec Chat checkout on its box; it needs nothing else of Spec Chat.

Case fieldHolds
aboutThe rule the case proves, with its anchor in this spec
question_setThe whole question set, frozen in the case so a tuned set's new version never changes it
questionThe question id, state, any question-supplied labels, sources, and the clock's now
heldThe record already held for the key, when the case starts from one
replyJev's reply body, or a failure with its status and given wait, or no key
expectThe request sent, or none; the key; and the record written, or none: every listed field must match exactly, and record_id is matched by its prefix

The cases cover at least: a shown answer, an unsure answer, an escalated answer, an oversize request, no key, a failure with a given wait, a failure without one, an ask during a pause, an ask after it, a question with its own labels, and two state orders with one key.

A change to any rule here changes its case in the same commit; a program that conforms to the contract at a commit passes that commit's cases.

Non-goals

No shared code, package, or library: each program writes its own adapter.

No program asks another program's server to ask Jev for it.

Where and how a program stores its records, and how it reads its provider key, stay its own.

What a person decides about a record is not part of this contract; Spec Chat's is its warning ledger.
