Box-side HTML review hosting

docs / specs / remote-handoff-proof.spec.html

Source issues: ANN-40 (box-side policy), ANN-30 (two-service topology).

One box-side policy governs two independent services: Spec Chat and annotateanything evidence.

User stories

As a reviewer on another machine, I can open a secret HTTP URL served directly by the review host.

As a host owner, I can start review hosting without operator or reviewer-machine setup when an approved ingress port is available.

As a host owner, I get a clear failure when no approved ingress port is usable.

As a host owner, I can start, verify, and stop the Spec Chat service and the evidence service independently on the box.

As a laptop user, I can point BB at the two verified public service URLs, and the box never requires, installs, or starts BB.

Decision

Apply one box-side hosting policy to two independent services: Spec Chat review HTML and annotateanything QA evidence HTML.

For each service, its own launcher discovers approved ingress ports, probes each for availability, binds that narrow service to the first usable approved port, and prints its secret URL.

The launcher fails before handoff when approved ports cannot be discovered or none is usable.

The launcher requires no external probe, operator receipt, laptop setup, tunnel, VPN, or reviewer-machine configuration.

Internal content checks never waive exact served bytes, exact baseline identity, approved-port collision safety, secret URL handling, service ownership, or Finish review lifecycle.

Internal content validation

The host runs the read-only verifier against the exact current HTML bytes and selected exact Git base before printing a review URL.

Validation requires HTTP 200 for the requested resource, byte equality for the served HTML, the exact /api/baseline response, the resolved baseline commit, and baseline HTML byte equality or an explicit new-file result.

Each service runs its own internal check against its own resource bytes and baseline, without a shared runtime or application-wide receipt state.

A source, baseline, selected port, service process, or resource-path change requires the host to rerun internal validation before handoff.

Remote access and secret handling

The serving box binds directly to a free approved ingress port so a reviewer on another machine can open the printed URL without a separate probe or relay.

The handoff consists of the active secret URL, resource path, and selected exact Git base after host-side validation.

No second transport ceremony, laptop probe, or reviewer-side setup is part of this policy.

Same-machine access uses the same host service when needed and does not create a second proof class.

The secret URL stays in the active handoff and is never written to Linear, a pull request, or another public durable record.

Approved ingress discovery, free-port selection, collision safety, narrow collection root, and explicit server and checker ownership remain mandatory.

Failure and refusal

If approved ingress cannot be discovered or no approved port is usable, the launcher fails and does not print a handoff URL.

A port collision, unapproved port, wrong bytes, substituted baseline, bind failure, broad collection root, or lost service ownership fails closed.

No operator or reviewer-machine action is required to recover; the host may retry after its ingress state changes.

A source, baseline, port, process, or resource-path change requires fresh host-side internal validation.

Lifecycle

Each service's launcher owns its approved-port discovery, availability probing, service process identity, URL capture, internal validation, and direct host binding.

The checker owns readiness detection and exact cursor advancement, and remains parked on the same server, URL, and cursor through empty spool, timeout, and manual-resume states.

Hosting and checker shutdown occur only after the processed empty Finish review hand-off records no draft, pending, acknowledged, unresolved, or data-spec-tbd work and the exact cursor advance succeeds.

Finish review means human HTML review completion only and never implementation authorization, acceptance, merge approval, deployment approval, or traffic shift.

Acceptance criteria

When remote Spec Chat or QA evidence HTML hosting starts, the host discovers and probes approved ingress ports, binds the narrow service to a free approved port, and prints a secret URL reachable from another machine.

Before the URL is printed, the host verifies exact current resource bytes and the applicable exact baseline response internally.

When approved ingress is unavailable, a port is occupied, binding fails, or internal content validation fails, the launcher fails closed without requiring operator or reviewer-machine intervention.

When review is parked or finished, the same server, URL, checker, cursor, and explicit Finish review lifecycle remain in force.

When box hosting boot starts both services, each starts through its own launcher with its own approved port, narrow root, secret URL, exact-byte check, and baseline check, and a failure in one fails only that service.

When box hosting boot runs on a box without BB, both services start and verify, and boot never requires, installs, or starts BB or any laptop component.

When BB on the laptop is configured, it consumes exactly the two verified public URLs, and no box service calls or depends on BB.

Modular boundaries

spec-chat owns the Spec Chat service startup and lifecycle, its launcher, narrow resource paths, exact HTML bytes, the /api/baseline route, annotation spools, cursors, and Finish review state. Caller-facing seam: the host launcher receives a narrow collection, resource path, and exact base and returns a secret URL after internal validation. Dependency direction: host ingress and Git source bytes flow into the self-contained Spec Chat review service. Observable scope: approved port, bound process, exact resource response, baseline response, URL, cursor, checker, and lifecycle.

annotateanything owns the evidence service startup and lifecycle, its launcher, narrow bundle paths, immutable manifests and artifacts, candidate baseline records, deterministic page hashes, checkers, and evidence review state. Caller-facing seam: the evidence launcher receives a narrow bundle collection and exact base and returns a secret URL after internal validation. Dependency direction: host ingress and the existing immutable bundle reader flow into the self-contained evidence service. Observable scope: approved port, bound process, exact bundle response, baseline record, page hash, URL, checker, and lifecycle.

This policy owns approved-port discovery, direct binding, internal exact-byte validation, secret handling, refusal rules, and service ownership rules that each service applies independently; shared helpers stay service-neutral. Caller-facing seam: each host supplies its narrow collection and exact base and receives a reachable secret URL or a fail-closed result. Dependency direction: self-contained policy semantics consume host-specific ingress, HTML, and Git results without importing a tracker or remote probe. Observable scope: bound service, internal validation, URL handoff, failure reason, checker, and Finish review.

BB and its workbench plugin own laptop presentation and local URL configuration. Caller-facing seam: the two public service URLs opened over HTTP. Dependency direction: external-provider direction from the laptop to the two box services only; box services never import, require, install, or start BB. Observable scope: two configured URLs on the laptop and no BB process, package, or install step on the box hosting path.

Non-goals

This policy does not add a second transport mechanism, application server, checker, or remote relay.

This policy does not implement the annotateanything evidence service or edit the installed shared profile.

This policy does not host BB, a laptop daemon, or any client component on the box.

This policy does not accept delivered software, merge work, promote preproduction, or shift live traffic.
