Remote handoff proof policy

docs / specs / remote-handoff-proof.spec.html

Source issue: ANN-40.

ANN-30 remains context only and is not changed by this policy.

User stories

As a remote reviewer, I can receive a review URL when an accepted transport proof and exact content proof establish the requested resource.

As a same-machine reviewer, I can use a local review transport after exact local content and baseline checks without a public URL.

As an operator, I can see which proof class was used, what it proves, and why a handoff remains refused when a required fact is missing.

Decision

Relax the mandatory non-loopback probe for remote handoff, but do not remove transport proof.

A remote handoff accepts either an executable non-loopback probe or an operator-confirmed public URL receipt for the unchanged review session.

A same-machine proof is valid only for a handoff explicitly scoped to a reviewer on the same machine.

No proof class silently waives exact resource bytes, exact baseline identity, approved-port selection, collision safety, secret URL handling, explicit process ownership, or Finish review lifecycle.

Exact content proof

Every class runs the read-only verifier against the exact current spec bytes and the selected exact Git base.

Spec Chat proof includes HTTP 200 for the requested resource, byte equality for the served spec, the exact /api/baseline response, the resolved baseline commit, and baseline HTML byte equality or an explicit new-file result.

A portable evidence service applies the same interface to its exact manifest and artifact bytes, candidate Git baseline record and hash, and deterministic served-page hash.

Any spec, baseline, server process, selected port, URL, resource path, or reviewer-vantage change invalidates the receipt and requires fresh proof.

Transport proof and operator receipt

The executable external probe remains the strongest automated class and verifies HTTP 200, exact served bytes, and the exact baseline response through the printed URL before URL delivery.

An operator-confirmed public URL is an accepted alternative only when the operator records an append-only local receipt containing proof class, UTC time, attestor identity, stated reviewer vantage, URL fingerprint, HTTP status, resource path, exact spec hash, selected baseline commit, baseline response hash, and the command or observation method.

The operator attestation proves only the facts explicitly recorded, and visual page inspection alone cannot claim exact byte equality.

Same-machine proof records reviewer scope as same-machine, host identity or equivalent local scope, selected approved port, process identity, exact content result, and local URL or transport path.

The secret URL is delivered only through the active handoff and is never written to Linear, a pull request, or another public durable record; the local receipt stores only a URL fingerprint.

Approved ingress discovery, free-port selection, collision safety, narrow collection root, and explicit server and checker ownership remain mandatory before any transport proof is accepted.

Failure and refusal

If neither an executable non-loopback probe nor a complete operator-confirmed public URL receipt exists for a remote handoff, URL delivery and checker parking remain refused.

An incomplete receipt, a loopback-only request presented as remote proof, a missing hash or baseline identity, an unknown vantage, a stale URL, a changed process, a port collision, an unapproved port, wrong bytes, or a substituted baseline fails closed.

When remote proof is unavailable, the operator may downgrade explicitly to same-machine scope and use local transport, or keep the server unparked while waiting for proof; the downgrade never claims public reachability.

A new handoff session, source edit, baseline edit, server restart, URL change, or reviewer-vantage change requires fresh local content proof and a fresh transport proof.

Lifecycle

The launcher owns approved-port discovery, server process identity, URL capture, local verification, and the selected transport proof receipt.

The checker owns readiness detection and exact cursor advancement, and remains parked on the same server, URL, receipt, and cursor through empty spool, timeout, and manual-resume states.

Hosting and checker shutdown occur only after the processed empty Finish review hand-off records no draft, pending, acknowledged, unresolved, or data-spec-tbd work and the exact cursor advance succeeds.

Finish review means human HTML review completion only and never implementation authorization, acceptance, merge approval, deployment approval, or traffic shift.

Acceptance criteria

When a remote review handoff is requested, the owning procedure accepts an executable non-loopback probe or a complete operator-confirmed public URL receipt and records the selected proof class.

When any proof class is selected, exact current resource bytes and the applicable exact baseline response are verified separately from transport reachability.

When reviewer and server are explicitly scoped to one machine, same-machine proof permits local transport and records that no remote reachability claim was made.

When transport proof, exact content proof, approved-port safety, or receipt identity is missing or stale, the procedure refuses remote URL delivery and checker parking without silently waiving the missing fact.

When review is parked or finished, the same server, URL, checker, cursor, and explicit Finish review lifecycle remain in force.

Modular boundaries

Spec Chat owns resource paths, exact spec bytes, the /api/baseline route, annotation spools, cursors, and Finish review state. Caller-facing seam: a review launcher receives a narrow collection, spec path, exact base, and one accepted transport proof and returns a secret URL plus local receipt. Dependency direction: external-provider direction from host ingress and Git source bytes into the self-contained Spec Chat review service. Observable scope: exact resource response, baseline response, proof class, receipt, cursor, checker, and lifecycle.

The annotateanything evidence service owns bundle paths, immutable manifests and artifacts, candidate baseline records, deterministic page hashes, checkers, and evidence review state. Caller-facing seam: an evidence launcher receives a narrow bundle collection, candidate baseline, and one accepted transport proof and returns a secret URL plus local receipt. Dependency direction: external-provider direction from host ingress and the existing immutable bundle reader into the self-contained evidence service. Observable scope: exact bundle responses, baseline record, page hash, proof class, receipt, checker, and lifecycle.

This policy owns proof classes, evidence separation, refusal rules, secret handling, and portable receipt fields. Caller-facing seam: each owner supplies transport and content facts and receives an allowed or refused handoff decision. Dependency direction: self-contained policy semantics consume owner-specific exact-byte and baseline results without importing either service or tracker runtime. Observable scope: same-machine, external-probe, and operator-confirmed outcomes and their failure reasons.

Non-goals

This policy does not implement a launcher, external probe, application server, checker, or receipt store.

This policy does not edit ANN-30, annotateanything, or the installed shared profile.

This policy does not accept delivered software, merge work, promote preproduction, or shift live traffic.
