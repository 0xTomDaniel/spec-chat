Compared commit range

docs / specs / compared-range.spec.html

Source issues: ANN-90, ANN-119.

Extends Git-derived focus: the page states which commits it compares and lets the reviewer change the base in place.

User stories

As a reviewer, I can see which commits the served spec compares, so I know what the highlighted changes mean.

As a reviewer, I can pick an earlier commit of this spec or paste a commit id and see the page re-diff, without editing the URL.

As a reviewer, however I open a spec, I see what changed since I last reviewed it, including changes merged in by others.

Acceptance criteria

When any spec is opened over HTTP, with or without focus=changes, the page shows Changes from <base> to <head> with short ids and dates matching base and head, and working copy of when the file is dirty.

When the reviewer picks a listed commit, highlighting and bar reflect that base without a page reload, and the URL carries focus=changes&base=<full id>.

When the reviewer pastes a valid commit id, the page re-diffs against it as if picked; an unknown or option-like value shows an inline error and the previous range stays.

When the picker opens, it lists at most 20 commits that changed this spec, newest first, matching git log for that file from head.

When the reviewer sends a human spec review, comment batch or spec acceptance, from a page showing bytes X, even after the file changed on disk, the spec's last reviewed version is X byte for byte and its registry row's reviewed_sha256 is the SHA-256 of X.

When a spec with a last reviewed version is opened with no base in the URL, exactly the changes since that version are highlighted and the bar reads Changes from last reviewed with its time; with none yet, the changes since the registry row's base are highlighted.

After a rebase or merge, spec text merged in by others is highlighted as new, and a rebase that leaves the spec bytes unchanged highlights nothing.

When the reviewer chooses Last reviewed in the picker after picking a commit, the page re-diffs against the last reviewed version in place and the URL has no base.

When the review host verifies a served resource, its existing base, htmlBase, and html checks pass unchanged.

When the page is 375px wide, bar and picker fit without horizontal page drift and cover no review control.

Modular boundaries

The review server owns range facts: resolved base, head, dirty state, dates, the spec's recent commits, and keeping the last reviewed version on each human spec review. Caller-facing seam: GET /api/baseline?path=<spec>[&base=<id>] and its JSON fields. Dependency direction: self-contained; the server reads local Git and writes only the spool and the review host's reviewed_sha256; nothing calls back into the runtime. Observable scope: baseline JSON, the kept bytes, and the registry field.

The browser runtime owns the bar, picker, in-place re-diff, URL replacement, and the shown bytes' SHA-256 on each hand-off. Caller-facing seam: the rendered bar and picker on every HTTP-served spec. Dependency direction: self-contained within Spec Chat; the runtime consumes the baseline route and existing focus classification and holds no Git logic. Observable scope: bar text, picker entries, highlighting, URL, and inline errors.

Range bar

Every spec served over HTTP shows one compact line above the spec header: Changes from <base> to <head>.

Each end shows a 7-character commit id and its commit date as YYYY-MM-DD; the full id is the hover title.

The base end is the selected base commit; a spec absent there is entirely new, as focus defines.

The head end is the current commit of the serving worktree; when the served spec differs from that commit, it reads working copy of <head>.

The bar sits in page flow, wraps on narrow screens, and never covers the spec or review controls.

A file:// page shows no bar, because it cannot read Git.

Changing the base

Change base opens a picker listing up to 20 most recent commits reachable from head that changed this spec file, each with short id, date, and subject, and a field for pasting a commit id.

Choosing a commit re-diffs in place through the same /api/baseline route, turns on change highlighting, and updates the bar.

The page then replaces its own URL with ?focus=changes&base=<full id> without reloading, so reload and a copied link keep the chosen range.

Every HTTP page highlights its changes against the current base; focus=changes is no longer needed.

A pasted value that does not resolve to a local commit shows an inline error and keeps the previous range and highlighting.

A base value beginning with - is refused, so no input is ever read as a Git option.

Last reviewed version

A spec's last reviewed version is set by each human spec review: every hand-off the human sends from the page, a comment batch or spec acceptance. Each human spec review keeps the exact spec bytes the page showed. It is content, not a commit, so rebases and merges cannot break it. Spec acceptance stays the delivery gate; it does not define the base.

Each human spec review's hand-off carries the SHA-256 of the spec bytes the page is showing. The server keeps those bytes in the spec's .review/ spool as its last reviewed version, even if the file changed after the page loaded, and the review host records the SHA-256 in the resource's registry row as reviewed_sha256.

Opened with no base in the URL, from any entry (Kanban, the index, the sidebar, an old link), the page highlights the changes since the last reviewed version. With none yet, it highlights the changes since the base it defaults to today: the registry row's base, the target main the lane started from. Changes merged in by others differ from the reviewed bytes, so they show as new.

When the base is the last reviewed version, the bar reads Changes from last reviewed <YYYY-MM-DD HH:MM> to <head>. The picker lists Last reviewed first; choosing it drops base from the URL.

Baseline response

Existing base, htmlBase, and html fields keep their meaning, so host baseline checks are unchanged.

Added fieldValue
headFull id of the serving worktree's current commit.
dirtyTrue when the spec file differs from head.
headDate, baseDateCommit dates of head and base as YYYY-MM-DD.
reviewed{sha256, at} of the last reviewed version, or null. With no base requested and a last reviewed version kept, htmlBase is those bytes and base is reviewed.
commitsUp to 20 {id, date, subject} entries, newest first, for commits reachable from head that changed the spec file.

The route stays read-only over local Git and the spool, as focus requires.

Non-goals

Changing the head end, comparing two arbitrary commits, or browsing other branches.

Side-by-side, deleted-text, or per-commit diff views.

Commit search, pagination beyond 20, or fetching from remotes.
