The Jev contract is data, with an adapter per program

Decision behind Jev contract.

Context

More than one program on a box asks Jev, each with its own question sets, request builder, cache key, record shape, outcome names, and retry rule, and they disagree on all of them.

A question set tuned and measured in one program never reaches the others, and their records cannot be read with one tool.

Each repository on the box must install, test, and run with no other installed, and none vendors or pins another.

Decision

Spec Chat owns the one written Jev contract: one spec plus conformance cases as plain JSON files in its repository.

Every program that asks Jev keeps its own small adapter that conforms to the contract; it shares formats, never code, and asks Jev itself, never through another program's server.

A program runs the cases from a Spec Chat checkout on its box; nothing else of Spec Chat is needed, and without a checkout it still builds and runs.

Why

Formats cross repositories without an import, a pin, or a running service, so each repository still works alone.

Cases with recorded replies turn the written rules into a check any language can run, so drift shows up as a named failing case instead of a field that differs in production.

Spec Chat already holds the tuned question sets and the eval loop, so the contract lives beside the data it governs.

Alternatives rejected

OptionRejected because
Other programs import Spec Chat's Jev moduleA repository could no longer test or run without Spec Chat installed
Other programs ask Spec Chat's review server over HTTPTheir own Jev features would vanish whenever Spec Chat is absent or its server is down
A published shared library or packageA pinned dependency between peers, and a shallow base class that moves code without removing any
Each program keeps a copy of the casesCopies drift and become a second owner of the same rules
No contract; each program keeps its own rulesThe disagreements stay, and tuning never crosses programs

Consequences

A contract change is a Spec Chat spec change with its cases in the same commit; other programs learn of it the next time they run the cases.

A program's own CI, with no Spec Chat checkout, cannot run the cases; conformance is checked on a box where both are present.

Two or more adapters exist on purpose: one contract, one adapter per program, not one mechanism duplicated.

Move trigger: if programs keep drifting despite the cases, revisit a published contract version that adapters declare.
