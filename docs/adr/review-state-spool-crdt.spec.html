Review state as grow-only sets over the spool

docs / adr / review-state-spool-crdt.spec.html

Supersedes Review state as a grow-only CRDT over the spool. Decision behind Shared review state.

Context

Review needs three things: several reviewers live on one spec, marks that survive the agent's edits, and offline merge from a browser on reconnect.

The spool already holds one immutable file per event with unique ids and reference-based causality, which is a grow-only set.

During review, spec text has one writer, the agent, editing a committed file; direct live editing by humans is expected later.

The review service is Python standard library only, and the runtime is one classic script with vendored libraries that must work over file://.

Decision

Review state is a state-based CRDT of two grow-only sets in the existing spool, events and stored spec versions, merged by union, with everything else derived by one deterministic fold.

A mark's place is computed from the spec version it was written against, never stored, so nothing is written when the agent edits.

Spec text stays in Git and the worktree file only; review state never holds a second live copy of it.

No third-party CRDT library while the agent is the one text writer.

Why

Union merge needs no coordination, so live sync, offline reconnect, and several reviewers are one mechanism over the store that already exists.

With one text writer, concurrent text editing is not a need, so a text CRDT would add a dependency, a second copy of spec text, and a doc-to-commit step for nothing.

Keeping text in Git leaves the existing commit-before-reply step the only path from edit to review.

Alternatives rejected

OptionRejected because
Yjs doc per spec with pycrdt in the serviceA binary service dependency, a second live copy of spec text, a new store beside the spool, and a CRDT client for agents, all for concurrent text editing nobody does yet
Automerge doc per specThe same costs as Yjs plus a heavier WASM runtime on the page
Yjs on the page with an opaque relay in the serviceA Node runtime on the service host and two processes to keep in step

Consequences

Marks on heavily rewritten text resolve as changed or gone rather than kept.

The spool is extended, not replaced; the agent's scan, cursor, reply, and wake keep their contracts.

The page has no login, agent events stay on disk, and event files are never overwritten.

Move trigger: direct human editing of spec text or any second concurrent text writer; then spec text moves to a text CRDT on the page, and only the mark resolver changes.
